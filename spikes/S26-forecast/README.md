# S26 — прогноз расхода (ARCH §20.11, ORGS-PLAN §10 «Прогноз», О13)

Критерии из PLAN.md: **меньше 1 с на сервере; на живом наборе цифры совпадают с внутренним калькулятором.**

## Что проверяли

1. Ядро `replayLimits` — чистая функция, которая прогоняет записанные ответы через лимиты тарифов, и `forecastNextMonth` — сводка на следующий месяц по тарифам.
2. Совпадают ли её цифры с внутренним калькулятором (`replay()` из файла вне репозитория) на одних и тех же данных.
3. Скорость на 1000 мест × 8 недель, синтетика с тяжёлым хвостом.
4. Два способа посчитать: **SQL-агрегаты** (ничего не выгружается) и **выборка строк в память + расчёт в TS**.
5. «Покрутить»: курс, комиссия, НДС, лимиты, цена, рост нагрузки, «все ответы на модели X» — пересчёт на сервере по запросу.

## Как запустить

База `spike_s26` на локальном Postgres (создана вручную, `purr` и `metobe` не трогаются; Redis не нужен). Адрес — `S26_DATABASE_URL`, по умолчанию `postgres://purr:purr@127.0.0.1:5432/spike_s26`.

```bash
cd spikes/S26-forecast
pnpm install --ignore-workspace

pnpm seed                      # 1000 мест, 8 недель → public.seats, public.model_runs (≈265 тыс. строк)
pnpm test                      # replayLimits против golden.json (ответы калькулятора на синтетике), без БД и без приватного файла
pnpm parity                    # против самого калькулятора: живой набор (из файла калькулятора) и синтетика
pnpm calibrate                 # форма синтетики против живого набора
pnpm bench -- --weeks=8        # скорость: SQL против TS (--schema=big для 1 млн строк: S26_SCHEMA=big pnpm seed --volume=4)
pnpm report                    # что показал бы экран: прогноз и несколько поворотов «покрутить»
```

`parity` и `calibrate` читают калькулятор из `~/dev/ai/metobe-private/seat-economics.html` (или `S26_CALCULATOR`). Его скрипт обрезается перед `dotPlot` и выполняется в `vm`: считает сам `replay()`, а не копия. Живой набор на время сверки заливается в схему `live` и удаляется; в репозиторий ничего из приватных данных не попало (`calibrate` печатает числа живого набора только в консоль).

## Данные

- 1000 мест × 8 недель, 265 тыс. строк `model_runs` (`purpose`: `chat` и служебные `title`, `memory`, `decide`), 33 строки на место в неделю.
- Тяжёлый хвост: число ответов в неделю — логнормальное (медиана 12, σ = 0,7) с недельным шумом; тяжёлые авторы к тому же запускают более длинные ответы с инструментами; 8 % мест не пишут вовсе, 15 % появляются в середине окна; ответы идут сессиями в рабочие часы по Москве. Тарифы 70 / 25 / 5 % (Обычный / Про / Макс), активные чаще на старших.
- **Форма сверена с живым набором (`calibrate.ts`): совпадает** по семи признакам: разброс стоимости ответа (p90/p50), служебных строк на ответ, ответов в активную человеко-неделю и разброс по неделям, доля расхода верхних 20 % людей, доля человеко-недель и 5-часовых окон выше лимита. Допуски широкие: живой набор мал (человек и недель немного). Хвост у синтетики чуть легче: доля человеко-недель в недельном лимите ниже, чем у живых, хотя и в допуске.
- Параметры формы (разбросы, соотношения) округлены; абсолютные цифры живой установки (цены моделей, тарифы, лимиты, курс) в код не переносились. Цены тарифов (3000 / 6000 / 12000 ₽), серверы 150 ₽ на место, курс 90 ₽ + 4 %, лимиты по правилу «неделя в ноль» и цены базовой модели — **допущения спайка**, не измерения.

## Сверка с калькулятором: цифры совпадают

`parity.ts` прогоняет случайные сценарии (модель: как записано или одна из моделей калькулятора; рост ×1…×3; календарная и скользящая неделя; курс, комиссия, НДС 0 / 22; серверы; лимиты по умолчанию, случайные и без лимитов; отдельно для трёх тарифов, у Макса нет окна 5 часов). По каждому человеку сравниваются: расход, отклонённые запросы, остановленные ответы, запросы, окна 5 часов в упоре, недели в упоре, активные недели, самая дорогая неделя и окно без лимитов. По каждому тарифу: средние модели на место, остаток, остаток в худшем случае, доля человеко-недель в упоре, доля отклонённых, число людей в упоре по 5 часам, остановленные, «близко к лимиту».

| набор                                                                  | сценариев | сравнений     | расхождений                  |
| ---------------------------------------------------------------------- | --------- | ------------- | ---------------------------- |
| живой (небольшой, из файла калькулятора)                               | 300       | десятки тысяч | 0 (разница побитово нулевая) |
| синтетика (935 активных мест, 265 тыс. строк, тот же код калькулятора) | 12        | 101 304       | 0                            |

Покрытие: в сценариях живого набора отклонения есть у 1412 человеко-сценариев, остановленных ответов — у 1464, упор в 5 часов — у 1171, в неделю — у 906, скользящая неделя — 1628, переоценка на другую модель — 3146. Чтение строк идёт через БД (`load.ts`), а не из массива в памяти.

`forecast.test.ts` проверяет то же без приватного файла: `golden.json` (35 КБ) хранит ответы калькулятора на небольшой синтетике (80 мест, генерируется из seed), 6 сценариев, 75 человек. Если убрать из ядра правило про служебные строки после отказа, падают 5 из 6 сценариев.

### Правила калькулятора, которые ядро повторяет (решить, что из этого — продукт)

1. Окно 5 часов открывает любой запрос, в том числе отклонённый.
2. После отклонённого запроса служебные строки не считаются до следующего принятого (в продукте служебный вызов идёт только после разрешённого запроса, так что смысл тот же).
3. Служебные строки пишутся без потолка и могут пройти лимит; потолок только у запроса: его ответ обрезается остатком.
4. Место считается со дня первой строки; места без единой строки в калькуляторе нет. В продукте место с самого начала в `org_seats`, и нулевые места разбавляют среднее. Формула §20.11 «средний `charge` места» должна это говорить явно; в ядре дни места — `since` в окне, не меньше суток. На сверке `since` приравнивался к первой строке.
5. Неделя — с понедельника 00:00 по фиксированному смещению (МСК, без перехода на летнее время); как это ложится на часовой пояс организации — S24.
6. Одна строка — одна валюта (доллары или рубли). В живом наборе нет строк с обеими, так что `cost` + `currency` достаточно.
7. Калькулятор прибавляет к каждому ответу оценку памяти. В продукте строки памяти есть в `model_runs` сами (`purpose = memory`), поэтому в ядре это необязательный параметр, по умолчанию 0.

## Скорость

Сервер = Node + локальный Postgres на одной машине. Медиана из 5–9 повторов (в скобках максимум), мс. **Машина была загружена другими сессиями (load average 8–11)**, цифры скорее пессимистичны; в тихие моменты чтение 265 тыс. строк занимало 0,25–0,3 с. Полные таблицы — `results/bench.txt`, экран — `results/report.txt`.

| окно                  | строк        | чтение строк в колонки | TS: чтение + расчёт | TS: только расчёт (данные в памяти) | SQL-агрегаты      |
| --------------------- | ------------ | ---------------------- | ------------------- | ----------------------------------- | ----------------- |
| 4 недели              | 137 тыс.     | 285                    | 280 (до 360)        | 2–3                                 | 90–105            |
| **8 недель**          | **265 тыс.** | 530                    | 530–600 (до 850)    | 3–4                                 | 190–200 (до 300)  |
| 8 недель, нагрузка ×4 | 1,04 млн     | 1200 (до 2400)         | 2200–2700 (до 3600) | 12–25                               | 690–850 (до 1200) |

Выводы по скорости:

- **Расчёт лимитов — не узкое место:** 3–4 мс на 265 тыс. строк, 12–25 мс на миллионе. Узкое место — выгрузка строк из БД в Node (разбор ≈ 2 млн значений драйвером).
- **Что ускорило чтение вдвое:** `numeric::float8` стоит ≈ 1 мкс на строку (идёт через строку), около 240 из 420 мс запроса. Заменено на `(cost * 1e12)::bigint::float8` и деление в JS (точно, если у `cost` не больше 12 знаков после запятой); `extract(epoch …)` (numeric) заменено на `round(date_part('epoch', …))`; результат пишется сразу в типизированные колонки, без массива на строку. `COPY … BINARY` и одна `bytea`-строка с бинарными значениями быстрее не вышли (0,3–1 с).
- **Память:** 53 байта на строку: 265 тыс. строк — 14 МБ, 1 млн — 55 МБ.

## SQL-агрегаты против выборки в память

`sql-forecast.ts` считает всё одним запросом: стоимость строки по сценарию, сумма по пятичасовым ведрам и неделям, потолки лимитов. Это приближение: окно 5 часов — фиксированное ведро (настоящее открывается первым запросом человека), а отклонения и остановки зависят от порядка строк внутри человека и агрегатами не выражаются.

Ошибка SQL относительно точного расчёта на 8 неделях (бенч на 6 сценариях):

| показатель                                                         | ошибка                                                                                           |
| ------------------------------------------------------------------ | ------------------------------------------------------------------------------------------------ |
| модели на место в месяц                                            | 0,0–0,5 %; 3,6 % в сценарии «все ответы на модели X» (около половины запросов упираются в лимит) |
| доля человеко-недель в недельном лимите                            | до 0,1 п.п.; 3–4 п.п. в сценарии X                                                               |
| людей, упёршихся в окно 5 часов                                    | занижено на 20–30 % (например, 154 → 122, 72 → 55, 10 → 7)                                       |
| доля отклонённых запросов, остановленные ответы, «близко к лимиту» | не считаются                                                                                     |

|                                               | SQL-агрегаты                    | выборка + TS            |
| --------------------------------------------- | ------------------------------- | ----------------------- |
| совпадение с калькулятором                    | нет (приближение)               | да, побитово            |
| 265 тыс. строк, холодный запрос               | 0,2 с                           | 0,5–0,6 с (до 0,85)     |
| 1 млн строк, холодный запрос                  | 0,7–0,85 с                      | 2,2–2,7 с               |
| повторный запрос «покрутить» на тех же данных | те же 0,2 с (каждый раз заново) | 3–25 мс из кеша колонок |
| модели, выручка, остаток                      | хорошо                          | точно                   |
| отклонения, остановки, 5 часов, кто близко    | нет                             | да                      |

Рекомендация: **основной путь — выборка + TS-расчёт с кешем колонок**; цифры должны совпадать с калькулятором, а SQL этого не даёт. SQL оставить, если понадобится, как быстрый путь для организаций с очень большим числом строк, помечая цифры «примерно».

## Что поправить в ARCH §20.11 (предложения)

1. **Сигнатура.** `replayLimits(runs, seats, tariffs, options)`: кроме прогонов, нужны места (`{тариф, since}`), без них нельзя ни разложить людей по тарифам, ни посчитать дни места. Результат — по человеку (расход, отклонено, остановлено, упоры, самая дорогая неделя/окно без лимитов), сводка по тарифам — отдельной функцией `forecastNextMonth`. Обе чистые, без часов и БД; прогоны — колонками, а не массивом объектов.
2. **Данные.** «`charge` и токены» не хватает: «покрутить» курс, комиссию и НДС нельзя из `charge` (он уже в рублях по курсу момента). Нужны `cost` + `currency` (они в `model_runs` есть) и токены; `charge` — только для «как записано» по историческому курсу. Переоценка «все ответы на модели X» касается только запросов человека (`purpose` = `chat`, `task`), служебные строки остаются как записаны.
3. **Среднее места.** Записать формулу: «расход за окно ÷ дни места в окне × 30,4», где дни — от `max(since, начало окна)`, места без прогонов считаются. Формула §20.11 «средний `charge` места × места × 30,4/7» это неявно предполагает; калькулятор считает иначе (место с первой строки) — зафиксировать в тесте.
4. **Чтение.** Не тянуть строки как объекты: `date_part` вместо `extract`, `(cost * 1e12)::bigint` вместо `cost::float8` (иначе +240 мс на 265 тыс. строк), порядок `(user_id, created_at, id)` — id нужен для совпадения с порядком записи при равном времени.
5. **Кеш колонок.** Держать колонки организации в памяти процесса `app` под ключом `(организация, окно, число строк / max(created_at))`, срок несколько минут; тогда «покрутить» — 3–25 мс. Память — около 55 МБ на миллион строк. Для следующего месяца окно по умолчанию 4 недели (0,3 с холодно), 8 недель — по просьбе. Если окно больше ~500 тыс. строк, холодное чтение не укладывается в 1 с: показывать «считаю…», держать расчёт вне цикла событий основного процесса (`worker`) или предложить окно короче.
6. **SQL-агрегаты** в прогноз не включать как основной путь: не совпадают с калькулятором и не дают отклонений и остановок. Если нужен быстрый первый показ — помечать «примерно».
7. **Тесты.** Сверка с калькулятором — на синтетике с записанными ответами калькулятора (`golden.json`, этот спайк показал, что так работает); живой набор в публичный репозиторий не кладём, его сверяют вручную скриптом `parity.ts`.
8. **Окно и неделя** — смещение часового пояса передаётся в ядро; DST и перенос границ недели — S24.

## Не проверено / угадано

- Запрос на чтение в базе с **несколькими организациями**: проверена одна (план использует `model_runs_user_time` с фильтром по организации; при многих организациях планировщик возьмёт `(organization_id, created_at)` и отсортирует — скорость не измерена).
- Масштаб `model_runs.cost` в настоящей БД (`numeric` без шкалы): ядро читает до 12 знаков после запятой; больше — потеря точности. На синтетике и живом наборе совпало.
- Объём строк на место взят из формы живых данных с запасом (33 строки на место в неделю; у живого набора меньше); настоящая нагрузка 1000 мест может быть как меньше, так и больше. Граница холодного запроса в 1 с — около 400–500 тыс. строк в окне.
- Задачи (`purpose = task`) в синтетике нет; в ядре они считаются запросами человека, как в ORGS-PLAN §7.3, калькулятор их не знает.
- Время замеров снято на загруженной машине (load average 8–11); на сервере без соседей будет быстрее, но это не проверено.
- Тариф «Макс» (без окна 5 часов) сверен с калькулятором через `l5 = null`: кода такого режима в интерфейсе калькулятора нет.
- SQL-вариант точного расчёта (рекурсивный CTE по строкам) не пробовался: миллион шагов рекурсии заведомо не быстрее выборки.
