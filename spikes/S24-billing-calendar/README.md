# S24. Календарь счетов (ARCH §20.10, ORGS-PLAN §6)

Чистая логика биллинга на одну организацию и идемпотентный прогон по всем организациям. Критерии из PLAN.md: **матрица тестов зелёная; повторный прогон биллинга ничего не меняет.** Модели, продуктовый код и `docs/` не затронуты.

## Модель

Состояние организации (`OrgBillingState`): пояс, статус и причина отключения, конец пробного периода, тарифы (цена в копейках, `vat: {rateBp, included}` — из настроек тарифа), места по тарифам (`seats`, `seatsNext`, `occupied`), журнал `seatChanges` (доплата в копейках, `invoicedIn`), счета, множество выполненных ключей, настройки (`invoiceDay` 25, `dueDay` 1, напоминания).

`tick` возвращает действия: `rollover`, `issueInvoice`, `markOverdue`, `disableOrg`, `notify` (владельцу или суперюзеру). Ключ действия — вид + организация + период (`invoice:org1:2026-12`, `notify:owner:1d:org1:2026-12`).

Правила (то, что записано в ARCH/ORGS, и то, что пришлось дополнить — отмечено «**угадал**»):

- **Доплата** = Δмест × цена × оставшиеся дни / дни месяца, день изменения входит, день — по поясу организации; одно округление на запись журнала. Пример ORGS-PLAN (18 ноября, +2 места, 13/30) = 86 667 коп. Повышение тарифа — (цена нового − цена старого) × та же доля; понижение — 0, с 1-го числа.
- **Перекат**: с 00:00 первого числа `seats = max(seatsNext, occupied)`; одно действие за период, как бы поздно ни пришёл тик. `seatsNext` не трогается (это пожелание владельца, оно остаётся).
- **Счёт**: с 00:00 25-го числа — за следующий месяц: места × цена + все доплаты без счёта + НДС по каждой строке. Количество мест в счёте — `max(seatsNext, occupied)` (так в ORGS-PLAN: «иначе счёт будет за 10»; в ARCH написано `seats_next` — см. ниже).
- **Срок**: 00:00 первого числа по поясу организации. Не оплачен — счёт `overdue`, организация `disabled` с причиной `unpaid`, в действии — номинальный момент (`effectiveAt`) и отдельно время прогона.
- **Напоминания**: владельцу за 5 и за 1 день, суперюзеру за 3 дня, с 09:00 по местному времени (**угадал** час). Не раньше дня после выставления, не после срока, при отставшем тике — только последнее из подходящих.

## Что показала матрица

**Пояса:** Europe/Moscow и Asia/Vladivostok (без перехода), Europe/Berlin (25.10.2026 — день счёта и конец летнего времени), America/New_York (1.11.2026 — день срока и конец летнего времени), Asia/Kolkata (+5:30). Отдельно в тестах `zonedInstant`: Pacific/Kiritimati (+14), Pago_Pago (−11), Australia/Lord_Howe (сдвиг 30 минут), America/Havana (8.03.2026 в 00:00 часы прыгают на 01:00).
**Месяцы:** 12 месяцев 2026 × 5 поясов × 3 проверки (счёт ровно в 00:00 25-го и не минутой раньше; перекат; срок и отключение) = 180 случаев, плюс февраль 28 и 29 дней, апрель, май, 2100 (не високосный), 2000 (високосный).
**Опоздание и повтор:** тик через 2 дня после 25-го; через 5 дней (срок сдвигается); без тиков с 25-го до 1 декабря; простой три недели через срок; повтор в тот же момент; потерянные ключи; устаревший снимок; два прогона одновременно; сбой одной организации. Год и два месяца (6 организаций, прогон каждый час) против прогона с пропусками по 1–2 дня подряд (5 случайных расписаний): те же счета и те же отключённые организации.

## Как встраивается в worker

Как устроены фоновые задачи сейчас (`apps/worker/src/index.ts`, `packages/core/src/tasks-*.ts`):

1. Периодические вещи двух видов. Дайджесты, напоминания, проверка почты — `setInterval` в процессе с флагом «уже идёт»; без Redis, без пояса, при двух worker защиты нет. Задачи пользователей — BullMQ: очередь `tasks`, один планировщик `upsertJobScheduler("tasks-dispatch", {pattern: "* * * * *"})`, `Worker` с `concurrency: 2`, остановка — функция, которую возвращает `startTasksWorker()`; включается только при `REDIS_URL`. Идемпотентность запусков — через `jobId` (задача + время).
2. Память — вторая очередь на том же Redis.

Для биллинга подходит второй вид, но **отдельная очередь `billing`**, не вид `kind` в `tasks`: у `tasks` одновременно идут запуски с вызовами моделей, минутный тик не должен ждать за ними, а биллинг не должен ждать модель.

```ts
// packages/core/src/billing-worker.ts (набросок)
export const BILLING_QUEUE = "billing";

export const startBillingWorker = async () => {
  const queue = new Queue(BILLING_QUEUE, { connection: tasksConnection() });
  // раз в час, на 7-й минуте; повтор после простоя — одно задание, очереди нет (bullmq-check)
  await queue.upsertJobScheduler(
    "billing-tick",
    { pattern: "7 * * * *", tz: "UTC" },
    { name: "tick", data: {}, opts: { attempts: 3, backoff: { type: "exponential", delay: 60_000 }, removeOnComplete: 100, removeOnFail: 500 } },
  );
  const worker = new Worker(BILLING_QUEUE, () => runBilling(pgBillingStore, new Date()), {
    concurrency: 1,
    connection: tasksConnection(),
  });
  worker.on("failed", (job, error) => console.error("billing: tick failed", error));
  return async () => { await worker.close(); await queue.close(); };
};
```

```ts
// apps/worker/src/index.ts — рядом со stopTasks и stopMemory, внутри if (process.env.REDIS_URL)
stopBilling = await startBillingWorker();
```

`pgBillingStore`:

- `orgIds()` — организации с тарифами (в self-hosted без тарифов список пуст, `tick` ничего не делает; процесс можно и не запускать);
- `load(orgId)` — снимок: организация, `org_seats`, `seat_changes` без счёта, счета, ключи `billing_actions` этой организации. Читается вне транзакции, **только чтобы решить, что пора**;
- `commit(orgId, action)` — одна транзакция: `SELECT … FOR UPDATE` строки организации и её `org_seats` (та же блокировка, что у изменений мест из S23) → `INSERT INTO billing_actions (key) … ON CONFLICT DO NOTHING RETURNING` (пусто — «duplicate», выход) → **повторное чтение состояния под блокировкой и пересчёт полезной нагрузки** теми же `planRollover`/`planInvoice` (кто-то мог занять место между чтением и коммитом) → запись эффекта. Письма и уведомления — не в транзакции, а строкой в outbox в той же транзакции; отправляет отдельный шаг, как минимум один раз.

Остаток: список суперюзеру «за 3 дня» — один список из `notify` с `to: "superuser"` за прогон, собирает отправитель из outbox. В `platform_events` пишутся `issueInvoice`, `rollover`, `disableOrg`, `enableOrg`, `markPaid` с `effectiveAt` и временем исполнения.

**Как часто.** Раз в сутки не годится: «00:00 по поясу организации» — это 21:00 UTC для Москвы, 14:00 UTC для Владивостока, 04:00–05:00 UTC для Нью-Йорка. Один суточный тик отключит организацию и прокатит места с опозданием до 24 часов от 00:00 местного (в зависимости от пояса и часа запуска). Предлагаю **каждый час**: отключение и перекат — не позже часа после 00:00 местного. Цена: 0,55 мс на организацию на `tick` плюс чтение состояния; на 1000 организаций это меньше секунды вычислений в час. Если важно именно 00:00 — снимок «просрочен» можно считать в проверке доступа (`dueAt <= now()` у неоплаченного счёта), но это второе место с правилом, не рекомендую.

## Что поправить в ARCH §20.10

1. **«Раз в сутки» → «каждый час»** (BullMQ, повторяемая задача `billing-tick`, отдельная очередь `billing`), см. выше. Идемпотентность — ключ действия в `billing_actions(key primary key)`, заносимый в той же транзакции, что и эффект. `unique (organization_id, period)` спасает только счёт: перекат, отключение и письма им не защищены (`db-check`, случай B: ключи потеряны, счёт защищён уникальным индексом; у остальных действий такого индекса нет).
2. **Количество мест в счёте — `max(seats_next, занято)`**, а не `seats_next` (ORGS-PLAN §6 так и говорит, ARCH — нет).
3. **Дыра в деньгах между 25-м и 1-м.** Если после выставления счёта на следующий месяц добавили место (или людей оказалось больше), доплата за остаток этого месяца записывается, а место следующего месяца в счёт уже не попало. Перекат должен сравнивать `seats` с количеством в выставленном счёте (`billedSeats`; в `invoices.lines` оно и так есть) и записывать в журнал строку `rollover` с суммой за полный месяц на разницу; она попадёт в следующий счёт. Если мест стало меньше, чем оплачено, возврата нет. Тест — «место добавлено 28 ноября».
4. **Месяц создания организации** отдельным счётом не оплачивается: места, купленные в первый месяц, — доплаты в журнале, их забирает счёт 25-го (**угадал**, ARCH молчит). Если организация создана после 25-го — счёт на следующий месяц выставляется на первом тике.
5. **Пропущенное 25-е.** Тик, пришедший после 25-го, выставляет счёт со сроком не раньше «сегодня + 3 дня» (`minNoticeDays`, **угадал**); если месяц уже начался, а счёта на него нет, и организация платила раньше, — запоздавший счёт на текущий месяц с тем же правилом срока. Иначе организацию отключили бы за счёт, который она не получала.
6. **Простой задачи** дольше срока: организация отключается при первом тике с номинальным моментом срока. Льготы за простой нет (**решение нужно**); напоминания после срока не шлются. Простой больше месяца счета не догоняет — нужна тревога «последний тик старше 3 часов» в консоли суперюзера (в `platform_events` писать метку тика).
7. **Отключённая организация**: новых счетов не выставляется, перекат идёт; после включения первый тик выставит запоздавший счёт на текущий месяц (**угадал**, ARCH молчит). Вручную отключённая (`manual`) оплатой не включается; вручную включённая после отключения за неоплату — не отключается снова за тот же счёт.
8. **Пробный период**: периоды, начавшиеся до `trial_ends_at`, бесплатны; доплаты, записанные до первого платного месяца, не выставляются (**угадал**).
9. **Напоминания.** В феврале (28 дней) от 25-го до 1-го 4 дня: напоминание «за 5 дней» приходится на 24 февраля, до счёта, и не отправляется; остаются письмо о счёте и «за день». В тексте: напоминания не раньше дня после выставления.
10. **Дни считаются по календарю пояса**, а не по часам: 23- и 25-часовые сутки на доплату и срок не влияют. Если 00:00 в поясе не существует (скачок часов), берётся первая минута суток. `invoiceDay` и `dueDay` — 1–28.
11. **Округление**: половина вверх, одно на строку журнала и одно на строку счёта; НДС — по строкам, итог — сумма строк. Бухгалтерии сверить с её счетом-фактурой (**угадал**), у разных тарифов с разной ставкой по-другому и не выйдет. Для повышения тарифа ставка и режим НДС берутся у нового тарифа (**угадал**, при смешанных режимах «в цене»/«сверху» разница цен некорректна).

## Где угадал

Час напоминаний (9:00), `minNoticeDays = 3`, правила пробного периода, месяца создания, отключённой организации, источник ставки НДС для повышения, округление НДС по строкам, «последнее из подходящих» напоминание при отставшем тике, один период в `rollover` при простое в несколько месяцев. Время `Intl`/ICU берётся из Node: при смене правил перехода в какой-либо стране нужен свежий Node (ICU вшит).
