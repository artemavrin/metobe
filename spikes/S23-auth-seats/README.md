# S23. Вход и места в одной транзакции

ARCH §20.10, §20.4; PLAN, этап 0. Better Auth 1.7.5 (как в `packages/core`), Postgres 18, база `spike_s23`. Модели и Redis не нужны.

## Что проверяли

1. Выполняются ли `databaseHooks.user.create.before/after` в одной транзакции с созданием пользователя.
2. Можно ли в хуке занять место под `SELECT … FOR UPDATE` строки `org_seats (организация, тариф)` и при отказе откатить создание пользователя с понятной ошибкой.
3. Если нельзя, то какая нужна альтернатива. Плюс гонки на последнее место для всех путей входа и e2e claim → организация.

## Как сейчас устроено (main)

- **Приглашение.** `redeemInvitation` (`packages/core/src/invitations.ts`) создаёт пользователя сам: своя транзакция, глобальный `pg_advisory_xact_lock(7272703)`. После этого действие вызывает `createVerificationOTP` и `signInEmailOTP`. Пользователь к этому моменту уже есть, поэтому хук `user.create` не срабатывает.
- **Claim.** `redeemClaimToken` (`claim.ts`) устроен так же: своя транзакция, `pg_advisory_xact_lock(7272702)`, вставка суперюзера, затем вход по коду.
- **Вход по домену.** Это единственный путь, где пользователя создаёт Better Auth: `signInEmailOTP` не находит пользователя и вызывает `internalAdapter.createUser`. Проверка домена — `canSignUp` в `user.create.before` (`auth-options.ts`).
- **Отказ из хука через `return false`.** `createUser` возвращает `null`, а `signInEmailOTP` падает на `newUser.id` с `TypeError: Cannot read properties of null (reading 'id')` (сценарий 3, `stranger`). Действие `verifyCode` ловит любую ошибку и показывает «Неверный код». Понятной ошибки этот путь не даёт.

## Что делает Better Auth 1.7.5 (по исходникам в node_modules)

- `createWithHooks` (`dist/db/with-hooks.mjs`) работает в таком порядке:
  1. Хук `before(data, endpointContext)`.
  2. Вставка через `getCurrentAdapter(adapter)`.
  3. Хук `after` через `queueAfterTransactionHook`: если транзакция открыта, он идёт после коммита, иначе сразу.

  Транзакции хук не получает. `getCurrentAdapter` даёт только API адаптера Better Auth, без сырого SQL и без `FOR UPDATE`.
- В `signInEmailOTP` (`plugins/email-otp/routes.mjs:414`) `createUser` и `createSession` в `runWithTransaction` не обёрнуты. Обёрнуты только `createOAuthUser` и вход по паролю (`sign-up.mjs:143`).
- У `drizzleAdapter` по умолчанию `transaction: false`: `adapter.transaction(cb)` выполняет `cb` без транзакции.
- **Итог:** при нынешней настройке хуки работают не в одной транзакции с созданием пользователя — транзакции там нет вообще. Блокировка, взятая в хуке, снимается до `INSERT` пользователя (вариант A).
- Вызовы `auth.api.*` не сбрасывают адаптер в AsyncLocalStorage, это делает только `auth.handler` (`runWithAdapter`). Поэтому внешний `runWithTransaction` (экспорт `@better-auth/core/context`) вокруг `auth.api.signInEmailOTP` переводит в одну транзакцию весь эндпоинт: расход кода, хук `before`, вставку пользователя и сессию. Это вариант B.

## Варианты входа по домену

- **A — своя транзакция в хуке.** `before` открывает короткую транзакцию: `FOR UPDATE` → подсчёт → коммит. Затем Better Auth вставляет пользователя отдельным запросом.
- **B — общая транзакция.** Настройка `drizzleAdapter(db, { transaction: true })`, где `db` — обёртка (Proxy). Она кладёт drizzle-транзакцию в свой `AsyncLocalStorage` (`txScope`), чтобы хук до неё дотянулся. Действие входа вызывает `runWithTransaction(ctx.adapter, () => auth.api.signInEmailOTP(…))`. Хук `before`:
  - берёт `tx` из `txScope`;
  - делает `FOR UPDATE org_seats` и подсчёт;
  - если мест нет, бросает `APIError("FORBIDDEN", { code: "NO_FREE_SEATS", message })`, и откатывается всё;
  - если `tx` нет (прямой `POST /api/auth/sign-in/email-otp` в обход действия), бросает `SIGN_UP_OUTSIDE_TRANSACTION`.

Занятые места считаются так:

- **приглашение, вход по домену, включение человека:** активные + открытые приглашения < мест;
- **принятие приглашения:** активные < мест. Приглашение своё место уже держит (ARCH §20.10), поэтому при принятии считаются только активные люди.

## Как запустить

```sh
pnpm install                    # в корне: спайк берёт пакеты workspace
./spikes/S23-auth-seats/setup.sh  # симлинки better-auth, @better-auth/core, drizzle-orm, postgres, tsx
createdb spike_s23              # или create database spike_s23
cd spikes/S23-auth-seats
S23_DATABASE_URL=postgres://USER:PASS@127.0.0.1:5432/spike_s23 node --import tsx s23.ts   # TRIALS=50 по умолчанию
```

Скрипт при каждом запуске пересоздаёт свои таблицы в `spike_s23` и отказывается работать с любой другой базой. Файлы:

- `schema.ts` — таблицы;
- `seats.ts` — `takeSeat`, приглашения, claim, хуки A/B, `makeAuth`;
- `s23.ts` — сценарии.

## Критерии готовности (PLAN, S23)

- **Двое одновременно принимают приглашения на последнее место — входит один, второй видит «Свободных мест нет»: да.** Это сценарии 4 (приглашения, своя транзакция) и 2 (вход по домену, хук Better Auth в общей транзакции). Без блокировки перебор воспроизводится в 47–50 случаях из 50, то есть тест гонку ловит.
- **e2e claim → организация: да.** Сценарий 7: claim создаёт организацию и владельца, вход идёт через `createVerificationOTP` + `signInEmailOTP`, сессия видит организацию.

## Вывод для О1, О6, О10

1. **Хуки Better Auth выполняются вне транзакции создания пользователя.** Занять место в одиночку хук не может: вариант A даёт перебор в 60 % гонок.
2. **Приглашения и claim остаются нашими функциями в своей транзакции** — Better Auth в создании пользователя не участвует, хуки ему не нужны.
   - **Принятие приглашения:** `FOR UPDATE` строки приглашения, затем `FOR UPDATE org_seats`. Глобальный advisory-lock 7272703 больше не нужен.
   - **Выдача приглашения, включение человека, смена тарифа, изменение числа мест:** `FOR UPDATE org_seats` в той же транзакции.
   - **Claim** сохраняет advisory-lock, создаёт организацию и делает суперюзера владельцем (О1).
3. **Вход по домену — вариант B.** Действие `verifyCode` оборачивает `signInEmailOTP` в `runWithTransaction`, а в `drizzleAdapter` включён `transaction: true`. Хук `user.create.before` под `FOR UPDATE` занимает место и бросает `APIError` с кодом `NO_FREE_SEATS`. `verifyCode` отличает этот код от неверного кода и показывает «Свободных мест нет. Владелец организации может добавить место».
   - Откат возвращает и код: тот же код можно ввести ещё раз, пока он не истёк (10 мин).
   - Прямой POST создать аккаунт не может. Вход уже существующих людей не меняется, хук для них не вызывается.
4. **Внутри общей транзакции хуки читают только через `tx`, не через `getDb()`.** Иначе при наплыве входов пул взаимно блокируется (сценарий 9). Это касается и `isSignInAllowed` в `session.create.before`.
5. **Отказ из хука — только через `throw APIError`, не `return false`.** `false` роняет `signInEmailOTP` с `TypeError`; это ошибка и в нынешнем main, её скрывает «Неверный код».

## Предложения в текст ARCH (docs не правил)

- **§20.10, пункт «Каждое изменение мест — в транзакции»** — добавить:
  > Better Auth создаёт пользователя только при входе по домену (`signInEmailOTP`), и его хуки работают вне транзакции. Действие входа оборачивает вызов в `runWithTransaction`, `drizzleAdapter` — с `transaction: true`. Хук `user.create.before` берёт транзакцию из `AsyncLocalStorage`, блокирует `org_seats` и при нехватке мест бросает `APIError` `NO_FREE_SEATS`; вне транзакции новый аккаунт не создаётся. Приглашения и claim создают пользователя своими функциями в своей транзакции. Хуки внутри транзакции не ходят в пул.
- **§20.10, «Занято по тарифу»** — дописать правило принятия:
  > Приглашение уже держит место, поэтому при принятии считаются только активные люди. Если мест стало меньше занятого, первым входит тот, кто первым принял приглашение.
- **§20.4** — нет места для доменов входа и тарифа, который получает человек по домену. Предлагаю `organization_domains (domain PK, organization_id, tariff_id)`: уникальный ключ сам обеспечивает критерий О6 «организации с разными доменами не пересекаются». *Догадка: тариф по домену задаёт владелец или суперюзер — продуктово не решено.*
- **§20.10** — если одно действие трогает два тарифа (смена тарифа человеку), строки `org_seats` блокировать в порядке `tariff_id`, иначе возможен deadlock. *Не проверял, вывод по общему правилу.*
- **Зависимости (§20.15):** `runWithTransaction` экспортирует `@better-auth/core/context`, а он сейчас транзитивный — нужно сделать его прямой зависимостью `packages/core` той же версии, что `better-auth`. Решение опирается на поведение Better Auth (AsyncLocalStorage адаптера, `queueAfterTransactionHook`), а не на документированный контракт хуков. Поэтому сценарии 2, 4 и 9 стоит перенести в тесты `core` как регрессию при обновлении Better Auth — это и есть «тест S23 на последнее место» в О10.
- **Отвергнутая альтернатива:** отключить регистрацию в Better Auth (`disableSignUp`) и создавать пользователя по домену своей функцией. Код нельзя проверить публичным API до появления пользователя (`checkVerificationOtp` требует существующего пользователя, `routes.mjs:255`). Пришлось бы создавать неподтверждённого пользователя до проверки кода, а это место, которое можно занять без доступа к почте. Ещё вариант — триггер Postgres на `INSERT` в `user`. Он работает, но ошибка доходит как 500 без кода, а правила мест уходят из TypeScript.
