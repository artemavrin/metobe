# S22 — счётчики лимитов

ARCH §20.8, ORGS-PLAN §7.4. Критерии из PLAN: p95 проверки меньше 10 мс на 100 тыс. строк человека; из пяти вкладок и задачи отвечают две, остальные видят «Дождитесь ответа»; перерасход — не больше шага на ответ.

Модели не вызывались: ответ моделируется паузами и стоимостями шагов.

## Как запустить

```sh
cd spikes/S22-limit-counters
env -u HTTPS_PROXY -u HTTP_PROXY pnpm install --ignore-workspace --prefer-offline
# .env: DATABASE_URL на базу spike_s22 (та же роль и пароль, что у apps/web/.env, имя базы другое), REDIS_URL=redis://127.0.0.1:6380
node --env-file=.env --import tsx create-db.ts   # создаёт spike_s22 (отказывается работать с другой базой)
pnpm seed                                         # ~45 с, 1,8 млн строк
pnpm bench                                        # часть 1: варианты индекса
node --env-file=.env --import tsx load.ts         # часть 1б: под нагрузкой
node --env-file=.env --import tsx counters.ts     # часть 1в: счётчик-строка вместо суммы
node --env-file=.env --import tsx fresh.ts        # часть 1г: покрывающий индекс без VACUUM
LEASE_MS=3000 HB_MS=1000 node --env-file=.env --import tsx slots.ts   # часть 2: Redis, префикс spike:s22:
node --env-file=.env --import tsx race.ts         # часть 3 (~3 мин)
```

Цифры — в `results/*.json`. Ключи Redis `spike:s22:*` скрипт удаляет сам (проверено: после прогона 0). База `spike_s22` осталась (≈400 МБ), снести: `drop database spike_s22`.

## Стенд и оговорки

- Postgres 18.6 в Docker, настройки по умолчанию (`shared_buffers` 128 МБ, `random_page_cost` 4), 12 ядер Mac. Таблица 272 МБ, не влезает в `shared_buffers`, влезает в кеш ОС.
- **Машина была занята другими спайками** (load average 7–16 на 12 ядрах), поэтому хвосты p95/p99 шумные: один и тот же вариант в двух прогонах отличается в 1,5–2 раза. Для p50 и плана запроса (`EXPLAIN`) шум меньше. Цифры ниже — порядок величины, не паспорт.
- Таблица `runs` повторяет `model_runs` (те же колонки) плюс `organization_id`, `charge numeric(14,6)`, `charge_u bigint`, `charge_currency`. Строки вставлены в порядке времени, люди перемешаны, как в живой базе.
- Данные: 1,8 млн строк.
  - `h_spread` — 100 тыс. строк за год (≈270 в день; неделя ≈ 1,9 тыс.).
  - `h_burst` — 100 тыс. строк **за одну неделю** (худший случай: сумма идёт по всем 100 тыс.).
  - `h_hot` — 100 тыс. строк: 50 тыс. за последние 5 часов (зациклившаяся задача) и 50 тыс. за остальную неделю.
  - 1500 других людей, 1,5 млн строк за 90 дней, распределение скошенное (у части людей тысячи строк).
- «Сейчас» зафиксировано: воскресенье 20:00 по Москве, чтобы неделя была полной. Часовой пояс организации — Europe/Moscow. Начало недели считается `startOfWeek(new TZDate(now, tz), { weekStartsOn: 1 })`; проверил вручную на Europe/Berlin (границы перехода на зимнее время), Europe/Moscow, Pacific/Auckland — понедельник 00:00 местного во всех случаях правильный.

## 1. Сумма `charge` в Postgres

### Проверка

Две части, как в ARCH §20.8:

1. `select started_at from limit_windows where user_id = $1 and kind = '5h'`. Если с `started_at` прошло 5 часов или строки нет, окно начинается с «сейчас» и израсходовано 0 (запись строки в замер не входит: раз в 5 часов, одна вставка по первичному ключу).
2. Одна сумма по индексу: `sum(charge) filter (where created_at >= начало_5ч)` и `sum(charge) filter (where created_at >= начало_недели)` при `created_at >= least(начало_5ч, начало_недели)`. `least` нужен: окно в 5 часов, открытое в воскресенье вечером, переходит через понедельник 00:00.

Два запроса быстрее, чем один с CTE (окно из `limit_windows` внутри запроса): CTE дал 10–30 мс вместо 6–14, планировщик хуже ограничивает диапазон. Брать два запроса.

### Варианты индекса и типа колонки

Все замеры — последовательные, один клиент, 300 повторов на человека (900 на 300 случайных остальных людей). Второй прогон, p50 / p95 в мс.

| индекс, тип колонки | размер индекса | `h_spread` (100 тыс. за год) | `h_burst` (100 тыс. за неделю) | `h_hot` | остальные люди |
|---|---|---|---|---|---|
| без индекса (только PK), seq scan | — | — | 101 / 169 | — | — |
| I0 `(user_id, created_at)` (как `model_runs_user_time`), numeric | 55 МБ | 3,0 / 9,8 | 22 / 36 | 23 / 38 | 1,2 / 6,0 |
| I0, bigint | 55 МБ | 2,0 / 4,7 | 25 / 69 | 24 / 59 | 0,7 / 1,8 |
| **I1** `(user_id, created_at) include (charge)`, numeric | 72 МБ | **0,7 / 1,3** | **8,1 / 14** | **8,0 / 9,5** | 0,6 / 1,0 |
| I2 `… include (charge_u)`, bigint | 71 МБ | 0,6 / 1,2 | 6,4 / 12,6 | 6,5 / 11,6 | 0,6 / 1,4 |

Первый прогон (машина чуть свободнее): I1 — `h_burst` p95 8,1, `h_hot` 9,7; I2 — `h_burst` 7,5, `h_hot` 8,2; `h_spread` p95 0,9–1,1 мс.

Что видно:

- Индекс `model_runs_user_time` как он есть (I0): на `h_spread` p95 5–10 мс (на границе), на `h_burst` 23–70 мс. План — Bitmap Heap Scan: за 100 тыс. строк идёт в кучу (6,5 тыс. страниц).
- **Покрывающий индекс** `include (charge)` даёт Index Only Scan, `Heap Fetches: 0`, 500 страниц индекса: на реалистичном распределении (`h_spread`) p95 ≈ 1 мс, на худшем (`h_burst`, `h_hot`) p50 6–8 мс, EXPLAIN-время исполнения 6,5–7,5 мс (≈65 нс на строку). Цена: индекс больше на 30 %.
- Тип колонки почти не важен: numeric и bigint отличаются на 10–20 %, меньше шума. Менять `charge` на целые «микро-единицы» ради скорости не нужно.
- Остальные люди (почти все пользователи) — p95 около 1 мс при любом индексе.
- Затраты на 100 тыс. строк — линейные. 100 тыс. строк в одной неделе одного человека — это потолок, а не обычный случай: при лимите, упирающемся в ~5 % человеко-недель (ORGS-PLAN §7.5), недельных строк у человека тысячи, не сотни тысяч. Критерий S22 («100 тыс. строк человека») я читал как «всего строк у человека», худший вариант «все за неделю» взял для запаса.

### Под нагрузкой (`load.ts`)

16 параллельных клиентов (больше, чем ядер: клиент и база делят процессор), 5 % проверок — по людям с 100 тыс. строк за неделю, плюс писатель 50 вставок/с. p95 в мс:

| | I0 | I1 |
|---|---|---|
| люди с 100 тыс. строк (`h_burst`, `h_hot`) | 87 | 24 |
| остальные люди | 10 | 5,4 |
| только «тяжёлые», 16 клиентов (стресс) | 142 | 37 |
| только «тяжёлые», 4 клиента | 35 | 21 |

То есть при насыщенном процессоре проверка 100 тыс. строк за неделю не укладывается в 10 мс ни в одном варианте. Для остальных людей укладывается с запасом (5 мс при 16 клиентах на 12 ядер). Нагрузка нереальная: 16 проверок одновременно по людям с 100 тыс. строк в неделе.

### Покрывающий индекс и VACUUM (`fresh.ts`)

Index Only Scan быстрый, только пока страницы кучи помечены в карте видимости. 100 тыс. свежих строк человека без `VACUUM` после вставки: `Heap Fetches: 100000`, p50 39 мс, p95 70 мс (хуже I0). После `VACUUM`: `Heap Fetches: 0`, p50 8,8 мс.

Автовакуум по вставкам срабатывает при 1000 + 20 % строк таблицы (`autovacuum_vacuum_insert_scale_factor = 0.2`): на таблице в миллионы строк последние сотни тысяч вставок могут остаться без карты видимости. Это как раз текущая неделя. Для людей, у которых за неделю десятки или сотни строк, цена — десятки обращений к куче, незаметно. Для таблицы `model_runs` стоит поставить `autovacuum_vacuum_insert_scale_factor = 0.01` (**не проверено в спайке**, угадал по документации Postgres; проверить на стенде, где поднимут миграцию).

### Счётчик-строка вместо суммы (`counters.ts`)

Строка `limit_usage (user_id pk, five_start, five_used, week_start, week_used)`, `update … set used = used + charge` в той же транзакции, что и вставка `model_runs`.

- Чтение по первичному ключу: p50 0,6 мс, p95 3 мс (шум), не зависит от числа строк.
- Запись: вставка + обновление счётчика в одной транзакции — p50 1,3 мс против 1,0 мс без счётчика (на одного писателя); два писателя одного человека — p95 7,7 против 2,5 мс; восемь — p95 20 мс (они сериализуются на блокировке строки счётчика).
- **Первая версия (строка на `(человек, kind)` и `update … where kind in ('5h','week')`) дала `deadlock detected`** при двух писателях одного человека. Строка на человека с двумя колонками, либо фиксированный порядок обновления, снимает.
- Цена агрегата: ещё одно место, где сумма может разойтись с `model_runs` (ответ, у которого запись расхода упала, правки задним числом, смена курса, перенос окна). Надо сверять с суммой и чинить дрейф. Источник правды остаётся сумма.

### Вывод по части 1

- **Агрегат в v1 не нужен.** Нужно заменить `model_runs_user_time` на `(user_id, created_at) include (charge)`. Тогда p95 проверки на человеке с 100 тыс. строк за год — около 1 мс; на человеке с 100 тыс. строк за одну неделю — 8–14 мс в зависимости от шума машины (на границе критерия, при пустой машине — 6,5–7,5 мс по EXPLAIN).
- Если эта граница станет проблемой (человек с > 50 тыс. строк в неделе, много параллельных проверок), следующий шаг — `limit_usage`, но не раньше: он добавляет второй источник правды.
- Источник правды остаётся Postgres (ORGS-PLAN §7.4 подтверждён).

## 2. Счётчик одновременных ответов в Redis (`slots.ts`)

### Схема

Ключ `limits:inflight:{userId}` — sorted set: член = id ответа, оценка = момент окончания аренды (мс по часам Redis). Один Lua-скрипт на acquire и heartbeat, release — обычный `ZREM`:

- **acquire**: убрать просроченных (`ZREMRANGEBYSCORE … -inf now`); если нашего id нет и `ZCARD ≥ 2` — вернуть 0 («Дождитесь ответа»); иначе `ZADD id now+lease`, `PEXPIRE ключ 2·lease`, вернуть 1.
- **heartbeat** каждые `lease/3`: тот же скрипт, продлевает аренду. Если слот потерян (аренда кончилась, Redis сброшен), берёт его снова, когда есть место; иначе возвращает 0 — ответ не обрывается, событие пишется в лог.
- **release**: `ZREM` в `finally` и в обработчике SIGTERM.

Время берётся внутри скрипта через `TIME` Redis: часы `app` и `worker` не нужны. Значения для прода: аренда 30 с, пульс 10 с. В тесте уменьшены до 3 с / 1 с (`LEASE_MS`, `HB_MS`).

### Результаты (аренда 3 с, пульс 1 с; процессы — отдельные `node`, как `app` и `worker`)

| сценарий | результат |
|---|---|
| 1. пять вкладок (процесс `app`) и задача (процесс `worker`) одного человека в один момент | 6 попыток → 2 приняты (по одной в каждом процессе в этом прогоне), 4 получили «занято»; в Redis 2 |
| 2. `SIGKILL` процесса, держащего слот; вкладка пробует каждые 100 мс (6 прогонов, момент убийства случайный внутри периода пульса) | слот освободился через 2155–2998 мс (ожидание: от `lease − пульс` до `lease`). В проде: 20–30 с |
| 3. `SIGTERM` (деплой) | слот свободен через 13 мс |
| 4. длинный ответ 4 × аренда, третья вкладка пробует каждые 250 мс | пущена 0 раз из ~48 попыток; слоты на месте |
| 5. цикл событий встал дольше аренды (пульс опоздал) | слоты истекли, третий ответ вошёл (три одновременных). Когда старый держатель проснулся, он забрал слот назад, а второй увидел «нет места» и продолжил работу. Цена короткой аренды |
| 6. ключ потерян (как после рестарта Redis без сохранения) | новый ответ принят (счётчик пустой, fail-open); пульс восстановил слоты до лимита, второй старый ответ остался без слота и не прерван |
| 7. гонка: 40 клиентов × 100 циклов acquire/hold/release одного человека, счётчик «держат» в отдельном ключе | максимум одновременно 2, превышений нет; 62 приняты, 3938 отказов; acquire под конкуренцией p50 2,3 / p95 8,1 мс |
| 8. задержка без конкуренции | acquire p50 0,4 / p95 1,8 мс; release 0,4 / 1,6 мс |

Все ключи `spike:s22:*` удалены.

### Что важно для О8

- **TTL «как у самого долгого ответа» из ARCH не годится.** Счётчик с `INCR`/`DECR` и TTL 10–30 минут после падения процесса держит слот до TTL: человек остаётся без ответа на десятки минут. Аренда с пульсом освобождает слот за ≤ `lease`.
- Падение Redis или его пустой ключ — «открыто»: счётчик на время пропадает, лимит денег всё равно работает (часть 3). Я так решил (угадал): отказать всем, пока Redis недоступен, хуже. Решение за владельцем продукта.
- Для задачи в `worker` отказ слота — не «Дождитесь ответа», а отложенный повтор (BullMQ `moveToDelayed`, 10–15 с) с тем же правилом «не больше двух». **В спайке BullMQ не проверялся**, это предложение.
- Один и тот же `acquire` вызывается и до запуска ответа, и из пульса; поэтому слот можно потерять незаметно только когда цикл событий стоит дольше аренды. Аренда ≥ 3 × пульс.
- Размер: 1 ключ на человека с ответом, 1–2 члена, 2·lease жизни.

## 3. Перерасход на границе лимита (`race.ts`)

Модель: два ответа одного человека начинают одновременно, оба проходят проверку (расход каждого ещё нигде не записан), остаток `R` — от 0,5 до 10 шагов. Шаг — 5–30 с (виртуальное время), стоимость шага — равномерно от 0 до `S` или «в основном мелкие, редкие большие» (до `S`). `S` — максимальная стоимость одного шага. 200 тыс. прогонов на ячейку. Перерасход — в единицах `S`.

Три политики:

- **A** — как написано в ARCH: остаток фиксируется на старте ответа, ответ останавливается, когда **его собственный** расход ≥ остатка.
- **B** — расход шага пишется в Postgres сразу после шага (ARCH §20.8 это уже требует), `stopWhen` после каждого шага заново читает сумму человека; сумма ≥ лимита — стоп.
- **C** — B плюс резерв: перед шагом ответ резервирует один максимальный шаг в Redis; шаг, который может не влезть, не стартует.

Перерасход (max, в `S`), равномерная стоимость шага:

| одновременных ответов | A | B | C |
|---|---|---|---|
| 1 | 1,0 | 1,0 | 0 |
| 2 | **11,7** (среднее 5,9) | **2,0** (среднее 0,8) | 0 |
| 3 | 22,3 | 2,9 | 0 |

- При остатке 50 `S` и двух ответах A даёт перерасход в среднем **50,7 `S`**: каждый ответ тратит весь остаток независимо от другого. B — 0,8 (max 2,0).
- B: перерасход не больше `числа одновременных ответов × S` (1,0 / 2,0 / 2,9 — в пределах), то есть «не больше шага на ответ». Это шаг, который другой ответ уже начал, когда сумма пересекла лимит.
- C: перерасхода нет, но не расходуется в среднем 0,67 `S` остатка (0,8 `S` при мелких шагах). При остатке лимита в тысячи `S` это ничто, но резерв требует оценки максимального шага (вход известен, выход — нет: нужен `maxOutputTokens × цена`). Усложнение не оправдано, если B укладывается в «шаг на ответ».
- Реальный Postgres (`runs`, 2 ответа, паузы 20–80 мс, `S = 0,2`, лимит 1,0, 300 прогонов): B — перерасход среднее 0,77 `S`, max 1,76 `S` (≤ 2), перепроверка суммы после шага p50 0,6 мс / p95 1,8 мс. A — среднее 3,9 `S`, max 7,5 `S`.

### Вывод по части 3

**Критерий выполняется только для B, не для A.** ARCH §20.8 сейчас говорит «остаток фиксируется на старте ответа»: при двух параллельных ответах (которые мы сами разрешаем) перерасход ограничен не шагом, а целым остатком на старте. Нужно: после каждого шага писать расход в `model_runs` и в `stopWhen` читать свежий остаток (или проверять сумму `used_с_старта + расход_ответа + сумма_других_ответов_в_пути`). Тогда перерасход ≤ шаг на каждый одновременный ответ, то есть ≤ 2 шагов на человека. «Дыру» одного ответа закрывает уже написанное «расход пишется по шагам».

## Критерии готовности

| критерий | выполнен |
|---|---|
| p95 проверки < 10 мс на 100 тыс. строк человека | **да, с покрывающим индексом.** 1 мс при 100 тыс. строк за год; 8–14 мс при 100 тыс. строк в одной неделе (граница); при перегрузке процессора в худшем случае — нет (24–37 мс). С текущим индексом `model_runs_user_time` — нет (23–70 мс в худшем случае) |
| из пяти вкладок и задачи отвечают две, остальные «Дождитесь ответа» | да (сценарии 1, 7; слот освобождается после падения процесса за ≤ аренду, сценарий 2) |
| перерасход ≤ шага на ответ | да, **при условии** B (расход по шагам + перечитывание суммы в `stopWhen`); по схеме A из ARCH — нет |

## Что поправить в ARCH §20.8 (предложение)

1. **Израсходовано.** Индекс `model_runs_user_time` заменить на `(user_id, created_at) include (charge)`; пояснить: сумма — источник правды, агрегата не нужно; для `model_runs` поставить `autovacuum_vacuum_insert_scale_factor` около 0,01, иначе покрывающий индекс на свежих строках уходит в кучу. Скорость на 100 тыс. строк — результат S22: ≈1 мс (за год), 8–14 мс (все 100 тыс. в одной неделе).
2. **Проверка до запроса.** Два запроса (окно из `limit_windows`, сумма с `least(начало_5ч, начало_недели)`), не один с CTE.
3. **Остановка внутри ответа.** Вместо «остаток фиксируется на старте ответа» — «остаток перечитывается после каждого шага: `stopWhen` берёт свежую сумму человека, куда уже вошёл записанный расход шагов всех его ответов». Фиксированный остаток при двух параллельных ответах даёт перерасход вплоть до всего остатка (S22).
