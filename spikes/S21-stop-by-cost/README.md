# S21 — остановка ответа по деньгам

ARCH §20.8, PLAN S21. Проверено: `stopWhen` в `ai@7.0.173` (версия из `apps/web`) останавливает ответ по накопленной стоимости шагов. Ещё проверено, что происходит при ошибке, отмене, подтверждении тула, resume и в проходе «итог».

Модели только моковые (`MockLanguageModelV4` из `ai/test`; в `ai@7` это актуальный мок, `V3` оставлен для старых провайдеров). Сеть, Postgres и Redis не используются: строки `model_runs` собираются в массив так же, как их считает `recordRun`. Нагрузка на сумму в базе — спайк S22.

## Как запустить

```sh
cd spikes/S21-stop-by-cost
env -u HTTPS_PROXY -u HTTP_PROXY pnpm install --ignore-workspace   # через прокси реестр npm не отвечает
pnpm test                                                           # 13 тестов, < 1 с
node /path/to/typescript/bin/tsc -p tsconfig.json                   # typecheck; tsc не ставится в спайк
```

Код приложения импортируется без копий:

- `packages/core/src/pricing.ts` (`costOf`, `addCosts`);
- `apps/web/lib/steps.ts` (`ANSWER_NOW*`, `MAX_STEPS`);
- `apps/web/lib/sum-up.ts` (`saidNothing`, `sumUpPrompt`);
- `apps/web/lib/resume-stream.ts` (`recordStream`, `resumeStream`). `server-only` для неё подменён пустым модулем.

| файл | что в нём |
| --- | --- |
| `budget.ts` | бюджет ответа: `stepCost` (Gateway `providerMetadata.gateway.cost`, иначе токены × прайс через `costOf`), `stop` для `stopWhen`, `onStepEnd` для записи, `lastStepIfShort` для `prepareStep`, `left`, `over` |
| `answer.ts` | маршрут чата, сокращённый до бюджета: проход, запись строки, «итог», строка про лимит (`data-limit`), запись стрима для resume |
| `mock-model.ts` | мок: токены входа считаются по промпту (≈ 4 символа), поэтому шаг дорожает с ростом истории. Режим Gateway отдаёт `gateway.cost` строкой. Прайс $3 / $15 за 1 млн токенов |
| `budget.test.ts` | критерии S21 |
| `callbacks.test.ts` | какие колбэки `streamText` реально срабатывают при сбое на третьем шаге |

## Цифры

Прайс мока $3 / $15 за 1 млн, тул отдаёт около 1800 символов. Семь шагов (шесть с тулом, последний — текст) стоят 0.000966 / 0.002517 / 0.004065 / 0.005616 / 0.007164 / 0.008715 / 0.011613 $.

Остаток 0.0055155 $ (кончается посреди третьего шага):

| вариант | вызовов модели | записано | сверх остатка | чем кончился ответ |
| --- | --- | --- | --- | --- |
| жёсткий (`stopWhen`), Gateway | 3 из 7 | 0.007548 | 0.002033 (половина 3-го шага) | тул-шаг без текста, затем строка про лимит |
| жёсткий, прайс источника | 3 из 7 | 0.007548 | 0.002033 | то же |
| мягкий (`prepareStep` снимает тулы) | 3 из 7 | 0.009207 | 0.003692 | текстом, затем строка про лимит |

Мягкий вариант перерасходует больше: отвечающий шаг пишет длиннее, чем шаг с тулом (150 токенов против 60). Оба варианта укладываются в «остаток + один шаг».

Проход «итог»: вся история на вход, короткий ответ на выход.

| шагов работы | работа, $ | последний шаг, $ | итог, $ | итог / последний шаг | итог / работа |
| --- | --- | --- | --- | --- | --- |
| 3 | 0.0075 | 0.0041 | 0.0073 | 1.79 | 96% |
| 10 | 0.0794 | 0.0149 | 0.0181 | 1.22 | 23% |
| 20 | 0.3139 | 0.0304 | 0.0336 | 1.11 | 11% |

Итог стоит как ещё один шаг, в 1,1–1,8 раза дороже последнего. Без кэша промпта в моке; с кэшем вход дешевле, но в долях будет похоже (оценка).

## Что выяснилось про `ai@7.0.173`

1. **`stopWhen` спрашивается только после шага, в котором были вызовы тулов с результатами.** Тулы этого шага к тому моменту уже выполнены. Шаг, который ответил текстом, или шаг, ждущий подтверждения, кончает цикл сам, и `stopWhen` не зовётся. Поэтому отдельно нужен `over()`: «готовые шаги дошли до остатка». Перед первым шагом `stopWhen` не спрашивается вовсе.
2. **Колбэки при сбое** (`callbacks.test.ts`, сбой на третьем шаге из трёх):

   | случай | что срабатывает |
   | --- | --- |
   | вызов провайдера отклонён (`doStream` reject) | `onError`, `onStepError`, затем **`onEnd`** с двумя готовыми шагами и пустым `totalUsage` |
   | чанк `error` от провайдера | `onError`, затем `onStepEnd` с `finishReason: error` (usage и `gateway.cost` есть), затем `onEnd` с тремя шагами |
   | поток оборвался посреди шага (нет `finish`) | только `onStepError` и ошибка потока; **ни `onError`, ни `onEnd`, ни `onAbort`** |
   | «Стоп» (abort) | `onAbort({ steps })` с готовыми шагами, `onEnd` нет |

   Что это значит для нынешнего маршрута (`route.ts:738–792`):
   - при отклонённом вызове пишутся две строки: `error` без расхода (`onError` шагов не получает) и `ok`. В строке `ok` стоимость Gateway верная (`stepsMetadata`), а у источника с прайсом токены из пустого `totalUsage` дают 0;
   - при обрыве потока не пишется ничего.

   Вывод: писать строку один раз — после `await result.consumeStream({ onError })`. Расход брать из шагов, накопленных в `onStepEnd`, статус — из флагов `onError` / `onStepError` / `onAbort`. Так сделано в `answer.ts`; все четыре случая дают одну строку с расходом готовых шагов (`budget.test.ts`).

3. **`result.response.messages` — только последний шаг** (поле deprecated). Накопленное — в `result.responseMessages`. `apps/web/lib/sum-up.ts:99` берёт `first.response`, поэтому нынешний «итог» видит только последний вызов тула и его результат, а не всю работу. Это ошибка вне S21, но она в том же месте. Тест: `the sum-up pass › needs responseMessages`.
4. **Недосчёт при отмене или обрыве.** Шаг, прерванный посреди потока, usage не отдаёт, и его стоимость теряется. Провайдер, вероятно, выставит счёт за прочитанные токены (**угадано**, у Gateway не проверялось). Недосчёт — не больше одного шага.

## Критерии готовности

| критерий | итог | тест |
| --- | --- | --- |
| ответ останавливается на шаге, где превышен остаток | **да** | `the hard stop › stops on the step…` (Gateway и прайс): 3 вызова из 7 |
| записанный `charge` ≤ остаток + один шаг | **да** (в валюте модели; `charge` = cost × курс — линейно, вывод тот же) | там же и в `the soft way…` |
| расход пройденных шагов пишется и при ошибке посреди ответа | **да**, но не так, как написано в ARCH: `onError` шагов не даёт, нужен `onStepEnd` + одна запись после `consumeStream` | `what the steps cost is written…` (4 случая) |
| в истории — строка про лимит | **да**, data-часть `data-limit` сохраняется в сообщении ответа (`onEnd` у `createUIMessageStream`) | `the line about the limit › is saved…` |
| resume показывает её же | **да**: `resumeStream` отдаёт те же части в том же порядке, что сохранены | там же |
| подтверждение тулов | **поведение описано, нужна правка маршрута** (ниже) | `approvals › …` |
| проход «итог» после остановки | после жёсткой остановки **невозможен по построению**: остаток уже 0. Стоит как ещё один шаг (таблица выше). Замена — мягкий последний шаг | `the sum-up pass › …`, `the soft way…` |

## Подтверждение тулов и resume

- Шаг, который просит подтверждения, кончает цикл без `stopWhen`. Если он исчерпал остаток (`over()`), ответ кончается карточкой подтверждения, а после неё — строкой про лимит.
- Продолжение после «Разрешить» — новый запрос с тем же сообщением (`originalMessages`). `streamText` выполняет одобренный тул **до** первого вызова модели, а `stopWhen` спрашивается только после шага. Поэтому при остатке 0 без проверки до запроса проходят тул и ещё один платный шаг (тест это показывает).
- Защищает только `checkLimits` в `refuse` (`route.ts:395`): при остатке ≤ 0 — карточка 429. `refuse` стоит до `saveMessages`, ответ на подтверждение не сохраняется, карточка остаётся «ждёт подтверждения», и после сброса её можно подтвердить снова.
- Если продолжение разрешено (окно сбросилось), старая строка `data-limit` остаётся в середине того же сообщения, над новым текстом. Это видно в тесте. `applyToLast` (`route.ts:292`) должен убирать `data-limit` из последнего сообщения.
- Resume: `recordStream` пишет все нетранзиентные чанки, `data-limit` — нетранзиентная data-часть. Страница, перезагруженная до сохранения, получает строку из записи стрима; после сохранения — из базы. Модель строку не видит: `convertToModelMessages` отбрасывает data-части (проверено).

## Куда встраивается в коде

Как сейчас пишется расход: `recordRun` (`packages/core/src/chat-run.ts:115`) — одна строка `model_runs` на проход.

- `cost` = сумма `gateway.cost` по шагам (`reportedCostOf`), иначе `costOf` от **`totalUsage`**.
- В маршруте вызывается из `onEnd` / `onError` / `onAbort` основного прохода (`route.ts:738–792`) и прохода «итог» (`:887–913`).
- Задачи (`task-run.ts:289`) и Telegram (`telegram-chat.ts:218`) устроены так же.

Предлагаемые места:

1. **До запроса** — `refuse` (`route.ts:384`): `checkLimits(ctx)` рядом с `checkChatLimit`. Отсюда же `remaining` = min(5 ч, неделя). Это и единственная защита продолжения после подтверждения.
2. **Бюджет ответа** — перед `streamText` (`route.ts:733`): `createBudget({ remaining, prices })` из `budget.ts`. Без тарифа бюджета нет.
3. **`streamText`**:
   - `stopWhen: [isStepCount(MAX_STEPS), budget.stop]` (`:804`);
   - `onStepEnd: budget.onStepEnd`;
   - `onStepError` / `onError` / `onAbort` только ставят флаги;
   - в `prepareStep` (`:795`) — `lastStepAnswers(...) ?? budget.lastStepIfShort(...)`.
4. **Запись расхода**:
   - `void result.consumeStream()` (`:870`) → `result.consumeStream({ onError }).then(() => record(...))`, одна строка на проход;
   - `recordRun` принимает шаги (`usage` + `providerMetadata` каждого) и считает стоимость по шагам: `gateway.cost` шага, иначе `costOf` шага. `totalUsage` не использовать: при сбое он пустой;
   - `endGeneration` остаётся в колбэках и в конце `execute`.
5. **«Итог»** (`lib/sum-up.ts`, `streamAnswer`):
   - запускать, только если `budget.left() > 0`. После жёсткой остановки это всегда ложно, и ответ кончается строкой про лимит;
   - `first.response` → `first.responseMessages` (`:99`).
6. **Строка про лимит**:
   - `streamAnswer` перед `finish` пишет `{ type: "data-limit", data: { window, resetAt } }`, если `budget.stopped()` или (последний шаг ждёт пользователя и `budget.over()`);
   - в `ChatDataParts` (`packages/contracts/src/chat.ts:67`) добавить `limit`, в UI — строку «Лимит … исчерпан, ответ остановлен. Сброс в …».
7. **Задачи и Telegram** — те же пункты 2–4 (`task-run.ts:297`, `telegram-chat.ts:230`). Строка про лимит там — в отчёт задачи и в текст сообщения.

## Рекомендация для ARCH §20.8 / §20.15

- «Остановка внутри ответа»:
  - дописать, что `stopWhen` спрашивается только после шага с тулами, после их выполнения. Перерасход — не больше одного шага, при мягком варианте — один отвечающий шаг;
  - дописать, что продолжение после подтверждения защищает только проверка до запроса: одобренный тул выполняется до первого шага.
- «Расход пишется по шагам»: заменить «`onStepEnd` в `ai@7` или `sumUsage` в `onError`» на «стоимость копится в `onStepEnd`; строка пишется один раз после `consumeStream`; статус — из `onError` / `onStepError` / `onAbort`». Указать, что `onError` шагов не получает, при отклонённом вызове после `onError` всё равно зовётся `onEnd` (сейчас это две строки), а при обрыве потока не зовётся ни `onError`, ни `onEnd` (сейчас строки нет).
- «Проход „итог“»:
  - после остановки по деньгам итог не запускается: остаток уже 0;
  - основной путь — мягкий: `prepareStep` снимает тулы со шага, который по оценке (стоимость прошлого шага) дойдёт до остатка, и ответ кончается текстом без лишнего вызова;
  - жёсткий `stopWhen` остаётся страховкой;
  - если итог всё же нужен, держать резерв ≈ 1,5 × последний шаг (по таблице).
- Строку про лимит записать как data-часть `data-limit` (`ChatDataParts`), не текстом: её не видит модель, она переживает resume и сохранение; при продолжении после подтверждения `applyToLast` её убирает.
- Отдельно (вне лимитов): `sum-up.ts:99` — `responseMessages` вместо `response.messages`.
- Модель без прайса не через Gateway: стоимость шага неизвестна, бюджет считает её как 0, и остановки не будет. Либо такие модели не входят в списки тарифов, либо для них нужна оценка. Сейчас `costOfSteps` считает такие шаги в `unknown`.

## Где угадано

- Формат `gateway.cost` — десятичная строка на каждом шаге. Так его разбирает `chat-run.ts:52`; на живом Gateway в этом спайке не проверялось. Число без экспоненты `stepCost` тоже понимает.
- Счёт провайдера за шаг, прерванный посреди потока, неизвестен (п. 4).
- Цифры «итога» — на моке без кэша промпта.
