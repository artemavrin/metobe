# S20 — изоляция организаций и RLS

## Что проверялось

- Правило импорта для схемы `catalog_items`: таблицу импортирует только `fixtures/core/catalog.ts`; `fixtures/core/chat.ts` имитирует чужой модуль.
- RLS на `catalog_items` и `model_runs` в отдельной базе `spike_s20`, две организации, роль приложения без `SUPERUSER` и `BYPASSRLS`.
- Пул `postgres-js` размером 10 и 40 долгоживущих ответов чата. Ответы живут по 120 секунд, каждый раз в секунду выполняют короткую транзакцию.
- Утечка контекста при сессионном `set_config(..., false)`, повторное использование backend из пула, транзакционный `set_config(..., true)` и запрет записи в чужую организацию.

Продуктовые файлы и документы не менялись. Вся схема и нагрузочные данные находятся только в `spike_s20`.

## Правило oxlint

Использована встроенная в установленный `oxlint 1.85.0` проверка `no-restricted-imports`. В `oxlint.config.json` запрещён точный путь схемы, а override разрешает его в модуле-владельце.

```sh
pnpm --dir spikes/S20-org-isolation-rls exec oxlint \
  --disable-nested-config \
  -c oxlint.config.json \
  fixtures/core
```

Команда намеренно завершается с кодом 1 и показывает:

```text
fixtures/core/chat.ts:2:1: error eslint(no-restricted-imports): '@metobe/db/schema/catalog_items' import is restricted from being used.
```

Проверка только владельца проходит с кодом 0:

```sh
pnpm --dir spikes/S20-org-isolation-rls exec oxlint \
  --disable-nested-config \
  -c oxlint.config.json \
  fixtures/core/catalog.ts
```

В рабочем конфиге ядра такой запрет нужно описать для каждой организационной схемы и оставить исключение только соответствующему модулю-владельцу. Правило проверяет строку import path; обход через общий barrel-экспорт нужно закрывать отдельным ограничением на barrel.

## Запуск базы и замера

Использовать локальные учётные данные PostgreSQL, но DSN должен оканчиваться на `/spike_s20`.

```sh
createdb -h 127.0.0.1 -p 5432 -U <local-role> -O <local-role> spike_s20
export S20_ADMIN_DATABASE_URL='postgres://<local-role>:<password>@127.0.0.1:5432/spike_s20'
psql "$S20_ADMIN_DATABASE_URL" -v ON_ERROR_STOP=1 \
  -f spikes/S20-org-isolation-rls/schema.sql
pnpm --dir spikes/S20-org-isolation-rls install --ignore-workspace
S20_ADMIN_DATABASE_URL="$S20_ADMIN_DATABASE_URL" \
  pnpm --dir spikes/S20-org-isolation-rls benchmark
```

Пример формы DSN: `postgres://<local-role>:<password>@127.0.0.1:5432/spike_s20`. Скрипт откажется работать, если путь не `/spike_s20`. `schema.sql` пересоздаёт только таблицы этого spike. Пользователь `spike_s20_app` имеет доступ только к `catalog_items` и `model_runs`; демонстрационный пароль `s20-local-only` предназначен только для локальной базы.

Параметры нагрузки можно переопределить через `S20_SESSIONS`, `S20_DURATION_MS`, `S20_WARMUP_MS`, `S20_INTERVAL_MS`. По умолчанию — 40 сессий, 120 секунд измерения, 5 секунд прогрева каждого режима и одна транзакция в секунду. Пул ограничен 10 соединениями.

## Результаты

Среда: PostgreSQL 18.6, `postgres-js 3.4.9`, `oxlint 1.85.0`. На каждую организацию создано 5 000 строк каталога и 50 000 `model_runs`. Административная роль локального `.env` — `SUPERUSER`; она использовалась только для схемы и переключения RLS. Замер работает как `spike_s20_app` (`NOSUPERUSER`, `NOBYPASSRLS`), потому что superuser обходит RLS. Перед каждым измерением режим прогревался 5 секунд; эти транзакции в таблицу не включены. Время — от начала транзакции до её commit, включая ожидание пула; в транзакции читаются обе таблицы. В baseline RLS выключен и запросы имеют явный `organization_id`; в RLS-фазе тот же запрос дополнительно получает `set_config('app.org_id', orgId, true)`.

| Режим                    | Транзакции | Соединения по `pg_backend_pid()` |      p50 |       p95 | Ошибки |
| ------------------------ | ---------: | -------------------------------: | -------: | --------: | -----: |
| Без RLS                  |      4 800 |                         10 из 10 | 7,900 мс | 48,655 мс |      0 |
| RLS + локальный контекст |      4 800 |                         10 из 10 | 5,628 мс | 24,673 мс |      0 |

В этом запуске p95 RLS был на 23,982 мс ниже baseline, но холодный предварительный запуск дал обратное направление. Хвост локальной задержки шумный; по этим цифрам нельзя утверждать, что RLS ускоряет запросы. Практический вывод — явной цены RLS в этом сценарии не видно. Отдельная короткая проверка подтвердила, что транзакция A видит только 5 000 строк каталога и 50 000 `model_runs` A, транзакция B — только строки B, запрос без контекста видит 0 строк обеих таблиц, а межорганизационные вставки в обе таблицы отклоняются с SQLSTATE `42501`.

### Что ломается без транзакции

С `set_config('app.org_id', orgA, false)` значение остаётся в backend после возврата соединения в пул. В тесте пул `max: 1` повторно выдал тот же PID: следующий запрос B без нового контекста увидел строки A. Если после этого открыть короткую транзакцию B с `set_config(..., true)`, внутри неё видны строки B, но после commit сессионное значение A возвращается. Поэтому одного `true` недостаточно, если в пуле уже оставили старое сессионное значение; во всём приложении нужно использовать только транзакционный путь и не устанавливать контекст с `false`.

## Решение для ARCH §20.5

**Рекомендация:** RLS включать как четвёртый слой для `catalog_items`, общих `skills`, `invitations` и `model_runs`. Приложение должно подключаться ролью без `SUPERUSER`/`BYPASSRLS`, не владельцем этих таблиц; каждая операция должна идти через короткую `sql.begin`-транзакцию с `set_config('app.org_id', orgId, true)`. Для межорганизационных функций платформы нужен явно выделенный и проверенный путь доступа; глобальные таблицы платформы под этот RLS не подпадают. Сохранить функции ядра с `orgId`, импортное правило и двухорганизационные тесты.

Предлагаемая формулировка: «RLS — четвёртый слой на `catalog_items`, общих `skills`, `invitations` и `model_runs`. Веб-приложение и worker подключаются ролью без `SUPERUSER` и `BYPASSRLS`, не владельцем таблиц. Каждая операция с организационной таблицей выполняется в короткой `sql.begin`-транзакции, которая первой устанавливает `set_config('app.org_id', orgId, true)`; сессионный `false` запрещён. Межорганизационный доступ платформы идёт через отдельный явно ограниченный путь. RLS не заменяет функции ядра с `orgId`, запрет прямых импортов схем и тесты на две организации».

## Критерии готовности S20

- Импорт `catalog_items` из чужого модуля обнаружен oxlint: **да**.
- RLS замерен на двух организациях, 40 долгоживущих запросах и пуле 10; измерены соединения и p50/p95: **да**.

## Допущения

- Угадано: 40 ответов одновременно, длительность 2 минуты, один DB-вызов в секунду. Такой профиль не снят с живой системы.
- Угадано: `model_runs` трактуется как данные организации, а не глобальная таблица платформы. Если платформенная аналитика должна читать её напрямую, сначала нужен отдельный проверенный путь доступа.
- Сессии чата — логические задачи Node.js, не HTTP/SSE и не вызовы модели. Набор строк синтетический; задержки описывают эту локальную среду и не являются прогнозом production.
