## 3. Д2 Разбор открытого по одному (вариант В2.1)

**Что уже решено.** В2.1 (§19.8.6): «давно открыто» — без перемен 30 дней, дано раньше 30 дней назад, срок не в будущем; строка «Сверка: N давно открытых» в «Не упустить»; страница с фильтром; «Оставить» на 30 дней (`memory_dismissals`, ключ `stale:<id>`). Не сделано. Этот шаг ничего не меняет в отборе и хранении — он добавляет в P20 второй вариант экрана.

- **P20, два варианта рядом:** список с фильтром (как в §19.8.6) и «по одному» — одно обещание на экране: кто, что, когда дано, срок, откуда; четыре действия «Выполнено», «Жду дальше», «Перенести», «Отменено»; клавиши 1–4, «Назад» возвращает последнее; счёт «3 из 11».

- Код: `core/memory-stale.ts` без базы и тест с датами — как в В2.1; экран — только клиент и существующие `PATCH`/`dismiss`.
- Проверка: тест сбора с датами; Playwright — пройти пять обещаний с клавиатуры, вернуть последнее.

## 4. Д3 Календарь как источник

**Задача.** Память знает о встречах без того, чтобы человек о них писал: перед встречей показывает открытое с этим человеком, после — предлагает записать итог, а «давно не было 1:1» считает по факту.

**Чего не делаем.** Запись в календарь, свой экран календаря, двусторонняя синхронизация, OAuth.

### 4.1 Д3.0 Spike S18 — до кода

`spikes/S18-calendar-ics`, только чтение, календари владельца, без модели и без расхода.

- Какие сервисы дают секретную ссылку ICS только на чтение: Яндекс, Google, Outlook, Mail.ru, Nextcloud. **Проверить** — я этого не проверял ни для одного.
- Есть ли в выгрузке участники (`ATTENDEE`) с адресами. Без них сверка с карточками идёт только по названию встречи — заметно слабее.
- Повторы: `RRULE`, `EXDATE`, изменённые вхождения (`RECURRENCE-ID`); пояса (`TZID`, без пояса, на весь день); отменённые встречи и отклонённые приглашения.
- Размер выгрузки за год, время разбора, поддержка `ETag`.
- Библиотека разбора с раскрытием повторов — выбрать по актуальной документации, а не по памяти.
- Запасной путь, если участников в ICS нет: CalDAV с паролем приложения (в DECISIONS стоит «позже»).

Критерий: за 30 дней календаря владельца не меньше 95 % встреч с людьми из памяти привязаны к верной карточке (сверка руками), 20 проверенных повторов раскрыты верно. Ниже — путь ICS не берём, решаем про CalDAV.

### 4.2 Д3.1 Подключение и сбор

- **Хранение** (одна миграция):
  - `memory_calendars`: `owner_id`, `sealed` — `{ url, title }`, `etag`, `checked_at`, `error`. Ссылка — секрет, запечатана ключом памяти.
  - `memory_meetings`: `owner_id`, `calendar_id` (каскад), `uid_key` — HMAC от `UID` и вхождения, `starts_at`, `ends_at`, `entity_ids`, `sealed` — `{ title, attendees }`. Окно — 30 дней назад и 14 вперёд, старше удаляется.
- **Допущение: встречи не становятся записями памяти.** Запись — то, что человек сказал; встреча из календаря — сигнал рядом. Так нет дублей с «вчера виделись с Ольгой» из чата, а отключение календаря убирает всё одной строкой. Через модель ничего не идёт, расхода нет.
- **Разбор** — `core/memory-calendar.ts`, без базы и сети: текст ICS → вхождения в окне → карточки по адресу участника (`card.email`), по названию — только если spike покажет, что это безопасно. Пропускаются: на весь день, отменённые, отклонённые, без других участников, больше 8 участников (**допущение:** общее собрание — не контакт).
- **Сбор** — задание очереди памяти раз в час, как проверка почты в Г3.1. Запрос через `fetchFor(null, url, { pinned: true })`, как в `fetchPage` (`core/web.ts`), предел 5 МБ, 15 секунд, `If-None-Match`. **Проверить:** пропустит ли `pinned` календарь на адресе внутренней сети (свой Nextcloud).
- **Экран** — поле «Календарь» в настройках памяти (`settings/account/memory-form.tsx`): ссылка, время последней проверки, текст ошибки, «Отключить». Слова — «собрано из календаря» (D38). Вид поля и строк — прототип P28; если к тому времени делается P24 (почта), это один прототип.
- «Забыть всё» и выключение памяти удаляют обе таблицы.

### 4.3 Д3.2 Последний контакт и ритм

- `cardContact` и строки ритма в `core/memory-today.ts` считают последний контакт по событиям памяти. Добавляется второй вход: прошедшие встречи карточки из `memory_meetings`; берётся более поздняя дата.
- На карточке: «Последний контакт: 6 ноября · встреча» и встречи в списке событий отдельной пометкой, без правки и удаления.
- Тест: событие позже встречи, встреча позже события, встреча группы раскрывается в состав, отключённый календарь.

### 4.4 Д3.3 Строки в «Не упустить»

Новый вид строки `meeting` в `todaySuggestions`, две причины:

- **Сегодня встреча.** Встреча с карточкой сегодня, и у карточки есть открытое в любую сторону. Строка: «Встреча с Ольгой Ли в 15:00 · 2 открытых». Нажатие кладёт в поле просьбу «Перед встречей» (тот же путь, что в Г2.1); с Д1 ответ — карточка.
- **Записать итог.** Встреча закончилась меньше суток назад (**допущение**), и после её конца о карточке ничего не записано. Строка: «Встреча с Ольгой Ли закончилась · записать итог». Нажатие ставит в поле начало сообщения; дальше обычная запись из чата.
- «Убрать» — `memory_dismissals` с ключом `meeting:<uid_key>:<причина>`.
- Тексты сухие, без «не забудьте».

### 8.2 «Не запоминать этот чат»

- Миграция: `chats.memory_off boolean not null default false`.
- `route.ts:901` не ставит сообщение такого чата в очередь; строки «Запомнено» нет.
- **Допущение:** выключается только запись. Чтение остаётся: блок памяти и инструменты работают.
- Пункт в меню чата и пометка в шапке. Уже записанное из этого чата не трогается.
- Тест: сообщение чата с флагом не попадает в `memory_writes`.

### 8.3 Выгрузка

- `GET /api/memory/export` — один файл Markdown: по карточкам, внутри открытое, известное, события, закрытое; отдельно правила и сведения о самом человеке. **Допущение:** Markdown, а не JSON — читается человеком и другой моделью.
- Кнопка в настройках памяти рядом с «Забыть всё».
- Тест: в файле есть всё, что отдаёт `memoryCard` по каждой карточке; чужих записей нет.
