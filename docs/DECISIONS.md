### D0. Ставки продукта — РЕШЕНО

Open WebUI и LibreChat уже умеют мультиисточникность, MCP, роли и артефакты (по памяти, детально не сверял). Своё имеет смысл, только если выигрываем в чём-то конкретном. Предлагаемые ставки (ARCHITECTURE §0):

1. установка и первый ответ за 2 минуты;
2. генеративный UI по живым данным;
3. сети с ограничениями: Яндекс, прокси HTTP и SOCKS5 — всё напрямую, через прокси только отмеченные объекты и домены;
4. MCP и скиллы как основа;
5. периодические задачи — поручение, которое запускается по расписанию твоими инструментами (ARCHITECTURE §16; до D38 называлось «фоновые агенты»).

«Ставка» — это то, ради чего продукт выбирают вместо готового. От ставок зависит порядок работ: то, что их поддерживает, делается первым и полируется до вау, а остальное режется первым, когда не хватает времени.

**Решение:** пятая ставка подтверждена явно, первые четыре не оспаривались и считаются принятыми. Следствие: периодические задачи — первый пункт v2, под них заранее затачиваются MCP (M4), поиск (D21) и уведомления (D24).

### D1. Мастер установки или compose — РЕШЕНО

Отказываемся от мастера в браузере. Инфраструктуру описывает compose, `install.sh` генерирует `.env`, entrypoint применяет миграции, а в браузере остаётся один экран — создание аккаунта по claim-ссылке.

- Мастер не может «выбрать» БД, в которой сам же хранит свой прогресс: проблема курицы и яйца.
- Миграции через HTTP — это DDL без авторизации, а две вкладки дадут две гонки.
- Первый пришедший на `/setup` становился суперюзером. Claim-токен из лога это закрывает.
- Исходное требование «при запуске определяется БД» не теряется: `install.sh` спрашивает, встроенная база или своя.

Источники, модели и MCP — это данные, а не инфраструктура. Они подключаются в интерфейсе, без мастера установки. Первый вход ведёт на настройки источников, чат открывается, когда есть хотя бы одна включённая модель (P1, решение пользователя 2026-09-23).

### D2. Один инстанс `app` — ПО УМОЛЧАНИЮ

Реестр отмены, MCP-клиенты и активные стримы живут в памяти процесса. Первая версия документа одновременно готовилась к нескольким инстансам (Redis pub/sub для отмены, S3 «ради масштабирования») и держала stdio MCP в памяти — это противоречие.

Redis остаётся: без него не работают BullMQ, rate limit и `config:changed` между процессами (resume стримов ему больше не нужен — D5). S3 тоже остаётся, но уже по другой причине — внешнее хранилище и бэкапы.

С периодическими задачами (v2) появляется второй процесс, `worker`, из того же образа. Web-инстанс по-прежнему один. Отмена запуска задачи идёт сигналом через Redis в `worker`.

**Отменить**, если нужен HA или несколько реплик. Тогда отмена переходит на Redis pub/sub, а stdio MCP запрещается.

**Потолок — S27 (2026-11-24, ветка `t3/s27-app-load-spike`): оставить один `app`.** Процесс держит ≈40 одновременных ответов, предел — CPU главного потока, не память и не база (ARCH §20.14). Сверх 40 — стоп-кран: новый ответ получает 503 с `retryAt`, а не очередь. Пересмотр — когда на живой установке p95 идущих ответов ≥30 или мест больше 100. Отмена D2 — это перенос отмены и записи для докачки на Redis. До неё — дешёвые рычаги: склейка кусков текста на входе (оценка 1,5–2×), разбор цепочки Web Streams.

### D3. Песочница — ПО УМОЛЧАНИЮ (v3) + SPIKE

> **2026-11-20: уточнено D47.** Песочница переехала в v2 (заказчик просит работу с файлами), делаем через Docker с gVisor, контейнер живёт весь ответ и ещё 5 минут после него, а не только на время кода. Остальное ниже в силе.

- Не в v1: это самый опасный и дорогой компонент, а ни одна ставка из D0 на нём не держится.
- **Никогда через `docker.sock`:** по документации Docker доступ к демону эквивалентен root на хосте, а исполнять будем код, написанный моделью. Единственный контейнер с сокетом — обновлятель (D35): наш неизменный код, одна команда, без входящих соединений.
- Кандидаты:
  - microsandbox (microVM на libkrun, заявлены Linux и macOS);
  - gVisor (только Linux; на Docker Desktop под macOS ставится вручную).
- Подключается профилем compose, по умолчанию выключен. Пока песочницы нет, `run_code` недоступен, и модель об этом знает.
- **Что взять из песочницы PlusPortal assistant** (разбор кода 2026-10-02 — за образец, а не за истину):
  - контейнер на один ответ модели: создаётся при первом вызове тула кода, удаляется в конце ответа; файлы прошлых ответов возвращаются явным тулом, а не живым контейнером;
  - сети нет по умолчанию, корень только для чтения, все capabilities сняты, не root, лимиты памяти, CPU, процессов и времени; запись — только в tmpfs с потолком размера;
  - файлы внутрь и наружу — через stdin/stdout `exec`, с проверкой размера до чтения;
  - ошибки тулов написаны для модели: «кончилась память» отдельно от «вышло время» (по счётчику OOM в cgroup), явная пометка об обрезке вывода;
  - описание окружения в системном промпте, и тест сверяет его с закреплёнными версиями в образе;
  - лимиты проверяются настоящими тестами, которые их нарушают.
- **Чего не повторять:**
  - сервис в группе `docker` (то же, что root на хосте) и runc без gVisor — у нас только gVisor или microVM в отдельном сервисе;
  - место в очереди занято на весь ответ, включая время, пока модель думает, а лимиты живут в памяти одного процесса — у нас лимиты в Redis и место только на время выполнения кода;
  - чистка при старте удаляет все контейнеры с меткой, в том числе чужие — у нас метка с id процесса-владельца;
  - обрезка вывода оставляет начало и теряет traceback в конце — у нас начало и конец;
  - описание окружения в промпте разошлось с образом (пакеты, пути) — у нас тест сверяет их.

### D4. S3-хранилище — ПО УМОЛЧАНИЮ (S6 пройден)

MinIO отпадает: `minio/minio` архивирован, в README написано «NO LONGER MAINTAINED». По вторичным источникам, community-образы перестали публиковать осенью 2025-го.

| Вариант | За | Против |
| --- | --- | --- |
| **SeaweedFS** (по умолчанию) | зрелый, Apache 2.0, S3-режим в одном контейнере | конфиг ключей через JSON — проверить |
| Garage | лёгкий | layout и ключи создаются командами после старта — нужно скриптовать в `install.sh` |
| RustFS | ближе всех к MinIO | в обзорах — «not production-ready» |
| Внешний S3 | ноль контейнеров | не «из коробки» |

**Spike S6 — пройден 2026-10-02** (`spikes/S6-seaweedfs`, 13 проверок из 13): `chrislusf/seaweedfs:4.48`, `weed mini` — один контейнер, бакет и ключи из переменных окружения (JSON не нужен), healthcheck `/healthz`, presigned PUT и POST из браузера с CORS только для своего origin, потолок размера, отказ неверному ключу и анониму, данные переживают перезапуск. Admin UI выключаем (`-admin.ui=false`: по умолчанию он без пароля). Цена: образ ~500 МБ, в покое ~180 МБ памяти. Клиент SDK — с `requestChecksumCalculation: "WHEN_REQUIRED"`, иначе presigned PUT из браузера падает с `BadDigest`. Как браузер достаёт до S3 (через приложение или presigned на отдельный адрес) — решается в D33.

### D5. Resume стримов — РЕШЕНО

Сделано **без `resumable-stream` и Redis**: приложение — один долгоживущий процесс (D2), поэтому ответ пишет в памяти процесса записывающий реестр (`lib/resume-stream.ts`, так же устроены реестр остановки D6 и сама генерация, которая доводится до конца при ушедшем клиенте). Сервер делит поток ответа надвое: клиенту и в запись. `GET /api/chat/[id]/stream` проигрывает записанное с начала и подключает к живому потоку; `204`, когда ответ не пишется. Запись снимается, когда ответ сохранён, — дальше показывается сохранённая копия.

- Клиент подключается только когда чат открыт с собственным сообщением пользователя в конце (ответ ещё пишется) — один раз, при открытии.
- Не охвачено: продолжение ответа после подтверждений (последнее сообщение — ответ), второй экземпляр приложения.
- Если понадобится несколько экземпляров, меняется только `lib/resume-stream.ts`: хранить чанки в Redis (`resumable-stream`).

### D6. Отмена генерации — РЕШЕНО

`Map<chatId, AbortController>` в памяти (следствие D2) и `POST /api/chat/[id]/stop`. Клиентский `stop()` при resumable-схеме только отключает клиента, поэтому отдельный эндпоинт обязателен.

### D7. Edit/regenerate при линейной истории — PROTOTYPE

Редактирование физически удаляет все сообщения ниже. Варианты UX:

- **без предупреждения** — быстро, но теряются ответы;
- **подтверждение** — безопасно, но раздражает на каждом редактировании;
- **undo-тост на ~10 с** — лучше всего по ощущению, но требует soft-delete (`messages.deleted_at`) и отложенной очистки.

Прототип P6 решает, стоит ли undo лишней колонки.

### D8. Режимы Fast/Normal/Deep — PROTOTYPE

В PlusPortal обычный пользователь выбирал режим, а эксперт — модель. Режимы проще для людей, но это ещё одна сущность (таблица «режим → модель + параметры»). В v1 — выбор модели плюс «модель по умолчанию». Прототип P3 покажет, нужны ли режимы.

### D9. Composer: что на виду — PROTOTYPE

Оси независимы: модель, thinking, MCP-серверы, скиллы, вложения. Все сразу на виду не помещаются. Прототип P2 решает, что показывать постоянно, что убрать за меню и что вызывать через `/` и `@`.

### D10. Виджет → артефакт — PROTOTYPE

Когда виджет из ленты становится артефактом в панели: по кнопке «развернуть», автоматически при размере больше N или только через `createDocument`? Как выглядит переход (shared-element анимация)? Прототип P5.

### D11. Большие данные тулов — РЕШЕНО + SPIKE

Полный результат хранится в `parts`, модели через `toModelOutput` уходит сжатая версия с `ref`, рендер-тул ссылается на `toolCallId`, данные подставляет сервер (ARCHITECTURE §9.2).

**Spike S5** проверяет, работает ли `toModelOutput` между шагами одного `streamText` и можно ли обернуть им MCP-тулы.

**Итоги S5 (2026-10-06, тест `apps/web/lib/tool-sources.test.ts` с `MockLanguageModelV4`, отдельной папки в `spikes/` нет):** да и да. `toModelOutput` применяется между шагами одного `streamText` и в `convertToModelMessages` (оба вызывают `createToolModelOutput` по `tools[name]`, в том числе для `dynamic-tool`), но только если те же `tools` переданы в `convertToModelMessages` — у нас они не передавались. MCP-тулы из `client.tools()` оборачиваются обычным spread с подменой `execute` и `toModelOutput`. Фактическая форма — ARCHITECTURE §9.2: `ref` — это `toolCallId`, виджеты берут данные по `from`, а не по отдельному рендер-тулу.

### D12. Гранты доступа — ПО УМОЛЧАНИЮ (v2)

В v1 только роли `superuser`/`admin`/`user`. Точечные гранты (`default_access` + `*_access`) на модели и пункты каталога появятся в v2, когда будет кому их выдавать. Схема закладывает поле `default_access` в `models` и `catalog_items`, чтобы потом не мигрировать данные.

### D13. Источники в v1 — ПО УМОЛЧАНИЮ

OpenAI, Anthropic, **Vercel AI Gateway**, OpenAI-compatible (через него же OpenRouter, vLLM, LM Studio, Ollama `/v1`) и Yandex AI Studio. Google — по запросу, это новый `kind` в фабрике.

AI Gateway добавлен по твоему запросу: один ключ даёт модели разных провайдеров, а discovery сразу возвращает цены (ARCHITECTURE §7.5). Предполагаю, что имелся в виду именно Vercel AI Gateway. Свой шлюз (LiteLLM и т.п.) подключается через `openai-compatible` и отдельного `kind` не требует.

### D14. Исходящий прокси — РЕШЕНО (S4 пройден)

Прокси — отдельная сущность в админке (ARCHITECTURE §18): несколько прокси `http` / `https` / `socks5` / `socks5h`, у каждого проверка с внешним IP и страной.

**По умолчанию всё идёт напрямую.** У каждого прокси админ отмечает, что через него ходит: конкретные источники, пункты каталога, бэкенды поиска — галочками, а трафик без объекта (чтение страниц, свои подключения пользователей, Web Push) — доменами. У объекта то же самое видно полем «Прокси: авто / напрямую / через X».

Маршрут запроса: явный выбор у объекта → прокси, в доменах которого есть адрес назначения (точный домен побеждает) → напрямую. Внутренние сервисы compose через прокси не ходят никогда. `HTTPS_PROXY` / `ALL_PROXY` из установки при первом старте превращаются в запись прокси, но ничего к нему не привязывают.

При добавлении источника, недоступного напрямую, система сама проверяет его через каждый прокси и предлагает рабочий.

Отвергнутые варианты:

- **Поле `proxyUrl` у каждого источника** (первая версия): не покрывает MCP, коннекторы, чтение страниц, push и почту; один и тот же прокси вводится много раз.
- **Умолчания по категориям** («все модели через прокси»): загоняют в прокси и то, чему он не нужен, — например Яндекс.
- **Только глобальный `HTTPS_PROXY`:** Яндексу прокси не нужен, OpenAI без него не работает — одним маршрутом этого не описать.

SearXNG ходит в поисковики из своего контейнера, его прокси задаётся при установке и в админке только отображается.

**Итоги spike S4** (2026-09-23, `spikes/S4-proxy`):

- `fetch` есть у всех четырёх источников, включая `anthropic`. Три маршрута — HTTP-прокси, SOCKS5 и напрямую — работают одновременно в одном процессе, стрим и тулы проходят.
- Маршрут — это undici-dispatcher, а источник получает `fetch` из пакета `undici` с этим dispatcher. HTTP — `ProxyAgent`, «напрямую» — явный `Agent`, чтобы не подхватить `HTTPS_PROXY` из окружения.
- SOCKS5 и закреплённый IP — свои коннекторы на `socks` и `undici.buildConnector`, без `fetch-socks`: он тянет второй мажор undici. Закрепление работает и через HTTP CONNECT, и через SOCKS5: туннель открывается на проверенный IP, SNI и `Host` — по имени.
- SMTP через SOCKS5 и HTTP CONNECT работает штатно в nodemailer. Закрепление IP для SMTP пользователей не проверено — это M4, коннектор `smtp`.

### D15. SMTP — РЕШЕНО

Настраивается в UI и хранится зашифрованным. Для работы не обязателен: приглашение — это копируемая ссылка, письмо лишь дублирует её.

**Уточнено 2026-10-05.** Письма уходят от отдельного ящика сервиса (например, `noreply@компания`), а не от ящика кого-то из сотрудников: иначе вход всех зависит от чужого личного пароля. Форма на тех же деталях, что личная почта (D27): пресеты Яндекс, Gmail, Mail.ru и «Другая», пароль приложения с подсказкой, те же тексты ошибок. Отличия: только SMTP; «Другая» может быть без логина — релей во внутренней сети; адрес задаёт админ, поэтому внутренние адреса разрешены, как у каталога и источников (ARCH §18.4), а через прокси почта идёт по его доменам. Сохраняется только то, что сервер принял; «Отправить себе» проверяет путь письма целиком. Почту можно отключить — тогда вход только по ссылке от админа, и `SMTP_URL` установки её не возвращает.

Отвергнуто: отправлять от ящика админа из «Моих подключений» — это его личный пароль, и с уходом человека вход сломается у всех.

### D16. Язык интерфейса — РЕШЕНО: только русский

Интерфейс пока только на русском, строки пишутся прямо в компонентах, словарей и `next-intl` нет. Если понадобится английский, строки придётся выносить — эту цену приняли осознанно.

Даты, числа и валюты форматируем через `Intl` с локалью `ru-RU`, а не вручную. Это ничего не стоит и не придётся переделывать.

### D17. Способы входа — РЕШЕНО: без паролей

**Паролей нет.** Вход — по магической ссылке. Она же подтверждает почту, а пароли нечего утекать, забывать и сбрасывать.

- **Письмо** содержит ссылку и шестизначный код. Код нужен, если письмо открыли на телефоне, а входят с ноутбука. Ссылка одноразовая, живёт 10 минут, запросы ограничены по email и IP.
- **Первый вход без почты.** Claim-ссылка из лога сама создаёт сессию суперюзера, ссылка-приглашение — сессию приглашённого. Это сохраняет ставку «первый ответ за 2 минуты»: SMTP для старта не нужен (D15).
- **Без SMTP** вход тоже возможен: админ выдаёт одноразовую ссылку для входа в интерфейсе пользователей или командой `cli login-link <email>`. Страница входа в этом случае честно говорит «вход по почте не настроен — попросите ссылку у администратора».
- **Сессия** — 30 дней, продлевается при использовании: входить приходится редко.
- `install.sh` может сразу спросить SMTP — необязательный вопрос. Настройки переносятся в админку при первом старте.
- **v2:** passkey — после первого входа предлагаем добавить ключ, дальше вход по отпечатку или Face ID без почты. OIDC — Яндекс ID, Google, Keycloak.

**Уточнено 2026-10-05: кто может войти сам.** Только по приглашению люди попадали в сервис неудобно: компании нужно, чтобы вошёл любой сотрудник. Админ перечисляет **домены почты** (`/settings/access`), и человек с адресом на таком домене получает код и входит без приглашения: аккаунт создаётся при первом входе, роль «Пользователь», одним вопросом спрашиваем имя (`/login/name`). Правила:

- **Работает только с почтой сервиса** (D15): без неё некуда слать код, список остаётся, но ничего не открывает.
- **Код уходит только** тому, кто уже в сервисе, или тому, чей домен в списке; остальным форма отвечает так же, как всем, чтобы не подсказывать, какие адреса есть.
- **Закрыто и на стороне Better Auth:** создание аккаунта через него (`databaseHooks.user.create.before`) пропускает только такие адреса, поэтому открытый маршрут отправки кода ничего не открывает. Claim и приглашения пишут пользователя напрямую и этот хук не касаются.
- **Публичную почту** (gmail.com, yandex.ru, mail.ru и подобные) добавить нельзя: адрес на ней заводит кто угодно. Поддомены отдельно не разрешаются, домен — точное совпадение.
- **Уход.** Убранный домен не выгоняет тех, кто уже вошёл. Удалённый в «Пользователях» человек может войти снова, пока его домен в списке: закрыть конкретного человека без закрытия домена пока нельзя (запись «отключён» — отдельная работа).

**Приглашения (уточнено 2026-10-05).** Ссылка на конкретный адрес сама подтверждает почту (она выдана этому человеку) и входит сразу. Ссылка без адреса раньше принимала любую набранную почту и входила без проверки: набравший чужой адрес получал сессию в аккаунте, который потом открыл бы настоящий владелец почты. Теперь такая ссылка создаёт аккаунт с неподтверждённой почтой и отправляет код, как при обычном входе; без кода войти нельзя. Без почты сервиса ссылку можно выпустить только на адрес. Если почта сервиса есть, ссылка на адрес уходит ещё и письмом. Неподтверждённый аккаунт виден в списке, пока его не откроет владелец почты или админ его не удалит.

**Лимит запросов кода:** 5 на адрес и 20 на IP за 10 минут, считается для любого адреса, известного или нет, чтобы ответ ничего не выдавал; в Redis, а без него — в памяти процесса. Маршруты Better Auth по HTTP ограничены им самим (3 в минуту, в проде).

**Отключить человека и ссылка от админа (уточнено 2026-10-05).** У аккаунта есть признак «отключён» (`user.disabled_at`): сеансы заканчиваются сразу, код ему не уходит, даже если его домен разрешён, а создание сеанса отклоняется хуком Better Auth (код, выданный до отключения, тоже не сработает). Чаты, файлы и подключения остаются и возвращаются при включении. Отключает и выдаёт одноразовую ссылку для входа тот, кто может удалить человека (`canManageAccess` = `canRemove`): админ не получит ссылку в аккаунт владельца. Ссылка — тот же код входа на 10 минут и один раз, для случая, когда почта не доходит или не настроена. Заодно починена ссылка из письма: она подставляла код, но входа не было — теперь под кодом кнопка «Войти» (автоотправки нет, чтобы почтовый сканер не сжёг код). Аккаунты, которые создаёт Better Auth, получают UUID, как у создаваемых claim и приглашением: страницы людей принимают только их.

Отвергнуто: заявки на доступ с одобрением админом (лишний шаг для админа, на который нужен свой экран и уведомления) и SSO (v2).

Плагины Better Auth для magic link, email OTP и passkey — имена и API **проверить** по документации пакета при реализации.

Отвергнуто:

- **Email + пароль** — первая версия решения: лишний экран, сброс пароля, хранение хэшей.
- **Только магическая ссылка без кода** — ломается, когда почта на телефоне, а работа за компьютером.

### D18. MCP stdio — РЕШЕНО (v3)

stdio — это по определению запуск команды на сервере. Правила:

- настраивает только суперюзер, с явным предупреждением;
- без личных кредов пользователей (иначе нужен процесс на каждого);
- работает только при одном инстансе (D2); stdio-клиенты живут только в процессе `worker`, а `web` вызывает их тулы через очередь — два процесса не запускают один и тот же сервер.

### D19. Цены и валюты — РЕШЕНО

Цена хранится за 1M токенов вместе с валютой. `model_runs` фиксирует стоимость в валюте модели. Дашборд суммирует по каждой валюте отдельно и не конвертирует.

**Тиры цен — ПО УМОЛЧАНИЮ: в v1 только базовая ставка.** У части моделей вход и выход дороже после 200K токенов контекста — Gateway отдаёт это как `input_tiers` / `output_tiers` (S4). В v1 храним базовую ставку. У Gateway стоимость запуска потом уточняется фактической (`getGenerationInfo`), так что тиры влияют только на прямые ключи с длинным контекстом. Тиры — v2.

### D20. UI-библиотеки — РЕШЕНО (приоритет ReUI, S2 пройден) + PROTOTYPE

**Приоритет — ReUI: его вид нравится больше.** Для любого компонента, включая графики, сначала ищем его в ReUI, потом берём shadcn в том же стиле (ARCHITECTURE §9.5).

**Итоги spike S2** (2026-09-23, проверено на скелете: Next 16.3.6, React 19.2.8, Tailwind v4, shadcn CLI 4.21):

- **Монорепо работает.** Структура взята из `shadcn init --monorepo`: `@source` в `globals.css` пакета указывает на `apps/**`, приложение переиспользует `postcss.config` пакета и подключает его через `transpilePackages`.
- **`shadcn add` запускаем из `packages/ui`.** Тогда и примитивы, и составные компоненты ReUI (`components/reui/*`) ложатся в дизайн-систему. Из `apps/web` составные компоненты ушли бы в приложение.
- **Перезаписей нет.** Голые зависимости ReUI (`button`, `input`…) создают файлы, а совпадающие пропускаются как идентичные. Риск из анализа реестров на практике не сработал.
- **База — `base`** (Base UI). **Пресет — `b1YmqvjO4`** (выбран 2026-09-23): стиль `nova`, базовый цвет `neutral`, тема и цвета графиков `blue`, шрифт Geist, иконки lucide. Смена пресета — `pnpm dlx shadcn@latest apply --preset <код> --yes` из `apps/web` (см. IMPLEMENTATION §6).
- **Иконки — `lucide-react`**: их тянет ReUI.
- **Графики — EvilCharts (ECharts), с 2026-09-28.** Сначала брали ReUI (`@reui/c-chart-*` на recharts), потом EvilCharts пробовали и отказались — «по ощущению вернулись к обычным». Теперь вернулись к нему сознательно: по виду он заметно лучше, а ECharts покрывает все виды (площадь, линия, столбцы, составной, радар, круговая, радиальная). Ставится `shadcn add @evilcharts/echarts-*` из `packages/ui` в `components/evilcharts/` (реестр в `components.json`), исходники с правками для подсказки описаны в `README.md` рядом. Цена: ~200 КБ gzip сверх recharts, поэтому график грузится отложенно, только когда он есть в ответе. Палитра — `--chart-1…8`, проверенная валидатором по dataviz (фиксированный порядок оттенков, свои шаги для тёмной темы); ряды бывают до 8, радар до 3. Одна ось: числа разного масштаба — в разных графиках, а не на второй оси. Графики ReUI `c-chart-*` остались только в dev-витрине, `recharts` в чате не используется.
- **Data Grid** — ReUI на TanStack Table **v9** и TanStack Virtual. Таблица с поиском, фильтром, сортировкой и пагинацией отрендерилась.
- **Ограничения:**
  - код ReUI не собирается с `noUncheckedIndexedAccess`, поэтому флаг включён только в `@metobe/tsconfig/node.json` для серверных пакетов;
  - вендорные компоненты (`packages/ui/src/components/**`) исключены из oxlint и oxfmt: их обновляют через `shadcn add --diff`, а не правят руками;
  - блоки ReUI импортируют `recharts` без `"use client"`, поэтому виджеты с графиками — клиентские компоненты.

### D21. Веб-поиск — РЕШЕНО (S8)

Свои тулы `web_search` и `web_fetch`, бэкенды настраиваются в админке. По умолчанию — SearXNG в compose и локальный `web_fetch`. Yandex Search API, TinyFish и Tavily — запасные адаптеры: подключаются, только если S8 или эксплуатация покажут капчи или слабое качество (ARCHITECTURE §8.1).

- Встроенный поиск источников не годится: он работает только с моделями своего источника.
- Официальные пакеты поиска для AI SDK пока только под `ai@5`/`@6`.
- N2 Free Search снят с npm, но идея — SearXNG без ключей — берётся за основу.

**Итоги S8 (2026-09-28, `spikes/S8-searxng`):** по-русски выдача хорошая — наверху первоисточники. Под постоянной нагрузкой (вопрос в секунду) настройки по умолчанию умирают за две минуты: duckduckgo отвечает капчей после ~5 вопросов подряд, brave — «too many requests» после ~10, google cse — после ~100; SearXNG сам выключает движок на час–сутки. В темпе чата (три вопроса раз в 20 с) с google + yahoo + brave — 45 из 45 с результатами. `outgoing.proxies` с SOCKS5 и логином работает. Отсюда:

- **SearXNG:** JSON включён, движки google, yahoo, brave, duckduckgo, google cse, wikipedia; приостановка движка — минуты, а не сутки.
- **Наш слой:** кеш одинаковых вопросов на час и страниц на сутки, не больше двух одновременных запросов к SearXNG.
- **`web_fetch`:** свой fetch через защищённый от SSRF транспорт (`fetchFor(…, { pinned: true })`: адрес проверяется на каждом соединении, в том числе после редиректа) и Defuddle — основной текст страницы в Markdown.
- **Когда не хватит** (задачи по расписанию, большая команда): прокси с разными IP в `outgoing.proxies` или платный бэкенд из запасных.

### D22. Права периодических задач — РЕШЕНО: как у Claude

Задаче по умолчанию доступны все подключения владельца, она действует его кредами и ничего не спрашивает во время запуска. Лишние подключения убираются в карточке задачи.

Страховка без подтверждений: лимиты (шаги, стоимость, время, минимальный интервал), журнал каждого запуска, выключатель «пауза всех задач», внешний ввод оборачивается как недоверенный.

**Политика админа сильнее прав задачи.** Если админ поставил тулу в каталоге `approval_policy = 'ask'`, задача тоже спрашивает: запуск паркуется, задача ждёт человека (`outcome = action`). `deny` скрывает тул. «Как у Claude» — умолчание для тулов без политики, а не обход решений админа.

Осознанный риск — prompt injection из прочитанных данных. Путь отступления: флаг задачи «спрашивать перед записью». Модель данных и approval-флоу `ai@7` это уже позволяют.

### D23. Расписание задач — ПО УМОЛЧАНИЮ

- **Источник правды — Postgres:** `tasks.cron`, `timezone`, `next_run_at`.
- **Исполнение — BullMQ:** один job scheduler раз в минуту атомарно захватывает созревшие задачи и ставит их в очередь.
- **Пропущенные запуски:** после простоя — ровно один догоняющий, без лавины.
- **Где выполняется:** в отдельном `worker`.
- **Смена исполнителя:** запуск спрятан за `executeRun(runId)`, при необходимости переезжает на Workflow DevKit (ARCHITECTURE §16).

Отвергнутые варианты:

- **Отдельный BullMQ-scheduler на каждую задачу:** расписания жили бы только в Redis, пропадали бы вместе с ним и не попадали бы в бэкапы.
- **eve:** preview и отдельный рантайм.
- **Workflow DevKit сейчас:** beta-линейка и нет cron.

### D24. Интерфейс задач и уведомления — РЕШЕНО (P11–P15, письма) + SPIKE (push)

**Поверхности** (ARCHITECTURE §16.4) — решено прототипами 2026-11-05:

- боковая панель: «Задачи» и под ним только задачи, которые ждут человека;
- список задач `/tasks` «по вниманию» (P13);
- страница задачи: карточка «О задаче», последний итог целиком, прошлые запуски под спойлером, поле «Что поменять в задаче…» (P12, P15);
- запуск открывается как обычный чат с плашкой.

**Отдельных «Входящих» нет.** Сначала планировались `/inbox` с Notify / Question / Alert / Review. Итоги в чате задачи и список «по вниманию» закрывают то же: что ждёт человека — видно в панели и наверху списка; второй список того же — лишний.

**Каналы** (§16.5): боковая панель и список → точка в открытой вкладке по SSE через Redis → почта (по задаче) → Web Push (решим) → Telegram (v3). «Нового нет» не уведомляет нигде.

Отвергнутые варианты:

- **Только опрос сервера:** точка отстаёт.
- **Общий `notify_policy` у пользователя:** человек решает про конкретную задачу, а не про все сразу.
- **Telegram как канал уведомлений в v2.** Коннектор `telegram_bot` в v2 есть, но это тул модели: «отправь в чат X». Канал уведомлений — другое: кнопки «открыть» и «ответить», ответы из Telegram обратно в запуск, привязка аккаунта. Это отдельная работа, она в v3.

**Spike S9:** Web Push в self-hosted Next 16 — service worker, VAPID, HTTPS, поведение на iPhone.

**Боковая панель (2026-11-05, решение пользователя).** Под «Задачами» — только задачи, которые ждут человека: новый итог, вопрос, решение (в том числе сбой, который исправляет человек), у каждой точка. Плюс открытая сейчас задача, без точки, если ничего не ждёт. Разобрал — задача уходит из панели; все задачи — на странице «Задачи» (P13).

### D25. Кто добавляет MCP и скиллы — ПО УМОЛЧАНИЮ

**Два уровня** (ARCHITECTURE §17.1):

- админ ведёт каталог организации;
- пользователь подключается к пунктам каталога своими кредами (`per_user`), может завести своё подключение (почта, `http_api`), а в v2 — свой MCP-сервер и свои скиллы.

Каталог общий для MCP и коннекторов — таблица `catalog_items`.

**Ограничения:**

- stdio — только суперюзер;
- свои подключения любого типа по умолчанию `public_only` (политика `personalConnections`): приватные адреса запрещены, чтобы не было SSRF во внутреннюю сеть;
- внутренние системы (1С и т.п.) добавляет админ.

**Почему не «только админ».** Задачи действуют инструментами владельца (D22), и ставка №5 без личных подключений не работает.

**Почему не «пользователь добавляет что угодно».** stdio — это запуск команд на сервере, а произвольный URL — дыра во внутреннюю сеть.

Что меняется в плане: личные подключения по токену — в v1 (M4). OAuth для MCP переезжает из v3 в v2: без кнопки «Подключить» пользователи не подключат GitHub и похожие сервисы, а задачам это нужно.

**Уточнено 2026-10-02.** OAuth для MCP сделан в v1 (M4), раньше срока: многие нужные серверы только на OAuth, и MCP — основной режим работы. Способы авторизации сервера в коде: нет / Bearer / свой заголовок / basic (логин и пароль) / OAuth (PKCE, DCR, refresh через `authProvider` из `@ai-sdk/mcp`, вход в окне сервиса). Политики `personalConnections` и `personalApprovalDefaults` сделаны 2026-10-13 на экране «Доступ» (ARCH §17.1).

### D26. Хранение секретов — РЕШЕНО + SPIKE

- **Где:** все секреты в одной таблице `secrets` (ARCHITECTURE §17.2).
- **Как шифруется:** AES-256-GCM, случайный IV, AAD привязывает шифртекст к его строке.
- **Мастер-ключ:** в env; ротация через `SECRETS_KEY_PREVIOUS` + `metobe secrets:rotate`; canary не даёт стартовать с чужим ключом.
- **Куда не попадает:** API write-only; модель, логи и ошибки тулов секретов не видят.

Отвергнутые варианты:

- **Колонка `*_sealed` в каждой таблице:** ротация и аудит размазаны по всей схеме.
- **Ключ от пароля пользователя:** задачи не могут работать без залогиненного пользователя.
- **Vault/Infisical по умолчанию:** ломает установку в одну команду. Появится адаптером позже.

Честная граница: от владельца сервера self-hosted не защищает.

**Spike S10 (сделан в v1, см. D25):** OAuth MCP через `authProvider` из `@ai-sdk/mcp` с хранением в нашей БД — PKCE, refresh, переподключение. Подключение работает; обновление токена после истечения и «отзыв → `needs_reauth`» вживую ещё не проверены.

### D27. Коннекторы и запрос кред у пользователя — ПО УМОЛЧАНИЮ + PROTOTYPE

**Коннекторы.** Кроме MCP есть встроенные коннекторы с описанием полей, проверкой и своими тулами. Первый — `email` (SMTP): сервер, порт, шифрование, логин, пароль, пресеты популярных почт. Подключения всех видов лежат в одной таблице `connections`. Несекретные поля хранятся в `config`, секретные — в `secrets` (ARCHITECTURE §17.7).

**Типы.** Встроенный коннектор делается для протокола, а не для сервиса. v1 — `mcp`, `email` (SMTP), `http_api`. v2 — `database` (только чтение), IMAP, `telegram_bot`, `webhook_out`. Позже — CalDAV, S3/WebDAV. Сервисы подключаются через MCP из каталога.

**Как модель спрашивает данные.** Встроенный тул `request_connection` без `execute` рисует в ленте форму. Значения уходят из браузера прямо в API, минуя модель. В историю и в контекст модели попадает только сводка «подключено, smtp.yandex.ru:465». Периодическая задача формы показать не может: запуск кончается `outcome = action`, задача ждёт человека, кнопка открывает ту же форму (ARCHITECTURE §17.7).

Отвергнутые варианты:

- **Попросить ввести пароль в чат:** пароль навсегда остаётся в истории и в контексте модели.
- **Отправить в настройки:** рвётся поток, пользователь теряет, где был.

Вид карточки-формы решает прототип P8.

**Уточнено 2026-09-28.** Карточка — «Плашка» из прототипа P8: строка в ответе «Нужен вход в X» с причиной от модели, поля — в диалоге, OAuth — в окне сервиса. Почта — сразу SMTP и IMAP (`email_send`, `email_search`, `email_read`), IMAP перенесён из v2 в v1; ящиков у пользователя может быть несколько. Ящики живут в своей таблице `mailboxes`, а не в `connections`: всё вокруг `connections` завязано на пункт каталога (уникальность, OAuth, проверки), и общая таблица потянула бы ветвления в MCP. Пароль — в `secrets` (`owner_type = 'mailbox'`). Каждое письмо уходит только после «Разрешить» в ленте. Пресеты — Яндекс, Gmail, Mail.ru и своя почта; Outlook.com не берём: Microsoft отключил вход по паролю, нужен OAuth.

### D28. Изменение задач — РЕШЕНО

Задача меняется словами — в поле «Что поменять в задаче…» на её странице. Тул `update_task` не применяет изменение, а показывает «было → стало» в карточке «О задаче»; применяет человек (ARCHITECTURE §16.1a).

- каждое изменение создаёт версию, запуски знают свою версию, есть откат;
- после изменения можно сразу сделать тестовый прогон — он без уведомлений и не идёт в счётчик сбоев;
- идущий запуск доигрывается на старой версии.
- версия хранит поля задачи, кто и когда изменил и текст просьбы; в интерфейсе — «изменена 30 ноя · Вернуть как было» в карточке задачи и строка «Изменена 12 ноя: …» в прошлых запусках под первым запуском новой версии. Отдельной страницы истории версий нет, пока задачи не правят часто и вдвоём (2026-11-05).

Отвергнутые варианты:

- **Модель правит задачу сама, без подтверждения.** Инструкции задачи — это то, что потом работает без присмотра. Незаметная правка из-за неверно понятой фразы проявится через неделю в виде странных сводок.
- **Менять только через форму настроек.** Рвёт поток: пользователь думает «в следующий раз сделай иначе», а не «открою настройки и найду поле».

Вид карточки «было → стало» — прототип P15, выбрана «Карточка задачи» (2026-11-05): изменение показывается в строках карточки «О задаче» наверху страницы задачи.

### D29. Источник и провайдер модели — РЕШЕНО

Решение пользователя 2026-09-24: это разные вещи, и называются они по-разному.

- **Источник** — кто даёт доступ к моделям: ключ OpenAI или Anthropic, Vercel AI Gateway, Yandex AI Studio, свой сервер (`openai-compatible`). У источника — ключ, маршрут через прокси, здоровье, расход.
- **Провайдер** — кто сделал модель: OpenAI, Anthropic, Google, Alibaba (Qwen), DeepSeek, xAI, Mistral, Meta, Яндекс… У провайдера — название и логотип. Их видит пользователь в выборе модели в чате.

Через один источник приходят модели многих провайдеров (Gateway — сотни, Яндекс — свои и открытые), а модели одного провайдера могут идти через несколько источников. Таблицы: `sources` и `providers` (ARCH §5.2).

Логотипы — встроенный набор `@lobehub/icons-static-svg` (MIT, без зависимостей; одноцветные рисуются маской в цвете текста). Админ может поменять название и картинку провайдера, выбрав из набора или загрузив свою (файл — в S3). В настройках — разделы «Источники» и «Провайдеры». У источника тоже можно сменить логотип и название: по умолчанию значок по типу, а у OpenAI-совместимого — угаданный по адресу (ollama, lmstudio, vllm, openrouter…); не угадали — первая буква названия. В пикере логотипа картинку можно вставить из буфера (⌘V / Ctrl+V, в том числе SVG-разметку), перетащить или загрузить файлом.

**Включение моделей — одно поле, два вида** (как маршрут в §18): «модель X в чате через источник Y». В источнике модели сгруппированы по провайдерам, у группы свой переключатель; у провайдера — его модели из всех источников с меткой источника. Отдельного раздела «Модели» в настройках нет. Массовых кнопок «включить показанные / выключить» тоже нет — массовое действие одно, переключатель группы.

До этого решения в документах «провайдером» называлось то, что теперь «источник», а провайдер модели — «вендором»; тексты переименованы 2026-09-24.

### D31. Язык и регион пользователя — РЕШЕНО

Решение пользователя 2026-09-24: интерфейс локализуется сразу, пока продуктового кода мало. Языки v1 — английский (по умолчанию, для глобальной аудитории) и русский. Язык в адресе не участвует: никаких `/en/...`.

- **Библиотека — `next-intl` 4.14** в режиме без i18n-роутинга (официальный пример на Next 16.3). Разбор `Accept-Language` — `negotiator` + `@formatjs/intl-localematcher`, как в руководстве Next. Альтернативы (Lingui 6, next-i18next 16, Paraglide 2) отвергнуты: у всех либо нет готового пути «кука + серверные компоненты», либо неясна совместимость с React Compiler.
- **Что хранится.** В профиле (`user`): `locale`, `time_zone`, `week_start` (ISO: 1, 6, 7), `date_format` (`dmy` / `mdy` / `ymd`). Все необязательные: пусто — «автоматически». Не `en` по умолчанию в базе: иначе русскоязычный пользователь после первого входа оказался бы в английском интерфейсе, ничего не выбирая.
- **Как выбирается на запросе** (`packages/i18n` → `resolvePrefs`, вызывается в `apps/web/i18n/request.ts`): кука → `Accept-Language` → `en`. Куки — копия профиля для рендера без запроса к базе; при входе и после сохранения их пишет `writePrefsCookies`. Неавтоматический выбор хранится и в куке, и в профиле.
- **Часовой пояс «автоматически»** — пояс браузера: клиент один раз сообщает его server action'ом (`tz`), страница перерисовывается на сервере уже в нём. Выбранный вручную пояс помечен `tz_manual` и браузером не перезаписывается.
- **Первый день недели «автоматически»** — по языку (CLDR: en — воскресенье, ru — понедельник). **Формат даты** действует на числовые даты (`formatNumericDate`); даты словами всегда по языку.
- **Вне страниц.** Server actions — `getTranslations`. Письма, CLI и worker — `getTranslator` из `@metobe/i18n/translator` (`use-intl/core`, работает без Next): письмо — на языке профиля получателя, иначе на языке страницы, с которой запросили код; CLI — по `LANG` контейнера.
- **Контракты без текста.** Сообщения Zod-схем в `@metobe/contracts` — ключи (`validation.*`), переводит вызывающая сторона.
- **Правило:** в продуктовом коде нет строк интерфейса вне `packages/i18n/messages/*.json`; ключи типизированы (`AppConfig.Messages`), опечатка ломает сборку. Прототипы в `/dev/prototypes` не переводятся — одноразовый код.
- **Цена.** Чтение куки делает страницы динамическими — для приложения за авторизацией это нормально. Если включим `cacheComponents`, язык придётся передавать в кешируемые функции аргументом: готового рецепта для кук у next-intl нет.

### D32. MCP-серверы в чате: по упоминаниям, большие — по запросу — РЕШЕНО

Решение пользователя 2026-09-27. Повод: в чате «как ты» модель заговорила о Битриксе, а «Готовит ответ…» висело 16–24 с. Битрикс упомянули раньше в вопросе, который потом отредактировали. Сервер при этом остался в чате, и его 106 тулов (25–29 тыс. токенов) уходили в каждый запрос.

- **Серверы чата — те, что упомянуты в вопросах треда** (`@Название`, как упоминание пишет композер). Упоминание — это и бейдж в сообщении, и тулы у модели; разбор у них общий (`apps/web/lib/mentions.ts`). Сервер работает и в следующих вопросах, пока вопрос с упоминанием остаётся в треде. Правка или удаление этого вопроса убирает и его серверы. Колонка `chats.catalog_ids` (липкий список) удалена миграцией 0017.
- **У большого сервера тулы подгружаются по запросу.** Если у сервера больше 12 тулов (`ON_DEMAND_AFTER`), они уходят модели с `deferLoading`, а вместо них модель видит `find_tools` (`toolSearch()` из AI SDK 7). В описании поиска перечислены сервисы за ним и самые частые слова из имён их тулов — так модель ищет теми же словами. Поиск локальный, по словам в именах и описаниях. Найденные тулы, до пяти за поиск, приходят модели со схемами на следующем шаге. Тулы, уже вызванные в треде, подгружены сразу; так и ответ после «спросить сначала» находит свой тул. В «Ходе работы» поиск — отдельный шаг: что искали и что нашлось.
- **Цена.** Когда модели нужен тул большого сервера, добавляется шаг поиска, а после него сбрасывается кеш промпта: список тулов меняется. Поиск идёт по словам без морфологии: «deals» не находит «deal», и модель ищет заново другими словами. Имена и описания тулов обычно на английском, поэтому модель ищет по-английски.

### D33. Вложения: три уровня чтения, служебная модель зрения — ПО УМОЛЧАНИЮ

Решение пользователя 2026-10-02. Не каждая модель читает файлы, а песочница (D3) — отдельный большой этап. Делаем как Anthropic в claude.ai (картинки и PDF — модели напрямую, остальные документы — только текстом, песочница — для работы с данными, а не для чтения):

1. **Как есть.** Картинка или PDF уходит модели напрямую, если её возможности это позволяют (`capabilities.vision`, поддержка PDF у источника).
2. **Текст на сервере.** Документ (PDF модели без PDF, DOCX, XLSX, CSV, TXT, MD, JSON…) один раз превращается в текст, текст хранится, а модель читает его тулом `read_attachment(id, страница)` по частям с подсказкой «дальше — страница N». Так большой файл не раздувает историю и сочетается с бюджетом контекста. Разбор чужого файла — риск (бомба, уязвимость парсера), поэтому он идёт в отдельном рабочем процессе с лимитами времени и размера, а не в процессе запроса. Кэш проверяется до скачивания файла из S3; страницы есть у любого текста, не только у документов.
3. **Песочница** — анализ CSV/XLSX кодом и создание файлов (D3, позже).

**Служебная модель «Зрение»** (слот `vision` рядом с `titles`, выбираются только модели с `capabilities.vision`): описывает картинку модели без зрения. Общее описание кэшируется и помечено как описание («картинка «…», описана моделью зрения»), ответ на конкретный вопрос о картинке не кэшируется. Без модели зрения картинку модели без зрения не отдаём и честно говорим об этом в композере.

Хранение — S3 (D4), файлы живут, пока жив чат. **Браузер с S3 не говорит** (решение пользователя 2026-10-02): загрузка и скачивание идут через приложение — один адрес, без CORS и второго открытого порта, права проверяет приложение; presigned-ссылки — позже, для внешнего S3 и больших файлов. Хранилище — `packages/core/src/storage.ts`, настраивается `S3_*` в `.env`; без них файлы выключены, `/api/health` показывает `s3: off`.

### D34. Зависимости сервера и чистая установка — ПО УМОЛЧАНИЮ

Решение пользователя 2026-10-02. С вложениями, S3 и песочницей зависимостей становится больше, а ставка №1 — установка одной командой.

- **Хосту — только Docker и compose v2** (плюс `curl` и `openssl` для `install.sh`). Ни библиотек, ни CLI на сервер не ставим: всё, что нужно Metobe, едет в образах.
- **Лёгкое — в образ приложения, тяжёлое — в свой образ.** Парсеры — на чистом JS или WASM, без нативных бинарей, чтобы жить в `node:*-alpine`. LibreOffice, OCR, Python никогда не попадают в образ приложения — только в отдельный образ (например, песочницы), который скачивается, если функция включена.
- **Необязательное — профилями compose**, как `db`: `s3` (встроенный SeaweedFS или внешний S3), `search` (SearXNG), `sandbox`. `install.sh` спрашивает, что включить, и пишет `COMPOSE_PROFILES` в `.env`; повторный запуск включает профиль позже.
- **Приложение само видит, что есть.** Чего нет — того не предлагают ни модели, ни пользователю; в настройках видно «не установлено» и как включить. `/api/health` проверяет только включённое.
- **Версии закреплены.** Свои образы собирает релизный CI с версией приложения. Обновление — кнопкой в «О системе» (D35) или повторным запуском `install.sh`.
- **Исключение — песочница.** Безопасная изоляция требует от хоста gVisor (`runsc` как runtime Docker) или KVM. `install.sh` проверяет это в `docker info`; если нет — предлагает поставить (нужен sudo) или пропустить. Песочницы без изоляции не будет.
- **Контроль.** Таблица зависимостей в ARCHITECTURE §2.4 обновляется в том же PR, где появляется зависимость. В CI — задача «чистая установка»: `install.sh` на пустом раннере → `/api/health` за 90 с (критерий M1), с профилями по умолчанию и со всеми. У образа приложения — бюджет размера.

### D35. Обновление из приложения: обновлятель в compose — РЕШЕНО + PROTOTYPE

Решение пользователя 2026-10-29: сервер — только Linux, выбирать то, что удобнее админу. Обновить Metobe должно быть можно из самого приложения, без терминала.

- **Почему не таймер на хосте.** Таймер systemd, который опрашивает приложение, работает только на Linux, срабатывает с задержкой и требует `sudo` при установке. Обновлятель в compose ставится вместе со всем остальным и срабатывает сразу.
- **Обновлятель — сервис `updater`** в `compose.yml`, из того же образа (`command: ["updater"]`), с `docker.sock` и каталогом установки (`compose.yml`, `.env`). Входящих соединений у него нет: заявку он забирает из Redis, ход и итог пишет туда же и в Postgres. Приложение к Docker не подключено и может только попросить «обнови до версии X».
- **Цель проверяет сам обновлятель:** X — опубликованный релиз Metobe в GHCR, новее текущего (или прежний — для отката). Подпись образов (cosign, без ключей через GitHub OIDC) — следующий шаг.
- **Порядок обновления:**
  1. скачать новый образ, пока старая версия работает — простой только на рестарт;
  2. бэкап базы (`pg_dump`, три последних хранятся в томе `backups`);
  3. дать ответам дописаться: приложение перестаёт принимать новые сообщения, пользователи видят плашку, обновлятель ждёт активные ответы до минуты;
  4. закрепить версию в `.env` (`METOBE_IMAGE=…:0.5.0`) и пересоздать `app` и `worker`; сам обновлятель пересоздаётся последним, отдельным контейнером;
  5. проверить здоровье и версию. Не прошло — вернуть прежний образ, а если миграции успели примениться — ещё и базу из бэкапа.
- **Админ видит** в «О системе»: текущую версию, новую с описанием изменений, ход обновления по шагам и историю обновлений. Точка на «О системе» и на аватаре, когда вышла новая версия. Расписание: «обновить ночью» и «ставить исправления (0.5.0 → 0.5.1) сами».
- **Без обновлятеля** (не включён при установке) «О системе» показывает новую версию и команду для терминала.
- **Цена:** контейнер с `docker.sock` — root на хосте, если его взломать. Снаружи до него не достучаться, а из приложения — только просьба поставить официальный релиз.
- **Обновление через несколько версий** (решение пользователя 2026-11-02). Обновлятель ставит сразу целевую версию, промежуточные образы не нужны: в каждом образе вся история миграций, и `metobe migrate` при старте применяет все недостающие по порядку. Чтобы прыжок 0.4 → 0.7 работал всегда:
  - **миграции только добавляются**: старые не удаляются, не правятся и не схлопываются — drizzle сверяет их по журналу;
  - **данные меняются SQL в миграции**, а не кодом приложения «при запуске версии X»: при прыжке через X такой код не выполнится. Всё, что приложение делает при старте, идемпотентно и выполняется каждый раз;
  - **долгие миграции не считаются сбоем**: у `app` в `compose.yml` `start_period: 10m`, обновлятель ждёт «здоров» до 15 минут. Иначе миграции нескольких версий на большой базе откатили бы обновление;
  - **CI проверяет прыжок** (задача `upgrade`): ставит 0.4.0 её же установщиком, пишет данные, переходит на образ из PR с его `compose.yml` и проверяет, что применены все миграции, данные на месте и `/api/health` в порядке. Самую старую версию, с которой обещаем обновление, поднимаем вместе с этой задачей.

### D36. Поделиться чатом: по ссылке для команды, только чтение — РЕШЕНО

Решение пользователя 2026-10-30.

- **Кому.** Любому, кто входит в эту установку Metobe и открыл ссылку на чат. Публичных ссылок без входа нет: в чате бывают данные из 1С и почты владельца.

- **Что видно.** Чат целиком, включая то, что владелец напишет после того, как поделился. Открытая страница сама подтягивает новое каждые 15 с, пока вкладка на экране. Выключил доступ — ссылка сразу отвечает 404.

Файлы открытого чата отдаёт `/api/files/[id]` любому вошедшему (`getReadableFile`). Писать, голосовать, останавливать и переподключать поток по-прежнему может только владелец: проверки в `/api/chat` не менялись.

### D37. Длинный чат: обрезка старого и сжатие итогом — РЕШЕНО (обрезка) + PROTOTYPE (сжатие)

Повод — сервер клиента на 0.6.0, 2026-11-03: один длинный чат с 1С, DeepSeek v4.1 Flash через Yandex AI Studio (0,3 ₽ за 1000 входных токенов), 730 ₽ за четыре ответа. Каждый шаг каждого ответа заново нёс ~170 тыс. токенов: старые результаты 1С, рассуждения прошлых ответов, всю историю.

**1. Обрезка на границе вопроса (сделано, PR #95).** Перед вызовом модели у ответов на прошлые вопросы:

- результаты инструментов заменяются заметкой «результат X (~N токенов) убран, вызовите снова»; вызовы и текст ответов остаются;
- рассуждения не отправляются (OpenAI-совместимый провайдер кладёт их в `reasoning_content` каждого прошлого ответа);
- целиком остаются `find_tools` (на нём держатся одолженные инструменты), ответы пользователя модели (`ask_user`) и всё меньше ~200 токенов.

Текущий вопрос не трогается: модели с рассуждениями нужны свои рассуждения между шагами. Правило зависит только от истории и от того, где начался вопрос, поэтому все шаги ответа видят одинаковое начало — кэш внутри ответа держится, а ломается раз на вопрос, где после паузы он и так был холодным. По образцу microcompact в Claude Code и `clear_tool_uses` в API Anthropic. Расчёт по тому чату: ответы дешевле в 2–3 раза.

Подрезку внутри ответа (порог `budgetMessages`, 100 тыс. оценочных токенов) не ужесточали: по тем же данным порог 50/30/20 тыс. экономит лишь 13–22 %, а модель теряет данные посреди своей работы и чаще ломает кэш.

**2. Сжатие чата итогом (проектируется).** Остальное съедают база и история прошлых ответов на каждом шаге — это убирает итог.

- **Только явно.** Человек нажимает «Сжать чат»; тихого auto-compact нет: в рабочем чате незаметная потеря деталей хуже явного предложения. Предлагаем сами — тихой строкой у поля ввода, когда последний ответ потяжелел по факту (входные токены на шаг из `model_runs`, после обрезки), и всегда в меню чата.
- **Кто пишет итог.** Новая служебная задача «Сжатие чатов» в «Служебных моделях» (слот рядом с «Названиями» и «Зрением»); без неё — модель чата. Запуск записывается в расходы с назначением `compact` (миграция: `model_runs.purpose`).
- **Итог — структурированный**, по образцу Claude Code, на языке чата: цель и запросы пользователя; важные данные и факты — с числами, периодами и источником; что сработало — точные запросы, инструменты, параметры; решения и договорённости; как пользователь хочет получать ответы; все его сообщения коротко; что осталось открытым. Служебная модель получает текст, вызовы инструментов с аргументами и урезанные результаты, без рассуждений; если история не влезает в её окно — по частям. Повторное сжатие — прошлый итог плюс то, что после него.
- **Где хранится.** Отдельным сообщением в истории с частью `data-compaction` (итог, модель, сколько было токенов). Поэтому правка вопроса раньше границы удаляет итог сама (история линейная), «Продолжить у себя» переносит его, общий доступ показывает его как есть. Сохранённая история не меняется — человек видит весь чат, на месте сжатия разделитель с итогом, который можно раскрыть.
- **Что уходит модели.** Итог первым сообщением (`<conversation-summary>`) и всё после последнего итога, дальше та же обрезка. Начало запроса после сжатия неизменно — кэш снова работает.
- **Когда нельзя.** Пока идёт ответ; пока ответ ждёт человека (вопрос модели, подтверждение); в чате короче нескольких вопросов. Ошибка служебной модели ничего не меняет — человеку говорим, что не вышло.
- **Не решено, решает прототип `/dev/prototypes/compact`:** вид разделителя в ленте, подсказки у поля ввода и состояния «сжимаем…».

- **Слот «Решения» (Б2b, 2026-11-09) — только экономия:** модель решений из Gateway отсеивает сообщения, где запоминать нечего, до модели «Память»; по умолчанию советуем Microsoft Decision-1 (S13, часть 6: 0 потерь, 13/13 пустых отсеяно, $0,000013 за сообщение). Выбор карточки и закрытие обязательств ей не отдаём — с этим справляется модель «Память».

**Предложение (ПО УМОЛЧАНИЮ, пока не отменено):**

- **Что хранится.** Сущности (человек, организация, проект) с другими именами; факты о сущностях; события (встреча, разговор, запрос) с участниками и датой; обязательства в обе стороны (кто, кому, что, срок, статус); правила. У каждой записи — источник: сообщение чата, позже отрезок записи. Факт, оценка («часто срывает сроки»), обязательство и событие — разные типы; модель не превращает одно в другое.
- **Всё в Postgres**, с `user_id` в каждой таблице и проверкой в одном месте доступа. Поиск — полнотекстовый (`russian`) плюс `pg_trgm` по именам; эмбеддинги и pgvector — когда поиск по смыслу окажется нужен на деле.
- **Два времени.** У факта — когда стал верен и когда перестал (`valid_from`, `valid_to`); у события — когда произошло (`occurred_at`); у обязательства — когда дано и срок. У всех — когда занесено (`recorded_at`) и когда запись заменена (`superseded_at`). Дата происшествия хранится с точностью (день, неделя, месяц, неизвестно): «в прошлый вторник» считается от времени сообщения в часовом поясе человека (D31), «на днях» — неделя, без даты — пусто, а `recorded_at` служит верхней границей. Правила:
  - «давно не было», «неделю ждём», просрочки считаются по времени происшествия, не занесения: «забыл сказать — в среду виделись с Андреем» убирает пункт из плана;
  - новый факт закрывает старый, только если произошёл позже: занесённое сегодня «в сентябре проект был на этапе дизайна» не отменяет «сейчас в тестировании», а ложится в историю;
  - исправление («не в среду, а в четверг») — новая запись, старая получает `superseded_at`; так видно и «как было», и «что я знал на дату»;
  - для записей встреч и аудио время происшествия — время встречи, занесения — загрузка.
- **Запись — в две ступени.** Сначала быстрая проверка: есть ли в сообщении что запомнить и что именно (ничего / факт / событие / обязательство / правило) с уверенностью. Большинство сообщений на этом заканчивается. Если есть — служебная модель «Память» (новый слот в «Служебных моделях», запуск в расходах с назначением `memory`) получает сообщение, ответ и найденные по именам карточки и возвращает операции «добавить / изменить / закрыть» через структурированный вывод. Низкая уверенность или спорное сопоставление («какой Андрей?») — черновик, а не молчаливая склейка. Обе ступени — слоты, их занимает любая модель из источников.
- **Модели решений (класс Jev).** Не пишут текст, а отвечают на типизированные вопросы — выбор из вариантов, шкала, да/нет — с вероятностями, за доли секунды и почти бесплатно. В `ai@7.0.113` (наша версия) это `experimental_evaluate`. Подходят не только на первую ступень, но и на всё, где ответ — выбор: какой из Андреев в карточках (выбор до 255 вариантов), закрывает ли сообщение открытое обязательство (да/нет по каждому), важность пункта плана (шкала). Текст факта по-прежнему пишет служебная модель. Кандидаты, проверено 2026-11-08 по описаниям, русский язык нигде не заявлен:
  - **Jev** (TypeSafe) — через Vercel AI Gateway, наш источник из v1: `typesafe-ai/jev`, $0,042 за 1 млн входных токенов, выход бесплатен, 64 тыс. токенов (state — до 32 тыс.), запрет хранения запросом (`zeroDataRetention`). Закрытая, только облако.
  - **Clef / Clef-flash** (Cloudflare) — открытые веса Apache 2.0, 27B и 9B на Qwen, формат запросов как у Jev; в облаке Workers AI. Свой сервер — пока исследовательская сборка на `transformers`, не команда в compose.
  - **Laya** — открытая, маленькая, многоязычная, но базовые веса без дообучения отвечают почти наугад — не сейчас.
  - **Любая модель чата** через адаптеры AI SDK (`openai`, `anthropic` дают `evaluationModel`; у `openai-compatible` — Яндекс, Ollama — его нет, нужен свой): работает, но вероятности не откалиброваны. Решение: ступень — отдельный слот «Решения»; Jev через Gateway с запретом хранения — первый кандидат, без источника с моделью решений — адаптер к модели чата. Что брать по умолчанию, решает S13 на русских диалогах. **S13, первая часть — 2026-11-08** (`spikes/S13-jev`): 274 решения на русских сообщениях, десять моделей решений через Gateway. С запретом хранения: Jev 97–98 %, Microsoft Decision-1 97–98 %, Mammoth-1 98 %; Perplexity Decider 27B — 100 %, но без ZDR. Русский работает, уверенные ответы (P ≥ 0,9) у Jev без ошибок, ошибки — около 0,5, их забирает черновик. Jev — ~$0,00004 за сообщение, p50 0,3 с; в одном прогоне из трёх — сбои по таймауту, поэтому запись идёт через очередь с повтором. Вторая ступень (текст факта) не проверялась. **S13, вторая часть — 2026-11-08:** служебная модель пишет записи из 30 русских сообщений (33 записи, 27 дат). DeepSeek v4.1 Flash через Яндекс — 100 % записей и дат, Gemini 3.5 Flash-Lite через Gateway — 100 % и 96 %, Sonnet 5 как эталон — 100 % и 92 % при цене в 10 раз выше. Alice AI и YandexGPT 5.1 путают прошедшие и будущие даты (21–50 %). Промпту нужны три правила, без которых проваливались все модели: «ждём ответа» — обязательство другой стороны, у обязательства «когда дано» ≠ «срок», ссылка у каждого упомянутого, даже без имени.
- **Чтение.** Имена из сообщения ищутся в карточках обычным запросом, найденное уходит модели коротким блоком; дальше — узкие инструменты (`search_memory`, `list_commitments`, карточка сущности), выбор за моделью, как с `find_tools` (D32).
- **Предложения на главной** собираются запуском по расписанию в часовом поясе человека (D31): просроченные и близкие обязательства, ожидание ответа дольше правила, правила ритма против последнего события с человеком — всё обычными запросами; модель только формулирует пункты. Говорим «собран утром», не «Metobe следит» (D38).
- **Шифрование.** Тексты памяти (факты, заметки, формулировки, имена) шифруются, как секреты (D26): AES-256-GCM, ключ данных у каждого пользователя, ключи закрыты мастер-ключом из env. Открытыми остаются только поля для запросов плана: даты, сроки, статусы, типы, связи между записями. Следствия:
  - поиск по тексту в Postgres (FTS, `pg_trgm`, эмбеддинги) по зашифрованному невозможен — индекс раскрыл бы текст; память одного человека — тысячи записей, поэтому её расшифровывают и ищут в процессе приложения;
  - **честная граница та же, что в D26:** защищает от утечки базы и бэкапа, не от владельца сервера — у него мастер-ключ. Ключ от пароля невозможен (входа по паролю нет, D17), а план и запись из встреч должны работать без вошедшего человека. Защита и от владельца сервера (ключ на устройстве, passkey с PRF) отклонена пользователем 2026-11-08: хватает защиты от утечки базы.

**Решения 2026-11-09 (после разбора ручного трекера поручений «На контроле»):**

- **У обязательства четыре статуса:** «открыто», «ждёт проверки», «выполнено», «отменено». «Отменено» — делать больше не нужно («Андрей передумал»), раньше записать это было некуда. «Ждёт проверки» — о выполнении сказал кто-то другой («Андрей говорит, API готов»): пункт остаётся в плане, пока человек не подтвердит одним нажатием на странице «Память» или в «На сегодня». Видел сам («Ольга прислала договор») — сразу «выполнено».
- **Флаг «важно» вместо матрицы Эйзенхауэра.** Срочность — из срока, отдельным полем её не храним: она устаревает. Важность модель не угадывает: флаг ставится, только если человек сказал это словами («горит», «критично», «главное») или отметил запись сам. В «На сегодня» сначала важное со сроком, потом остальное по сроку. Квадрантов, доски и ручных приоритетов нет — это ручное ведение задач, не память.
- **Для экранов P16 и P17:** история обязательства строками («Срок перенесён: 13 ноя → 17 ноя», «Статус: открыто → выполнено», из какого чата); «Перенести срок» — завтра, послезавтра, в понедельник, через неделю (вместо одного «Отложить до завтра»); «Сверка» на карточке человека и в «На сегодня» — кладёт в поле просьбу написать человеку по всем открытым договорённостям с ним, письмо пишет модель чата; сроки словами («просрочено на 2 дн.», «завтра», «через 5 дн.»), у человека в списке — число открытых и просроченных; в поиске — «Ещё N выполненных — показать».
- **Статус по сообщению ставит служебная модель слота «Память»**, а не модель решений: она и так читает каждое сообщение, видит открытые обязательства и закрывает их тем же вызовом; работает без моделей решений, которые есть только в Gateway. Слоту «Решения» остаётся первая ступень.
- **Человек и его команда (2026-11-09).** Навыки и чем занимается человек — факты, по одному на навык, мнение о нём — оценка. Подпись карточки следует за новой ролью из разговора («Андрея назначили тимлидом»). Собственные цели и подход человека («развиваю подчинённых») — факты о нём самом и идут модели чата с каждым сообщением. Поиск по смыслу («кому отдать анализ данных» при «сильный в SQL») — пока нет, слова; эмбеддинги — когда упрёмся.
- **Не берём:** этапы и подзадачи, доску, диаграмму сроков, экспорт, «как передано» (источник уже записан), всплывающие напоминания о сроке — по D38 говорим «собрано утром».

**Прототипы:** страница «Память» (P16) — выбраны «Карточки» (2026-11-09); предложения на экране нового чата (P17) — выбраны «Строки»: раздел «На сегодня» над «Начать с», остальной экран и приложение не меняются (2026-11-09); строка «Запомнено» под ответом — третий вариант P16; вопрос памяти в чате (P18) — выбрана «Плашка и тост»: плашка с вариантами под ответом, а если вопрос пришёл вне экрана или человек пишет — тост sonner с вариантами (2026-11-09). Вопрос приходит по SSE и не попадает в историю чата; без ответа ждёт в «Не записано». **Решают spikes:** качество тихой записи на наборе диалогов с известными правильными операциями (S13); Телемост — может ли запись встречи попасть к нам без человека (S14).

### D40. Память, второй проход: порядок записи, кандидаты, слияние, уборка, качество — ПО УМОЛЧАНИЮ + РЕШЕНО + PROTOTYPE

2026-11-09. Разбор сделанной памяти (D39, ARCHITECTURE §19) до включения у живых людей. Модель данных, шифрование, статусы и вопросы держатся. Слабые места — запись под нагрузкой, рост памяти, то, что она не убирается, и то, что её ошибки не видны. Как устроено — ARCHITECTURE §19.8, этапы — PLAN, «Память, второй проход».

**Что не учли** (по коду, не воспроизводилось):

1. Сообщения одного человека читаются параллельно: две записи сразу, порядка по человеку нет. «Созвонился с Павлом из „Вектора"» и «Павел обещал прайс к пятнице» дают две карточки «Павел»; «он прислал», прочитанное раньше обещания, ничего не закрывает — обещание висит.
2. Дубли карточек нельзя объединить, а они будут: «Ольга», «Ольга Ли», «Ольга из Альфы».
3. Служебная модель получает все карточки и 60 новейших открытых обязательств. Цена растёт вместе с памятью; выбор карточки из сотен не проверялся (S13 — 8 карточек); старое обязательство вне окна сообщением не закрыть.
4. Вставленный чужой текст (письмо, протокол) читается как слова человека: «мы обязуемся» поставщика ложится обязательством самого человека.
5. То, что ассистент узнал из почты или CRM и пересказал («„Вектор" ответил: согласны»), в память не попадает: обязательство остаётся открытым, «Не упустить» продолжает напоминать.
6. Свои обязательства без срока и чужие без правила ожидания не всплывают никогда; вопросы «Не записано» без ответа висят вечно.
7. Повторяющиеся даты не выразить: день рождения — факт, «отчёт каждую пятницу» — никак.
8. «Не упустить» видно только на экране нового чата.
9. Качество на живых сообщениях не измеряется, смена модели в Gateway может уронить его незаметно.
10. Человек, о котором записано, не может потребовать удаления: админ памяти не видит.

**Решения (ПО УМОЛЧАНИЮ):**

- **Очередь по человеку.** Запись сообщения создаётся при постановке в очередь; задание worker'а — «дочитать очередь человека» по порядку отправки под замком в Redis. Разные люди читаются параллельно, сообщения одного — по одному. Отвергнуто: пачка сообщений одной записью — ломает «Запомнено» и «Отменить» у каждого сообщения; группы BullMQ — только в платной версии; замок в Postgres на время вызова модели — держит соединение до минуты.
- **Контекст — сообщения чата после прошлой прочитанной**, до 6 сообщений и 4000 знаков, а не один обмен. Вместе с очередью рассказ в несколько сообщений читается целиком: записи предыдущих уже лежат.
- **Служебная модель видит кандидатов, а не всю память.** Карточки — названные в сообщении и контексте по имени, другим именам и словам подписи, все группы, недавние; до 40. Обязательства — со сторонами из этих карточек, свои за 30 дней, совпавшие по словам; до 40. Старое обязательство закрывается, когда назван его человек.
- **Чужой текст.** Цитаты (строки с «>», «Пересланное сообщение», заголовки письма) модель получает отдельно от слов человека с правилом: «я» и «мы» в них — автор, не человек; записывается только то, что относится к людям из памяти или что человек назвал своим. Цитата без маркеров — то же правило в промпте. Блок `<memory>` для модели чата — данные: указания внутри не выполняются.
- **Объединение карточек.** «Объединить с…» в меню карточки и предложения «Похоже, один человек: Ольга — Ольга Ли» в «Не записано», без модели, по совпадению слов имени; «Разные люди» больше не предлагается. Объединение переносит записи, другие имена, членство в группах и «Убрать» из «Не упустить»; «Вернуть» отменяет.
- **Уборка.** Обязательство без движения 30 дней — строка «Сверка: 5 давно открытых» в «Не упустить» раз в неделю и фильтр «Давно открыто» на странице; «Оставить» убирает его из сверки на 30 дней. Вопрос без ответа 14 дней снимается вместе с записями, которые его ждут.
- **Повторяющиеся даты** — правило вида `date`: каждый год, месяц или неделю от даты («день рождения Ольги 14 ноября», «отчёт каждую пятницу»). В «Не упустить» — в день и накануне, день рождения — за 3 дня.
- **Качество видно админу без чтения текстов.** У слота «Память»: сообщений, записано, отменено под ответом, удалено и исправлено руками, «Не запоминать», сбоев, цена — за 7 и 30 дней. При смене модели слота в разработке — прогон всех наборов S13 и S15. Модель в слоте — версией, не псевдонимом.
- **Память в задачах — только чтение**, те же инструменты, что в чате. Задачи по-прежнему ничего не пишут (D39 в этой части меняется).

**РЕШЕНО пользователем 2026-11-09 — все три «да»:**

1. **Ответ ассистента закрывает обязательства.** Предложение: служебная модель читает и ответ на сообщение, но только чтобы найти, что открытое обязательство выполнено по тому, что ассистент получил из инструмента («„Вектор" ответил: согласны»). Такое закрытие — «ждёт проверки» с пометкой «из ответа», человек подтверждает одним нажатием; новых фактов из ответа нет.
2. **Письмо «Не упустить» по утрам.** Предложение: выключено, включается в настройках памяти; в 9:00 по поясу человека; уходит, только если в разделе есть то, чего не было в прошлом письме (D38: «нового нет» не пишем).
3. **Удаление упоминаний человека во всей установке.** Предложение: команда для владельца сервера (у него мастер-ключ) находит карточки по имени во всех памятях и удаляет их записи; в журнал — только число.

**Прототипы:** P19 — объединение карточек, P20 — «Сверка», P21 — письмо по утрам. **Spike:** S15 — память на 300 карточках, чужой текст, повторяющиеся даты, ответ ассистента.

### D41. Память, третий проход: доверие, выводы из накопленного, почта — ПО УМОЛЧАНИЮ

2026-11-10. Память — главная ставка продукта (слова владельца). После второго прохода (D40) основа держится: записи с типами и источником, «Не упустить» считается кодом, память спрашивает, а не угадывает. - **Г2. Выводы из накопленного, без новых источников.**
  1. «Досье» карточки и «Перед встречей»: что он должен мне, что я ему, что изменилось с прошлого разговора, как с ним говорить. Сводка пересобирается в фоне.
  2. «Надёжность»: сколько обещаний стороны выполнено в срок — запросом по `memory_changes`, без модели. Показывается на карточке и рядом с новым обещанием; слова — сухие, без оценки человека.

- **Г3. Почта.** Задача по расписанию читает новые письма людей из памяти; говорим «собрано из почты» (D38).
  1. Без модели: отправленное без ответа дольше правила ожидания. **Сделано 2026-11-15** (P24 «Предложение»): включается на ящик («Замечать письма без ответа», по умолчанию выключено; предложение в «Не упустить», пока ни один ящик не читается). Читаются только конверты и заголовки цепочки, тексты писем — нет; хранится тема, адрес и `Message-ID` письма, запечатанные ключом человека. Ждём только от тех, кто уже писал в этот ящик (S16: ящик, куда не отвечают, дал бы одни ложные строки). «Напомнить» — ответ в цепочке по шаблону, без модели. Адрес карточки — внесённый на неё или тот, которому письма ящика дают её полное имя (одной карточке, одному адресу); на карточку он сам не записывается.
  2. С моделью: обещания из писем и их закрытие ответом; источник записи — письмо.
  3. Записи встреч — после S14.
- **Источник — только способ добычи** (владелец, 2026-11-10). Память, решения и отношения не зависят от входа: чат, ответ ассистента, почта, записи встреч и Телемост — адаптеры, которые дают ядру материал из реплик с говорящими. Правила зависят от того, кто говорит (свои слова, чужие, пересказ), а не от источника. Одна очередь по времени, одно и то же из двух источников — одна запись. Шаг И1 идёт до любого второго источника — `docs/MEMORY-PLAN.md` §1, §5.
- **Не берём:** общую память команды, векторный поиск «на всякий случай», действия без подтверждения.

**Открыто:** шифрование всего текста не даёт искать в базе — при объёме почты понадобится кэш расшифрованной памяти или индекс (замер §19.8.3: 64 мс на 5 000 записей); простые выборы («выполнено или ждёт проверки», «какой Андрей») можно отдать модели «Решений» (D39) — не проверено.

### D42. Память: свои типы карточек — ПО УМОЛЧАНИЮ (S15 «types» пройден)

2026-11-10. Виды карточек закрыты: человек, организация, проект, группа. Автобус, договор, стройку, кота записать некуда — теряются или ложатся «проектом». Заранее типы не угадать.

**Решения пользователя:**

- **Тип определяет модель решений** (слот «Решения»), выбором из списка: встроенные типы, типы, которые у человека уже есть, «новый тип», «не карточка».
- **Общего слова в интерфейсе нет** («предмет» отвергнут: это может быть и питомец). Человек видит только тип, названный им самим: разделы «Автобусы», «Договоры»; подпись карточки «Барсик · кот».
- **Проверять только на Decision-1.**

**ПО УМОЛЧАНИЮ:**

- В данных — вид `custom` и текстовое поле типа. Люди, организации, проекты и группы — встроенные типы в том же списке; своё поведение («кто кому должен», ожидание ответа) есть только у них, у своего типа — то, что человек сказал правилом.
- Писатель отдаёт упоминание и слово типа, как сказал человек; модель решений выбирает тип. «Новый тип» — берётся слово писателя, и человек один раз отвечает «Завести карточки для автобусов?»; дальше тихо. «Не карточка» — запись ложится без карточки.
- Модель решений видит у каждого своего типа до трёх его карточек: «машина 305» и «борт 540» попадают в «автобус».
- Раздел по типу на странице «Память» — с двух карточек; одиночки — в «Другое». Типы можно объединить руками.
- Своих полей у типа (госномер, пробег колонками) нет: это факты. Таблица с колонками — отдельная фича, не память.
- Без слота «Решения» тип определяет писатель по правилу в подсказке — запасной путь, мерить отдельно.

**Сделано 2026-11-11 (ARCH §19.9.9), с отличиями от решения:**

- Тип выбирает модель решений только у **вещей, которых назвал писатель** (`new_entities` вида `thing`, слово типа в `about`); встроенные виды писатель выбирает сам, как и раньше. Модель решений при этом может вернуть вещь во встроенный вид или «не карточка».
- **Вопрос «Завести карточки для автобусов?» не задаётся:** новый тип заводится тихо, слово — писателя. Поправить можно на карточке (тип правится на месте). Вопрос — отдельным шагом, если неверные типы начнут мешать.
- **Раздел списка — слово типа в единственном числе** («Автобус», не «Автобусы»): склонять произвольное слово нечем. Раздел — с двух карточек, одиночки и карточки без типа — в «Другое».
- **Слияния типов руками нет:** чужой тип поправляется на каждой карточке отдельно.
- Без слота «Решения» вещь остаётся с типом писателя; этот запасной путь не измерялся.

**S15, часть 6 «types» (`pnpm types`, Decision-1, 2026-11-10):** 40 упоминаний × 3 прогона и 11 отложенных × 3.

- «Карточка или нет» (ноутбук, отчёт, «нужен автобус на корпоратив») — 153/153 во всех прогонах.
- Встроенные типы 21/21; ещё одна вещь своего типа другими словами 42/42; кот и собака — не «человек».
- Новый тип рядом с имеющимся — слабое место. Первая редакция вопроса: 18/30 — «Маршрут 17» уходил в «автобус» с P 0,97, склад и магазин — в «объект». С правилом «связанное с типом — не тот же тип» и примерами — 30/30, на отложенных случаях, которых нет в примерах (остановка, счёт, гараж, путевой лист, акт, попугай) — 21/24: страховой полис ушёл в «договор» (0,90).
- Порог уверенности не спасает: ошибки идут с P ≥ 0,9. Поэтому слияние с имеющимся типом человек видит («Маршрут 17 · автобус») и может поправить тип карточки; тип с размытым названием («объект») притягивает чужое — в вопросе показываем карточки типа, а не только слово.
- Цена — $0,00002 за упоминание.

### D43. Входы, доступы и каналы: место Telegram — РЕШЕНО (2026-11-11)

Четыре слоя, которые не смешиваются:

| Слой | Что доказывает | Чем сделан |
| --- | --- | --- |
| Вход человека | «это пользователь X» → сессия | код на почту (Better Auth `emailOTP`), claim, приглашение, ссылка от админа (D17) |
| Доступы Metobe наружу | «Metobe может ходить в систему Y» | `secrets` (D26); токен бота уведомлений — `TELEGRAM_BOT_TOKEN` в env, один на установку |
| Каналы пользователя | «этот адрес принадлежит X, туда можно писать» | почта аккаунта (подтверждена входом); Telegram — строка в `user_channels` |
| Действия без сессии | «у предъявителя право на одно действие» | подписанная ссылка в письме (`/mail-off`); кнопки под сообщением бота |

**Решения пользователя:**

- **Telegram — канал уведомлений, раньше v3** (D24 переносил его на v3). Бот один на установку, токен в env.
- **Текст уходит полностью.** Человек сам решил получать сообщения в Telegram; удобство важнее того, что текст памяти лежит у третьей стороны.
- **Кнопки под сообщением действуют без входа**, но только у привязанного чата.

**ПО УМОЛЧАНИЮ:**

- **Telegram не способ входа.** Кодов входа и ссылок, которые сами входят в аккаунт, в Telegram нет: «почтовый ящик и есть аккаунт» (D17) остаётся. Привязка возможна только после входа, поэтому первый вход без SMTP она всё равно не решает.
- **Привязка:** «Привязать Telegram» в настройках «Уведомления» → одноразовый код на 10 минут → `t.me/<бот>?start=<код>` (на компьютере ещё и QR) → бот получает `/start <код>` и id чата → worker пишет id чата в строку пользователя и стирает код. Хранится хеш кода, в той же строке `user_channels` со статусом `pending`.
- **`user_channels`:** пользователь, вид (`telegram`), id чата, имя для показа, статус, последняя ошибка; одна строка на пользователя и вид. Почте строка не нужна.
- **Приём:** `getUpdates` из worker (у self-hosted часто нет публичного адреса), один читатель на токен — стенду и деву нужны разные боты. Только личные чаты. Отключённому пользователю ничего не уходит. Бот заблокирован — статус ошибки в настройках.
- **Кнопки — только обратимое:** «Выполнено», «Убрать», «Отложить». Остальное — ссылка в приложение, она требует сессию.
- **Доставка — одна функция `notify(пользователь, событие)`:** выбирает каналы, письмо и сообщение рисуются из одних блоков (`letterBlocks`). «Что присылать» остаётся у источника события (флажок задачи по D24, свой у сводки памяти); у пользователя только «куда»: почта, Telegram, оба.
- **Не то же, что коннектор `telegram_bot`** (D27, v2): там свой бот пользователя как тул модели.

**Порядок:** привязка и настройки → `notify` и перевод писем задач на неё → сводка памяти в выбранное время → кнопки.

**Не проверено:** работает ли `@chat-adapter/telegram` (ARCH §16.5) без вебхука. Для уведомлений хватает прямых вызовов Bot API.

**Напоминания по просьбе (2026-11-11, решение владельца: «напомни мне то-то и это», «часто будет»).**

- **Не отдельный механизм.** «Напомни мне завтра в 15:00 позвонить Ольге» — обещание пользователя со сроком; к нему добавлен момент напоминания (`memory_records.remind_at`, `reminded_at`, миграция 0061). Оно само видно в «Не упустить», «Календаре» и «Сверке».
- **Пишет тот же тихий писатель** (D39), отдельного инструмента в чате нет: в схему ответа добавлено последнее поле `remind` (`HH:MM`, `morning`, `none`), правило про напоминания входит в промпт только для сообщения со словом «напомни» (как правило про повторяющиеся даты). Срок — день, когда сработает напоминание; без дня напоминания нет.
- **Доставка.** Минутный тик worker (тот же, что у сводки) берёт наступившие, помечает как отправленные до отправки (две копии не уйдут) и шлёт через `notify` — почта, Telegram или оба, как выбрал человек. Под сообщением «Готово», «Через час», «Завтра» (Telegram). «Через час» и «Завтра» ставят новый момент, и напоминание уходит снова.
- **Пропущенное** (worker не работал) уходит на следующем тике, с опозданием. Если некому сообщить (нет ни почты, ни привязанного чата), оно считается отправленным и остаётся видно в приложении.
- **Замер:** S15 «напоминания» (`pnpm run reminders`), muse-ember, 14 сообщений: 14/14, $0,0075. Все прежние наборы — в пределах обычного разброса (279 из 288 против 284).
- **Календарь встреч** — отдельный следующий шаг (D-плана Д3, нужна ссылка на календарь).

**Повтор и автозакрытие (2026-11-14, шаг 6 плана памяти, P29 «Раздел»).**

- **Повтор — у того же обещания.** «Каждый понедельник в 10 — отчёт» — одно обещание с `repeat` (день, будни, неделя, месяц, год; миграция 0062 разрешила колонку правилам-датам и обещаниям с напоминанием). Писатель ставит его в том же поле `repeat`, что и у правил-дат; правило про напоминания говорит, что такое напоминание — не правило-дата.
- **Следующий раз.** При отправке обещание берётся одним обновлением с условием на старое `remind_at` (две копии тика не отправят дважды): срок — день, когда пришло, напоминание — следующий раз в то же время дня. «Готово» не закрывает, а переносит срок и напоминание на первый раз после срока, который ещё впереди: пропущенные недели не копятся. «Отменено» заканчивает повтор, снятое напоминание снимает и повтор.
- **Под повторяющимся в Telegram — только «Готово».** «Через час» сдвинул бы время дня для всех следующих раз.
- **Простое закрывается само.** Своё напоминание без второй стороны после доставки (почта или Telegram) отмечается выполненным; не доставленное остаётся открытым. «Через час» и «Завтра» в Telegram и «Не сделано» на странице открывают его снова. Обещание кому-то после напоминания остаётся открытым.
- **Ограничение:** месячный повтор с 31-го, пришедший 30-го, дальше идёт 30-го — опорный день не хранится.

**Сообщения боту (2026-11-14, решение владельца; шаг 7 плана памяти).** Бот — не только канал уведомлений: в привязанном чате ему пишут, как в чат Metobe. Вход в аккаунт через Telegram по-прежнему не делается.

- **Разговор — обычный чат приложения «Telegram».** Ссылка на него — `user_channels.app_chat_id` (миграция 0063); удалённый чат — новый при следующем сообщении. Чат виден в списке, ищется, в нём можно продолжить из приложения; память читает его сообщения как любые (источник `chat`, «Откуда» ведёт в него) — отдельного источника `telegram` не понадобилось.
- **Отвечает как чат:** та же модель (последняя, на которой писал человек; иначе первая в чате), блок памяти и её инструменты, напоминания, время, веб, таблицы и графики — текстом Telegram (`letterBlocks`), карточка и список обещаний — строками. В сообщение идут слова последнего шага и показанное: «проверю дату…» перед вызовом тула — шаг, не ответ.
- **Пересланное** начинается строкой «Переслано от …» — писатель читает его как чужой текст (`splitQuoted`). Комментарий и пересланное приходят разными сообщениями: что пришло за 1,5 с, отвечается одним. Ответы одного чата — по очереди; «печатает…», пока модель пишет.
- **Пока без почты и MCP:** их вызовы могут ждать «да», которому в Telegram нет места. Фото и файлы — только подпись.
- **Ошибка `getUpdates: TypeError`** — сетевой сбой `fetch`; цикл повторяет через 5 с. Теперь в тексте ошибки есть код причины (`ECONNRESET`…), URL с токеном по-прежнему не пишется.

### D44. Память, пересмотр записи: один вызов на обмен, голос у каждой записи, без отсева — РЕШЕНО (2026-11-15)

Свежий взгляд на память после шагов 1–9 (владелец: «делай лучшее»). Запись обросла заплатками ради того, чтобы промпт сообщения не менялся слово в слово с S13: отдельный вызов для ответа ассистента, правило по голосу на весь материал разом, отсев моделью решений.

- **Промпт не заморожен.** Цифры S13/S15 — набор регрессии, а не ограничение: правка промпта = прогон `pnpm memory:eval` (около $0,2 на Muse Ember, `RUNS=2`) против базовой линии. Базовая линия Muse Ember снята 2026-11-15.
- **Обмен — один вызов.** Ответ ассистента, где он пересказывает найденное инструментом (почта, MCP, веб), идёт писателю после сообщения как `<answer>` — отдельного вызова больше нет (`memory-retold.ts` только решает, какой ответ считается).
- **Голос у каждой записи.** Схема ответа получила `from` у записей и закрытий: `user` — слова человека, `other` — чужие (цитата, пересланное, письмо, реплика встречи), `answer` — пересказ ассистента. Код (`memory-evidence.ts`) верит метке, только если такой голос есть в материале, и пропускает то, что голосу положено: чужое — свои обещания и факты, закрытие только «ждёт проверки», без оценок и правил; ответ — только «ждёт проверки», без записей.
- **Отсев остаётся (поправка 2026-11-16).** Сначала я убрал его, предположив, что он молча теряет короткие ответы; замер (`spikes/S15-memory/gate-short.ts`: 20 реплик, понятных только с контекстом, и 10 пустых) показал обратное — Microsoft Decision-1 сохранил 19 из 20 и отсеял 10 из 10 за $0,000014 на сообщение; потерялось только «горит» в ответ на вопрос о важности. Отсев возвращён с вопросом `reply` (ответ на вопрос ассистента, дающий деталь): 20 из 20 и 10 из 10 дважды, старый набор отсева 84/84. Не спрашивается, когда ответ ассистента пересказывает найденное инструментом — он может закрыть обещание.
- **Замер.** Регрессия против базовой линии — в пределах шума (±1 случай на набор), входных токенов +3 %. S15 «ответ» в одном вызове: 15/15 дважды, ложных закрытий 0, «выполнено» из ответа 0, записей из ответа 0.
- **«Запиши» и «напомни» — инструментом.** Попросил словами — модель чата вызывает `remember`: сообщение проходит очередь памяти сразу (та же запись, что ставится после ответа, — второй раз не читается), модель получает, что записано, и говорит правду: «Записал: Ольга Ли пришлёт договор к 20 ноября», «Напомню 16 ноября в 10:00». Сказанное между делом пишется после ответа, как было. Без воркера ждёт до 20 с и отвечает «хорошо». Проверено живьём через Telegram-путь на Muse Ember.

### D45. Память: обещания отдельно от расписаний — РЕШЕНО (2026-11-16)

Пункт 5 пересмотра D44. Обещание несло четыре смысла: договорённость между людьми, своё дело, напоминание по времени, повторяющееся напоминание; поле `repeat` было общим у напоминаний и правил-дат, день рождения хранился «правилом», а своё напоминание — обещанием, которое закрывалось само (`isPlain`).

- **Три понятия.** Знания о карточках (факты, оценки, события), обязательства (кто, кому, срок, статус) и расписания — то, что приходит само по времени.
- **Расписание — вид записи `schedule`** в `memory_records`, а не своя таблица: у записей уже есть шифрование (привязано к таблице и id строки), версии, «Запомнено · Отменить», источники и карточки. Вид расписания (`schedule_kind`): `reminder` — напоминание, `date` — день, который приходит снова (день рождения, оплата 20-го), `rhythm` — «раз в N дней с человеком».
- **«Напомни позвонить Ольге» — только расписание**, без обещания (решение владельца). Напоминание об обещании («напомни в пятницу про договор для Ольги» при обещании Ольге) — расписание со ссылкой `for_record_id`: закрыли обещание — напоминание больше не приходит.
- **Когда в следующий раз.** У напоминания — хранимое `next_at` (оно срабатывает: воркер берёт `next_at <= now`) и `fired_at` (пришло, не отмечено). У даты и ритма — считается при чтении одной функцией из повтора или последнего контакта: хранимое поле пришлось бы пересчитывать на каждом контакте.
- **Ритмы — тоже расписания** (решение владельца). Правилом остаётся только «ждём N дней» — это порог, а не расписание.
- **Запись моделью не меняется:** модель по-прежнему отдаёт «обещание + напомнить» и «правило дата/ритм», в расписание их переводит код при разборе — промпт и цифры S13/S15 те же.
- **У напоминания об обещании нет своего текста** (`sealed` пустой): говорится текст обещания.
- **Экран — «Расписание» (P30, выбран 2026-11-16).** Раздел «Напоминания» в «Памяти» стал «Расписанием»: напоминания, даты и ритмы одним списком по времени, вид — значком; сверху «Отправлено, не отмечено» и «Просрочено». У даты «Уже сделано» и «Удалить», у ритма «Уже было», «Убрать до следующей встречи» и «Удалить». В «Правилах» остались только правила. Данные — те же, что у календаря (`/api/memory/due`, поля `dates` и `rhythms`).
- **Перенос данных — SQL:** правила-даты и ритмы и свои напоминания меняют вид на месте — id строк, шифр и отметки «убрано» по ним остаются; у обещания с напоминанием напоминание уходит в новую строку со ссылкой на него.

### D46. Защита данных: как встроить PII Guard — РЕШЕНО (2026-11-16)

План — [PII-GUARD-PLAN.md](PII-GUARD-PLAN.md), §2 и §6.

- **А. Шлюз как источник `openai-compatible`.** Ноль кода в Metobe, но всё идёт как chat completions: теряются Responses API, кэш Anthropic, `providerOptions.gateway`, Yandex; эндпоинт шлюза с копией ключа на каждый источник; «что ушло» — только из echo.
- **Б. Middleware в `getLanguageModel`, шлюз как служба маскирования (рекомендую).** Любой источник, одна точка на все 12 вызовов, Metobe сам хранит запись «что ушло». В форке нужен метод «маскировать куски» с русским слоем и восстановление в потоке.
- **Выбран Б.** Шлюз недоступен — запрос во внешнюю модель не уходит. «Что увидела модель» видит каждый у своих ответов. Картинки и файлы уходят как есть, с пометкой. Память маскируется как чат. В поле ввода — кликабельный предпросмотр того, что получит модель. Шлюз — отдельный сервис и образ `ghcr.io/artemavrin/pii-guard` под профилем `pii`.
- **Вид — P31 (выбран 2026-11-17).** Вместо панели под ответом — значок-щит с числом скрытого у каждого сообщения, шага с тулом и ответа; нажатие меняет текст на месте на версию модели (сообщение — как ушло, шаг — что ушло в тул и вернулось, ответ — как модель его написала). В поле ввода версия модели раскрывается над текстом. Раздел настроек — как в прототипе.
- **Уточнения владельца (2026-11-17).** Метки — в цвете своего типа везде, а не серые. Память, которую Metobe ставит перед сообщением, показывается отдельно, всплывающим окном из строки действий; под сообщениями ничто не меняет высоту (лента прижата к низу). «Запомнено» — в строке действий ответа справа. Образ шлюза — публичный пакет из приватного форка `artemavrin/pii-guard`, модель ru-s34.

### D47. Песочница и работа с файлами — РЕШЕНО (2026-11-20) + SPIKE (S11) + PROTOTYPE

Решение пользователя 2026-11-20: заказчик просит работу с файлами, поэтому песочница переезжает из v3 в v2. Образец — песочница ассистента PlusPortal v2 (`docs/services/assistant.md`, «Песочница») и проект `docs/proposals/infra-sandboxes.md`; из него не берём отдельный сервис infra с квотами по сервисам, своей базой и правами — у нас один потребитель.

- **Docker.** Сервис `sandbox` в compose (профиль `sandbox`, по умолчанию выключен, D34) — второй после обновлятеля (D35), кто видит сокет Docker. Это наш код без секретов базы, S3 и ключей моделей, без входящих снаружи; принимает только приложение и воркер по внутреннему токену. Создаёт только контейнеры профилей из своего конфига, со своей меткой и id своего процесса; образ, сеть и ресурсы запрос не задаёт, он называет профиль.
- **Изоляция — gVisor** (`runsc` как runtime Docker), как в D3; `install.sh` проверяет его в `docker info` и предлагает поставить. Хост без gVisor (S11, 2026-11-20): `install.sh` песочницу не включает (D34); для разработки — `SANDBOX_RUNTIME=runc` явно, с предупреждением на экране «Песочница»; gVisor на Mac — через Colima. Под gVisor нехватка памяти роняет всю песочницу, поэтому у каждого `exec` свой `ulimit -v` ниже потолка контейнера, а смерть контейнера модель получает словами.
- **Контейнер** — как в D3: сети нет, корень только для чтения, все capabilities сняты, не root, лимиты памяти без swap, CPU, процессов, запись только в tmpfs с потолком. Файлы внутрь и наружу — tar через `exec`, с проверкой размера до чтения: archive API Docker с корнем только для чтения не работает (S11). Клиент Docker — свой, на `node:http` по сокету: `dockerode` тянет нативные сборки (D34).
- **Песочница на чат, живёт 5 минут после ответа (поправка D3; уточнение пользователя 2026-11-20).** Контейнер берётся при первом вызове тула кода и привязан к чату. После ответа он не снимается, а ждёт следующего сообщения 5 минут (срок — настройка админа): следующий ответ попадает в ту же песочницу с теми же файлами, без нового старта и повторного копирования вложений. Срок отсчитывается от конца последнего ответа; упало приложение — контейнер снимается по тому же сроку, его продлевает только приложение. Лимиты: всего и на человека (в памяти сервиса, см. «Как сделано»). Считаются только **занятые** песочницы, то есть те, где сейчас идёт ответ. Ждущие песочницы снимаются первыми (давно ждущие — раньше), когда места нет, или когда тот же человек начинает код в другом чате. Две очереди: чат (человек ждёт) обгоняет запуски задач; задача, прождавшая дольше порога, идёт как чат. Задача берёт песочницу на один запуск, без ожидания.
- **Когда песочница не переживает ответ.** Снимается сразу при правке или повторе сообщения (в ней могли остаться файлы отброшенной ветки), при удалении чата и при смене образа. Первый вызов тула в ответе говорит модели, новая ли песочница или прежняя с файлами прошлого ответа, и перечисляет файлы. Полагаться на неё модель не должна: созданное в прошлых ответах возвращает `use_file`. Вложения чата лежат в `/workspace/in` только для чтения; новые вложения добавляются туда же.
- **Отдача — явным `share_file`.** Файл сразу уходит в S3 и в `files` (`origin = 'generated'`), в ленте — карточка, картинка — самой картинкой. Промпт запрещает ссылки на пути песочницы: у человека они не открываются. Автосбор папки `out` отвергнут: в ленту попадали бы промежуточные файлы.
- **Тулы:** `run_code` (Python, срок внутри контейнера; ошибка кода — данные для модели, нехватка времени, памяти и места — отдельными словами; вывод обрезается с начала и конца), `share_file`, `use_file`; `pack_files` (zip из файлов чата) собирает приложение без песочницы. Посчитанное кодом таблица и график берут JSON-файлом (`data_file`), а не числами в аргументах. Песочницы нет, она выключена или занята — тулов нет, и модель об этом знает.
- **Готовые тулы провайдеров** (code execution Anthropic, code interpreter OpenAI) — не делаем: данные уходят провайдеру, есть не у всех моделей. Необязательный режим «без своей песочницы» — только по сигналу.
- **Защита данных.** Вывод `run_code` и прочитанное из файлов идут модели через PII Guard (D46), как любой результат тула. В саму песочницу файлы идут как есть: она локальная. Проверить, что middleware маскирует результаты тулов, а не только текст сообщений.
- **Как сделано (2026-11-20).** Посчитанное кодом таблица и график берут через тул `load_data` (JSON-файл песочницы становится источником, `from.ref`), а не полем `data_file`: так работает уже готовый путь виджетов. Пределы — в `.env` сервиса (на экране «Песочница» только чтение), очередь и учёт — в памяти сервиса, а не в Redis: распределяет один процесс. Тип файла решает сервер: с песочницей принимается любой (`other`, модель знает, что он в `/workspace/in`). Скан PDF `read_attachment` читает в песочнице ответа (poppler + tesseract). `pack_files` не делали: архив модель собирает кодом (`zipfile`) из файлов песочницы и `use_file`, отдаёт `share_file`.
- **Этапы и прототипы** — PLAN, «Песочница и файлы».

### D48. Организации, места и лимиты — ПО УМОЛЧАНИЮ + НУЖНО РЕШЕНИЕ + PROTOTYPE (2026-11-24)

План — [ORGS-PLAN.md](ORGS-PLAN.md). Задача владельца продукта:

- в организации есть владелец: он решает, сколько мест будет в месяце и кто их займёт, и приглашает людей — как в Claude Team;
- суперюзер видит все организации и всех людей и знает, сколько организация должна за следующий месяц;
- лимиты — на 5 часов и на неделю, цена места должна покрывать модели.

- **А. Организации внутри одной установки (рекомендую).**
  - Плюсы: как в Claude — суперюзер видит всех, сервер общий.
  - Риск: изоляция. Всё общее читается только с организацией, на каждый маршрут — тесты на две организации.
- **Б. Своя установка на организацию и консоль над ними.**
  - Плюсы: изоляция есть сразу.
  - Минусы: сервер, бэкапы и обновления на каждую организацию; консоль — второй продукт.
- **По умолчанию — А.**
  - Организация есть всегда. Self-hosted — одна организация; с 2026-11-28 у него своя лицензия, места и лимиты админа (D49).
  - Роль в установке и роль в организации раздельны. В организации три роли: владелец, админ, участник.
- **Места.**
  - Место занимает каждый активный человек и каждое приглашение без ответа. Отключённый человек места не занимает.
  - Добавленные места появляются сразу, доплата за остаток месяца идёт в следующий счёт. Убрать места можно только со следующего месяца.
  - Счёт — предоплата за календарный месяц.
- **Лимиты.**
  - Считаются в рублях стоимости моделей по курсу платформы.
  - Окно в 5 часов открывается первым запросом. Неделя начинается в понедельник.
  - Ответ останавливается на шаге, где кончился лимит.
- **Деньги видит только платформа.** Людям и владельцам — проценты лимитов. Слова владельца 2026-11-24: «расходы пользователя убрать, чтоб он не видел суммы».
- **Решено владельцем 2026-11-24:**
  - три тарифа места — Обычный, Про и Макс; Про вдвое дороже Обычного, Макс — вчетверо;
  - тарифы, доступные модели, лимиты, валюта, НДС и прогноз — в настройках суперюзера;
  - не оплатила к сроку — организация отключается сразу; суперюзер отключает и включает организации и людей руками;
  - организации заводит суперюзер;
  - владелец занимает место.

### D49. Две схемы — облако и self-hosted; лицензия self-hosted и главный узел — РЕШЕНО (2026-11-28) + ПО УМОЛЧАНИЮ + НУЖНО РЕШЕНИЕ + SPIKE + PROTOTYPE

D48 писался под одну модель: организации живут в одной установке, а self-hosted — та же установка с одной организацией, без тарифов и без оплаты. 2026-11-28 владелец разделил продукт на две схемы. План — [ORGS-PLAN.md §14](ORGS-PLAN.md#14-self-hosted-лицензия-места-и-лимиты), архитектура — [ARCHITECTURE.md §21](ARCHITECTURE.md#21-self-hosted-лицензия-и-главный-узел-d49).

- **Решено владельцем 2026-11-28:**
  - **Облако** — наш сервер на домене metobe: много организаций, тарифы, лимиты и ключи моделей наши. Это D48 и ARCH §20.
  - **Self-hosted** — сервер клиента, одна организация. Ключи моделей клиента, их расход нас не касается, деньги в интерфейсе видны, как сейчас.
  - Лицензия на сервер бессрочная, оплачивается один раз. Плюс помесячная оплата за место по одной цене, тарифов нет.
  - Места как в Claude Team: занято — включённые люди и приглашения без ответа. Добавить человека можно в любой момент, оплатив ему место.
  - Лимиты: админ клиента создаёт сколько угодно лимитов со своими значениями и назначает их людям. Цены у лимитов нет.
  - Сервер сообщает узлу число людей, версию и ошибки. Позже, возможно, телеметрию сценариев.
  - Главный узел — раздел суперюзера в облаке, не отдельный сервис. Клиент self-hosted — организация в облаке без людей: места, цена и счета как у облачной. Лицензия его сервера считается из этой организации.
  - Льготного срока нет: не оплатили к сроку — сразу только чтение, как отключение в облаке.
  - Режима «без лицензии» нет: без активации сервер показывает только экран ввода кода. Пробный период, если будет, — лицензия от узла, привязанная к клиенту.
  - Код активации привязан к клиенту. Тот же код на второй машине — перенос.
  - Запас лицензии — только на обрыв связи. Срок истёк — сервер обращается к узлу раз в час.
  - Сервер без интернета: проверку файлом предусмотреть, делать не сейчас.
- **По умолчанию** (предложения оркестратора, ORGS-PLAN §14, ARCH §21):
  - **Активация.** Суперюзер заводит клиента и получает код. Админ вводит его в `install.sh` или на экране кода. Сервер создаёт ключ установки Ed25519, узел привязывает его к организации клиента и отвечает лицензией.
  - **Лицензия** — запись, подписанная ключом узла: id установки, схема, признак оплаченной лицензии сервера, места, «оплачено до», время узла, срок действия. Публичный ключ узла вшит в образ, ключ подписи — только в секретах облака. Схему установки (облако или self-hosted) задаёт лицензия, а не переменная окружения.
  - **Запас на связь — 7 дней.** Лицензия выдаётся на 7 дней вперёд, но не дальше «оплачено до». Связи нет больше суток — плашка у админа.
  - **Связь раз в сутки** — от сервера к узлу, через прокси установки. Подписанный отчёт: места, люди, версия, ошибки; в ответ — свежая лицензия. Список полей публичный.
  - **Потолок мест держит сервер** — та же транзакция с `FOR UPDATE org_seats`, что в облаке, число мест из лицензии.
  - **Покупка места** — запрос на узел с id: доплата по дням в счёт клиента, сразу новая лицензия. Повтор после обрыва доплату не удваивает. Без связи место не купить.
  - **Копии** видны по цепочке ответов узла, суперюзер получает отметку, блокировки нет.
  - **Ошибки** — без текстов, имён и почт, человек под обезличенным номером. Админ выключает ошибки и телеметрию, но не связь для лицензии.
  - **Лимиты self-hosted** — тот же механизм окон, что в облаке, значения задаёт админ.
  - **Нынешние установки** получают код до выхода версии с лицензией. Обновлятель не ставит её, пока код не введён.
- **Защита, честно.** Код публичный, у клиента root: пересобрать образ без проверки можно всегда. От обычных попыток защищают подписанная лицензия, активация по клиенту, ежедневная связь и видимость копий. От пересборки — только договор и лицензия кода. Таблица угроз — ARCH §21.11.
- **Как у других** (ORGS-PLAN §2): связь раз в сутки — GitLab, Grafana Enterprise, n8n; привязка к id установки — GitLab, n8n, Plane; закрытый контур — отдельный платный режим с файлом (GitLab, n8n, Metabase).
- **Нужно решение** (ORGS-PLAN §13):
  - нужен ли пробный период и на сколько;
  - 7 дней запаса на обрыв связи;
  - выключение ошибок и телеметрии админом клиента;
  - лицензия кода: файла `LICENSE` нет, предложение — Elastic License 2.0. Решает владелец с юристом.
