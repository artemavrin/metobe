### D0. Ставки продукта — РЕШЕНО

Open WebUI и LibreChat уже умеют мультиисточникность, MCP, роли и артефакты (по памяти, детально не сверял). Своё имеет смысл, только если выигрываем в чём-то конкретном. Предлагаемые ставки (ARCHITECTURE §0):

1. установка и первый ответ за 2 минуты;
2. генеративный UI по живым данным;
3. сети с ограничениями: Яндекс, прокси HTTP и SOCKS5 — всё напрямую, через прокси только отмеченные объекты и домены;
4. MCP и скиллы как основа;
5. фоновые агенты — чат, который работает без тебя (ARCHITECTURE §16).

«Ставка» — это то, ради чего продукт выбирают вместо готового. От ставок зависит порядок работ: то, что их поддерживает, делается первым и полируется до вау, а остальное режется первым, когда не хватает времени.

**Решение:** пятая ставка подтверждена явно, первые четыре не оспаривались и считаются принятыми. Следствие: агенты — первый пункт v2, под них заранее затачиваются MCP (M4), поиск (D21) и уведомления (D24).

### D1. Мастер установки или compose — РЕШЕНО

Отказываемся от мастера в браузере. Инфраструктуру описывает compose, `install.sh` генерирует `.env`, entrypoint применяет миграции, а в браузере остаётся один экран — создание аккаунта по claim-ссылке.

- Мастер не может «выбрать» БД, в которой сам же хранит свой прогресс: проблема курицы и яйца.
- Миграции через HTTP — это DDL без авторизации, а две вкладки дадут две гонки.
- Первый пришедший на `/setup` становился суперюзером. Claim-токен из лога это закрывает.
- Исходное требование «при запуске определяется БД» не теряется: `install.sh` спрашивает, встроенная база или своя.

Источники, модели и MCP — это данные, а не инфраструктура. Они подключаются в интерфейсе, без мастера установки. Первый вход ведёт на настройки источников, чат открывается, когда есть хотя бы одна включённая модель (P1, решение пользователя 2026-09-23).

### D2. Один инстанс `app` — ПО УМОЛЧАНИЮ

Реестр отмены, MCP-клиенты и активные стримы живут в памяти процесса. Первая версия документа одновременно готовилась к нескольким инстансам (Redis pub/sub для отмены, S3 «ради масштабирования») и держала stdio MCP в памяти — это противоречие.

Redis остаётся: без него не работают BullMQ, rate limit и `config:changed` между процессами (resume стримов ему больше не нужен — D5). S3 тоже остаётся, но уже по другой причине — внешнее хранилище и бэкапы.

С фоновыми агентами (v2) появляется второй процесс, `worker`, из того же образа. Web-инстанс по-прежнему один. Отмена запуска агента идёт сигналом через Redis в `worker`.

**Отменить**, если нужен HA или несколько реплик. Тогда отмена переходит на Redis pub/sub, а stdio MCP запрещается.

### D3. Песочница — ПО УМОЛЧАНИЮ (v3) + SPIKE

- Не в v1: это самый опасный и дорогой компонент, а ни одна ставка из D0 на нём не держится.
- **Никогда через `docker.sock`:** по документации Docker доступ к демону эквивалентен root на хосте, а исполнять будем код, написанный моделью.
- Кандидаты:
  - microsandbox (microVM на libkrun, заявлены Linux и macOS);
  - gVisor (только Linux; на Docker Desktop под macOS ставится вручную).
- Подключается профилем compose, по умолчанию выключен. Пока песочницы нет, `run_code` недоступен, и модель об этом знает.
- **Что взять из песочницы PlusPortal assistant** (разбор кода 2026-10-02 — за образец, а не за истину):
  - контейнер на один ответ модели: создаётся при первом вызове тула кода, удаляется в конце ответа; файлы прошлых ответов возвращаются явным тулом, а не живым контейнером;
  - сети нет по умолчанию, корень только для чтения, все capabilities сняты, не root, лимиты памяти, CPU, процессов и времени; запись — только в tmpfs с потолком размера;
  - файлы внутрь и наружу — через stdin/stdout `exec`, с проверкой размера до чтения;
  - ошибки тулов написаны для модели: «кончилась память» отдельно от «вышло время» (по счётчику OOM в cgroup), явная пометка об обрезке вывода;
  - описание окружения в системном промпте, и тест сверяет его с закреплёнными версиями в образе;
  - лимиты проверяются настоящими тестами, которые их нарушают.
- **Чего не повторять:**
  - сервис в группе `docker` (то же, что root на хосте) и runc без gVisor — у нас только gVisor или microVM в отдельном сервисе;
  - место в очереди занято на весь ответ, включая время, пока модель думает, а лимиты живут в памяти одного процесса — у нас лимиты в Redis и место только на время выполнения кода;
  - чистка при старте удаляет все контейнеры с меткой, в том числе чужие — у нас метка с id процесса-владельца;
  - обрезка вывода оставляет начало и теряет traceback в конце — у нас начало и конец;
  - описание окружения в промпте разошлось с образом (пакеты, пути) — у нас тест сверяет их.

### D4. S3-хранилище — ПО УМОЛЧАНИЮ (S6 пройден)

MinIO отпадает: `minio/minio` архивирован, в README написано «NO LONGER MAINTAINED». По вторичным источникам, community-образы перестали публиковать осенью 2025-го.

| Вариант | За | Против |
| --- | --- | --- |
| **SeaweedFS** (по умолчанию) | зрелый, Apache 2.0, S3-режим в одном контейнере | конфиг ключей через JSON — проверить |
| Garage | лёгкий | layout и ключи создаются командами после старта — нужно скриптовать в `install.sh` |
| RustFS | ближе всех к MinIO | в обзорах — «not production-ready» |
| Внешний S3 | ноль контейнеров | не «из коробки» |

**Spike S6 — пройден 2026-10-02** (`spikes/S6-seaweedfs`, 13 проверок из 13): `chrislusf/seaweedfs:4.48`, `weed mini` — один контейнер, бакет и ключи из переменных окружения (JSON не нужен), healthcheck `/healthz`, presigned PUT и POST из браузера с CORS только для своего origin, потолок размера, отказ неверному ключу и анониму, данные переживают перезапуск. Admin UI выключаем (`-admin.ui=false`: по умолчанию он без пароля). Цена: образ ~500 МБ, в покое ~180 МБ памяти. Клиент SDK — с `requestChecksumCalculation: "WHEN_REQUIRED"`, иначе presigned PUT из браузера падает с `BadDigest`. Как браузер достаёт до S3 (через приложение или presigned на отдельный адрес) — решается в D33.

### D5. Resume стримов — РЕШЕНО

Сделано **без `resumable-stream` и Redis**: приложение — один долгоживущий процесс (D2), поэтому ответ пишет в памяти процесса записывающий реестр (`lib/resume-stream.ts`, так же устроены реестр остановки D6 и сама генерация, которая доводится до конца при ушедшем клиенте). Сервер делит поток ответа надвое: клиенту и в запись. `GET /api/chat/[id]/stream` проигрывает записанное с начала и подключает к живому потоку; `204`, когда ответ не пишется. Запись снимается, когда ответ сохранён, — дальше показывается сохранённая копия.

- Клиент подключается только когда чат открыт с собственным сообщением пользователя в конце (ответ ещё пишется) — один раз, при открытии.
- Не охвачено: продолжение ответа после подтверждений (последнее сообщение — ответ), второй экземпляр приложения.
- Если понадобится несколько экземпляров, меняется только `lib/resume-stream.ts`: хранить чанки в Redis (`resumable-stream`).

### D6. Отмена генерации — РЕШЕНО

`Map<chatId, AbortController>` в памяти (следствие D2) и `POST /api/chat/[id]/stop`. Клиентский `stop()` при resumable-схеме только отключает клиента, поэтому отдельный эндпоинт обязателен.

### D7. Edit/regenerate при линейной истории — PROTOTYPE

Редактирование физически удаляет все сообщения ниже. Варианты UX:

- **без предупреждения** — быстро, но теряются ответы;
- **подтверждение** — безопасно, но раздражает на каждом редактировании;
- **undo-тост на ~10 с** — лучше всего по ощущению, но требует soft-delete (`messages.deleted_at`) и отложенной очистки.

Прототип P6 решает, стоит ли undo лишней колонки.

### D8. Режимы Fast/Normal/Deep — PROTOTYPE

В PlusPortal обычный пользователь выбирал режим, а эксперт — модель. Режимы проще для людей, но это ещё одна сущность (таблица «режим → модель + параметры»). В v1 — выбор модели плюс «модель по умолчанию». Прототип P3 покажет, нужны ли режимы.

### D9. Composer: что на виду — PROTOTYPE

Оси независимы: модель, thinking, MCP-серверы, скиллы, вложения. Все сразу на виду не помещаются. Прототип P2 решает, что показывать постоянно, что убрать за меню и что вызывать через `/` и `@`.

### D10. Виджет → артефакт — PROTOTYPE

Когда виджет из ленты становится артефактом в панели: по кнопке «развернуть», автоматически при размере больше N или только через `createDocument`? Как выглядит переход (shared-element анимация)? Прототип P5.

### D11. Большие данные тулов — РЕШЕНО + SPIKE

Полный результат хранится в `parts`, модели через `toModelOutput` уходит сжатая версия с `ref`, рендер-тул ссылается на `toolCallId`, данные подставляет сервер (ARCHITECTURE §9.2).

**Spike S5** проверяет, работает ли `toModelOutput` между шагами одного `streamText` и можно ли обернуть им MCP-тулы.

### D12. Гранты доступа — ПО УМОЛЧАНИЮ (v2)

В v1 только роли `superuser`/`admin`/`user`. Точечные гранты (`default_access` + `*_access`) на модели и пункты каталога появятся в v2, когда будет кому их выдавать. Схема закладывает поле `default_access` в `models` и `catalog_items`, чтобы потом не мигрировать данные.

### D13. Источники в v1 — ПО УМОЛЧАНИЮ

OpenAI, Anthropic, **Vercel AI Gateway**, OpenAI-compatible (через него же OpenRouter, vLLM, LM Studio, Ollama `/v1`) и Yandex AI Studio. Google — по запросу, это новый `kind` в фабрике.

AI Gateway добавлен по твоему запросу: один ключ даёт модели разных провайдеров, а discovery сразу возвращает цены (ARCHITECTURE §7.5). Предполагаю, что имелся в виду именно Vercel AI Gateway. Свой шлюз (LiteLLM и т.п.) подключается через `openai-compatible` и отдельного `kind` не требует.

### D14. Исходящий прокси — РЕШЕНО (S4 пройден)

Прокси — отдельная сущность в админке (ARCHITECTURE §18): несколько прокси `http` / `https` / `socks5` / `socks5h`, у каждого проверка с внешним IP и страной.

**По умолчанию всё идёт напрямую.** У каждого прокси админ отмечает, что через него ходит: конкретные источники, пункты каталога, бэкенды поиска — галочками, а трафик без объекта (чтение страниц, свои подключения пользователей, Web Push) — доменами. У объекта то же самое видно полем «Прокси: авто / напрямую / через X».

Маршрут запроса: явный выбор у объекта → прокси, в доменах которого есть адрес назначения (точный домен побеждает) → напрямую. Внутренние сервисы compose через прокси не ходят никогда. `HTTPS_PROXY` / `ALL_PROXY` из установки при первом старте превращаются в запись прокси, но ничего к нему не привязывают.

При добавлении источника, недоступного напрямую, система сама проверяет его через каждый прокси и предлагает рабочий.

Отвергнутые варианты:

- **Поле `proxyUrl` у каждого источника** (первая версия): не покрывает MCP, коннекторы, чтение страниц, push и почту; один и тот же прокси вводится много раз.
- **Умолчания по категориям** («все модели через прокси»): загоняют в прокси и то, чему он не нужен, — например Яндекс.
- **Только глобальный `HTTPS_PROXY`:** Яндексу прокси не нужен, OpenAI без него не работает — одним маршрутом этого не описать.

SearXNG ходит в поисковики из своего контейнера, его прокси задаётся при установке и в админке только отображается.

**Итоги spike S4** (2026-09-23, `spikes/S4-proxy`):

- `fetch` есть у всех четырёх источников, включая `anthropic`. Три маршрута — HTTP-прокси, SOCKS5 и напрямую — работают одновременно в одном процессе, стрим и тулы проходят.
- Маршрут — это undici-dispatcher, а источник получает `fetch` из пакета `undici` с этим dispatcher. HTTP — `ProxyAgent`, «напрямую» — явный `Agent`, чтобы не подхватить `HTTPS_PROXY` из окружения.
- SOCKS5 и закреплённый IP — свои коннекторы на `socks` и `undici.buildConnector`, без `fetch-socks`: он тянет второй мажор undici. Закрепление работает и через HTTP CONNECT, и через SOCKS5: туннель открывается на проверенный IP, SNI и `Host` — по имени.
- SMTP через SOCKS5 и HTTP CONNECT работает штатно в nodemailer. Закрепление IP для SMTP пользователей не проверено — это M4, коннектор `smtp`.

### D15. SMTP — РЕШЕНО

Настраивается в UI и хранится зашифрованным. Для работы не обязателен: приглашение — это копируемая ссылка, письмо лишь дублирует её.

**Уточнено 2026-10-05.** Письма уходят от отдельного ящика сервиса (например, `noreply@компания`), а не от ящика кого-то из сотрудников: иначе вход всех зависит от чужого личного пароля. Форма на тех же деталях, что личная почта (D27): пресеты Яндекс, Gmail, Mail.ru и «Другая», пароль приложения с подсказкой, те же тексты ошибок. Отличия: только SMTP; «Другая» может быть без логина — релей во внутренней сети; адрес задаёт админ, поэтому внутренние адреса разрешены, как у каталога и источников (ARCH §18.4), а через прокси почта идёт по его доменам. Сохраняется только то, что сервер принял; «Отправить себе» проверяет путь письма целиком. Почту можно отключить — тогда вход только по ссылке от админа, и `SMTP_URL` установки её не возвращает.

Отвергнуто: отправлять от ящика админа из «Моих подключений» — это его личный пароль, и с уходом человека вход сломается у всех.

### D16. Язык интерфейса — РЕШЕНО: только русский

Интерфейс пока только на русском, строки пишутся прямо в компонентах, словарей и `next-intl` нет. Если понадобится английский, строки придётся выносить — эту цену приняли осознанно.

Даты, числа и валюты форматируем через `Intl` с локалью `ru-RU`, а не вручную. Это ничего не стоит и не придётся переделывать.

### D17. Способы входа — РЕШЕНО: без паролей

**Паролей нет.** Вход — по магической ссылке. Она же подтверждает почту, а пароли нечего утекать, забывать и сбрасывать.

- **Письмо** содержит ссылку и шестизначный код. Код нужен, если письмо открыли на телефоне, а входят с ноутбука. Ссылка одноразовая, живёт 10 минут, запросы ограничены по email и IP.
- **Первый вход без почты.** Claim-ссылка из лога сама создаёт сессию суперюзера, ссылка-приглашение — сессию приглашённого. Это сохраняет ставку «первый ответ за 2 минуты»: SMTP для старта не нужен (D15).
- **Без SMTP** вход тоже возможен: админ выдаёт одноразовую ссылку для входа в интерфейсе пользователей или командой `cli login-link <email>`. Страница входа в этом случае честно говорит «вход по почте не настроен — попросите ссылку у администратора».
- **Сессия** — 30 дней, продлевается при использовании: входить приходится редко.
- `install.sh` может сразу спросить SMTP — необязательный вопрос. Настройки переносятся в админку при первом старте.
- **v2:** passkey — после первого входа предлагаем добавить ключ, дальше вход по отпечатку или Face ID без почты. OIDC — Яндекс ID, Google, Keycloak.

Плагины Better Auth для magic link, email OTP и passkey — имена и API **проверить** по документации пакета при реализации.

Отвергнуто:

- **Email + пароль** — первая версия решения: лишний экран, сброс пароля, хранение хэшей.
- **Только магическая ссылка без кода** — ломается, когда почта на телефоне, а работа за компьютером.

### D18. MCP stdio — РЕШЕНО (v3)

stdio — это по определению запуск команды на сервере. Правила:

- настраивает только суперюзер, с явным предупреждением;
- без личных кредов пользователей (иначе нужен процесс на каждого);
- работает только при одном инстансе (D2); stdio-клиенты живут только в процессе `worker`, а `web` вызывает их тулы через очередь — два процесса не запускают один и тот же сервер.

### D19. Цены и валюты — РЕШЕНО

Цена хранится за 1M токенов вместе с валютой. `model_runs` фиксирует стоимость в валюте модели. Дашборд суммирует по каждой валюте отдельно и не конвертирует.

**Тиры цен — ПО УМОЛЧАНИЮ: в v1 только базовая ставка.** У части моделей вход и выход дороже после 200K токенов контекста — Gateway отдаёт это как `input_tiers` / `output_tiers` (S4). В v1 храним базовую ставку. У Gateway стоимость запуска потом уточняется фактической (`getGenerationInfo`), так что тиры влияют только на прямые ключи с длинным контекстом. Тиры — v2.

### D20. UI-библиотеки — РЕШЕНО (приоритет ReUI, S2 пройден) + PROTOTYPE

**Приоритет — ReUI: его вид нравится больше.** Для любого компонента, включая графики, сначала ищем его в ReUI, потом берём shadcn в том же стиле (ARCHITECTURE §9.5).

**Итоги spike S2** (2026-09-23, проверено на скелете: Next 16.3.6, React 19.2.8, Tailwind v4, shadcn CLI 4.21):

- **Монорепо работает.** Структура взята из `shadcn init --monorepo`: `@source` в `globals.css` пакета указывает на `apps/**`, приложение переиспользует `postcss.config` пакета и подключает его через `transpilePackages`.
- **`shadcn add` запускаем из `packages/ui`.** Тогда и примитивы, и составные компоненты ReUI (`components/reui/*`) ложатся в дизайн-систему. Из `apps/web` составные компоненты ушли бы в приложение.
- **Перезаписей нет.** Голые зависимости ReUI (`button`, `input`…) создают файлы, а совпадающие пропускаются как идентичные. Риск из анализа реестров на практике не сработал.
- **База — `base`** (Base UI). **Пресет — `b1YmqvjO4`** (выбран 2026-09-23): стиль `nova`, базовый цвет `neutral`, тема и цвета графиков `blue`, шрифт Geist, иконки lucide. Смена пресета — `pnpm dlx shadcn@latest apply --preset <код> --yes` из `apps/web` (см. IMPLEMENTATION §6).
- **Иконки — `lucide-react`**: их тянет ReUI.
- **Графики — EvilCharts (ECharts), с 2026-09-28.** Сначала брали ReUI (`@reui/c-chart-*` на recharts), потом EvilCharts пробовали и отказались — «по ощущению вернулись к обычным». Теперь вернулись к нему сознательно: по виду он заметно лучше, а ECharts покрывает все виды (площадь, линия, столбцы, составной, радар, круговая, радиальная). Ставится `shadcn add @evilcharts/echarts-*` из `packages/ui` в `components/evilcharts/` (реестр в `components.json`), исходники с правками для подсказки описаны в `README.md` рядом. Цена: ~200 КБ gzip сверх recharts, поэтому график грузится отложенно, только когда он есть в ответе. Палитра — `--chart-1…8`, проверенная валидатором по dataviz (фиксированный порядок оттенков, свои шаги для тёмной темы); ряды бывают до 8, радар до 3. Одна ось: числа разного масштаба — в разных графиках, а не на второй оси. Графики ReUI `c-chart-*` остались только в dev-витрине, `recharts` в чате не используется.
- **Data Grid** — ReUI на TanStack Table **v9** и TanStack Virtual. Таблица с поиском, фильтром, сортировкой и пагинацией отрендерилась.
- **Ограничения:**
  - код ReUI не собирается с `noUncheckedIndexedAccess`, поэтому флаг включён только в `@metobe/tsconfig/node.json` для серверных пакетов;
  - вендорные компоненты (`packages/ui/src/components/**`) исключены из oxlint и oxfmt: их обновляют через `shadcn add --diff`, а не правят руками;
  - блоки ReUI импортируют `recharts` без `"use client"`, поэтому виджеты с графиками — клиентские компоненты.

### D21. Веб-поиск — РЕШЕНО (S8)

Свои тулы `web_search` и `web_fetch`, бэкенды настраиваются в админке. По умолчанию — SearXNG в compose и локальный `web_fetch`. Yandex Search API, TinyFish и Tavily — запасные адаптеры: подключаются, только если S8 или эксплуатация покажут капчи или слабое качество (ARCHITECTURE §8.1).

- Встроенный поиск источников не годится: он работает только с моделями своего источника.
- Официальные пакеты поиска для AI SDK пока только под `ai@5`/`@6`.
- N2 Free Search снят с npm, но идея — SearXNG без ключей — берётся за основу.

**Итоги S8 (2026-09-28, `spikes/S8-searxng`):** по-русски выдача хорошая — наверху первоисточники. Под постоянной нагрузкой (вопрос в секунду) настройки по умолчанию умирают за две минуты: duckduckgo отвечает капчей после ~5 вопросов подряд, brave — «too many requests» после ~10, google cse — после ~100; SearXNG сам выключает движок на час–сутки. В темпе чата (три вопроса раз в 20 с) с google + yahoo + brave — 45 из 45 с результатами. `outgoing.proxies` с SOCKS5 и логином работает. Отсюда:

- **SearXNG:** JSON включён, движки google, yahoo, brave, duckduckgo, google cse, wikipedia; приостановка движка — минуты, а не сутки.
- **Наш слой:** кеш одинаковых вопросов на час и страниц на сутки, не больше двух одновременных запросов к SearXNG.
- **`web_fetch`:** свой fetch через защищённый от SSRF транспорт (`fetchFor(…, { pinned: true })`: адрес проверяется на каждом соединении, в том числе после редиректа) и Defuddle — основной текст страницы в Markdown.
- **Когда не хватит** (агенты по расписанию, большая команда): прокси с разными IP в `outgoing.proxies` или платный бэкенд из запасных.

### D22. Права фоновых агентов — РЕШЕНО: как у Claude

Агенту по умолчанию доступны все подключения владельца, он действует его кредами и ничего не спрашивает во время запуска. Лишние подключения убираются в карточке агента.

Страховка без подтверждений: лимиты (шаги, стоимость, время, минимальный интервал), журнал каждого запуска, выключатель «пауза всех агентов», внешний ввод оборачивается как недоверенный.

**Политика админа сильнее прав агента.** Если админ поставил тулу в каталоге `approval_policy = 'ask'`, агент в фоне тоже спрашивает: запуск паркуется, во входящих появляется Review. `deny` скрывает тул. «Как у Claude» — умолчание для тулов без политики, а не обход решений админа.

Осознанный риск — prompt injection из прочитанных данных. Путь отступления: флаг агента «спрашивать перед записью». Модель данных и approval-флоу `ai@7` это уже позволяют.

### D23. Расписание агентов — ПО УМОЛЧАНИЮ

- **Источник правды — Postgres:** `agents.cron`, `timezone`, `next_run_at`.
- **Исполнение — BullMQ:** один job scheduler раз в минуту атомарно захватывает созревших агентов и ставит их в очередь.
- **Пропущенные запуски:** после простоя — ровно один догоняющий, без лавины.
- **Где выполняется:** в отдельном `worker`.
- **Смена исполнителя:** запуск спрятан за `executeRun(runId)`, при необходимости переезжает на Workflow DevKit (ARCHITECTURE §16).

Отвергнутые варианты:

- **Отдельный BullMQ-scheduler на каждого агента:** расписания жили бы только в Redis, пропадали бы вместе с ним и не попадали бы в бэкапы.
- **eve:** preview и отдельный рантайм.
- **Workflow DevKit сейчас:** beta-линейка и нет cron.

### D24. Интерфейс агентов и уведомления — ПО УМОЛЧАНИЮ + PROTOTYPE + SPIKE

**Поверхности** (ARCHITECTURE §16.4):

- сайдбар со счётчиком входящих и секцией агентов;
- входящие `/inbox` — Notify / Question / Alert / Review;
- список агентов `/agents`;
- страница агента с лентой запусков;
- запуск открывается как обычный чат с плашкой.

Точный вид решают прототипы P11–P14.

**Каналы уведомлений** (§16.5): входящие → тост в открытой вкладке по SSE через Redis → Web Push браузера → email → Telegram (v3).

Правило по умолчанию — `if_new`: «ничего нового» не уведомляет. Плюс тихие часы и дайджест.

Отвергнутые варианты:

- **Только email:** медленно и тонет в почте.
- **Только опрос сервера:** счётчик отстаёт, нет тоста в момент результата.
- **Telegram как канал уведомлений в v2.** Коннектор `telegram_bot` в v2 есть, но это тул агента: «отправь в чат X». Канал уведомлений — другое: кнопки «открыть» и «ответить», ответы из Telegram обратно в запуск, привязка аккаунта. Это отдельная работа, она в v3.

**Spike S9:** Web Push в self-hosted Next 16 — service worker, VAPID, HTTPS, поведение на iPhone.

### D25. Кто добавляет MCP и скиллы — ПО УМОЛЧАНИЮ

**Два уровня** (ARCHITECTURE §17.1):

- админ ведёт каталог организации;
- пользователь подключается к пунктам каталога своими кредами (`per_user`), может завести своё подключение (почта, `http_api`), а в v2 — свой MCP-сервер и свои скиллы.

Каталог общий для MCP и коннекторов — таблица `catalog_items`.

**Ограничения:**

- stdio — только суперюзер;
- свои подключения любого типа по умолчанию `public_only` (политика `personalConnections`): приватные адреса запрещены, чтобы не было SSRF во внутреннюю сеть;
- внутренние системы (1С и т.п.) добавляет админ.

**Почему не «только админ».** Агенты действуют инструментами владельца (D22), и ставка №5 без личных подключений не работает.

**Почему не «пользователь добавляет что угодно».** stdio — это запуск команд на сервере, а произвольный URL — дыра во внутреннюю сеть.

Что меняется в плане: личные подключения по токену — в v1 (M4). OAuth для MCP переезжает из v3 в v2: без кнопки «Подключить» пользователи не подключат GitHub и похожие сервисы, а агентам это нужно.

**Уточнено 2026-10-02.** OAuth для MCP сделан в v1 (M4), раньше срока: многие нужные серверы только на OAuth, и MCP — основной режим работы. Способы авторизации сервера в коде: нет / Bearer / свой заголовок / basic (логин и пароль) / OAuth (PKCE, DCR, refresh через `authProvider` из `@ai-sdk/mcp`, вход в окне сервиса). Политики `personalConnections` и `personalApprovalDefaults` в коде пока нет: свои подключения вне каталога есть только у почты, и приватные адреса для неё запрещены всегда (как `public_only`). Политики придут вместе с экраном «Доступы» в настройках админа.

### D26. Хранение секретов — РЕШЕНО + SPIKE

- **Где:** все секреты в одной таблице `secrets` (ARCHITECTURE §17.2).
- **Как шифруется:** AES-256-GCM, случайный IV, AAD привязывает шифртекст к его строке.
- **Мастер-ключ:** в env; ротация через `SECRETS_KEY_PREVIOUS` + `metobe secrets:rotate`; canary не даёт стартовать с чужим ключом.
- **Куда не попадает:** API write-only; модель, логи и ошибки тулов секретов не видят.

Отвергнутые варианты:

- **Колонка `*_sealed` в каждой таблице:** ротация и аудит размазаны по всей схеме.
- **Ключ от пароля пользователя:** агенты не могут работать без залогиненного пользователя.
- **Vault/Infisical по умолчанию:** ломает установку в одну команду. Появится адаптером позже.

Честная граница: от владельца сервера self-hosted не защищает.

**Spike S10 (сделан в v1, см. D25):** OAuth MCP через `authProvider` из `@ai-sdk/mcp` с хранением в нашей БД — PKCE, refresh, переподключение. Подключение работает; обновление токена после истечения и «отзыв → `needs_reauth`» вживую ещё не проверены.

### D27. Коннекторы и запрос кред у пользователя — ПО УМОЛЧАНИЮ + PROTOTYPE

**Коннекторы.** Кроме MCP есть встроенные коннекторы с описанием полей, проверкой и своими тулами. Первый — `email` (SMTP): сервер, порт, шифрование, логин, пароль, пресеты популярных почт. Подключения всех видов лежат в одной таблице `connections`. Несекретные поля хранятся в `config`, секретные — в `secrets` (ARCHITECTURE §17.7).

**Типы.** Встроенный коннектор делается для протокола, а не для сервиса. v1 — `mcp`, `email` (SMTP), `http_api`. v2 — `database` (только чтение), IMAP, `telegram_bot`, `webhook_out`. Позже — CalDAV, S3/WebDAV. Сервисы подключаются через MCP из каталога.

**Как агент спрашивает данные.** Встроенный тул `request_connection` без `execute` рисует в ленте форму. Значения уходят из браузера прямо в API, минуя модель. В историю и в контекст модели попадает только сводка «подключено, smtp.yandex.ru:465». Фоновый агент вместо формы присылает во входящие «нужно подключение» с той же формой.

Отвергнутые варианты:

- **Попросить ввести пароль в чат:** пароль навсегда остаётся в истории и в контексте модели.
- **Отправить в настройки:** рвётся поток, пользователь теряет, где был.

Вид карточки-формы решает прототип P8.

**Уточнено 2026-09-28.** Карточка — «Плашка» из прототипа P8: строка в ответе «Нужен вход в X» с причиной от модели, поля — в диалоге, OAuth — в окне сервиса. Почта — сразу SMTP и IMAP (`email_send`, `email_search`, `email_read`), IMAP перенесён из v2 в v1; ящиков у пользователя может быть несколько. Ящики живут в своей таблице `mailboxes`, а не в `connections`: всё вокруг `connections` завязано на пункт каталога (уникальность, OAuth, проверки), и общая таблица потянула бы ветвления в MCP. Пароль — в `secrets` (`owner_type = 'mailbox'`). Каждое письмо уходит только после «Разрешить» в ленте. Пресеты — Яндекс, Gmail, Mail.ru и своя почта; Outlook.com не берём: Microsoft отключил вход по паролю, нужен OAuth.

### D28. Изменение агентов — ПО УМОЛЧАНИЮ + PROTOTYPE

Агент меняется словами из любого места: из его запуска, из оценки 👎 с комментарием, со страницы агента. Тул `update_agent` не применяет изменение, а показывает карточку «было → стало»; применяет человек (ARCHITECTURE §16.1a).

- каждое изменение создаёт версию, запуски знают свою версию, есть откат;
- после изменения можно сразу сделать тестовый прогон — он без уведомлений и не идёт в счётчик сбоев;
- идущий запуск доигрывается на старой версии.

Отвергнутые варианты:

- **Модель правит агента сама, без подтверждения.** Инструкции агента — это то, что потом работает без присмотра. Незаметная правка из-за неверно понятой фразы проявится через неделю в виде странных сводок.
- **Менять только через форму настроек.** Рвёт поток: пользователь думает «в следующий раз сделай иначе», а не «открою настройки и найду поле».

Вид карточки «было → стало» решает прототип P15.

### D29. Источник и провайдер модели — РЕШЕНО

Решение пользователя 2026-09-24: это разные вещи, и называются они по-разному.

- **Источник** — кто даёт доступ к моделям: ключ OpenAI или Anthropic, Vercel AI Gateway, Yandex AI Studio, свой сервер (`openai-compatible`). У источника — ключ, маршрут через прокси, здоровье, расход.
- **Провайдер** — кто сделал модель: OpenAI, Anthropic, Google, Alibaba (Qwen), DeepSeek, xAI, Mistral, Meta, Яндекс… У провайдера — название и логотип. Их видит пользователь в выборе модели в чате.

Через один источник приходят модели многих провайдеров (Gateway — сотни, Яндекс — свои и открытые), а модели одного провайдера могут идти через несколько источников. Таблицы: `sources` и `providers` (ARCH §5.2).

Логотипы — встроенный набор `@lobehub/icons-static-svg` (MIT, без зависимостей; одноцветные рисуются маской в цвете текста). Админ может поменять название и картинку провайдера, выбрав из набора или загрузив свою (файл — в S3). В настройках — разделы «Источники» и «Провайдеры». У источника тоже можно сменить логотип и название: по умолчанию значок по типу, а у OpenAI-совместимого — угаданный по адресу (ollama, lmstudio, vllm, openrouter…); не угадали — первая буква названия. В пикере логотипа картинку можно вставить из буфера (⌘V / Ctrl+V, в том числе SVG-разметку), перетащить или загрузить файлом.

**Включение моделей — одно поле, два вида** (как маршрут в §18): «модель X в чате через источник Y». В источнике модели сгруппированы по провайдерам, у группы свой переключатель; у провайдера — его модели из всех источников с меткой источника. Отдельного раздела «Модели» в настройках нет. Массовых кнопок «включить показанные / выключить» тоже нет — массовое действие одно, переключатель группы.

До этого решения в документах «провайдером» называлось то, что теперь «источник», а провайдер модели — «вендором»; тексты переименованы 2026-09-24.

### D30. Название: Metobe — РЕШЕНО

Решение пользователя 2026-09-24: проект называется **Metobe**, а не Purr — он будет расти дальше чата (проектная работа, совещания, память агента). В коде `metobe` (пакеты `@metobe/*`, переменные `METOBE_*`, CLI `metobe`), в интерфейсе `Metobe`. Репозиторий — `github.com/artemavrin/metobe`, образ — `ghcr.io/artemavrin/metobe` (CI берёт имя из репозитория). История в `CHANGELOG.md` не переписывается.

Для установок до 0.2.0 это несовместимое изменение: у compose другое имя проекта (а значит, и томов), другие имена базы и переменных. Чтобы обновиться без потери данных, в `.env` существующей установки: переименовать `PURR_*` в `METOBE_*` и добавить `COMPOSE_PROJECT_NAME=purr`, `POSTGRES_DB=purr`, `POSTGRES_USER=purr`, `POSTGRES_PASSWORD=<прежний>` — тогда подхватятся старые тома и база.

### D31. Язык и регион пользователя — РЕШЕНО

Решение пользователя 2026-09-24: интерфейс локализуется сразу, пока продуктового кода мало. Языки v1 — английский (по умолчанию, для глобальной аудитории) и русский. Язык в адресе не участвует: никаких `/en/...`.

- **Библиотека — `next-intl` 4.14** в режиме без i18n-роутинга (официальный пример на Next 16.3). Разбор `Accept-Language` — `negotiator` + `@formatjs/intl-localematcher`, как в руководстве Next. Альтернативы (Lingui 6, next-i18next 16, Paraglide 2) отвергнуты: у всех либо нет готового пути «кука + серверные компоненты», либо неясна совместимость с React Compiler.
- **Что хранится.** В профиле (`user`): `locale`, `time_zone`, `week_start` (ISO: 1, 6, 7), `date_format` (`dmy` / `mdy` / `ymd`). Все необязательные: пусто — «автоматически». Не `en` по умолчанию в базе: иначе русскоязычный пользователь после первого входа оказался бы в английском интерфейсе, ничего не выбирая.
- **Как выбирается на запросе** (`packages/i18n` → `resolvePrefs`, вызывается в `apps/web/i18n/request.ts`): кука → `Accept-Language` → `en`. Куки — копия профиля для рендера без запроса к базе; при входе и после сохранения их пишет `writePrefsCookies`. Неавтоматический выбор хранится и в куке, и в профиле.
- **Часовой пояс «автоматически»** — пояс браузера: клиент один раз сообщает его server action'ом (`tz`), страница перерисовывается на сервере уже в нём. Выбранный вручную пояс помечен `tz_manual` и браузером не перезаписывается.
- **Первый день недели «автоматически»** — по языку (CLDR: en — воскресенье, ru — понедельник). **Формат даты** действует на числовые даты (`formatNumericDate`); даты словами всегда по языку.
- **Вне страниц.** Server actions — `getTranslations`. Письма, CLI и worker — `getTranslator` из `@metobe/i18n/translator` (`use-intl/core`, работает без Next): письмо — на языке профиля получателя, иначе на языке страницы, с которой запросили код; CLI — по `LANG` контейнера.
- **Контракты без текста.** Сообщения Zod-схем в `@metobe/contracts` — ключи (`validation.*`), переводит вызывающая сторона.
- **Правило:** в продуктовом коде нет строк интерфейса вне `packages/i18n/messages/*.json`; ключи типизированы (`AppConfig.Messages`), опечатка ломает сборку. Прототипы в `/dev/prototypes` не переводятся — одноразовый код.
- **Цена.** Чтение куки делает страницы динамическими — для приложения за авторизацией это нормально. Если включим `cacheComponents`, язык придётся передавать в кешируемые функции аргументом: готового рецепта для кук у next-intl нет.

### D32. MCP-серверы в чате: по упоминаниям, большие — по запросу — РЕШЕНО

Решение пользователя 2026-09-27. Повод: в чате «как ты» модель заговорила о Битриксе, а «Готовит ответ…» висело 16–24 с. Битрикс упомянули раньше в вопросе, который потом отредактировали. Сервер при этом остался в чате, и его 106 тулов (25–29 тыс. токенов) уходили в каждый запрос.

- **Серверы чата — те, что упомянуты в вопросах треда** (`@Название`, как упоминание пишет композер). Упоминание — это и бейдж в сообщении, и тулы у модели; разбор у них общий (`apps/web/lib/mentions.ts`). Сервер работает и в следующих вопросах, пока вопрос с упоминанием остаётся в треде. Правка или удаление этого вопроса убирает и его серверы. Колонка `chats.catalog_ids` (липкий список) удалена миграцией 0017.
- **У большого сервера тулы подгружаются по запросу.** Если у сервера больше 12 тулов (`ON_DEMAND_AFTER`), они уходят модели с `deferLoading`, а вместо них модель видит `find_tools` (`toolSearch()` из AI SDK 7). В описании поиска перечислены сервисы за ним и самые частые слова из имён их тулов — так модель ищет теми же словами. Поиск локальный, по словам в именах и описаниях. Найденные тулы, до пяти за поиск, приходят модели со схемами на следующем шаге. Тулы, уже вызванные в треде, подгружены сразу; так и ответ после «спросить сначала» находит свой тул. В «Ходе работы» поиск — отдельный шаг: что искали и что нашлось.
- **Цена.** Когда модели нужен тул большого сервера, добавляется шаг поиска, а после него сбрасывается кеш промпта: список тулов меняется. Поиск идёт по словам без морфологии: «deals» не находит «deal», и модель ищет заново другими словами. Имена и описания тулов обычно на английском, поэтому модель ищет по-английски.

### D33. Вложения: три уровня чтения, служебная модель зрения — ПО УМОЛЧАНИЮ

Решение пользователя 2026-10-02. Не каждая модель читает файлы, а песочница (D3) — отдельный большой этап. Делаем как Anthropic в claude.ai (картинки и PDF — модели напрямую, остальные документы — только текстом, песочница — для работы с данными, а не для чтения):

1. **Как есть.** Картинка или PDF уходит модели напрямую, если её возможности это позволяют (`capabilities.vision`, поддержка PDF у источника).
2. **Текст на сервере.** Документ (PDF модели без PDF, DOCX, XLSX, CSV, TXT, MD, JSON…) один раз превращается в текст, текст хранится, а модель читает его тулом `read_attachment(id, страница)` по частям с подсказкой «дальше — страница N». Так большой файл не раздувает историю и сочетается с бюджетом контекста. Разбор чужого файла — риск (бомба, уязвимость парсера), поэтому он идёт в отдельном рабочем процессе с лимитами времени и размера, а не в процессе запроса. Кэш проверяется до скачивания файла из S3; страницы есть у любого текста, не только у документов.
3. **Песочница** — анализ CSV/XLSX кодом и создание файлов (D3, позже).

**Служебная модель «Зрение»** (слот `vision` рядом с `titles`, выбираются только модели с `capabilities.vision`): описывает картинку модели без зрения. Общее описание кэшируется и помечено как описание («картинка «…», описана моделью зрения»), ответ на конкретный вопрос о картинке не кэшируется. Без модели зрения картинку модели без зрения не отдаём и честно говорим об этом в композере.

Хранение — S3 (D4), файлы живут, пока жив чат. **Браузер с S3 не говорит** (решение пользователя 2026-10-02): загрузка и скачивание идут через приложение — один адрес, без CORS и второго открытого порта, права проверяет приложение; presigned-ссылки — позже, для внешнего S3 и больших файлов. Хранилище — `packages/core/src/storage.ts`, настраивается `S3_*` в `.env`; без них файлы выключены, `/api/health` показывает `s3: off`.

### D34. Зависимости сервера и чистая установка — ПО УМОЛЧАНИЮ

Решение пользователя 2026-10-02. С вложениями, S3 и песочницей зависимостей становится больше, а ставка №1 — установка одной командой.

- **Хосту — только Docker и compose v2** (плюс `curl` и `openssl` для `install.sh`). Ни библиотек, ни CLI на сервер не ставим: всё, что нужно Metobe, едет в образах.
- **Лёгкое — в образ приложения, тяжёлое — в свой образ.** Парсеры — на чистом JS или WASM, без нативных бинарей, чтобы жить в `node:*-alpine`. LibreOffice, OCR, Python никогда не попадают в образ приложения — только в отдельный образ (например, песочницы), который скачивается, если функция включена.
- **Необязательное — профилями compose**, как `db`: `s3` (встроенный SeaweedFS или внешний S3), `search` (SearXNG), `sandbox`. `install.sh` спрашивает, что включить, и пишет `COMPOSE_PROFILES` в `.env`; повторный запуск включает профиль позже.
- **Приложение само видит, что есть.** Чего нет — того не предлагают ни модели, ни пользователю; в настройках видно «не установлено» и как включить. `/api/health` проверяет только включённое.
- **Версии закреплены.** Свои образы собирает релизный CI с версией приложения, обновление — повторный запуск `install.sh`.
- **Исключение — песочница.** Безопасная изоляция требует от хоста gVisor (`runsc` как runtime Docker) или KVM. `install.sh` проверяет это в `docker info`; если нет — предлагает поставить (нужен sudo) или пропустить. Песочницы без изоляции не будет.
- **Контроль.** Таблица зависимостей в ARCHITECTURE §2.4 обновляется в том же PR, где появляется зависимость. В CI — задача «чистая установка»: `install.sh` на пустом раннере → `/api/health` за 90 с (критерий M1), с профилями по умолчанию и со всеми. У образа приложения — бюджет размера.
