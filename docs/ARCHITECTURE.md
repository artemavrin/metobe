# Архитектура

> Версия 2 — переписана после разбора первой версии. Спорные решения и их статусы — в [DECISIONS.md](DECISIONS.md), этапы и прототипы — в [PLAN.md](PLAN.md).
>
> Сверено с `ai@7.0.109` (локальные `docs/` и `src/`), `@ai-sdk/openai-compatible@3.0.53`, шаблоном [`vercel/chatbot`](https://github.com/vercel/chatbot) @ `main`, документацией Next.js 16, Better Auth и Yandex AI Studio. Непроверенное помечено **проверить** или **spike**.

## 0. Продукт

Self-hosted AI-рабочее место для команды. Инфраструктура описана в `docker compose`, а всё содержательное — провайдеры, модели, цены, MCP, скиллы, пользователи — настраивается в интерфейсе после установки.

### Ставки

То, ради чего продукт существует рядом с Open WebUI и LibreChat. Если ставка не подтверждается, её функциональность режется первой.

1. **Установка и первый ответ за 2 минуты.** Одна команда в терминале, одна ссылка в браузере, вставленный ключ — и уже идёт переписка.
2. **Генеративный UI.** Графики, таблицы и метрики строятся по живым данным тулов, модель цифры не переписывает.
3. **Работа в сетях с ограничениями.** Yandex AI Studio из коробки, прокси HTTP и SOCKS5 в админке: всё ходит напрямую, через прокси — только то, что админ явно отметил (§18).
4. **MCP и скиллы как основа, а не плагины.**
5. **Фоновые агенты.** Чат, который работает без тебя: по расписанию, твоими инструментами, с результатом во входящих и уведомлением туда, где ты сейчас (§16).

### UX-принципы

Это правила, по которым принимается каждое UI-решение. Спорные экраны проверяются прототипом до реализации (PLAN.md, раздел «Прототипы»).

1. **Метрика №1 — время до первого ответа.** Весь путь от `install.sh` до первого сообщения проходится без правки конфигов.
2. **Пустой экран — это действие.** Нет провайдеров → чата нет, первый вход ведёт на настройки провайдеров (P1). Нет MCP → карточка «подключите первый сервер» с примером.
3. **Ничего не молчит дольше секунды.** Вместо спиннера — фаза работы: «думает», «читает файл X», «спрашивает GitHub», «ждёт Яндекс».
4. **Ошибка = что случилось + почему + что сделать.** Для 429 — автоповтор с обратным отсчётом. Стектрейсы пользователь не видит никогда.
5. **Проверка в момент ввода.** Ключ провайдера проверяется при вставке, MCP-сервер сразу показывает список своих тулов.
6. **Мгновенная реакция.** Оптимистичный UI, стрим без прыжков вёрстки, скелет виджета появляется ещё до прихода данных.
7. **Клавиатура наравне с мышью.** `⌘K` — палитра команд, `⌘/` — выбор модели, `Esc` — стоп, `↑` — редактировать последнее.
8. **Движение со смыслом.** Анимация показывает, откуда элемент пришёл и куда ушёл (виджет → панель артефакта). `prefers-reduced-motion` соблюдается.
9. **Обратимость.** Опасное подтверждается, разрушительное по возможности отменяется.

## 1. Границы

- **Один инстанс `app`.** Отмена генерации, MCP-клиенты и реестр стримов живут в памяти процесса. Горизонтального масштабирования нет, и мы его не имитируем (D2). Фоновые агенты выполняются в отдельном процессе `worker` из того же образа, чтобы тяжёлые запуски не тормозили чат (§16).
- **Self-hosted, долгоживущий Node-процесс** в Docker, не serverless.
- **Single-tenant с ролями.** Организаций нет.
- **Линейная история сообщений**, как в `vercel/chatbot`.

### 2.2 Установка без мастера

Мастер в браузере отменён (D1). Всё, без чего приложение не может стартовать, решается до старта:

```
./install.sh
  1. проверяет docker и compose
  2. задаёт 3 вопроса с дефолтами: адрес (домен/порт), БД встроенная или своя, S3 встроенный или свой
  3. генерирует .env: SECRETS_KEY, BETTER_AUTH_SECRET, пароли postgres и s3, VAPID-ключи для push-уведомлений
     + необязательный вопрос «нужен исходящий прокси?» → HTTPS_PROXY / ALL_PROXY (§18)
     + необязательный вопрос «настроить почту сейчас?» → SMTP_* (при первом старте переносится в настройки, как прокси); без почты вход по ссылкам от админа
     → крупно печатает: «сохраните SECRETS_KEY — без него ключи провайдеров не восстановить»
  4. docker compose up -d, ждёт healthcheck
  5. печатает адрес и одноразовую claim-ссылку
```

Для автоматизации есть неинтерактивный режим: те же ответы передаются переменными окружения.

**Entrypoint `app`** при каждом старте:

1. применяет миграции под `pg_advisory_lock` (два процесса не мигрируют одновременно);
2. обновляет seed-справочники: вендоры и известные модели с ценами и возможностями;
3. если суперюзера ещё нет — выпускает claim-токен (в БД хранится хэш, TTL 24 ч) и печатает ссылку в лог;
4. запускает сервер.

Потерянную ссылку можно перевыпустить: `docker compose exec app purr claim-link`.

**В браузере** остаётся один экран: `/claim?token=…` → «Создать аккаунт» (имя и email, пароля нет — D17). Claim-ссылка сама создаёт сессию, поэтому для первого входа почта не нужна. После этого экрана пользователь попадает в настройки провайдеров. Чат открывается, когда подключён хотя бы один провайдер с включённой моделью: без моделей в нём нечего делать (P1, вид — P7).

### 2.3 Что где настраивается

| `.env` (инфраструктура, до старта) | БД через UI (данные, после старта) |
| --- | --- |
| `DATABASE_URL`, `REDIS_URL`, `S3_*`, `APP_URL` | провайдеры, ключи, модели, цены |
| `SECRETS_KEY`, `BETTER_AUTH_SECRET` | MCP-серверы, скиллы |
| `HTTPS_PROXY` / `ALL_PROXY` — стартовый прокси: при первом запуске превращается в запись в админке | прокси и что через каждый ходит (§18) |
|  | пользователи, роли, лимиты, SMTP |

SMTP живёт в UI (D15): для старта он не нужен, приглашения работают и без него, а в UI его удобно проверить кнопкой «отправить тестовое письмо».

### 5.2 Провайдеры и модели

```ts
providers; // kind: 'openai'|'anthropic'|'openai-compatible'|'yandex'|'gateway'
// title, base_url, enabled; ключ — secrets (owner_type = 'provider', purpose = 'api_key', §17)
// options jsonb — Zod discriminated union по kind:
//   yandex: folderId
// proxy_mode: 'auto' | 'direct' | 'proxy', proxy_id? (§18)
model_vendors;
models; // provider_id, vendor_id, model_id, title, enabled, default_access
// context_window, capabilities jsonb,
// capabilities_source: 'discovered' | 'seed' | 'manual'
// price_input / price_output / price_cached — за 1M токенов, price_currency
// used_for_titles
model_runs; // chat_id (SET NULL), user_id, model_id,
// input / output / cached tokens, cost, currency, latency_ms, status
```

- `capabilities`: `null` — «источник не сообщил», `false` — «точно нет». От этого зависит, деградировать функциональность или падать (§7.3).
- Источники значений: `discovered` пришло от провайдера; `seed` — из справочника, который поставляется с приложением (нужен, когда `/models` отдаёт только id, как у Яндекса); `manual` — правка админа, синк её не перетирает.
- **Цены** нормализованы к 1M токенов, валюта хранится рядом. Дашборд суммирует по валютам и **курсы не пересчитывает** (D19).

### 5.3 Чат

Форма взята из `vercel/chatbot`:

```ts
chats; // id, user_id, title, visibility, created_at
// kind: 'chat' | 'agent_run', agent_id? — запуск агента это обычный чат (§16)
messages; // id, chat_id, role, parts jsonb, attachments jsonb, created_at
streams; // id, chat_id, created_at
votes; // (chat_id, message_id), is_upvoted
documents; // PK (id, created_at) — версии артефактов, v2
```

`messages.parts` хранит `UIMessage['parts']` как есть, в формате AI SDK — так рекомендует официальная дока по persistence. Цена: мажорный апгрейд `ai` может потребовать миграции данных (в шаблоне так появилась таблица `Message_v2`).

## 6. Сообщения и стрим

Паттерн официального шаблона.

### 6.1 Контракт

```ts
POST /api/chat
{ id, message: UIMessage, modelId, connectionIds?: string[], skillSlugs?: string[] }
```

- Клиент шлёт только последнее сообщение, историю сервер берёт из БД.
- **Подключения:** `undefined` — все активные подключения пользователя плюс доступные ему `shared`-пункты каталога (то же множество, что у агентов, D22); `[]` — ни одного; явный список — ровно эти. Сузить набор можно в composer (P2).
- **Встроенные тулы** (`web_search`, `web_fetch`, рендер виджетов, `request_connection`) доступны всегда, если админ их не выключил в `policies.builtinTools`, и от `connectionIds` не зависят.

### 6.2 Генерация

```ts
const stream = createUIMessageStream({
  originalMessages: uiMessages,
  execute: async ({ writer }) => {
    writer.write({
      type: "data-status",
      data: { phase: "waiting-model" },
      transient: true,
    });
    const result = streamText({
      model,
      instructions,
      tools,
      messages: await convertToModelMessages(uiMessages, { tools }), // тот же ToolSet — ради toModelOutput
      stopWhen: isStepCount(5),
      abortSignal: activeGenerations.register(chatId),
      onAbort: ({ steps }) => persistPartial(steps),
    });
    writer.merge(toUIMessageStream({ stream: result.stream }));
  },
  onEnd: ({ messages }) => saveMessages(messages),
  onError: toHumanError,
});
return createUIMessageStreamResponse({ stream, consumeSseStream });
```

- Пользовательское сообщение сохраняется **до** генерации, ассистентское — в `onEnd`.
- Если клиент отвалился, `result.consumeStream()` доводит генерацию до конца, и ответ всё равно сохраняется.
- Перед подачей в модель история проходит `validateUIMessagesForAgent`: части исчезнувших тулов (например, отключённого MCP-сервера) превращаются в dynamic.
- Сигнатура `convertToModelMessages(messages, { tools })` — **проверить** при реализации. Дока требует передавать туда тот же ToolSet, что и в `streamText`.

### 6.3 Остановка

При resumable-стриме клиентский `stop()` только отключает клиента, генерация продолжает тратить токены. Поэтому:

- `POST /api/chat/[id]/stop` находит `AbortController` в реестре `activeGenerations` (обычный `Map` в памяти — следствие D2), дёргает `abort()` и очищает активный стрим;
- `onAbort` сохраняет частичный ответ;
- уход со страницы стоп не вызывает — только явная кнопка или `Esc`.

### 6.4 Resume — spike (D5)

В `vercel/chatbot` рабочий GET заменили на заглушку `204` в PR #1392 от 2026-01-15, причина не указана. Прежде чем строить на resume, проверяем его на `ai@7` + `resumable-stream`.

**Запасной вариант без resume.** Генерация всё равно доводится до конца на сервере. Вернувшись в чат, пользователь видит «ответ ещё пишется», клиент опрашивает статус и подтягивает сохранённый ответ.

### 6.5 Статусы

Transient `data-status` показывает фазы: `waiting-model` → `thinking` → `tool:<name>` → `writing`. Если модель молчит дольше N секунд, статус меняется на «модель отвечает дольше обычного». Подписи к тулам строятся по словарю «имя тула → фраза» (идея PlusPortal), а для MCP-тулов по умолчанию используется их `title`/`description`.

## 7. Провайдеры и модели

### 7.1 Реестр из БД

Фабрика собирает инстанс провайдера по `kind`: `createOpenAI`, `createAnthropic`, `createOpenAICompatible`, `gateway`. Готовые инстансы кешируются. При изменении провайдера событие `config:changed` уходит через Redis pub/sub, и кеш сбрасывают оба процесса — `app` и `worker`.

- **Ключи** лежат в общем хранилище `secrets`: AES-256-GCM, write-only API, canary-проверка мастер-ключа (§17). Без мастер-ключа записать секрет нельзя: в открытый текст не деградируем.
- **Discovery** забирает список моделей у провайдера, а seed-справочник дополняет контекст, возможности и цены.
- **«Рекомендованных» моделей нет:** ни один провайдер их не отдаёт, а свой кураторский список быстро протухает. После подключения ничего не включено заранее. Список сортируется по дате выпуска из API (`released` у Gateway, `created_at` у Anthropic, `created` у OpenAI; у Яндекса — из seed), «новая» — это факт: моложе 90 дней. Для длинных списков (Gateway — сотни моделей) — поиск, фильтр по вендору и возможностям, «выбрать показанные» и список фиксированной высоты (P7).

### 7.2 Исходящий прокси

Реальный сценарий: OpenAI и Anthropic доступны только через прокси, а Яндекс — напрямую. Провайдер получает `fetch`, который выбирает маршрут по правилам §18. По умолчанию — напрямую: Яндекс ходит напрямую, OpenAI — через прокси, только если админ его туда отметил.

Опция `fetch` есть у всех четырёх провайдеров (S4). Это `fetch` из пакета `undici` с dispatcher маршрута, а не глобальный: dispatcher из npm-undici и встроенный в Node fetch — разные версии.

### 7.3 Деградация вместо отказа

Если модель не умеет tools, vision или structured output, эта возможность отключается, а в `instructions` добавляется объяснение почему. Если capability равна `null`, пробуем, а ошибку превращаем в понятное сообщение и помечаем модель.

### 7.4 Yandex AI Studio

Официального провайдера для AI SDK нет, community-пакет `yandex-ai` сидит на `ai@6`. Подключаем через `createOpenAICompatible`: его `headers` применяются после `apiKey`.

```ts
createOpenAICompatible({
  name: "yandex",
  baseURL: "https://ai.api.cloud.yandex.net/v1",
  headers: { Authorization: `Api-Key ${apiKey}`, "OpenAI-Project": folderId }, // нужен ли OpenAI-Project — spike S3
});
```

- В `models.model_id` храним короткое имя (`aliceai-llm`, `yandexgpt-5.1`), фабрика собирает URI `gpt://<folderId>/<model>`.
- AI Studio хостит и чужие открытые модели (Qwen, DeepSeek, gpt-oss): вендор у них свой, провайдер — Яндекс.
- Авторизация — API-ключ сервисного аккаунта с ролью `ai.languageModels.user`. IAM-токены (живут ≤ 12 ч) отложены.
- `/v1/models` отдаёт только id, всё остальное берём из seed.
- Ограничения, которые учитывает model router:
  - `tool_choice` принимает только `auto` и `none`;
  - изображения — только base64 data-URL, поэтому вложения из S3 инлайним;
  - structured output подтверждён только для YandexGPT;
  - стрим с tools не подтверждён — spike S3;
  - квота по умолчанию — 10 одновременных синхронных генераций, так что 429 будут и требуют понятного UX.
- Оплата в рублях. Нерезиденты России и Казахстана платят в USD и только картами нероссийских банков.

### 7.5 Vercel AI Gateway

Один ключ — доступ к моделям разных вендоров. Проверено по `@ai-sdk/gateway@4.0.88`, который реэкспортируется из `ai` как `gateway`.

```ts
createGateway({ apiKey, fetch: proxiedFetch }); // есть baseURL и headers; fetch — для прокси (§7.2)
```

- **Discovery богаче, чем у остальных.** `GET /v1/models` публичный, ключ не нужен (S4). У каждой модели есть:
  - возможности (`tags`: `tool-use`, `vision`, `reasoning`, `structured-output`, `file-input`…);
  - `context_window`, `max_tokens`, `type` (`language`, `embedding`, `image`…), `modalities`;
  - `pricing` — USD **за токен**, строками, с тирами по длине контекста.

  Всё пишем как `discovered`, цены при сохранении умножаем на 1M (тиры — D19). В чат берём только `type: language`. Вендор определяется по префиксу id (`anthropic/…`, `openai/…`). `/v1/models/{id}/endpoints` — разбивка по апстрим-провайдерам, для возможностей не нужен.

- **Фактическая стоимость.** `generationId` приходит в `providerMetadata.gateway`, а `gateway.getGenerationInfo({ id })` отдаёт `totalCost`. Записи появляются асинхронно, поэтому API отвечает 404, пока запись не готова. Поэтому `model_runs` сначала получает оценку по прайсу, а worker потом уточняет её фактической стоимостью. Проверено по типам и докам, вживую — нет.
- Для self-hosted нужна авторизация API-ключом. OIDC-режим Vercel работает только на их платформе.

### 7.6 Ollama

В v1 — через `createOpenAICompatible` поверх `/v1`. Работают ли так tools, проверяет spike S7. Если нет — community-пакет `ai-sdk-ollama` (peer `ai ^7`), тогда в `providers.kind` добавится `'ollama'`. `ollama-ai-provider` несовместим с `ai@7`.

## 8. Инструменты

1. **Встроенные:** `web_search` и `web_fetch` (§8.1), рендер виджетов (§9), `request_connection` (§17.7); в v2 — `createDocument`/`updateDocument`, `create_agent`, `update_agent` и `report` для запусков агентов (§16).
2. **MCP:** `createMCPClient` из `@ai-sdk/mcp`, discovery через `client.tools()`.
   - Серверы бывают из каталога организации и личные. Креды у сервера либо общие, либо у каждого пользователя свои (§17.1).
   - В v1 только `http`. Опция `redirect` по умолчанию `'error'` (защита от SSRF) — не переопределяем.
   - Имена тулов получают префикс: `catalog_items.key` для пунктов каталога, короткий id подключения для своих серверов (v2). Поверх того, что отдал сервер, работает наш allowlist `allowed_tools`.
   - **Подтверждения у своих подключений** (почта, `http_api` без каталога): политика берётся из `policies.personalApprovalDefaults` по тулу коннектора. По умолчанию `email_send`, `webhook_out`, `telegram_send` и записывающие `http_api`-операции — `ask`, остальное — `auto`.
   - Аннотации `readOnlyHint`/`destructiveHint` приходят от сервера и недоверенные. Политику подтверждений задаёт админ в пункте каталога: `approval_policy` — `auto` / `ask` / `deny` на каждый тул, в том числе на тулы коннекторов (`email_send`, `http_request`). `deny` скрывает тул совсем. Что `ask` значит для фоновых агентов — D22.
   - Результаты любых тулов — недоверенные данные, а не инструкции.
   - `stdio` — в v3, только для суперюзера, с явным предупреждением «это запуск команды на сервере» и без личных кредов (D18).
3. **Скиллы — v2.** Формат совместим с Agent Skills (`SKILL.md` + frontmatter): уже существующие скиллы импортируются zip-архивом. В промпт попадают имя и описание, тело подгружается тулом `load_skill`. Скиллы бывают общие (от админа) и личные. Секретов в скиллах нет: если скиллу нужен доступ куда-то, он работает через подключение (§17).

**Подтверждения.** Используем штатный approval-флоу AI SDK v7 (`approval-requested` → `approval-responded` → `output-denied`), UI — `addToolApprovalResponse`.

**Песочница — v3** (D3). Никогда через `docker.sock`: он даёт root на хосте. Кандидаты — microsandbox и gVisor, выбор будет отдельным spike. Пока песочницы нет, `run_code` недоступен, и модель об этом знает (§7.3).

### 8.1 Поиск в интернете

Встроенного поиска провайдеров мало. `openai.tools.webSearch` и аналоги в `ai@7` — это provider-executed tools: они выполняются на стороне провайдера и работают только с его моделями. У Яндекса, Ollama и openai-compatible их нет, а фоновым агентам поиск нужен на любой модели. Официальные пакеты поиска для AI SDK (Tavily, Exa, Perplexity, Parallel) пока поддерживают только `ai@5`/`@6`.

Поэтому свои тулы `web_search` и `web_fetch`. Бэкенды настраиваются в админке так же, как провайдеры моделей:

| Бэкенд | Роль |
| --- | --- |
| **SearXNG** в compose | по умолчанию: локально, бесплатно, без ключей. JSON включается в `settings.yml`, иначе ответ 403 |
| Yandex Search API — запасной | качество на русском. Платно: ≈ $4 за 1000 запросов днём, ≈ $0.25 в отложенном режиме, бесплатного тарифа нет |
| TinyFish — запасной | облачные Search и Fetch бесплатно (30 поисков и 150 URL в минуту), нужен ключ, скорее всего через прокси |
| Tavily — запасной | 1000 запросов в месяц бесплатно |

**Почему SearXNG может не хватить.** У него нет своего индекса: он с нашего сервера сам запрашивает Google, Bing, DuckDuckGo и собирает их выдачу. При ровном потоке запросов с одного IP — а фоновые агенты по расписанию дают именно такой поток — поисковики могут начать отвечать капчей. Часть движков из корпоративной сети может быть недоступна без прокси, а русскоязычная выдача Яндекса даже внутри SearXNG идёт через платный Yandex Search API. Поэтому платные бэкенды — **запасной путь, а не план:** адаптер подключается, только если S8 или эксплуатация покажут капчи или слабое качество. Интерфейс адаптера закладывается сразу, так что это будет настройка, а не переделка.

- **Чтение страниц — локально по умолчанию:** свой `fetch` плюс извлечение основного текста страницы в Markdown (библиотеку выбрать при реализации). Скачивание с нашего сервера — только с защитой от SSRF: запрет приватных диапазонов и повторная проверка адреса после каждого редиректа. Иначе модель достанет внутренние ресурсы корпоративной сети. TinyFish Fetch и Jina Reader — запасные варианты для страниц, которые не читаются без браузера. Firecrawl на своём сервере для «одной команды» слишком тяжёл: Postgres, Redis, RabbitMQ, Playwright.
- **Источники:** тул пишет части `source-url`, поэтому кликабельные цитаты работают у любой модели.
- **Недоверенный контент:** найденное — это данные, а не инструкции (§8). Для агентов это часть осознанного риска D22.
- **Хранение:** бэкенды — таблица `search_backends`, ключи — в `secrets` (`owner_type = 'search_backend'`), настройки — `/settings/search`. В v1 — SearXNG и локальный fetch. Остальные адаптеры — по результатам S8 и эксплуатации.
- **N2 Free Search не берём:** это была MCP-обёртка над SearXNG, 2026-03-23 её сняли с npm, репозиторий удалён. Идею реализуем сами.
- **Риск:** при нагрузке поисковики могут отвечать SearXNG капчей. Для команды обычно хватает, для большой нагрузки нужен платный бэкенд. На практике не проверено — spike S8.

## 9. Генеративный UI

### 9.1 Контракт

Модель не порождает разметку. Она выбирает `kind` из закрытого реестра и заполняет спек по Zod-схеме этого вида. Спек плоский: один виджет — один объект, без деревьев компонентов. Для дашбордов позже появится один composite-вид с ограниченной сеткой.

```ts
widgetRegistry = { chart: {...}, table: {...}, metrics: {...} }   // schema + Component
```

- Рендер через `safeParse`: невалидный или неизвестный виджет показывается фолбэком, сообщение от этого не падает.
- Схемы только расширяются: старые сообщения должны рендериться после любого релиза.

### 9.2 Данные не проходят через модель: `sourceRef` + `toModelOutput`

Главная дыра первой версии документа — откуда виджет берёт данные. Решение:

1. **Полный** результат любого тула (включая MCP) хранится в `messages.parts` — он нужен UI и ссылкам.
2. Модели через `toModelOutput` уходит **сжатая** версия: схема колонок, первые N строк, число строк и `ref` на вызов. `toModelOutput` есть в `ai@7`, его вызывает `convertToModelMessages`.
3. Рендер-тул принимает `{ kind, spec, source: { toolCallId } }`. Сервер берёт полный результат из истории чата, применяет спек (колонки, сортировку, агрегат) и отдаёт виджету готовые данные.

Модель решает, _что_ показать, и никогда не переписывает цифры. Большие выборки не съедают контекст.

**Spike S5** должен проверить две вещи: применяется ли `toModelOutput` между шагами внутри одного `streamText` и можно ли обернуть им MCP-тулы из `client.tools()`.

### 9.3 Где живёт виджет

- Виджет в ленте — это tool-часть: она сохраняется в историю. `transient`-части для виджетов не годятся, они в историю не попадают.
- На `input-streaming` уже доступен частичный спек, поэтому скелет виджета показывается сразу.
- Фильтры и сортировка — локальное состояние компонента, в URL и в модель не попадают. Учесть текущий срез в следующем ответе — явное действие «обсудить выделенное».
- Как виджет превращается в артефакт в правой панели — прототип P5.

### 9.4 Артефакты — v2

Структура шаблона: `artifacts/<kind>/{server.ts,client.tsx}`. Дельты идут накопленным контентом в transient `data-*`, содержимое сохраняется в `documents` с версиями. Типы: `text`, `code`, `sheet` (на ReUI Data Grid вместо `react-data-grid`), `dashboard`.

### 9.5 UI-библиотеки: приоритет ReUI

**ReUI — первый выбор для любого компонента, не только для рендерера: его вид нравится больше.** Правило выбора:

1. Если нужный компонент или блок есть в ReUI — берём его.
2. Если нет — берём shadcn/ui. Стиль shadcn в `components.json` выбираем тот же, что у ReUI (`<base>-<variant>`, например `base-nova`), чтобы базовые примитивы выглядели как ReUI.
3. Графики — тоже ReUI: бесплатные блоки `@reui/c-chart-*` на shadcn `chart` + recharts. EvilCharts пробовали и отказались (D20).

| Задача | Выбор |
| --- | --- |
| Все компоненты интерфейса | ReUI → shadcn/ui в стиле ReUI |
| Таблицы | ReUI Data Grid (TanStack Table + Virtual + dnd-kit) |
| Графики | ReUI — блоки `@reui/c-chart-*` на shadcn `chart` + recharts (D20) |

Вариант стиля ReUI (`vega`, `nova`, `maia`, `lyra`, `mira`, `luma`, `sera`, `rhea`) — решение визуальное, выбирается глазами на прототипе (D20).

Итоги S2 (D20):

- `shadcn add` запускаем из `packages/ui` — тогда примитивы и составные компоненты ReUI ложатся в дизайн-систему; перезаписей нет, совпадающие файлы пропускаются.
- База — Base UI (`base-nova`), иконки — `lucide-react`.
- ReUI работает на React 19 / Tailwind v4; контракт виджетов §9.1 от конкретной библиотеки не зависит.

## 10. Auth и доступ

- **Better Auth, без паролей (D17):** вход по магической ссылке — письмо со ссылкой и шестизначным кодом, код нужен, если письмо открыли на другом устройстве. Ссылка одноразовая, живёт 10 минут, запросы ограничены по email и IP. Магическая ссылка заодно подтверждает почту. Claim-ссылка и ссылка-приглашение сами создают сессию, для них почта не нужна. Сессия — 30 дней, продлевается при использовании. Без SMTP вход возможен по одноразовой ссылке от админа (в интерфейсе пользователей или `cli login-link <email>`). Passkey — v2, OIDC — v2.
- **`proxy.ts`** проверяет только наличие cookie (`getSessionCookie`) — так рекомендуют и Next, и Better Auth. Полная проверка (`auth.api.getSession`) выполняется в layout групп маршрутов, в серверных функциях и route handlers.
- **Роли:** `superuser` (единственный, создаётся через claim) / `admin` (настройки) / `user`. Точечные гранты на модели и пункты каталога — v2 (D12).
- **Приглашения:** админ получает ссылку и копирует её. Если SMTP настроен — ссылка уходит и письмом.
- **Rate limit:** счётчики в Redis, лимиты по роли.

- **Оболочка — «Режимы»** (решено 2026-09-24, прототип `/dev/prototypes/app-shell`).
  - **Чат:** лёгкий плавающий сайдбар — новый чат, «Агенты» и «Входящие» (v2), история по дням; внизу аккаунт и шестерёнка.

Вход — ⌘, или шестерёнка, выход — Esc.

- `useChat` + `DefaultChatTransport` + `prepareSendMessagesRequest` (§6.1). Инпут управляется нами: в v7 из хука это убрали.
- `message.parts` рендерит диспетчер по типу части: `text` → markdown со стрим-достройкой, `reasoning` → сворачиваемый блок, `tool-*` → карточка вызова или виджет, `file` → вложение.
- TanStack Query отвечает за состояние сервера в настройках. Сам чат живёт в `useChat` и в Query не дублируется.
- TanStack Form + Zod — формы; схемы общие с сервером.
- TanStack Hotkeys — клавиатура (UX-принцип 7). `nuqs` — вкладки, фильтры и периоды в настройках и usage.
- `motion` — переходы; «прилипание» ленты к низу делаем готовой библиотекой.

## 14. Эксплуатация

- **Обновление:** новый образ → `docker compose up -d`, миграции применит entrypoint.
- **Бэкапы:** `pg_dump` и копия S3-бакета. Скрипт `install.sh backup` — v2. Без `SECRETS_KEY` бэкап ключей бесполезен, и `install.sh` предупреждает об этом при генерации.
- **Health:** `GET /api/health` проверяет БД, Redis и S3; используется в healthcheck compose.
- **Логи:** stdout в JSON; claim-ссылка печатается отдельной заметной строкой.

## 15. Компромиссы

| Решение | Цена | Почему |
| --- | --- | --- |
| Один инстанс `app` | нет горизонтального масштабирования | простая отмена, MCP-клиенты в памяти, честность |
| Без мастера, инфраструктура в compose | один шаг в терминале | нет проблемы «курицы и яйца», DDL не идёт через HTTP, первый визит нельзя перехватить |
| Линейная история | варианты ответа теряются | путь шаблона, простота |
| `parts` в формате AI SDK | миграции при мажорных апгрейдах `ai` | нет конвертера и рассинхрона форматов |
| Плоский спек виджета | нет произвольных дашбордов от модели | типизация, стрим, стабильное качество |
| Валюты без конвертации | нельзя одной цифрой «всего потрачено» | не выдумываем курсы |
| Только allow-правила | нельзя запретить конкретному человеку | предсказуемость |
| Права агентов как у Claude | prompt injection из прочитанных данных может привести к записи от имени владельца | агент реально работает сам, без постоянных «одобрите» |
| Расписания в Postgres, BullMQ только исполняет | тик раз в минуту — точность запуска до минуты | расписания попадают в бэкапы и не теряются вместе с Redis |
| Секреты шифруются мастер-ключом сервера, а не ключом от пароля пользователя | владелец сервера технически может прочитать любой секрет | иначе агенты не работают, пока пользователь не залогинен (ставка №5) |

## 16. Фоновые агенты — v2

**Агент** — это чат, который работает без пользователя: инструкции + модель + инструменты владельца + расписание + куда слать результат. **Запуск** — обычный чат `kind='agent_run'` с теми же частями, виджетами и карточками тулов. Его можно открыть и продолжить разговор.

### 16.1 Создание

- **Фразой в чате.** Модель вызывает встроенный тул `create_agent`, он возвращает черновик. Пользователь видит карточку: что агент делает, когда (словами и ближайшие три запуска), какими инструментами, куда шлёт результат. Кнопка «Создать».
- **Cron предлагает модель, а даты ближайших запусков считает сервер** (`cron-parser`). Арифметике дат от модели не доверяем.
- **«Сделать регулярным»** на любом чате собирает инструкции агента из этого разговора.
- Часовой пояс берётся из браузера в момент создания.

### 16.1a Изменение

Агент меняется так же, как создаётся — словами. Модель вызывает встроенный тул `update_agent({ agentId, patch })`, он возвращает **черновик изменений, а не применяет их**. В ленте появляется карточка «было → стало»:

- инструкции — diff по смыслу, а не по символам: «+ смотреть ещё в Jira», «− присылать всё → только срочное»;
- расписание — словами и ближайшие три запуска до и после;
- инструменты — что добавилось и что убралось;
- уведомления и лимиты — если менялись.

Кнопки: «Применить», «Применить и прогнать сейчас», «Отменить».

**Откуда можно менять:**

- **Из запуска.** Открываешь вчерашнюю сводку и пишешь «в следующий раз не включай рассылки». Модель отличает разовый вопрос по этому запуску от постоянного изменения и во втором случае предлагает карточку «запомнить для следующих запусков?». Молча агента она не меняет никогда.
- **Из оценки результата.** 👎 на запуске с комментарием («слишком длинно») превращается в предложение правки той же карточкой.
- **Со страницы агента.** Кнопка «Изменить» открывает чат, в контексте которого текущая конфигурация. Вкладка «Настройки» — обычная форма: редактор инструкций, расписание с подписью словами, список инструментов галочками.

**Версии и безопасность изменений:**

- Каждое применение создаёт запись `agent_versions` с кратким описанием изменения. Каждый запуск знает свою версию (`agent_runs.agent_version`), поэтому видно, какая настройка дала какой результат.
- На странице агента есть история версий с кнопкой «откатить к этой».
- **Тестовый прогон** (`trigger = 'test'`) запускает агента с новой версией сразу. Результат приходит только во входящие, без push и email, и не считается в счётчик сбоев.
- Если в момент изменения идёт запуск, он доигрывается на старой версии, а новая действует со следующего. При смене расписания `next_run_at` пересчитывается сразу.
- Менять агента может только владелец. Админ может поставить чужого агента на паузу, но не менять его.

### 16.2 Запуск по расписанию

```
BullMQ job scheduler «agents-dispatch», cron * * * * * — один на всё приложение
│
├─ тик раз в минуту в worker (если не стоит policies.agentsPaused):
│    BEGIN
│      SELECT id, cron, timezone, next_run_at FROM agents
│      WHERE enabled AND next_run_at <= now()
│      FOR UPDATE SKIP LOCKED              -- два тика не возьмут одного агента
│      → для каждого в JS: scheduledFor = next_run_at;
│        next = cronParser(cron, { tz: timezone, currentDate: now() }).next()
│        UPDATE agents SET next_run_at = next WHERE id = …
│    COMMIT
│    → queue.add('agent-run', { agentId, scheduledFor },
│                { jobId: `${agentId}-${scheduledFor.getTime()}` })   -- без «:», см. ниже
│    → тот же тик рассылает созревшие дайджесты уведомлений (§16.5)
│
└─ обработчик 'agent-run' (concurrency ограничена, в том числе под квоты провайдеров):
     1. создаёт agent_run и chat(kind='agent_run')
     2. проверка готовности:
        · нужного подключения нет или оно needs_reauth → outcome needs_attention + форма во входящих (§17.7), сбоем не считается
        · сервер не отвечает, ошибка сети → status failed с понятной причиной
     3. собирает тулы так же, как чат (§6.1): подключения владельца + встроенные
     4. ToolLoopAgent с лимитами шагов, стоимости и времени, abortSignal
     5. сохраняет сообщения; запуск обязан закончиться тулом report({ outcome, summary })
     6. запись во входящие и рассылка по каналам согласно notify_policy (§16.5)
     7. после 5 сбоев (failed) подряд агент встаёт на паузу, владелец получает алерт
```

`next_run_at` считается в JS (`cron-parser` с часовым поясом агента), а не в SQL: Postgres не умеет вычислять cron. В custom jobId BullMQ, насколько известно, нельзя использовать `:`, поэтому разделитель `-` — **проверить** при реализации.

Почему так:

- **Источник правды для расписаний — Postgres, а не Redis.** Расписания попадают в бэкапы, «ближайшие запуски» читаются из одного места, а потеря Redis не стирает агентов. BullMQ только исполняет.
- **Пропущенные запуски.** Если сервер лежал ночь, `next_run_at` окажется в прошлом, и будет **ровно один** догоняющий запуск, а следующий посчитается от текущего момента. Никакой лавины из 12 запусков утром.
- **Дубли.** `jobId` из id агента и времени запуска не даёт одному тику запустить агента дважды.
- **Не велосипед.** Так же eve делает расписания, которые создают пользователи: строки в БД и один тик раз в минуту.
- **Ручной запуск.** «Запустить сейчас» ставит тот же джоб.
- **Вебхук (v3).** `POST /api/agents/:id/fire` с токеном, payload оборачивается как недоверенные данные.
- **Отмена.** Кнопка «остановить» → сигнал через Redis в `worker` → `worker.cancelJob(jobId)` (есть в BullMQ 6.x, отменяет только на своём инстансе воркера — поэтому сигнал) → `abortSignal`.

### 16.3 Права — как у Claude (D22)

- По умолчанию агенту доступны **все подключения владельца** (`connection_ids = null`), лишние убираются в карточке.
- Агент действует кредами владельца и **ничего не спрашивает** во время запуска.
- **Исключение — политика админа.** Тул с `approval_policy = 'ask'` (§8) и в запуске агента требует подтверждения: запуск получает статус `waiting_approval`, во входящих появляется Review. После ответа в очередь снова ставится `agent-run` с тем же `runId`: обработчик дописывает ответ на approval в сообщения запуска и продолжает `ToolLoopAgent` — состояние целиком лежит в сообщениях. `deny` скрывает тул. Права «как у Claude» — это умолчание для тулов без политики, а не обход решений админа.
- Страховка, которая не требует подтверждений:
  - лимиты шагов, стоимости и времени: владелец задаёт их у агента в пределах потолков админа (`policies.agentMax*`), минимальный интервал между запусками задаёт админ;
  - каждый запуск — открываемый чат, то есть полный журнал действий;
  - выключатель «пауза всех агентов»;
  - внешний ввод (payload вебхука) оборачивается как недоверенные данные, как у Claude.
- Осознанный риск: prompt injection из прочитанных писем или страниц может заставить агента что-то записать от имени владельца. Если это станет проблемой, у агента появится флаг «спрашивать перед записью». Approval-флоу в `ai@7` держится на сообщениях, поэтому ожидание подтверждения — просто сохранённый чат.

### 16.4 Интерфейс

Пять поверхностей. Как именно они выглядят, решают прототипы P11–P15.

**Сайдбар** — агенты видны постоянно, а не спрятаны в настройках:

- наверху пункт «Входящие» со счётчиком непрочитанного;
- секция «Агенты» под чатами: у каждого точка состояния (идёт запуск / ждёт / на паузе / ошибка).

**Входящие** (`/inbox`) — единая лента результатов по модели ambient agents от LangChain:

- **Notify** — «вот сводка»;
- **Question** — агенту нужен ответ или подключение (`outcome = needs_attention`);
- **Alert** — сбой или пауза: «агент остановлен после 5 ошибок: MCP-сервер не отвечает» → «проверить подключение»;
- **Review** — подтвердить действие: тул, которому админ поставил `ask` (§16.3), а позже — всё при флаге агента «спрашивать перед записью».

Карточка показывает агента, исход, 1–3 строки сводки и время, из неё можно сразу:

- открыть запуск;
- ответить — продолжение разговора в чате запуска;
- прочитать или архивировать;
- поставить агента на паузу.

Фильтры в URL через `nuqs`: непрочитанные, требуют внимания, по агенту. Группировка по дням. С клавиатуры: `j`/`k` — навигация, `e` — в архив, `Enter` — открыть.

**Агенты** (`/agents`) — карточки:

- имя и одна строка о том, что агент делает;
- расписание словами и обратный отсчёт до следующего запуска («через 2 ч 14 мин»);
- лента исходов последних запусков цветными точками: сделано / ничего нового / нужно внимание / сбой;
- переключатель вкл/выкл и «Запустить сейчас».

Пустое состояние — шаблоны («утренняя сводка», «следить за изменениями», «дайджест по теме») и поле «или опиши своими словами», которое создаёт агента фразой.

**Страница агента** (`/agents/[id]`):

- в шапке состояние, переключатель, «Запустить сейчас», «Изменить»;
- вкладки в URL:
  - **Запуски** — лента: исход, триггер, длительность, стоимость в валюте модели; клик открывает чат запуска;
  - **Настройки** — инструкции, расписание, инструменты, `notify_policy`, лимиты;
  - **Статистика** — доля успешных запусков, расходы по месяцам.

**Запуск** — обычный экран чата с плашкой: «Агент „Сводка“ · по расписанию · 09:00 · 42 с · 0,8 ₽». Уже работающий запуск в v2 показывается статусом с опросом. Живой стрим запуска — позже.

### 16.5 Уведомления

Каналы по нарастанию навязчивости. Пользователь выбирает их в `/settings/notifications`, у агента — `notify_policy`.

| Канал | Когда срабатывает | Как устроено |
| --- | --- | --- |
| **Входящие** | всегда | запись `inbox_items` |
| **В приложении** | вкладка открыта | `worker` публикует событие в Redis → `app` отдаёт его по SSE (`/api/notifications/stream`) → тост и обновление счётчика без перезагрузки. Если SSE не поднялся — опрос через TanStack Query |
| **Push браузера** | вкладка закрыта | Web Push: service worker + VAPID-ключи, которые генерирует `install.sh`. Нужен HTTPS (кроме localhost). На iPhone — только если приложение установлено на экран «Домой» — **проверить** (S9) |
| **Email** | по настройке, можно дайджестом | nodemailer + react-email, через очередь |
| **Telegram** | v3 | Vercel Chat SDK + `@chat-adapter/telegram`: уведомление с кнопками «открыть» и «ответить» |

**Правила против спама — это часть вау, а не ограничение:**

- по умолчанию `if_new`: «ничего нового» во входящие не попадает и не уведомляет;
- тихие часы: уведомления копятся и приходят утром одним сообщением;
- дайджест: вместо N писем — одно в заданное время;
- алерты о сбоях приходят всегда, но не чаще раза на агента за окно времени.

### 16.6 Исполнитель

Своё ядро: BullMQ + Postgres + `ToolLoopAgent`. Выполнение спрятано за `executeRun(runId)`. Если шаги станут долгими и дорогими для повтора, исполнитель переезжает на Workflow DevKit + Postgres World (`WorkflowAgent` из `@ai-sdk/workflow`), а остальное не меняется.

Сейчас не берём:

- **Workflow DevKit:** нужна beta-линейка 5.x, Postgres World в README назван «reference implementation», своего cron нет.
- **eve:** preview и отдельный рантайм со своими сессиями и auth. Оставляем как spike — у него интересная песочница, которая сама выбирает Docker или microsandbox.

## 17. Подключения и секреты

### 17.1 Кто что добавляет

|  | Админ (организация) | Пользователь |
| --- | --- | --- |
| MCP-серверы | каталог: URL, транспорт, разрешённые тулы, способ авторизации | подключается к серверу из каталога своими кредами; свой сервер — если админ разрешил (v2) |
| stdio MCP | только суперюзер (v3, D18) | нельзя |
| Скиллы | общие | личные (v2), плюс «сохранить как скилл» из чата |
| Встроенные коннекторы (почта и т.п.) | включает типы коннекторов, задаёт пресеты | подключает свои: сервер, порт, логин, пароль (§17.7) |
| Ключи провайдеров моделей | да | нет |

Креды сервера из каталога задаются одним из двух режимов:

- **`shared`** — один служебный токен на всех, например внутренний поиск по вики. Такой сервер доступен без личного подключения.
- **`per_user`** — каждый подключает свои креды. Так устроены 1С, где у каждого свои права, и GitHub. Для агентов (D22) это главный режим: агент действует кредами владельца.

**Свои подключения пользователя** — любого типа, не из каталога: свой MCP-сервер (v2), почта с хостом `custom`, `http_api` — регулируются политикой `personalConnections: 'off' | 'public_only' | 'on'`, по умолчанию `public_only`.

- Адреса из приватных диапазонов (`10.*`, `192.168.*`, `localhost` и т.п.) запрещены: иначе через наш сервер можно достучаться до внутренней сети (SSRF). Адрес проверяется после DNS-резолва и повторно при каждом соединении.
- **Через прокси проверка должна работать так же** (§18.4): адрес резолвится у нас, проверяется, и прокси получает уже **IP**, а не имя. Иначе прокси, который сам стоит во внутренней сети, разрешит имя по своему DNS и пустит запрос внутрь.
- `verify` при подключении ограничен по частоте, чтобы форма не превращалась в сканер портов.
- Внутренние системы — корпоративный SMTP, 1С, базы, внутренние API — админ добавляет в каталог. Каталог в v1 (M4).

Термины: **подключение к каталогу** — пользователь вводит свои креды к пункту, который завёл админ (`per_user`). **Своё подключение** — пользователь сам задаёт и адрес.

### 17.2 Хранение

Все секреты — ключи провайдеров, SMTP, токены MCP и OAuth — лежат в одной таблице:

```ts
secrets; // id, owner_type: 'system' | 'provider' | 'catalog_item' | 'connection' | 'search_backend' | 'proxy'
//   (| 'agent' — токен вебхука, v3), owner_id
// purpose: 'api_key' | 'password' | 'token' | 'headers' | 'oauth_access' | 'oauth_refresh' | …
// связь владелец → секреты идёт через (owner_type, owner_id), массивов id нет
// ciphertext, iv, auth_tag, key_version
// hint ('sk-…a1B2'), expires_at?, created_at, rotated_at, last_used_at
```

- **Шифрование:** AES-256-GCM из `node:crypto`, случайный IV на каждую запись.
- **AAD = `owner_type:owner_id:purpose`.** Шифртекст привязан к своей строке: если в БД скопировать чужой токен в свою запись, расшифровка просто упадёт.
- **Мастер-ключ `SECRETS_KEY`** хранится только в env, никогда в БД.
- **Ротация:** на время смены ключа задаётся `SECRETS_KEY_PREVIOUS` и `key_version`. `purr secrets:rotate` перешифровывает всё и сообщает, когда старый ключ можно убрать.
- **Canary.** При установке в `system_settings` пишется зашифрованная контрольная строка. При старте приложение её расшифровывает. Если не вышло, оно отказывается стартовать с понятным сообщением «SECRETS_KEY не совпадает с ключом установки». Иначе с чужим ключом начнут писаться новые секреты, и база окажется зашифрована двумя ключами вперемешку.
- **Одна точка чтения:** `secrets.use(id, fn)` расшифровывает значение прямо перед использованием и обновляет `last_used_at`. В памяти секрет живёт только внутри инстансов провайдеров и MCP-клиентов. При изменении событие `config:changed` через Redis сбрасывает кеш в обоих процессах (`app` и `worker`).

### 17.3 Куда секрет не попадает

- **В клиент.** API write-only: секрет можно задать или заменить, но не прочитать. Интерфейс видит только `hint` и статус.
- **В модель — никогда.** Креды уходят в заголовки транспорта, а не в промпт и не в результаты тулов. Ошибки тулов перед показом модели проходят маскирование: заголовки и query-параметры вроде `token` и `key` вырезаются. Поэтому prompt injection не может «попросить» ключ — модель его просто не видит.
- **В логи.** Логгер маскирует `authorization`, `apiKey`, `token`, `password`.
- **В бэкап в открытом виде.** Дамп БД содержит только шифртекст, без `SECRETS_KEY` он бесполезен (§14).

### 17.4 OAuth для MCP — v2

Многие публичные MCP-серверы (GitHub, Linear, Notion и т.п.) авторизуются через OAuth 2.1 с PKCE по спецификации MCP. Поток:

1. кнопка «Подключить» открывает окно авторизации;
2. callback приходит на `/api/oauth/callback?state=…` — по `state` находится поток в `oauth_flows`, а через него пункт каталога или своё подключение;
3. токены сохраняются в `secrets`, PKCE-состояние — в `oauth_flows`.

В `@ai-sdk/mcp` для этого есть `authProvider` — реализуем его поверх нашей БД и обновляем токен по `expires_at` перед вызовом. Точный интерфейс — **проверить** (S10).

Refresh выполняется **под блокировкой на подключение** (Redis lock): `app` и `worker` могут одновременно захотеть обновить один токен, а при ротации refresh-токенов второй запрос получил бы отказ и перевёл подключение в `needs_reauth` на ровном месте.

Если токен истёк или отозван, подключение переходит в статус `needs_reauth`. Агенты владельца присылают алерт «переподключите GitHub» (§16.5), в чате появляется инлайн-карточка.

### 17.5 Модель угроз

**Защищаемся от утечки** через интерфейс и API, через дамп БД и бэкапы, через логи, через модель.

**Не защищаемся от владельца сервера.** В self-hosted у того, кто держит `SECRETS_KEY` и доступ к серверу, технически есть все секреты. Это закрыло бы шифрование ключом от пароля пользователя, но тогда агенты не смогут работать, пока пользователь не залогинен, — а это ломает ставку №5. Вариант отвергнут.

**Внешние хранилища** (Vault/OpenBao, Infisical) — адаптер позже, если его потребует корпоративная безопасность. По умолчанию хранилище своё, чтобы установка оставалась в одну команду.

### 17.6 Интерфейс

- **`/settings/connections` — «Мои подключения».**
  - Каталог организации с кнопкой «Подключить».
  - Статус каждого подключения: работает / нужно переподключить / ошибка.
  - Когда подключение использовалось последний раз, и кнопка «Отключить».
  - «Добавить своё подключение» — если политика разрешает; свой MCP-сервер — v2.
- **Подключение прямо из чата.** В инструкции модели передаётся список серверов из каталога, которые пользователь ещё не подключил. Если модели нужен один из них, встроенный тул `request_connection` рисует в ленте карточку «Подключите 1С, чтобы продолжить» с кнопкой. Точный вид — прототип P8.
- **Поле секрета** умеет только «задать» и «заменить» и показывает маску вроде `sk-…a1B2`.
  - Это не пароль, и браузер не должен его так понимать. `type="password"` зовёт автозаполнение (Связка ключей iCloud, 1Password, Chrome), поэтому поле — `type="text"` с маской CSS `-webkit-text-security: disc`, `autocomplete="off"` и атрибутами-исключениями менеджеров паролей (`data-1p-ignore`, `data-lpignore`, `data-bwignore`, `data-form-type="other"`). То же для адресов прокси и прочих полей подключений. Проверено в прототипе P7; в M2 — компонент `SecretInput` в `@purr/ui`.

### 17.7 Коннекторы и запрос данных у пользователя

Не всё, чем агент работает, — MCP. Почта по SMTP/IMAP — встроенный **коннектор**: у него есть описание полей, проверка и свои тулы.

```ts
connectorTypes.email = {
  fields: z.object({
    preset: z.enum(['yandex', 'gmail', 'mailru', 'outlook', 'custom']),
    host, port, security: z.enum(['ssl', 'starttls', 'none']),
    username, from,
    password: secret(),                     // secret() → в `secrets`, остальное → `connections.config`
  }),
  presets: { yandex: { host: 'smtp.yandex.ru', port: 465, security: 'ssl', hint: 'нужен пароль приложения' }, … },
  verify: (c) => transporter.verify(),      // nodemailer: проверить соединение до сохранения
  tools: ['email_send'],                     // + 'email_search' через IMAP — позже
}
```

У MCP-серверов из каталога с `per_user` тот же механизм: поля задаёт админ в `connection_fields`.

**Типы коннекторов.** Правило: встроенный коннектор делается для **протокола**, а не для конкретного сервиса. Сервисы (GitHub, Notion, Bitrix24, amoCRM, Яндекс 360, Jira…) подключаются как MCP из каталога — поддерживать свой адаптер к каждому API бесконечно.

| type | Поля | Тулы агента | Проверка | Когда |
| --- | --- | --- | --- | --- |
| `mcp` | `connection_fields` пункта каталога; OAuth — v2 | тулы сервера | `client.tools()` | v1 |
| `email` | пресет, SMTP-хост, порт, SSL/STARTTLS, логин, пароль | `email_send` | `verify()` | v1 |
| `http_api` | base URL, авторизация (bearer / заголовок / basic / query), OpenAPI-спека по желанию | тул на каждую операцию из спеки, иначе общий `http_request` | тестовый запрос | v1 |
| `database` | тип (Postgres / MySQL / MSSQL / ClickHouse), хост, порт, база, логин, пароль, SSL | `sql_query` — только чтение, таймаут, лимит строк | `SELECT 1` | v2 |
| `email` + IMAP | те же поля + IMAP-хост | `email_search`, `email_read` | вход по IMAP | v2 |
| `telegram_bot` | токен бота, chat id | `telegram_send` | `getMe` | v2 |
| `webhook_out` | URL, секрет | `webhook_send` (Slack, Teams, n8n, Discord) | тестовая отправка | v2 |
| CalDAV / CardDAV | сервер, логин, пароль | календарь, контакты | вход | позже |
| S3 / WebDAV / Яндекс Диск | endpoint, ключи | список, чтение, запись файлов | листинг | позже |

- **`http_api`** закрывает всё, у чего нет MCP: 1С через HTTP-сервисы или OData, внутренние API. Для 1С — пресет «OData 1С»: адрес базы и логин.
- **`database`** работает на ставку №2: «покажи продажи графиком» = `sql_query` + виджет (§9.2). По умолчанию только чтение. Форма рекомендует отдельного пользователя БД с правами на чтение.
- **Не делаем:** `ssh` и «выполнить команду» — это песочница (v3), не коннектор.
- **Внутренняя сеть.** `database` и `http_api` обычно смотрят во внутреннюю сеть, а личным подключениям приватные адреса запрещены (§17.1). Поэтому такие подключения админ добавляет в каталог с `per_user`: адрес задаёт он, а логин и пароль каждый вводит свои в той же форме.

**Как агент спрашивает данные — кейс «хочу, чтобы агент отправлял почту»:**

1. Модель видит, что для задачи нужен коннектор `email`, а у пользователя его нет. Она вызывает встроенный тул `request_connection({ type: 'email', reason: 'чтобы отправлять сводку' })`.
2. У тула **нет `execute`** — это human-in-the-loop на клиенте. Генерация останавливается, в ленте появляется **карточка-форма**:
   - выбор почты (Яндекс / Gmail / Mail.ru / Outlook / своя) — хост, порт и шифрование заполняются сами;
   - для Яндекса подсказка «нужен пароль приложения» со ссылкой на настройку;
   - логин и пароль (поле маскируется), кнопка «Проверить и подключить».
3. **Значения уходят из браузера прямо в `POST /api/connections`, минуя модель.** Сервер проверяет соединение (`verify`), пароль кладёт в `secrets`, остальное — в `config`.
4. Клиент отвечает на вызов тула через `addToolOutput` только сводкой: `{ status: 'connected', connectionId, summary: 'smtp.yandex.ru:465 SSL, ivan@…' }`. Пароля нет ни в истории, ни в контексте модели. Диалог продолжается сам (`sendAutomaticallyWhen`).
5. Ошибка проверки («неверный пароль», «порт закрыт») показывается прямо в карточке с подсказкой — пользователь исправляет, не выходя из чата.

**Если пароль всё-таки ввели в сообщение**, composer до отправки подсвечивает похожее на пароль и предлагает «подключить через форму». То, что уже ушло модели, из её контекста не вернуть — поэтому предупреждаем до отправки, а не после.

**Фоновый агент** показать форму не может, пользователя рядом нет. Он заканчивает запуск с `outcome: 'needs_attention'`, во входящих появляется «Агенту „Сводка“ нужно подключение почты» с той же формой. После подключения следующий запуск идёт уже с ним, есть и кнопка «повторить сейчас».

Тот же путь есть без чата: «Мои подключения» → «Добавить» → выбор типа → та же форма.

## 18. Прокси

Сети с ограничениями — ставка №3. Прокси — не поле в настройках провайдера, а отдельная сущность в админке: их может быть несколько, и у каждого вида исходящего трафика свой маршрут.

### 18.1 Прокси

`/settings/proxies` — список прокси. У каждого:

- тип: `http`, `https`, `socks5`, `socks5h` (у `socks5h` DNS разрешается на стороне прокси — нужно, когда блокируют и DNS);
- хост, порт, логин; пароль — в `secrets`;
- кнопка **«Проверить»**: запрос через прокси показывает внешний IP, страну и задержку. Результат сохраняется и виден в списке.

Первый прокси можно задать ещё при установке: `install.sh` спрашивает «нужен исходящий прокси?», а entrypoint при первом старте превращает `HTTPS_PROXY` / `ALL_PROXY` в запись в админке, ничего к ней не привязывая. Тот же ответ `install.sh` записывает в `settings.yml` SearXNG. Дальше прокси приложения живёт только в админке, прокси SearXNG меняется повторным запуском `install.sh`.

### 18.2 Что через что ходит

**Главное правило: по умолчанию всё идёт напрямую.** Прокси не «включается для категории»: админ отмечает у конкретного прокси, что именно через него ходит. Так нельзя случайно загнать в прокси Яндекс только потому, что он тоже «провайдер моделей».

**Внутренние сервисы compose** — Postgres, Redis, S3, SearXNG — не ходят через прокси никогда. Это не настраивается.

У каждого прокси — список «что через меня ходит», из двух частей:

1. **Объекты** — галочки по списку того, что уже заведено:
   - провайдеры моделей: ☑ OpenAI, ☑ Anthropic, ☐ Yandex AI Studio;
   - пункты каталога — MCP-серверы и коннекторы;
   - бэкенды поиска.
2. **Домены** — для трафика, у которого нет объекта:
   - чтение страниц моделью (`web_fetch`) на произвольные сайты;
   - свои подключения пользователей: почта `smtp.gmail.com`, их `http_api`;
   - доставка Web Push (`fcm.googleapis.com`, `push.apple.com`).

   Домен покрывает поддомены — как в PAC-файле или `proxyctl`.

Те же данные видны и с другой стороны: в форме провайдера или пункта каталога есть поле «Прокси» со значениями «авто» (по доменам), «напрямую» или «через X». Два вида одного поля, а не две настройки.

**Как выбирается маршрут** для конкретного запроса:

1. у объекта явно выбран прокси или «напрямую» → так и идёт;
2. объект на «авто» или его нет → ищется прокси, в доменах которого есть адрес назначения;
3. ничего не нашлось → **напрямую**.

Если адрес подходит под домены двух прокси, побеждает более точный домен (`api.openai.com` точнее, чем `openai.com`). При равенстве форма не даёт сохранить конфликт.

**SearXNG** ходит в поисковики из своего контейнера. Его прокси задаётся в `settings.yml` (`outgoing.proxies`) при установке. В админке он показывается только для чтения: сменить его без перезапуска контейнера нельзя, а управлять Docker из приложения мы не даём (D3). Поддержку SOCKS5 в SearXNG — **проверить** (S8).

### 18.3 Удобство

- **Прокси подбирается сам, когда нужен.** При добавлении провайдера ключ сначала проверяется напрямую. Если упало по сети или на гео-блоке, та же проверка автоматически прогоняется через каждый включённый прокси, и в форме появляется: «Напрямую OpenAI недоступен, через „Корп-прокси“ работает — использовать?». Одна кнопка, без похода в настройки прокси. Если прокси ещё нет (свежая установка, в `install.sh` его не задали), подобрать нечего: форма честно говорит «ключ подошёл, но провайдер из этой сети не отвечает» и предлагает ввести адрес прокси прямо здесь или взять провайдера, доступного напрямую. Введённый прокси проверяется и сохраняется первой записью в «Прокси», через него идёт только этот провайдер.
- **Подсказка при создании прокси.** «Обычно через прокси ходят OpenAI, Anthropic, Google — отметить те, что у вас заведены?». Это подсказка, а не умолчание: ничего не отмечается само.
- **Прозрачность.** На странице прокси видно, что через него ходит и сколько запросов за сутки прошло и упало. В списке провайдеров у каждого значок маршрута: напрямую или через какой прокси.
- **Честные ошибки.** Если прокси перестал отвечать, объекты на нём получают ошибку «прокси X недоступен», а не таймаут модели. Админ получает алерт.

### 18.4 Реализация

- **HTTP/HTTPS** — `undici` `ProxyAgent` как dispatcher у `fetch`. «Напрямую» — явный `Agent`, а не глобальный dispatcher: так `HTTPS_PROXY` из окружения никуда не просачивается.
- **SOCKS5** — свой коннектор для `undici` `Agent` на пакете `socks` и `buildConnector` (S4). `fetch-socks` не берём: он тянет второй мажор undici. У `socks5h` имя уходит в прокси, у `socks5` резолвим сами.
- **SMTP через прокси** — `nodemailer`, опция `proxy`: `socks5://` (с `proxy_socks_module`) и `http://` через `CONNECT` (S4).
- **Web Push через прокси** — опция `proxy` у библиотеки `web-push` — **проверить** (S9).
- Dispatcher'ы кешируются на прокси и сбрасываются по `config:changed`, как провайдеры (§7.1).
- **SSRF-проверка (§17.1) применяется к адресу назначения, а не к прокси.** Сам прокси обычно во внутренней сети — это нормально, его задал админ.
- **Трафик с SSRF-защитой** (`web_fetch`, свои подключения пользователей) идёт через прокси только с закреплённым IP: мы сами резолвим имя, проверяем адрес и открываем туннель (`CONNECT` / SOCKS5) на этот IP, а имя передаём только в `Host` и TLS SNI. `socks5h` для такого трафика запрещён: при нём имя разрешает прокси, и проверка теряет смысл. Как именно: свой коннектор — `dns.lookup` → проверка → туннель на IP (`Client.connect` у HTTP-прокси, `SocksClient` у SOCKS) → TLS через `buildConnector` с SNI по имени (S4). Для SMTP пользователей — то же через `host: IP` + `tls.servername` или `getSocket` в nodemailer; это M4. Каталог админа и провайдеры под это правило не попадают: их адреса задал админ.
- Прокси — только админский ресурс. Свои подключения пользователей идут через прокси по его доменам, иначе напрямую; выбирать прокси пользователь не может.
- Счётчики «сколько запросов прошло и упало» хранятся в Redis поминутно за последние сутки — для экрана прокси этого достаточно, в Postgres их не пишем.
