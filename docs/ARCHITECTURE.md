# Архитектура

> Версия 2 — переписана после разбора первой версии. Спорные решения и их статусы — в [DECISIONS.md](DECISIONS.md), этапы и прототипы — в [PLAN.md](PLAN.md).
>
> Сверено с `ai@7.0.109` (локальные `docs/` и `src/`), `@ai-sdk/openai-compatible@3.0.53`, шаблоном [`vercel/chatbot`](https://github.com/vercel/chatbot) @ `main`, документацией Next.js 16, Better Auth и Yandex AI Studio. Непроверенное помечено **проверить** или **spike**.

## 0. Продукт

Self-hosted AI-рабочее место для команды. Инфраструктура описана в `docker compose`, а всё содержательное — источники, модели, цены, MCP, скиллы, пользователи — настраивается в интерфейсе после установки.

### Ставки

То, ради чего продукт существует рядом с Open WebUI и LibreChat. Если ставка не подтверждается, её функциональность режется первой.

1. **Установка и первый ответ за 2 минуты.** Одна команда в терминале, одна ссылка в браузере, вставленный ключ — и уже идёт переписка.
2. **Генеративный UI.** Графики, таблицы и метрики строятся по живым данным тулов, модель цифры не переписывает.
3. **Работа в сетях с ограничениями.** Yandex AI Studio из коробки, прокси HTTP и SOCKS5 в админке: всё ходит напрямую, через прокси — только то, что админ явно отметил (§18).
4. **MCP и скиллы как основа, а не плагины.**
5. **Периодические задачи.** Поручение, которое запускается по расписанию твоими инструментами; итог — на странице задачи и, если включено, на почту; «нового нет» не беспокоит (§16, D38).
6. **Память.** Metobe помнит людей, обещания и проекты из разговоров и утром предлагает, что сделать; запись тихая, тексты зашифрованы, без модели «Память» в «Служебных моделях» всё выключено (§19, D39).

### UX-принципы

Это правила, по которым принимается каждое UI-решение. Спорные экраны проверяются прототипом до реализации (PLAN.md, раздел «Прототипы»).

1. **Метрика №1 — время до первого ответа.** Весь путь от `install.sh` до первого сообщения проходится без правки конфигов.
2. **Пустой экран — это действие.** Нет источников → чата нет, первый вход ведёт на настройки источников (P1). Нет MCP → карточка «подключите первый сервер» с примером.
3. **Ничего не молчит дольше секунды.** Вместо спиннера — фаза работы: «думает», «читает файл X», «спрашивает GitHub», «ждёт Яндекс».
4. **Ошибка = что случилось + почему + что сделать.** Для 429 — автоповтор с обратным отсчётом. Стектрейсы пользователь не видит никогда.
5. **Проверка в момент ввода.** Ключ источника проверяется при вставке, MCP-сервер сразу показывает список своих тулов.
6. **Мгновенная реакция.** Оптимистичный UI, стрим без прыжков вёрстки, скелет виджета появляется ещё до прихода данных.
7. **Клавиатура наравне с мышью.** `⌘K` — палитра команд, `⌘/` — выбор модели, `Esc` — стоп, `↑` — редактировать последнее.
8. **Движение со смыслом.** Анимация показывает, откуда элемент пришёл и куда ушёл (виджет → панель артефакта). `prefers-reduced-motion` соблюдается.
9. **Обратимость.** Опасное подтверждается, разрушительное по возможности отменяется.

## 1. Границы

- **Один инстанс `app`.** Отмена генерации, MCP-клиенты и реестр стримов живут в памяти процесса. Горизонтального масштабирования нет, и мы его не имитируем (D2). Периодические задачи выполняются в отдельном процессе `worker` из того же образа, чтобы тяжёлые запуски не тормозили чат (§16).
- **Self-hosted, долгоживущий Node-процесс** в Docker, не serverless.
- **Организации и две схемы (D48, D49, §20, §21) — в работе.** Сейчас одна установка — одна команда с ролями. Дальше в установке живёт одна или несколько организаций. Облако — много организаций, тарифы мест, лимиты в деньгах и счета, ключи моделей наши. Self-hosted — сервер клиента с одной организацией, лицензией от главного узла и лимитами, которые задаёт админ клиента. План и этапы — [ORGS-PLAN.md](ORGS-PLAN.md).
- **Линейная история сообщений**, как в `vercel/chatbot`.

## 2. Инфраструктура и установка

### 2.1 Compose

```
app        Next.js standalone: UI, API, генерация, MCP-клиенты
worker     тот же образ: периодические задачи, диспетчер расписаний, email — v2
           (до этого очереди обрабатываются внутри app)
postgres   основная БД                                  (или внешняя по DATABASE_URL)
redis      config:changed между процессами, rate limit, очереди BullMQ (resume стримов — в памяти процесса, D5)
s3         профиль s3: SeaweedFS в режиме S3 — spike (D4)   (или внешний S3 по S3_*)
searxng    профиль search: веб-поиск (§8.1)
mailpit    только в dev-профиле: перехват писем
updater    профиль updater, тот же образ: обновление из приложения, единственный с docker.sock (D35)
           app читает том backups только для защищённого скачивания администратором; updater — его writer
sandbox    профиль compose, выключен по умолчанию — v3 (D3)
```

MinIO не используем: репозиторий архивирован, в README написано «NO LONGER MAINTAINED» (D4).

### 2.2 Установка без мастера

Мастер в браузере отменён (D1). Всё, без чего приложение не может стартовать, решается до старта:

```
./install.sh
  1. проверяет docker и compose
  2. задаёт 3 вопроса с дефолтами: адрес (домен/порт), БД встроенная или своя, S3 встроенный или свой
  3. генерирует .env: SECRETS_KEY, BETTER_AUTH_SECRET, пароли postgres и s3, VAPID-ключи для push-уведомлений
     + необязательный вопрос «нужен исходящий прокси?» → HTTPS_PROXY / ALL_PROXY (§18)
     + необязательный вопрос «настроить почту сейчас?» → SMTP_* (при первом старте переносится в настройки, как прокси); без почты вход по ссылкам от админа
     → крупно печатает: «сохраните SECRETS_KEY — без него ключи источников не восстановить»
  4. docker compose up -d, ждёт healthcheck
  5. печатает адрес и одноразовую claim-ссылку
```

Для автоматизации есть неинтерактивный режим: те же ответы передаются переменными окружения.

**Entrypoint `app`** при каждом старте:

1. применяет миграции под `pg_advisory_lock` (два процесса не мигрируют одновременно);
2. обновляет seed-справочники: провайдеры и известные модели с ценами и возможностями;
3. если суперюзера ещё нет — выпускает claim-токен (в БД хранится хэш, TTL 24 ч) и печатает ссылку в лог;
4. запускает сервер.

Потерянную ссылку можно перевыпустить: `docker compose exec app metobe claim-link`.

**В браузере** остаётся один экран: `/claim?token=…` → «Создать аккаунт» (имя и email, пароля нет — D17). Claim-ссылка сама создаёт сессию, поэтому для первого входа почта не нужна. После этого экрана пользователь попадает в настройки источников. Чат открывается, когда подключён хотя бы один источник с включённой моделью: без моделей в нём нечего делать (P1, вид — P7).

### 2.3 Что где настраивается

| `.env` (инфраструктура, до старта) | БД через UI (данные, после старта) |
| --- | --- |
| `DATABASE_URL`, `REDIS_URL`, `S3_*`, `APP_URL` | источники, ключи, модели, цены |
| `SECRETS_KEY`, `BETTER_AUTH_SECRET` | MCP-серверы, скиллы |
| `HTTPS_PROXY` / `ALL_PROXY` — стартовый прокси: при первом запуске превращается в запись в админке | прокси и что через каждый ходит (§18) |
| `SMTP_URL` / `SMTP_FROM` — стартовая почта: при первом запуске превращается в настройки «Почта» | пользователи, роли, лимиты, почта сервиса |

Почта сервиса живёт в UI (D15, `/settings/mail`): для старта она не нужна, приглашения работают и без неё, а в UI её удобно проверить кнопкой «Отправить себе».

## 5. Модель данных

### 5.1 Система и пользователи

```ts
system_settings; // синглтон: secrets_canary; пароль почты сервиса — secrets (owner_type = 'system', owner_id = 'mail', purpose = 'password')
// policies jsonb: { personalConnections: 'off'|'public_only'|'on',
//   taskMinIntervalMin, tasksPaused, taskMaxSteps, taskMaxCost, taskMaxTimeoutS,
//   rateLimits: { [role]: … },
//   builtinTools: { web_search, web_fetch, … : bool },
//   mail: { preset, smtp, address, name, username, check } | null — почта сервиса (D15); null — админ её отключил,
//     и SMTP_URL установки её больше не возвращает,
//   personalApprovalDefaults: { [connectorTool]: 'auto'|'ask' } — для своих подключений (§8) }
users; // Better Auth + role: 'superuser' | 'admin' | 'user', timezone (из браузера)
(sessions, accounts, verifications); // Better Auth
claim_tokens; // token_hash, expires_at, used_at

```

С организациями (§20.4) у `users` появляются организация, роль в ней, тариф и отметка «отключён платформой». У приглашений — организация и тариф места. Организационные части `policies` переезжают в `organizations.settings`.

### 5.2 Источники и модели

```ts
sources; // kind: 'openai'|'anthropic'|'openai-compatible'|'yandex'|'gateway'
// title, logo? (своя картинка админа), base_url, enabled; ключ — secrets (owner_type = 'source', purpose = 'api_key', §17)
// health jsonb — последняя настоящая проверка: state, checked_at, latency_ms, error
// options jsonb — Zod discriminated union по kind:
//   yandex: folderId
// proxy_mode: 'auto' | 'direct' | 'proxy', proxy_id? (§18)
providers; // кто сделал модель: openai, anthropic, google, alibaba, deepseek, xai, yandex… (D29)
// slug, title, logo — ключ встроенного значка или своя картинка в S3; title и logo правит админ,
// edited = true — синк их больше не перетирает; slug 'other' — для неузнанных
models; // source_id (CASCADE), provider_id (RESTRICT), model_id, title, enabled (по умолчанию false), default_access, released_at
// original_title — название от источника, пока в title стоит название админа; null — не переименована
// context_window, capabilities jsonb,
// capabilities_source: 'discovered' | 'seed' | 'manual'
// price_input / price_output / price_cache_read / price_cache_write — как ввёл админ или сообщил источник,
// за price_unit_tokens токенов (любое число: 1, 1000, 1M), price_currency; numeric без ограничения точности
model_slots; // slot ('titles', дальше — картинки, сжатие, поиск) → model_id (SET NULL): служебные модели вне чата
model_runs; // chat_id (SET NULL, ключ появится с таблицей чатов), user_id (SET NULL), model_id (SET NULL),
// input / output / cache_read / cache_write tokens, cost (точный numeric), currency, latency_ms, status
```

- **Источник и провайдер — разные сущности (D29).** Источник даёт доступ (ключ, маршрут, здоровье), провайдер сделал модель (название, логотип в чате). Через один источник — модели многих провайдеров (Gateway, Яндекс с Qwen и DeepSeek), один провайдер — через разные источники (Claude и по ключу Anthropic, и через Gateway).
- **Провайдер модели определяется сам:** у Gateway — по префиксу id (`anthropic/…`) и `owned_by`, у прямых ключей — по источнику, у Яндекса и `openai-compatible` — по seed-справочнику имён (`qwen*` → Alibaba, `deepseek*` → DeepSeek, `llama*` → Meta). Не угадали — модель попадает к провайдеру «Другие», админ переназначает.
- `capabilities`: `null` — «источник не сообщил», `false` — «точно нет». От этого зависит, деградировать функциональность или падать (§7.3).
- **Возможности и контекст — от самого источника:** у Gateway — теги `/v1/models`, у Anthropic — `capabilities` и `max_input_tokens` в `/v1/models`, у Ollama — `/api/show` на каждую модель (с учётом `num_ctx`, если админ урезал контекст), у Яндекса — только инструменты (проверены в S3), у OpenAI и прочих OpenAI-совместимых — «неизвестно». Внешних справочников (models.dev и т. п.) нет: новый релиз не нужен, чтобы появилась новая модель, и сведения не устаревают.
- Источники значений: `discovered` пришло от источника; `seed` — наше проверенное знание (инструменты у Яндекса); `manual` — правка админа, синк её не перетирает.
- **Синк** добавляет новые модели выключенными и обновляет у существующих название, провайдера, возможности, контекст и дату; не трогает `enabled`, `default_access`, ручные возможности и цены, введённые админом.
- **Название модели правит админ** (карточка модели в «Источниках»), чтобы в выборе модели было «DeepSeek 4.1 Flash», а не `deepseek/deepseek-v4.1-flash`. Своё название пишется в `title`, а название источника откладывается в `original_title`: синк обновляет только его и `title` не трогает; «Вернуть» кладёт название источника обратно. Переименование в то же имя, что у источника, — не переименование. Все места чтения по-прежнему читают `title`. Модели, которые источник перестал отдавать, не удаляются — синк сообщает их списком.
- **Цены** — вход, выход, чтение из кеша, запись в кеш — хранятся как ввели, за любую единицу токенов, в своей валюте. Ни нормализации, ни округления: стоимость считается точной арифметикой (`core/pricing`, BigInt), поэтому крошечные цены за токен не превращаются в нули. Цены сообщает только Gateway (за 1 токен); у остальных источников цену вводит админ, иначе стоимость — «неизвестно», а токены считаются всегда. Яндекс стоимости в ответе не отдаёт (проверено). Дашборд суммирует по валютам и **курсы не пересчитывает** (D19).

### 5.3 Чат

Форма взята из `vercel/chatbot`:

```ts
chats; // id, user_id, title, visibility, created_at
// visibility: 'private' | 'team' — чат открыт по ссылке всем вошедшим, только чтение (D36)
// kind: 'chat' | 'task_run', task_id? — запуск задачи это обычный чат (§16)
messages; // id, chat_id, role, parts jsonb, attachments jsonb, created_at
streams; // id, chat_id, created_at
votes; // (chat_id, message_id), is_upvoted
documents; // PK (id, created_at) — версии артефактов, v2
```

`messages.parts` хранит `UIMessage['parts']` как есть, в формате AI SDK — так рекомендует официальная дока по persistence. Цена: мажорный апгрейд `ai` может потребовать миграции данных (в шаблоне так появилась таблица `Message_v2`).

## 6. Сообщения и стрим

Паттерн официального шаблона.

### 6.1 Контракт

```ts
POST /api/chat
{ id, message: UIMessage, modelId, connectionIds?: string[], skillSlugs?: string[] }
```

- Клиент шлёт только последнее сообщение, историю сервер берёт из БД.
- **Подключения:** `undefined` — все активные подключения пользователя плюс доступные ему `shared`-пункты каталога (то же множество, что у задач, D22); `[]` — ни одного; явный список — ровно эти. Сузить набор можно в composer (P2).
- **Встроенные тулы** (`web_search`, `web_fetch`, рендер виджетов, `request_connection`) доступны всегда, если админ их не выключил в `policies.builtinTools`, и от `connectionIds` не зависят.

### 6.2 Генерация

```ts
const stream = createUIMessageStream({
  originalMessages: uiMessages,
  execute: async ({ writer }) => {
    writer.write({
      type: "data-status",
      data: { phase: "waiting-model" },
      transient: true,
    });
    const result = streamText({
      model,
      instructions,
      tools,
      messages: await convertToModelMessages(uiMessages, { tools }), // тот же ToolSet — ради toModelOutput
      stopWhen: isStepCount(5),
      abortSignal: activeGenerations.register(chatId),
      onAbort: ({ steps }) => persistPartial(steps),
    });
    writer.merge(toUIMessageStream({ stream: result.stream }));
  },
  onEnd: ({ messages }) => saveMessages(messages),
  onError: toHumanError,
});
return createUIMessageStreamResponse({ stream, consumeSseStream });
```

- Пользовательское сообщение сохраняется **до** генерации, ассистентское — в `onEnd`.
- Если клиент отвалился, `result.consumeStream()` доводит генерацию до конца, и ответ всё равно сохраняется.
- Перед подачей в модель история проходит `validateUIMessagesForAgent`: части исчезнувших тулов (например, отключённого MCP-сервера) превращаются в dynamic.
- Сигнатура `convertToModelMessages(messages, { tools })` — **проверить** при реализации. Дока требует передавать туда тот же ToolSet, что и в `streamText`.

### 6.3 Остановка

При resumable-стриме клиентский `stop()` только отключает клиента, генерация продолжает тратить токены. Поэтому:

- `POST /api/chat/[id]/stop` находит `AbortController` в реестре `activeGenerations` (обычный `Map` в памяти — следствие D2), дёргает `abort()` и очищает активный стрим;
- `onAbort` сохраняет частичный ответ;
- уход со страницы стоп не вызывает — только явная кнопка или `Esc`.

### 6.4 Resume (D5)

Ответ записывается на сервере, пока пишется (реестр в памяти процесса, `lib/resume-stream.ts`): чанки потока копятся, а `GET /api/chat/[id]/stream` отдаёт их с начала и подключает к живому потоку — так страница, обновлённая посреди ответа, продолжает его читать. `204`, если ничего не пишется. Запись снимается после сохранения ответа. `useChat({ resume })` включается, когда чат открыт с сообщением пользователя в конце.

Для нескольких экземпляров приложения чанки переедут в Redis (`resumable-stream`) — изменится только этот файл.

### 6.5 Статусы

Transient `data-status` показывает фазы: `waiting-model` → `thinking` → `tool:<name>` → `writing`. Если модель молчит дольше N секунд, статус меняется на «модель отвечает дольше обычного». Подписи к тулам строятся по словарю «имя тула → фраза» (идея PlusPortal), а для MCP-тулов по умолчанию используется их `title`/`description`.

## 7. Источники и модели

### 7.1 Реестр из БД

Фабрика собирает инстанс источника по `kind`: `createOpenAI`, `createAnthropic`, `createOpenAICompatible`, `gateway`. Готовые инстансы кешируются. При изменении источника событие `config:changed` уходит через Redis pub/sub, и кеш сбрасывают оба процесса — `app` и `worker`.

- **Ключи** лежат в общем хранилище `secrets`: AES-256-GCM, write-only API, canary-проверка мастер-ключа (§17). Без мастер-ключа записать секрет нельзя: в открытый текст не деградируем.
- **Discovery** забирает список моделей у источника, а seed-справочник дополняет контекст, возможности и цены.
- **«Рекомендованных» моделей нет:** ни один источник их не отдаёт, а свой кураторский список быстро протухает. После подключения ничего не включено заранее. Список сортируется по дате выпуска из API (`released` у Gateway, `created_at` у Anthropic, `created` у OpenAI; у Яндекса — из seed), «новая» — это факт: моложе 90 дней. Для длинных списков (Gateway — сотни моделей) — поиск, фильтр по провайдеру и возможностям, «выбрать показанные» и список фиксированной высоты (P7).

### 7.2 Исходящий прокси

Реальный сценарий: OpenAI и Anthropic доступны только через прокси, а Яндекс — напрямую. Источник получает `fetch`, который выбирает маршрут по правилам §18. По умолчанию — напрямую: Яндекс ходит напрямую, OpenAI — через прокси, только если админ его туда отметил.

Опция `fetch` есть у всех четырёх источников (S4). Это `fetch` из пакета `undici` с dispatcher маршрута, а не глобальный: dispatcher из npm-undici и встроенный в Node fetch — разные версии.

### 7.3 Деградация вместо отказа

Если модель не умеет tools, vision или structured output, эта возможность отключается, а в `instructions` добавляется объяснение почему. Если capability равна `null`, пробуем, а ошибку превращаем в понятное сообщение и помечаем модель.

### 7.4 Yandex AI Studio

Официального источника для AI SDK нет, community-пакет `yandex-ai` сидит на `ai@6`. Подключаем через `createOpenAICompatible` — проверено spike S3 (`spikes/S3-S7-openai-compatible`).

```ts
createOpenAICompatible({
  name: "yandex",
  baseURL: "https://ai.api.cloud.yandex.net/v1",
  apiKey, // уходит как Bearer — Яндекс принимает; OpenAI-Project не нужен
  fetch: yandexFetch(proxiedFetch), // чинит поток Alice AI с инструментами (ниже)
});
```

- В `models.model_id` храним короткое имя (`aliceai-llm`, `yandexgpt-5.1`), фабрика собирает URI `gpt://<folderId>/<model>/latest` — короткие id API не принимает.
- AI Studio хостит и чужие открытые модели (Qwen, DeepSeek, gpt-oss): провайдер у них свой, источник — Яндекс.
- Авторизация — API-ключ сервисного аккаунта с ролью `ai.languageModels.user`. IAM-токены (живут ≤ 12 ч) отложены.
- `/v1/models` отдаёт готовые URI всех моделей каталога (чат `gpt://`, эмбеддинги `emb://`, голос `speech-realtime-*`); для чата берём `gpt://` без `speech-*`. Всё остальное — названия, возможности, цены — из seed.
- Ограничения, которые учитывает model router:
  - `tool_choice` принимает `auto`, `none` и `required` (S3);
  - изображения — только base64 data-URL, поэтому вложения из S3 инлайним;
  - structured output подтверждён только для YandexGPT;
  - стрим с tools работает у всех моделей (S3). **Alice AI** ломает поток: без `finish_reason` при `auto`, служебный `[TOOL_CALL_END]` в тексте при `required`, `id` вызова равен имени функции. Обёртка `yandexFetch` в `core/ai` чинит все три на лету и остальным моделям не мешает;
  - стрим у YandexGPT идёт крупными кусками (≈ по предложению) — текст в UI сглаживаем `smoothStream`;
  - квота по умолчанию — 10 одновременных синхронных генераций, так что 429 будут и требуют понятного UX.
- Оплата в рублях. Нерезиденты России и Казахстана платят в USD и только картами нероссийских банков.

### 7.5 Vercel AI Gateway

Один ключ — доступ к моделям разных провайдеров. Проверено по `@ai-sdk/gateway@4.0.88`, который реэкспортируется из `ai` как `gateway`.

```ts
createGateway({ apiKey, fetch: proxiedFetch }); // есть baseURL и headers; fetch — для прокси (§7.2)
```

- **Discovery богаче, чем у остальных.** `GET /v1/models` публичный, ключ не нужен (S4). У каждой модели есть:
  - возможности (`tags`: `tool-use`, `vision`, `reasoning`, `structured-output`, `file-input`…);
  - `context_window`, `max_tokens`, `type` (`language`, `embedding`, `image`…), `modalities`;
  - `pricing` — USD **за токен**, строками, с тирами по длине контекста.

  Всё пишем как `discovered`, цены при сохранении умножаем на 1M (тиры — D19). В чат берём только `type: language`. Провайдер определяется по префиксу id (`anthropic/…`, `openai/…`). `/v1/models/{id}/endpoints` — разбивка по апстрим-хостингам модели, для возможностей не нужен.

- **Фактическая стоимость.** `generationId` приходит в `providerMetadata.gateway`, а `gateway.getGenerationInfo({ id })` отдаёт `totalCost`. Записи появляются асинхронно, поэтому API отвечает 404, пока запись не готова. Поэтому `model_runs` сначала получает оценку по прайсу, а worker потом уточняет её фактической стоимостью. Проверено по типам и докам, вживую — нет.
- Для self-hosted нужна авторизация API-ключом. OIDC-режим Vercel работает только на их платформе.

### 7.6 Ollama

Через `createOpenAICompatible` поверх `/v1` — проверено spike S7: стрим, инструменты в обычном и стрим-режиме и цикл «вызов → результат → ответ» работают (`qwen3`, `gemma4`, `gpt-oss`). Отдельный `ai-sdk-ollama` не нужен, `sources.kind` остаётся `'openai-compatible'`. Первый запрос к модели идёт 8–14 с — сервер загружает её в память; статус генерации это подписывает (P9).

## 8. Инструменты

1. **Встроенные:** `web_search` и `web_fetch` (§8.1), рендер виджетов (§9), `request_connection` (§17.7); в v2 — `createDocument`/`updateDocument`, `update_task` и `report` для запусков задач (§16); задачу создаёт сама модель на экране «Задачи» (§16.1).
2. **MCP:** `createMCPClient` из `@ai-sdk/mcp`, discovery через `client.tools()`.
   - Серверы бывают из каталога организации и личные. Креды у сервера либо общие, либо у каждого пользователя свои (§17.1).
   - В v1 только `http`. Опция `redirect` по умолчанию `'error'` (защита от SSRF) — не переопределяем.
   - Имена тулов получают префикс: `catalog_items.key` для пунктов каталога, короткий id подключения для своих серверов (v2). Поверх того, что отдал сервер, работает наш allowlist `allowed_tools`.
   - **Какие серверы в чате:** упомянутые (`@Название`) в вопросах, которые сейчас есть в треде. Правка или удаление вопроса убирает и его серверы. Если у сервера больше 12 тулов, они подгружаются по запросу через `find_tools` (D32).
   - **Модель знает, какой сервис за что отвечает:** в инструкциях перечислены серверы чата с префиксом их тулов и необязательным описанием от админа (`catalog_items.description`, поле «Описание» на странице сервера). То же описание стоит у большого сервера в `find_tools`.
   - **Подтверждения у своих подключений** (почта, `http_api` без каталога): политика берётся из `policies.personalApprovalDefaults` по тулу коннектора. По умолчанию `email_send`, `webhook_out`, `telegram_send` и записывающие `http_api`-операции — `ask`, остальное — `auto`.
   - Аннотации `readOnlyHint`/`destructiveHint` приходят от сервера и недоверенные. Политику подтверждений задаёт админ в пункте каталога: `approval_policy` — `auto` / `ask` / `deny` на каждый тул, в том числе на тулы коннекторов (`email_send`, `http_request`). `deny` скрывает тул совсем. Что `ask` значит для периодических задач — D22.
   - Результаты любых тулов — недоверенные данные, а не инструкции.
   - `stdio` — в v3, только для суперюзера, с явным предупреждением «это запуск команды на сервере» и без личных кредов (D18).
3. **Скиллы — v2.** Формат совместим с Agent Skills (`SKILL.md` + frontmatter): уже существующие скиллы импортируются zip-архивом. В промпт попадают имя и описание, тело подгружается тулом `load_skill`. Скиллы бывают общие (от админа) и личные. Секретов в скиллах нет: если скиллу нужен доступ куда-то, он работает через подключение (§17).

**Подтверждения.** Используем штатный approval-флоу AI SDK v7 (`approval-requested` → `approval-responded` → `output-denied`), UI — `addToolApprovalResponse`.

**Песочница — v2** (D3, D47). Docker с gVisor; сокет видит только сервис `sandbox` (наш код без секретов), приложение — никогда. Проверка — spike S11. Пока песочницы нет, `run_code` недоступен, и модель об этом знает (§7.3).

### 8.1 Поиск в интернете

Встроенного поиска источников мало. `openai.tools.webSearch` и аналоги в `ai@7` — это provider-executed tools: они выполняются на стороне источника и работают только с его моделями. У Яндекса, Ollama и openai-compatible их нет, а периодическим задачам поиск нужен на любой модели. Официальные пакеты поиска для AI SDK (Tavily, Exa, Perplexity, Parallel) пока поддерживают только `ai@5`/`@6`.

Поэтому свои тулы `web_search` и `web_fetch`. Бэкенды настраиваются в админке так же, как источники моделей:

| Бэкенд | Роль |
| --- | --- |
| **SearXNG** в compose | по умолчанию: локально, бесплатно, без ключей. JSON включается в `settings.yml`, иначе ответ 403 |
| Yandex Search API — запасной | качество на русском. Платно: ≈ $4 за 1000 запросов днём, ≈ $0.25 в отложенном режиме, бесплатного тарифа нет |
| TinyFish — запасной | облачные Search и Fetch бесплатно (30 поисков и 150 URL в минуту), нужен ключ, скорее всего через прокси |
| Tavily — запасной | 1000 запросов в месяц бесплатно |

**Почему SearXNG может не хватить.** У него нет своего индекса: он с нашего сервера сам запрашивает Google, Bing, DuckDuckGo и собирает их выдачу. При ровном потоке запросов с одного IP — а задачи по расписанию дают именно такой поток — поисковики могут начать отвечать капчей. Часть движков из корпоративной сети может быть недоступна без прокси, а русскоязычная выдача Яндекса даже внутри SearXNG идёт через платный Yandex Search API. Поэтому платные бэкенды — **запасной путь, а не план:** адаптер подключается, только если S8 или эксплуатация покажут капчи или слабое качество. Интерфейс адаптера закладывается сразу, так что это будет настройка, а не переделка.

- **Чтение страниц — локально по умолчанию:** свой `fetch` плюс извлечение основного текста страницы в Markdown (библиотеку выбрать при реализации). Скачивание с нашего сервера — только с защитой от SSRF: запрет приватных диапазонов и повторная проверка адреса после каждого редиректа. Иначе модель достанет внутренние ресурсы корпоративной сети. TinyFish Fetch и Jina Reader — запасные варианты для страниц, которые не читаются без браузера. Firecrawl на своём сервере для «одной команды» слишком тяжёл: Postgres, Redis, RabbitMQ, Playwright.
- **Источники:** тул пишет части `source-url`, поэтому кликабельные цитаты работают у любой модели.
- **Недоверенный контент:** найденное — это данные, а не инструкции (§8). Для задач это часть осознанного риска D22.
- **Хранение:** бэкенды — таблица `search_backends`, ключи — в `secrets` (`owner_type = 'search_backend'`), настройки — `/settings/search`. В v1 — SearXNG и локальный fetch. Остальные адаптеры — по результатам S8 и эксплуатации.
- **N2 Free Search не берём:** это была MCP-обёртка над SearXNG, 2026-03-23 её сняли с npm, репозиторий удалён. Идею реализуем сами.
- **Риск:** при нагрузке поисковики могут отвечать SearXNG капчей. Для команды обычно хватает, для большой нагрузки нужен платный бэкенд. На практике не проверено — spike S8.

## 9. Генеративный UI

### 9.1 Контракт

Модель не порождает разметку. Она выбирает `kind` из закрытого реестра и заполняет спек по Zod-схеме этого вида. Спек плоский: один виджет — один объект, без деревьев компонентов. Для дашбордов позже появится один composite-вид с ограниченной сеткой.

```ts
widgetRegistry = { chart: {...}, table: {...}, metrics: {...} }   // schema + Component
```

- Рендер через `safeParse`: невалидный или неизвестный виджет показывается фолбэком, сообщение от этого не падает.
- Схемы только расширяются: старые сообщения должны рендериться после любого релиза.

### 9.2 Данные не проходят через модель: `from` + `toModelOutput`

Откуда виджет берёт данные. Решение:

1. **Полный** результат любого тула (включая MCP) хранится в `messages.parts` — он нужен UI и ссылкам.
2. Модели через `toModelOutput` уходит **сводка** длинной таблицы: колонки с суммой, минимумом и максимумом, первые строки, число строк и `ref` (id вызова). Короткая таблица уходит как есть, тоже с `ref`. Правило детерминированное, поэтому кеш промпта держится. `toModelOutput` вызывается и между шагами одного `streamText`, и в `convertToModelMessages` — туда нужно передавать те же `tools`.
3. Виджет (`show_chart`, `show_table`) вместо `points` / `rows` принимает `from`: `ref` (без него — последняя таблица чата), колонка для оси `x`, `bucket` для дат, `aggregate`, `sort`, `limit` — и `field` у каждого ряда или колонки. Сервер берёт полный результат (из истории и из текущего ответа), собирает точки или строки и кладёт их в `output.data`; клиент рисует их. Нет такой колонки, она не число, точек больше 200 — ошибка с перечнем колонок, модель читает её и повторяет вызов.

`show_metrics` целиком построен так: у него нет места для чисел, только колонки и способ чтения (`field`, `aggregate`, `x`, `by`), а цель берётся из слов пользователя.

Модель решает, _что_ показать, и никогда не переписывает цифры. Большие выборки не съедают контекст. Числа, которых нет в результате тула (из слов пользователя, со страницы), модель по-прежнему передаёт в `points` / `rows` сама.

**Проверено** (S5, DECISIONS D11): `toModelOutput` работает между шагами и на истории, MCP-тулы оборачиваются.

### 9.3 Где живёт виджет

- Виджет в ленте — это tool-часть: она сохраняется в историю. `transient`-части для виджетов не годятся, они в историю не попадают.
- На `input-streaming` уже доступен частичный спек, поэтому скелет виджета показывается сразу.
- Фильтры и сортировка — локальное состояние компонента, в URL и в модель не попадают. Учесть текущий срез в следующем ответе — явное действие «обсудить выделенное».
- Как виджет превращается в артефакт в правой панели — прототип P5.

### 9.4 Артефакты — v2

Структура шаблона: `artifacts/<kind>/{server.ts,client.tsx}`. Дельты идут накопленным контентом в transient `data-*`, содержимое сохраняется в `documents` с версиями. Типы: `text`, `code`, `sheet` (на ReUI Data Grid вместо `react-data-grid`), `dashboard`.

### 9.5 UI-библиотеки: приоритет ReUI

**ReUI — первый выбор для любого компонента, не только для рендерера: его вид нравится больше.** Правило выбора:

1. Если нужный компонент или блок есть в ReUI — берём его.
2. Если нет — берём shadcn/ui. Стиль shadcn в `components.json` выбираем тот же, что у ReUI (`<base>-<variant>`, например `base-nova`), чтобы базовые примитивы выглядели как ReUI.
3. Графики — тоже ReUI: бесплатные блоки `@reui/c-chart-*` на shadcn `chart` + recharts. EvilCharts пробовали и отказались (D20).

| Задача | Выбор |
| --- | --- |
| Все компоненты интерфейса | ReUI → shadcn/ui в стиле ReUI |
| Таблицы | ReUI Data Grid (TanStack Table + Virtual + dnd-kit) |
| Графики | ReUI — блоки `@reui/c-chart-*` на shadcn `chart` + recharts (D20) |

Вариант стиля ReUI (`vega`, `nova`, `maia`, `lyra`, `mira`, `luma`, `sera`, `rhea`) — решение визуальное, выбирается глазами на прототипе (D20).

Итоги S2 (D20):

- `shadcn add` запускаем из `packages/ui` — тогда примитивы и составные компоненты ReUI ложатся в дизайн-систему; перезаписей нет, совпадающие файлы пропускаются.
- База — Base UI (`base-nova`), иконки — `lucide-react`.
- ReUI работает на React 19 / Tailwind v4; контракт виджетов §9.1 от конкретной библиотеки не зависит.

## 10. Auth и доступ

- **Better Auth, без паролей (D17):** вход по магической ссылке — письмо со ссылкой и шестизначным кодом, код нужен, если письмо открыли на другом устройстве. Ссылка одноразовая, живёт 10 минут, запросы ограничены по email и IP. Магическая ссылка заодно подтверждает почту. Claim-ссылка и ссылка-приглашение сами создают сессию, для них почта не нужна. Сессия — 30 дней, продлевается при использовании. Без SMTP вход возможен по одноразовой ссылке от админа (в интерфейсе пользователей или `cli login-link <email>`). Passkey — v2, OIDC — v2.
- **`proxy.ts`** проверяет только наличие cookie (`getSessionCookie`) — так рекомендуют и Next, и Better Auth. Полная проверка (`auth.api.getSession`) выполняется в layout групп маршрутов, в серверных функциях и route handlers.
- **Роли:** `superuser` (единственный, создаётся через claim) / `admin` (настройки) / `user`. Точечные гранты на модели и пункты каталога — v2 (D12).
- **Вход по доменам (D17):** админ перечисляет домены почты (`system_settings.policies.access.domains`), человек с адресом на таком домене входит кодом без приглашения; аккаунт создаётся при первом входе с ролью `user`, имя спрашивается на `/login/name`. Нужна почта сервиса. `disableSignUp` у email OTP выключен, а создание аккаунта пропускает хук `databaseHooks.user.create.before` только для разрешённого адреса; код уходит тому, кто в сервисе или чей домен разрешён.
- **Приглашения:** админ получает ссылку и копирует её. Если SMTP настроен — ссылка уходит и письмом.
- **Rate limit:** счётчики в Redis, лимиты по роли.
- **С организациями (§20):**
  - роли две: установки (`user.role`) и организации (`user.org_role`);
  - вход по домену и приглашения ведут в свою организацию и занимают место тарифа в той же транзакции;
  - отключённая организация впускает человека только на экран с причиной;
  - лимиты по роли заменяются лимитами тарифа в деньгах, минутный остаётся.

Строки интерфейса только из словарей; даты и числа — через форматтеры next-intl в поясе пользователя, без голого `toLocaleString()`.

## 15. Компромиссы

| Решение | Цена | Почему |
| --- | --- | --- |
| Один инстанс `app` | нет горизонтального масштабирования | простая отмена, MCP-клиенты в памяти, честность |
| Без мастера, инфраструктура в compose | один шаг в терминале | нет проблемы «курицы и яйца», DDL не идёт через HTTP, первый визит нельзя перехватить |
| Линейная история | варианты ответа теряются | путь шаблона, простота |
| `parts` в формате AI SDK | миграции при мажорных апгрейдах `ai` | нет конвертера и рассинхрона форматов |
| Плоский спек виджета | нет произвольных дашбордов от модели | типизация, стрим, стабильное качество |
| Валюты без конвертации | нельзя одной цифрой «всего потрачено» | не выдумываем курсы |
| Только allow-правила | нельзя запретить конкретному человеку | предсказуемость |
| Права задач как у Claude | prompt injection из прочитанных данных может привести к записи от имени владельца | задача реально работает сама, без постоянных «одобрите» |
| Расписания в Postgres, BullMQ только исполняет | тик раз в минуту — точность запуска до минуты; задача запускается не чаще раза в 5 минут (`isTooFrequent`: черновик с таким cron возвращается модели) | расписания попадают в бэкапы и не теряются вместе с Redis |
| Секреты шифруются мастер-ключом сервера, а не ключом от пароля пользователя | владелец сервера технически может прочитать любой секрет | иначе задачи не работают, пока пользователь не залогинен (ставка №5) |

## 16. Периодические задачи — v2

**Задача** — инструкция + модель + подключения владельца + расписание + куда писать итог (D38: не «агент», запусков между запусками нет). **Запуск** — обычный чат `kind='task_run'` с теми же частями, виджетами и карточками тулов: это журнал работы. **Итог запуска** — последний ответ модели в нём, обычный ответ, как в чате (текст, таблица, список, виджеты), плюс `report({ outcome, summary })`.

### 16.1 Создание (P11)

- **Фразой на экране «Задачи».** Пустая страница «Задачи» — это экран «Что поручить?» с полем ввода, как новый чат. Модель разбирает просьбу на части — что делать, когда, откуда брать, куда писать итог — и показывает карточку с ними. Чего не хватает, спрашивает тут же по одному вопросу. Когда всё есть, предлагает название и цвет; человек нажимает «Создать задачу». Тестовый запуск доступен до создания.
- **Cron предлагает модель, а даты ближайших запусков считает сервер** (`cron-parser`). Арифметике дат от модели не доверяем.
- Часовой пояс берётся из браузера в момент создания.
- Чат, в котором задачу создали, становится чатом задачи (`tasks.chat_id`): дальше в нём её меняют.

**Сделано (этап 2в).** «Что поручить?» — это `/tasks/new`, а без задач и `/tasks`: новый чат с конвейером и четырьмя частями задачи («Что делать · Когда · Откуда · Куда»), поле «Опишите задачу…». Запрос несёт `intent: "task"`, и модель сразу составляет черновик. Тул `draft_task` (`core/chat-tools/task-draft-tool`) есть в каждом чате без задачи: модель присылает черновик (cron может быть пуст), а сервер проверяет cron, говорит расписание словами (`scheduleWords`) и считает три ближайших запуска в поясе пользователя. Неверный cron возвращается модели. Карточка в ответе показывает строки «что / когда / откуда / куда»; живая только последняя, прошлые сворачиваются в строку. Когда всё заполнено — название, цвет из палитры графиков (`TASK_COLORS`) и «Создать задачу». Задача создаётся из черновика, сохранённого в чате, а не из того, что прислала страница: модель берётся из ответа, первая просьба — из чата, пояс — из браузера. В чате с задачей тула больше нет. Почта и сайты показываются источниками, но не попадают в `catalog_ids`: они не серверы каталога. Тестового запуска до создания пока нет.

### 16.1a Изменение (P15, D28)

Задача меняется словами — в поле «Что поменять в задаче…» на её странице. Модель вызывает `update_task({ taskId, patch })`, он возвращает **черновик изменений, а не применяет их**. Изменение показывается в карточке «О задаче» наверху страницы: в изменённых строках старое зачёркнуто, новое ниже, добавленное выделено; строка «что не меняется». Кнопки: «Применить», «Тестовый запуск», «Отменить».

- Каждое применение создаёт `task_versions` с кратким описанием и текстом просьбы. Каждый запуск знает свою версию. В карточке — «изменена 30 ноя · Вернуть как было», в прошлых запусках — строка «Изменена 12 ноя: …» под первым запуском новой версии. Отдельной страницы истории версий нет, пока задачи не правят часто и вдвоём.
- **Тестовый запуск** (`trigger = 'test'`) идёт с новой версией сразу, без писем, и не считается в счётчик сбоев.
- Идущий запуск доигрывается на старой версии. При смене расписания `next_run_at` пересчитывается сразу.
- Менять задачу может только владелец. Админ может поставить чужую на паузу, но не менять её.

**Сделано (этап 3).** Поле «Что поменять в задаче…» внизу страницы задачи. Модель задачи заполняет `update_task` только изменёнными полями (`taskChangeSchema`); cron проверяется так же, как в черновике (формат, не чаще раза в 5 минут), ошибка возвращается модели. Изменение хранится как следующая версия (`task_versions.version = tasks.version + 1`), задача на неё ещё не переведена; новая просьба заменяет её вместе с её тестовыми запусками. Тестовый запуск (`trigger = 'test'`) идёт на этой версии: `createRun` берёт последнюю версию. «Применить» переводит задачу на версию и сразу пересчитывает `next_run_at`, если расписание поменялось. «Отменить» удаляет версию, её тестовые запуски и их чаты. «Вернуть как было» записывает версию перед текущей как новую и применяет её: линия версий не рвётся. Новое в «стало» выделяется целыми словами (`lib/task-change.ts`). Если модель не сделала изменения, её ответ показывается над полем. Код: `core/task-change.ts`, `components/tasks/task-about.tsx`. Нет пока: продолжения запуска после подтверждения (`waiting_approval`).

**Модель, файлы, скиллы задачи.** Внизу страницы задачи стоит тот же composer, что в чате. Модель задачи видна в карточке («Модель») и меняется в его пикере: смена сразу пишется применённой версией (`setTaskModel`), «Вернуть как было» её откатывает; изменение, ждущее применения, сдвигается на версию вперёд и получает новую модель. Файл, приложенный к просьбе, становится файлом задачи (`files.task_id`, черновиком больше не считается, удаляется вместе с задачей), `/скилл` — скиллом задачи, `@сервис` модель изменения учитывает в источниках. Списки — в версии (`snapshot.fileIds`, `snapshot.skillIds`), в карточке это строки «Файлы» и «Скиллы» с «было → стало»; убрать файл или скилл можно словами. Каждый запуск получает файлы задачи в первом сообщении, как модель чата получает вложения (`filePartsFor`, `read_attachment`), и загружает скиллы задачи первым делом, как при `/name` в чате; остальные скиллы предлагаются по описанию, писать свои запуск не может. Чтение вложений и тулы скиллов для этого переехали из `apps/web/lib` в `packages/core` (`attachments.ts`, `attachment-text.ts`, `chat-tools/attachment-tool.ts`, `chat-tools/skill-tools.ts`, `skill-mentions.ts`): воркер — отдельное приложение.

### 16.2 Запуск по расписанию

```
BullMQ job scheduler «tasks-dispatch», cron * * * * * — один на всё приложение
│
├─ тик раз в минуту в worker (если не стоит policies.tasksPaused):
│    BEGIN
│      SELECT id, cron, timezone, next_run_at FROM tasks
│      WHERE enabled AND next_run_at <= now()
│      FOR UPDATE SKIP LOCKED              -- два тика не возьмут одну задачу
│      → для каждой в JS: scheduledFor = next_run_at;
│        next = cronParser(cron, { tz: timezone, currentDate: now() }).next()
│        UPDATE tasks SET next_run_at = next WHERE id = …
│    COMMIT
│    → queue.add('task-run', { taskId, scheduledFor },
│                { jobId: `${taskId}-${scheduledFor.getTime()}` })   -- без «:», см. ниже
│
└─ обработчик 'task-run' (concurrency ограничена, в том числе под квоты источников):
     1. создаёт task_run и chat(kind='task_run')
     2. проверка готовности:
        · нужного подключения нет или оно needs_reauth → outcome action («Нет доступа к почте: срок входа истёк»), сбоем не считается
        · сервер не отвечает, ошибка сети → status failed с понятной причиной
     3. собирает тулы так же, как чат (§6.1): подключения владельца + встроенные
     4. ToolLoopAgent с лимитами шагов, стоимости и времени, abortSignal
     5. сохраняет сообщения; запуск обязан закончиться тулом report({ outcome, summary })
     6. итог — на страницу задачи; если outcome ≠ quiet — задача ждёт человека (боковая панель, §16.4),
        а при tasks.notify_email — письмо (§16.5)
     7. после 5 сбоев (failed) подряд задача встаёт на паузу, это outcome action
```

`report` — встроенный тул только для запусков: `outcome` — `news` (есть итог), `quiet` («нового нет» — при `report_when = 'changes'` итога не показываем и не шлём), `question` (нужен ответ человека), `action` (нужно действие: войти, подключить, исправить); `summary` — итог одной строкой, он же тема письма и строка в списке задач. Модель отвечает за смысл, `outcome` решает, писать ли человеку.

`next_run_at` считается в JS (`cron-parser` с часовым поясом задачи), а не в SQL: Postgres не умеет вычислять cron. В custom jobId BullMQ нельзя использовать `:` (проверено: `Custom Id cannot contain :`), поэтому разделитель `-`. BullMQ 6 работает через `node-redis` — тот же клиент, что у остального `core`: `ioredis` в BullMQ 6 стал необязательным и не нужен. Код: `core/tasks`, `task-schedule`, `tasks-queue`, `tasks-worker`, `task-run`.

**Тулы запуска (сделано).** Те же, что в чате: модули тулов чата переехали в `core/chat-tools` и общие для маршрута чата и запуска — серверы владельца (большой — по требованию), виджеты таблицы, показателей и графика, время, веб (как оставил админ), почта владельца. Нет тех, что требуют человека рядом: вопроса (это `report` с `question`), чтения файлов треда, «подключите X» (это `action`). Вызов, ждущий подтверждения (почта, тул с политикой `ask`), пока заканчивает запуск исходом `action`; продолжение после «да» — вместе с изменением задачи. Если модель вызвала `report`, не написав итога, второй проход без тулов дописывает его, как «итог, если промолчал» в чате.

Почему так:

- **Источник правды для расписаний — Postgres, а не Redis.** Расписания попадают в бэкапы, «ближайшие запуски» читаются из одного места, а потеря Redis не стирает задачи. BullMQ только исполняет.
- **Пропущенные запуски.** Если сервер лежал ночь, `next_run_at` окажется в прошлом, и будет **ровно один** догоняющий запуск, а следующий посчитается от текущего момента. Никакой лавины из 12 запусков утром.
- **Дубли.** `jobId` из id задачи и времени запуска не даёт одному тику запустить задачу дважды.
- **Не велосипед.** Так же eve делает расписания, которые создают пользователи: строки в БД и один тик раз в минуту.
- **Ручной запуск.** «Прогнать сейчас» ставит тот же джоб.
- **Отмена.** Кнопка «остановить» → сигнал через Redis в `worker` → `worker.cancelJob(jobId)` (есть в BullMQ 6.x, отменяет только на своём инстансе воркера — поэтому сигнал) → `abortSignal`.

### 16.3 Права — как у Claude (D22)

- По умолчанию задаче доступны **все подключения владельца** (`connection_ids = null`), лишние убираются в карточке.
- Задача действует кредами владельца и **ничего не спрашивает** во время запуска.
- **Исключение — политика админа.** Тул с `approval_policy = 'ask'` (§8) и в запуске требует подтверждения: запуск получает статус `waiting_approval`, задача ждёт человека (`outcome = action`). Ответ даётся на странице задачи — те же карточки, что в чате (блок «Ждёт подтверждения»), владельцу уходит письмо «Нужно действие». `answerRunAction` дописывает решение в ответ запуска; когда без ответа не осталось ни одного вызова, в очередь ставится задание `resume` (`enqueueResume`, id — запуск и ответ: второй клик не продолжит дважды). `resumeRun` в воркере продолжает тот же чат с того же ответа (`originalMessages` и `readUIMessageStream({ message })`): разрешённый вызов выполняется, на отклонённый модель получает отказ — и по инструкции не повторяет его, а пишет итог об этом. Состояние целиком лежит в сообщениях. `deny` скрывает тул. Права «как у Claude» — это умолчание для тулов без политики, а не обход решений админа.
- **Исключение — нет доступа.** Перед работой `executeRun` проверяет сервисы, которые задача называет поимённо (задача «со всеми сервисами» не проверяется: ей нужный может и не понадобиться). Сервис ждёт личного входа владельца — запуск сразу заканчивается итогом `action` с `task_runs.fix = { kind: 'server', id }`; вход настраивает админ или сервис отключён/закрыт — итог `action` без `fix`, с пояснением. После работы так же заканчивается запуск, в котором почтовый тул упал на пароле ящика (`needs_reauth`): `fix = { kind: 'mailbox', id }`. На странице задачи и в списке `fix` показывается кнопкой («Войти в …», `components/tasks/task-fix.tsx`); после входа задача идёт по расписанию как обычно. Код: `core/task-run.ts` (`accessGap`, `mailGap`), миграция 0038.
- **Сайдбар узнаёт о новом итоге сам.** Список задач для сайдбара (`listSidebarTasks`: цвет, «ждёт человека») оболочка перечитывает экшеном `sidebarTasksAction`, когда сервер говорит, что задачи сдвинулись (§16.5), и раз в минуту на случай потерянного слова; вне `/tasks` — на странице задач перечитывается весь layout (`router.refresh()`). Ждёт человека — итог не просмотрен, вопрос или действие не закрыты, запуск остановлен на подтверждении или упал. Такая задача показывается своей цветной точкой с `animate-ping` (при `prefers-reduced-motion` — без анимации); так же отмечен новый итог в списке «Задач» (`components/tasks/task-dot.tsx`).
- Страховка, которая не требует подтверждений:
  - лимиты шагов, стоимости и времени: владелец задаёт их у задачи в пределах потолков админа (`policies.taskMax*`), минимальный интервал между запусками задаёт админ;
  - каждый запуск — открываемый чат, то есть полный журнал действий;
  - выключатель «пауза всех задач».
- Осознанный риск: prompt injection из прочитанных писем или страниц может заставить задачу что-то записать от имени владельца. Если это станет проблемой, у задачи появится флаг «спрашивать перед записью». Approval-флоу в `ai@7` держится на сообщениях, поэтому ожидание подтверждения — просто сохранённый чат.

### 16.4 Интерфейс (P11–P15)

Прототипы выбраны: `/dev/prototypes/first-agent`, `task-results`, `task-edit`, `tasks-list`. Отдельных «Входящих» нет: итоги живут на странице задачи.

**Боковая панель.** Пункт «Задачи»; под ним — только задачи, которые ждут человека (новый итог, вопрос, действие), у каждой точка, и открытая сейчас. Разобрал — задача уходит из панели.

**Список задач** (`/tasks`, P13) — по вниманию:

- **Нужно действие** — исправление кнопкой прямо в строке: «Войти в почту» → «Проверяю доступ…» → «Доступ есть, идёт запуск…» → итог;
- **Новые итоги** — свежие сверху, итог раскрывается в строке (тот же ответ, что на странице задачи), «Отметить прочитанными» с возвратом;
- **Остальные** — имя, итог серым, следующий запуск словами («завтра в 8:30»);
- **Выключены** — под спойлером, «Включить · Отменить».

Строки не уезжают, пока страница открыта. Без задач — экран «Что поручить?» (P11). Есть вид загрузки и ошибки.

**Страница задачи** (`/tasks/[id]`, P12 + P15):

- шапка: название, расписание, следующий запуск, «Прогнать сейчас», выключатель, меню «⋯» с «Удалить задачу» (с подтверждением; вместе с задачей удаляются её запуски, версии и чаты запусков, чат настройки остаётся); на телефоне — строкой над карточкой;
- карточка «О задаче» (свёрнута в строку): что делает, расписание, источники, итог, когда создана, «На почту»; изменения — в её строках (§16.1a);
- **последний итог** целиком; сбой или «нового нет» после него — строкой над ним, у сбоя кнопка исправления;
- «Прошлые запуски» под спойлером: дата, итог одной строкой, длительность; раскрываются до ответа;
- поле «Что поменять в задаче…».

**Сделано (этап 2а–2б).** Пункт «Задачи» в боковой панели с ждущими задачами, страница задачи (шапка, карточка «О задаче» только для чтения с «На почту», последний итог, до трёх строк после него, прошлые запуски с ответом по запросу, опрос раз в 3 с, пока запуск в очереди или идёт), простой список `/tasks` — без группировки по вниманию (она в этапе 4). «Прогнать сейчас» ставит джоб, а затем ту же строку запуска, которую сделает воркер: «в очереди» видно сразу. Сбой запуска показывает причину от провайдера (первая ошибка потока), а не «No output generated». Нет пока: поля «Что поменять…», кнопок исправления «Войти в …» (сбой предлагает «Прогнать ещё раз»), строк версий в прошлых запусках. Код: `apps/web/app/(app)/(chat)/tasks`, `components/tasks/task-view.tsx`, `lib/task-runs.ts`.

**Запуск** — обычный экран чата с плашкой: «Задача „Сводка“ · по расписанию · 09:00 · 42 с · 0,8 ₽». Идущий запуск виден на странице задачи по шагам: воркер пишет ответ в чат запуска не чаще раза в 1,5 с, страница перечитывается, когда сервер говорит, что задачи сдвинулись (§16.5), и раз в 10 с, пока запуск идёт, раз в минуту в остальное время — на случай потерянного слова. Побуквенного стрима нет: шаги приходят не чаще раза в 1,5 с.

### 16.5 Уведомления (P14, D24)

| Канал | Когда срабатывает | Как устроено |
| --- | --- | --- |
| **Боковая панель и список** | всегда | задача ждёт человека: `outcome ∈ {news, question, action}` и итог не просмотрен или не закрыт |
| **В приложении** | вкладка открыта | **Сделано.** Запуск стал в очередь, пошёл, остановился для человека или кончился, итог просмотрен, задача включена, выключена, создана или удалена — `core/task-events` публикует в Redis `tasks:changed` с id владельца (без данных). `app` отдаёт его владельцу по SSE (`/api/notifications/stream`, `retry: 3000`, строка-пульс раз в 20 с), вкладка держит один поток на всех слушателей (`use-task-events`) и по слову перечитывает своё: сайдбар — `sidebarTasksAction`, страницы задач — `router.refresh()`. Слово, которого никто не услышал (обрыв), не теряется: при переподключении и при возврате на вкладку страница читает один раз, плюс редкий опрос. Ограничение: у HTTP/1.1 около 6 соединений на источник, много вкладок на одном адресе без HTTPS его выберут |
| **Почта** | у задачи включено «На почту» | только новый итог, вопрос или действие; «нового нет» — никогда. `letterBlocks` (`@metobe/core/letter-blocks`) переводит ответ запуска в блоки письма, `taskLetter` (`@metobe/emails/task-letter`) рисует его, письмо уходит через очередь. Внизу — «Отключить для этой задачи»: ссылка с подписанным токеном, работает без входа |
| **Push браузера** | открыто | Web Push: service worker + VAPID-ключи из `install.sh`, HTTPS. Решим, когда будет понятно, сколько задач у людей |
| **Telegram** | v3 | Vercel Chat SDK + `@chat-adapter/telegram` |

Против спама:

- «нового нет» не уведомляет нигде;
- сбой подряд не шлёт письмо каждый раз: одно на задачу, пока не исправлено;
- если задач много, одно письмо в день сводкой — решим по опыту (P14 открыт).

**Сделано (этап 5, письма).** После запуска воркер зовёт `sendRunLetter` (`core/task-mail.ts`): письмо уходит владельцу, если у задачи включены уведомления и запуск ждёт человека — новый итог, вопрос, действие; первый сбой подряд (`consecutive_failures = 1`) и остановка после пяти — тоже; «нового нет» и тестовые запуски — никогда. Тема — «Задача: итог одной строкой», тело — `letterBlocks` из ответа запуска, язык — `user.locale`. «Отключить для этой задачи» ведёт на публичную страницу `/mail-off/[id]?t=…` (своя группа маршрутов `(notice)`, без бренд-панели входа) с подписью HMAC на `BETTER_AUTH_SECRET`: она спрашивает один раз (почтовые сканеры открывают ссылки сами), заголовок `List-Unsubscribe` с `List-Unsubscribe-Post` ведёт на `POST /api/mail-off/[id]` — отписка в один клик. Без сервисной почты письма не шлются. Воркер теперь запускается без условия `react-server`: под ним React не даёт `react-dom/server`, которым React Email рисует письмо; `server-only` в сборке воркера — алиас на пустой модуль, в деве — хук загрузчика `apps/worker/no-server-only.mjs`. Шаблоны писем помечены `@jsxRuntime automatic`: `tsx` не применяет `tsconfig` к файлам workspace-пакетов. Нет пока: сводки раз в день при многих задачах, событий по SSE.

### 16.6 Исполнитель

Своё ядро: BullMQ + Postgres + `ToolLoopAgent`. Выполнение спрятано за `executeRun(runId)`. Если шаги станут долгими и дорогими для повтора, исполнитель переезжает на Workflow DevKit + Postgres World (`WorkflowAgent` из `@ai-sdk/workflow`), а остальное не меняется.

Сейчас не берём:

- **Workflow DevKit:** нужна beta-линейка 5.x, Postgres World в README назван «reference implementation», своего cron нет.
- **eve:** preview и отдельный рантайм со своими сессиями и auth. Оставляем как spike — у него интересная песочница, которая сама выбирает Docker или microsandbox.

| --- | --- | --- |
| MCP-серверы | каталог: URL, транспорт, разрешённые тулы, способ авторизации | подключается к серверу из каталога своими кредами; свой сервер — если админ разрешил (v2) |
| stdio MCP | только суперюзер (v3, D18) | нельзя |
| Скиллы | общие | личные и «сохранить как скилл» из чата (сделано) |
| Встроенные коннекторы (почта и т.п.) | включает типы коннекторов, задаёт пресеты | подключает свои: сервер, порт, логин, пароль (§17.7) |
| Ключи источников моделей | да | нет |

Креды сервера из каталога задаются одним из двух режимов:

- **`shared`** — один служебный токен на всех, например внутренний поиск по вики. Такой сервер доступен без личного подключения.
- **`per_user`** — каждый подключает свои креды. Так устроены 1С, где у каждого свои права, и GitHub. Для задач (D22) это главный режим: задача действует кредами владельца.

**Свои подключения пользователя** — любого типа, не из каталога: свой MCP-сервер (v2), почта с хостом `custom`, `http_api` — регулируются политикой `personalConnections: 'off' | 'public_only' | 'on'`, по умолчанию `public_only`.

- Адреса из приватных диапазонов (`10.*`, `192.168.*`, `localhost` и т.п.) запрещены: иначе через наш сервер можно достучаться до внутренней сети (SSRF). Адрес проверяется после DNS-резолва и повторно при каждом соединении.
- **Через прокси проверка должна работать так же** (§18.4): адрес резолвится у нас, проверяется, и прокси получает уже **IP**, а не имя. Иначе прокси, который сам стоит во внутренней сети, разрешит имя по своему DNS и пустит запрос внутрь.
- `verify` при подключении ограничен по частоте, чтобы форма не превращалась в сканер портов.
- Внутренние системы — корпоративный SMTP, 1С, базы, внутренние API — админ добавляет в каталог. Каталог в v1 (M4).
- **Статус в коде (2026-10-13):** обе политики — на экране «Доступ» (`/settings/access`, `core/personal.ts`). Свои подключения вне каталога пока есть только у почты: `off` — новый ящик не добавить, подключённые остаются, но чат их не использует и не просит подключить, а их серверам ничего не уходит; `public_only` — приватные адреса запрещены; `on` — разрешены, адрес всё равно резолвится у нас и прокси получает IP. `personalApprovalDefaults` — умолчание «спрашивать?» по тулу почты: что человек выбрал у ящика, важнее.

Термины: **подключение к каталогу** — пользователь вводит свои креды к пункту, который завёл админ (`per_user`). **Своё подключение** — пользователь сам задаёт и адрес.

### 17.2 Хранение

Все секреты — ключи источников, SMTP, токены MCP и OAuth — лежат в одной таблице:

```ts
secrets; // id, owner_type: 'system' | 'source' | 'catalog_item' | 'connection' | 'search_backend' | 'proxy'
//   (| 'agent' — токен вебхука, v3), owner_id
// purpose: 'api_key' | 'password' | 'token' | 'headers' | 'oauth_access' | 'oauth_refresh' | …
// связь владелец → секреты идёт через (owner_type, owner_id), массивов id нет
// ciphertext, iv, auth_tag, key_id (отпечаток ключа)
// hint ('sk-…a1B2'), expires_at?, created_at, rotated_at, last_used_at
```

- **Шифрование:** AES-256-GCM из `node:crypto`, случайный IV на каждую запись.
- **AAD = `owner_type:owner_id:purpose`.** Шифртекст привязан к своей строке: если в БД скопировать чужой токен в свою запись, расшифровка просто упадёт.
- **Мастер-ключ `SECRETS_KEY`** хранится только в env, никогда в БД.
- **Ротация:** на время смены ключа задаётся `SECRETS_KEY_PREVIOUS`. У каждой записи есть `key_id` — отпечаток ключа, которым она зашифрована (первые байты SHA-256), поэтому номера версий вести не нужно. `metobe secrets:rotate` перешифровывает всё на текущий ключ и сообщает, когда старый можно убрать.
- **Canary.** При установке в `system_settings` пишется зашифрованная контрольная строка. При старте приложение её расшифровывает. Если не вышло, оно отказывается стартовать с понятным сообщением «SECRETS_KEY не совпадает с ключом установки». Иначе с чужим ключом начнут писаться новые секреты, и база окажется зашифрована двумя ключами вперемешку.
- **Одна точка чтения:** `withSecret(владелец, purpose, fn)` расшифровывает значение прямо перед использованием и обновляет `last_used_at`. В памяти секрет живёт только внутри инстансов источников и MCP-клиентов. При изменении событие `config:changed` через Redis сбрасывает кеш в обоих процессах (`app` и `worker`).

### 17.3 Куда секрет не попадает

- **В клиент.** API write-only: секрет можно задать или заменить, но не прочитать. Интерфейс видит только `hint` и статус. У пароля и у короткого секрета (меньше 12 символов) `hint` без единого символа — «••••••»: только то, что он задан.
- **В модель — никогда.** Креды уходят в заголовки транспорта, а не в промпт и не в результаты тулов. Ошибки тулов перед показом модели проходят маскирование: заголовки и query-параметры вроде `token` и `key` вырезаются. Поэтому prompt injection не может «попросить» ключ — модель его просто не видит.
- **В логи.** Логгер маскирует `authorization`, `apiKey`, `token`, `password`.
- **В бэкап в открытом виде.** Дамп БД содержит только шифртекст, без `SECRETS_KEY` он бесполезен (§14).

### 17.4 OAuth для MCP — v1 (сделано, D25 уточнено 2026-10-02)

Многие публичные MCP-серверы (GitHub, Linear, Notion и т.п.) авторизуются через OAuth 2.1 с PKCE по спецификации MCP. Поток:

1. кнопка «Подключить» открывает окно авторизации;
2. callback приходит на `/api/mcp/oauth/callback?state=…` — по `state` находится поток в `oauth_flows`, а через него пункт каталога или своё подключение;
3. токены сохраняются в `secrets`, PKCE-состояние — в `oauth_flows`.

В `@ai-sdk/mcp` для этого есть `authProvider` — реализуем его поверх нашей БД и обновляем токен по `expires_at` перед вызовом. Точный интерфейс — **проверить** (S10).

Refresh выполняется **под блокировкой на подключение** (Redis lock): `app` и `worker` могут одновременно захотеть обновить один токен, а при ротации refresh-токенов второй запрос получил бы отказ и перевёл подключение в `needs_reauth` на ровном месте.

Если токен истёк или отозван, подключение переходит в статус `needs_reauth`. Задачи владельца, которым оно нужно, ждут действия «переподключите GitHub» (§16.4), в чате появляется инлайн-карточка.

### 17.5 Модель угроз

**Защищаемся от утечки** через интерфейс и API, через дамп БД и бэкапы, через логи, через модель.

**Не защищаемся от владельца сервера.** В self-hosted у того, кто держит `SECRETS_KEY` и доступ к серверу, технически есть все секреты. Это закрыло бы шифрование ключом от пароля пользователя, но тогда задачи не смогут работать, пока пользователь не залогинен, — а это ломает ставку №5. Вариант отвергнут.

**Внешние хранилища** (Vault/OpenBao, Infisical) — адаптер позже, если его потребует корпоративная безопасность. По умолчанию хранилище своё, чтобы установка оставалась в одну команду.

### 17.6 Интерфейс

- **`/settings/connections` — «Подключения»** (личная группа настроек, прототип P8 «Погружение · 2»).
  - Раздел-список в сайдбаре: доступные пользователю серверы — свои (с личными учётками) сверху, «От организации» ниже.
  - Страница на сервер: статус (подключено / нужно войти заново / не работает / не подключено), когда использовался, учётка — логин и пароль, токен или значение заголовка правятся в строке (пароль не показывается совсем), OAuth — «Войти заново».
  - «Отключение» — отдельный раздел в конце, как удаление любого объекта в настройках: учётка и все её секреты удаляются, сервер остаётся в списке.
  - Статус ведёт чат: тулы загрузились — «использовался …» и снова «подключено»; токен или пароль отклонён (401/403) — «не работает»; OAuth истёк — «войдите заново».
  - «Добавить своё подключение» — если политика разрешает; свой MCP-сервер — v2.
- **`/settings/mcp` — «MCP-серверы»** (админ): каталог организации. На странице сервера — только общая учётка; с личными учётками там нечего вводить, кроме имени заголовка. Админ подключается к таким серверам сам, в «Подключениях», как все.
- **OAuth — в окне сервиса.** Страницу входа нельзя показать внутри нашей модалки: провайдеры запрещают фреймы, а поле пароля без адресной строки — вид фишинга. Поэтому по клику открывается отдельное окно (с посредника `/mcp-oauth` — «открываем страницу входа…»), наша модалка ждёт; после колбэка посредник сообщает результат странице через `BroadcastChannel` (связь `window.opener` страница провайдера может оборвать через COOP) и закрывается. Со страницы никто не уходит — в чате не теряется набранный текст. Заблокированное окно — тот же вход в этой вкладке.
- **Подключение прямо из чата.** В инструкции модели передаётся список серверов из каталога, которые пользователь ещё не подключил. Если модели нужен один из них, встроенный тул `request_connection` рисует в ленте карточку «Подключите 1С, чтобы продолжить» с кнопкой. Точный вид — прототип P8.
- **Поле секрета** умеет только «задать» и «заменить» и показывает маску вроде `sk-…a1B2`.
  - Это не пароль, и браузер не должен его так понимать. `type="password"` зовёт автозаполнение (Связка ключей iCloud, 1Password, Chrome), поэтому поле — `type="text"` с маской CSS `-webkit-text-security: disc`, `autocomplete="off"` и атрибутами-исключениями менеджеров паролей (`data-1p-ignore`, `data-lpignore`, `data-bwignore`, `data-form-type="other"`). То же для адресов прокси и прочих полей подключений. Проверено в прототипе P7; в M2 — компонент `SecretInput` в `@metobe/ui`.

### 17.7 Коннекторы и запрос данных у пользователя

Не всё, чем работает модель, — MCP. Почта по SMTP/IMAP — встроенный **коннектор**: у него есть описание полей, проверка и свои тулы.

```ts
connectorTypes.email = {
  fields: z.object({
    preset: z.enum(['yandex', 'gmail', 'mailru', 'outlook', 'custom']),
    host, port, security: z.enum(['ssl', 'starttls', 'none']),
    username, from,
    password: secret(),                     // secret() → в `secrets`, остальное → `connections.config`
  }),
  presets: { yandex: { host: 'smtp.yandex.ru', port: 465, security: 'ssl', hint: 'нужен пароль приложения' }, … },
  verify: (c) => transporter.verify(),      // nodemailer: проверить соединение до сохранения
  tools: ['email_send', 'email_search', 'email_read'], // IMAP — в v1 (D27)
}
```

У MCP-серверов из каталога с `per_user` тот же механизм: поля задаёт админ в `connection_fields`.

**Типы коннекторов.** Правило: встроенный коннектор делается для **протокола**, а не для конкретного сервиса. Сервисы (GitHub, Notion, Bitrix24, amoCRM, Яндекс 360, Jira…) подключаются как MCP из каталога — поддерживать свой адаптер к каждому API бесконечно.

| type | Поля | Тулы модели | Проверка | Когда |
| --- | --- | --- | --- | --- |
| `mcp` | `connection_fields` пункта каталога; авторизация: нет / bearer / заголовок / basic / OAuth | тулы сервера | `client.tools()` | v1 |
| `email` | пресет, SMTP- и IMAP-хост, порт, SSL/STARTTLS, логин, пароль; в коде — своя таблица `mailboxes`, не `connections` (D27) | `email_send`, `email_search`, `email_read` | `verify()` и вход по IMAP | v1 |
| `http_api` | base URL, авторизация (bearer / заголовок / basic / query), OpenAPI-спека по желанию | тул на каждую операцию из спеки, иначе общий `http_request` | тестовый запрос | v1 |
| `database` | тип (Postgres / MySQL / MSSQL / ClickHouse), хост, порт, база, логин, пароль, SSL | `sql_query` — только чтение, таймаут, лимит строк | `SELECT 1` | v2 |
| `telegram_bot` | токен бота, chat id | `telegram_send` | `getMe` | v2 |
| `webhook_out` | URL, секрет | `webhook_send` (Slack, Teams, n8n, Discord) | тестовая отправка | v2 |
| CalDAV / CardDAV | сервер, логин, пароль | календарь, контакты | вход | позже |
| S3 / WebDAV / Яндекс Диск | endpoint, ключи | список, чтение, запись файлов | листинг | позже |

- **`http_api`** закрывает всё, у чего нет MCP: 1С через HTTP-сервисы или OData, внутренние API. Для 1С — пресет «OData 1С»: адрес базы и логин.
- **`database`** работает на ставку №2: «покажи продажи графиком» = `sql_query` + виджет (§9.2). По умолчанию только чтение. Форма рекомендует отдельного пользователя БД с правами на чтение.
- **Не делаем:** `ssh` и «выполнить команду» — это песочница (v3), не коннектор.
- **Внутренняя сеть.** `database` и `http_api` обычно смотрят во внутреннюю сеть, а личным подключениям приватные адреса запрещены (§17.1). Поэтому такие подключения админ добавляет в каталог с `per_user`: адрес задаёт он, а логин и пароль каждый вводит свои в той же форме.

**Как модель спрашивает данные — кейс «хочу, чтобы письма уходили сами»:**

1. Модель видит, что для задачи нужен коннектор `email`, а у пользователя его нет. Она вызывает встроенный тул `request_connection({ type: 'email', reason: 'чтобы отправлять сводку' })`.
2. У тула **нет `execute`** — это human-in-the-loop на клиенте. Генерация останавливается, в ленте появляется **карточка-форма**:
   - выбор почты (Яндекс / Gmail / Mail.ru / Outlook / своя) — хост, порт и шифрование заполняются сами;
   - для Яндекса подсказка «нужен пароль приложения» со ссылкой на настройку;
   - логин и пароль (поле маскируется), кнопка «Проверить и подключить».
3. **Значения уходят из браузера прямо в `POST /api/connections`, минуя модель.** Сервер проверяет соединение (`verify`), пароль кладёт в `secrets`, остальное — в `config`.
4. Клиент отвечает на вызов тула через `addToolOutput` только сводкой: `{ status: 'connected', connectionId, summary: 'smtp.yandex.ru:465 SSL, ivan@…' }`. Пароля нет ни в истории, ни в контексте модели. Диалог продолжается сам (`sendAutomaticallyWhen`).
5. Ошибка проверки («неверный пароль», «порт закрыт») показывается прямо в карточке с подсказкой — пользователь исправляет, не выходя из чата.

**Если пароль всё-таки ввели в сообщение**, composer до отправки подсвечивает похожее на пароль и предлагает «подключить через форму». То, что уже ушло модели, из её контекста не вернуть — поэтому предупреждаем до отправки, а не после.

**Периодическая задача** показать форму не может, пользователя рядом нет. Она заканчивает запуск с `outcome: 'action'`: задача ждёт человека, в списке и на её странице — «Нет подключения к почте» с кнопкой, которая открывает ту же форму. После подключения запуск повторяется.

Тот же путь есть без чата: «Мои подключения» → «Добавить» → выбор типа → та же форма.

## 18. Прокси

Сети с ограничениями — ставка №3. Прокси — не поле в настройках источника, а отдельная сущность в админке: их может быть несколько, и у каждого вида исходящего трафика свой маршрут.

### 18.1 Прокси

`/settings/proxies` — список прокси. У каждого:

- тип: `http`, `https`, `socks5`, `socks5h` (у `socks5h` DNS разрешается на стороне прокси — нужно, когда блокируют и DNS);
- хост, порт, логин; пароль — в `secrets`;
- кнопка **«Проверить»**: запрос через прокси показывает внешний IP, страну и задержку. Результат сохраняется и виден в списке.

Экран — такой же список → деталь, как у источников (прототип P7, `providers/v3`): в списке флаг страны выхода, тип, задержка и логотипы того, что через прокси ходит. В детали — подключение строками с правкой на месте (адрес проверяется сразу после сохранения), «Что через него ходит» (источники с переключателем и домены, §18.2), график запросов за сутки и удаление с перечнем того, что уйдёт на «напрямую».

Первый прокси можно задать ещё при установке: `install.sh` спрашивает «нужен исходящий прокси?», а entrypoint при первом старте превращает `HTTPS_PROXY` / `ALL_PROXY` в запись в админке, ничего к ней не привязывая. Тот же ответ `install.sh` записывает в `settings.yml` SearXNG. Дальше прокси приложения живёт только в админке, прокси SearXNG меняется повторным запуском `install.sh`.

### 18.2 Что через что ходит

**Главное правило: по умолчанию всё идёт напрямую.** Прокси не «включается для категории»: админ отмечает у конкретного прокси, что именно через него ходит. Так нельзя случайно загнать в прокси Яндекс только потому, что он тоже «источник моделей».

**Внутренние сервисы compose** — Postgres, Redis, S3, SearXNG — не ходят через прокси никогда. Это не настраивается.

У каждого прокси — список «что через меня ходит», из двух частей:

1. **Объекты** — галочки по списку того, что уже заведено:
   - источники моделей: ☑ OpenAI, ☑ Anthropic, ☐ Yandex AI Studio;
   - пункты каталога — MCP-серверы и коннекторы;
   - бэкенды поиска.
2. **Домены** — для трафика, у которого нет объекта:
   - чтение страниц моделью (`web_fetch`) на произвольные сайты;
   - свои подключения пользователей: почта `smtp.gmail.com`, их `http_api`;
   - доставка Web Push (`fcm.googleapis.com`, `push.apple.com`).

   Домен покрывает поддомены — как в PAC-файле или `proxyctl`.

Те же данные видны и с другой стороны: в форме источника или пункта каталога есть поле «Прокси» со значениями «авто» (по доменам), «напрямую» или «через X». Два вида одного поля, а не две настройки.

**Как выбирается маршрут** для конкретного запроса:

1. у объекта явно выбран прокси или «напрямую» → так и идёт;
2. объект на «авто» или его нет → ищется прокси, в доменах которого есть адрес назначения;
3. ничего не нашлось → **напрямую**.

Если адрес подходит под домены двух прокси, побеждает более точный домен (`api.openai.com` точнее, чем `openai.com`). При равенстве форма не даёт сохранить конфликт.

**SearXNG** ходит в поисковики из своего контейнера. Его прокси задаётся в `settings.yml` (`outgoing.proxies`) при установке. В админке он показывается только для чтения: сменить его без перезапуска контейнера нельзя, а управлять Docker из приложения мы не даём (D3). Поддержку SOCKS5 в SearXNG — **проверить** (S8).

### 18.3 Удобство

- **Прокси подбирается сам, когда нужен.** При добавлении источника ключ сначала проверяется напрямую. Если упало по сети или на гео-блоке, та же проверка автоматически прогоняется через каждый включённый прокси, и в форме появляется: «Напрямую OpenAI недоступен, через „Корп-прокси“ работает — использовать?». Одна кнопка, без похода в настройки прокси. Если прокси ещё нет (свежая установка, в `install.sh` его не задали), подобрать нечего: форма честно говорит «ключ подошёл, но источник из этой сети не отвечает» и предлагает ввести адрес прокси прямо здесь или взять источника, доступного напрямую. Введённый прокси проверяется и сохраняется первой записью в «Прокси», через него идёт только этот источник.
- **Подсказка при создании прокси.** «Обычно через прокси ходят OpenAI, Anthropic, Google — отметить те, что у вас заведены?». Это подсказка, а не умолчание: ничего не отмечается само.
- **Прозрачность.** На странице прокси видно, что через него ходит и сколько запросов за сутки прошло и упало. В списке источников у каждого значок маршрута: напрямую или через какой прокси.
- **Честные ошибки.** Если прокси перестал отвечать, объекты на нём получают ошибку «прокси X недоступен», а не таймаут модели. Админ получает алерт.

### 18.4 Реализация

- **HTTP/HTTPS** — `undici` `ProxyAgent` как dispatcher у `fetch`. «Напрямую» — явный `Agent`, а не глобальный dispatcher: так `HTTPS_PROXY` из окружения никуда не просачивается.
- **SOCKS5** — свой коннектор для `undici` `Agent` на пакете `socks` и `buildConnector` (S4). `fetch-socks` не берём: он тянет второй мажор undici. У `socks5h` имя уходит в прокси, у `socks5` резолвим сами.
- **SMTP через прокси** — `nodemailer`, опция `proxy`: `socks5://` (с `proxy_socks_module`) и `http://` через `CONNECT` (S4).
- **Web Push через прокси** — опция `proxy` у библиотеки `web-push` — **проверить** (S9).
- Dispatcher'ы кешируются на прокси и сбрасываются по `config:changed`, как источники (§7.1).
- **SSRF-проверка (§17.1) применяется к адресу назначения, а не к прокси.** Сам прокси обычно во внутренней сети — это нормально, его задал админ.
- **Трафик с SSRF-защитой** (`web_fetch`, свои подключения пользователей) идёт через прокси только с закреплённым IP: мы сами резолвим имя, проверяем адрес и открываем туннель (`CONNECT` / SOCKS5) на этот IP, а имя передаём только в `Host` и TLS SNI. `socks5h` для такого трафика запрещён: при нём имя разрешает прокси, и проверка теряет смысл. Как именно: свой коннектор — `dns.lookup` → проверка → туннель на IP (`Client.connect` у HTTP-прокси, `SocksClient` у SOCKS) → TLS через `buildConnector` с SNI по имени (S4). Для SMTP пользователей — то же через `host: IP` + `tls.servername` или `getSocket` в nodemailer; это M4. Каталог админа и источники под это правило не попадают: их адреса задал админ.
- Прокси — только админский ресурс. Свои подключения пользователей идут через прокси по его доменам, иначе напрямую; выбирать прокси пользователь не может.
- Счётчики «сколько запросов прошло и упало» хранятся в Redis поминутно за последние сутки — для экрана прокси этого достаточно, в Postgres их не пишем.

## 19. Память — v2

Что решено и почему — D39. Здесь — как устроено. Ставка №6 (§0): Metobe помнит, что человек рассказал о работе, и утром предлагает, что сделать.

### 19.1 Включение

- **Память работает, только пока назначена модель в слоте «Память»** (§7, «Служебные модели»). Слот пуст или его источник не работает — память выключена у всех: не пишется, не читается, нет строки «Запомнено», раздела «На сегодня» и пункта в боковой панели. Уже записанное лежит и ждёт.
- **Слот «Решения» необязателен** (Б2b). Есть — первая ступень записи отсеивает сообщения, где нечего запоминать; нет — служебная модель смотрит каждое сообщение. Закрытие обязательств и выбор карточки решает служебная модель слота «Память» (по S13 ~$0,0008 на сообщение). Модели решений есть только в Gateway, поэтому без них память не отваливается.
- **У человека свой выключатель и «Забыть всё»** (настройки аккаунта, раздел «Память» — только пока в службе есть модель «Память»; сделано): `user.memory_off` — его сообщения не встают в очередь, уже стоящие не читаются, нет пункта в боковой панели, строки «Запомнено» и заметки для модели чата; страница «Память» говорит, что выключил он сам, и ведёт в настройки. «Забыть всё» стирает записи и ключ данных; процесс, у которого ключ остался в кэше (worker), перед записью сверяет его с таблицей по `iv` и не запечатывает новое забытым ключом.

### 19.2 Данные

Всё в Postgres, `owner_id` в каждой таблице (каскадное удаление с пользователем), доступ — только через `core/memory.ts`, где проверка владельца одна. Открыты лишь поля, по которым план ищет запросами; тексты шифруются (§19.3).

```ts
memory_keys; // owner_id — ключ данных человека, закрытый SECRETS_KEY: ciphertext, iv, auth_tag, key_id
memory_entities; // kind: 'self' | 'person' | 'org' | 'project'; sealed — {name, aliases, role}
// подпись карточки — самое новое из двух: ручная правка role или живой факт с role («теперь тимлид»), см. memory_records
// write_id — какая запись создала карточку: отмена записи убирает карточку, если больше ничто за неё не держится
// 'self' — сам человек, одна на владельца: без неё нельзя записать «кто кому должен»
memory_writes; // одна строка на обработанное сообщение: chat_id (set null — чат удалён, память остаётся),
// message_id, status: 'queued' | 'skipped' | 'done' | 'failed' | 'undone', error, finished_at;
// unique (owner_id, message_id) — одно сообщение не обработается дважды; через неё «Запомнено» отменяется целиком
memory_records; // kind: 'fact' | 'assessment' | 'event' | 'commitment' | 'rule'; sealed — {text, role?}
// role — у факта о том, кто карточка теперь («тимлид бэкенда»): удалён или отменён факт — подпись прежняя
// write_id — откуда (null — внесено руками на странице «Память»)
// occurred_at + occurred_precision ('day' | 'week' | 'month' | 'year'; пусто — неизвестно) — когда произошло
// valid_from, valid_to — у факта; given_at, due_at, status, done_at, important — у обязательства
// status: 'open' | 'unconfirmed' (сказал другой, ждёт подтверждения) | 'done' | 'cancelled'; done_at — выполнено или отменено
// important — человек назвал важным словами или отметил сам; модель не угадывает
// recorded_at — занесено; superseded_at, superseded_by — заменено; deleted_at — удалено с возвратом
// closed_by_write — какая запись закрыла (valid_to у факта, новый статус у обязательства): отмена записи открывает снова
memory_record_entities; // record_id, entity_id, role: 'about' | 'participant' | 'debtor' | 'creditor' | 'subject'
memory_changes; // история обязательства: field ('status' | 'due' | 'important'), before, after, at, write_id (null — руками)
// отмена записи возвращает before, только пока стоит её after (поправленное руками остаётся), и убирает её строки;
// новый текст — не строка здесь, а новая версия записи (superseded_by)
```

Правила времени — D39: «давно не было» и просрочки считаются по `occurred_at`, не по `recorded_at`; новый факт закрывает старый, только если произошёл позже; исправление — новая запись, у старой `superseded_at`. Столбцы для детекторов правил (ритм, срок ожидания) — в Б5, когда станет ясна их форма.

### 19.3 Шифрование

- Ключ данных человека — 32 случайных байта; хранится закрытым `SECRETS_KEY` теми же `seal` и `open`, что секреты (§17.2). Ротация мастер-ключа перешифровывает только эти ключи, а не тексты.
- Текст записи и имена шифруются AES-256-GCM ключом данных. AAD — `memory:<owner>:<таблица>:<id строки>:<поле>`: перенесённая строка не расшифруется. Идентификатор строки задаёт приложение до вставки.
- Честная граница та же, что в §17.5: защита от утечки базы и бэкапа, не от владельца сервера.
- Поиск по тексту — в процессе приложения над расшифрованной памятью одного человека (тысячи записей); индексов по тексту в Postgres нет.
- `forgetAll` удаляет ключ данных вместе с записями.

- **Экран** `/memory` (`components/memory/*`, P16 «Карточки»): пункт «Память» в боковой панели под «Задачами», только пока память включена. Слева — поиск, «Не записано», люди, организации и проекты (число открытых, красная точка — есть просроченные), «Правила»; справа — карточка: обязательства («важно» первыми, потом по сроку; срок словами — «просрочено на 3 дн.», «завтра», «через 5 дн.»; «Выполнено» или «Подтвердить» у «ждёт проверки»), «Известно» с «Раньше», события, закрытые свёрнуты. Меню записи — «Откуда» (слова, прежние тексты, история), «Изменить» на месте, «Перенести срок» (завтра, послезавтра, в понедельник, через неделю, без срока), «важно», отменить или открыть снова, «Удалить» с «Вернуть» в тосте. Дни считаются в часовом поясе человека (`lib/memory-dates`). «Сверка» на карточке человека или организации открывает новый чат с просьбой и списком открытых договорённостей в поле (`/?say=`, экран нового чата кладёт её в поле один раз). На телефоне — список, потом карточка.
- `GET /api/memory/chats/[id]` — по своему чату: «Запомнено» по сообщениям и открытые вопросы; при выключенной памяти — `on: false`, и чат ничего не показывает. `POST /api/memory/questions/[id]` — ответ; `POST /api/memory/writes/[id]/undo` — отмена.
- Событие `memory` с id чата идёт той же шиной Redis, что задачи (`core/task-events`), и тем же потоком `/api/notifications/stream`; вкладка слушает один `EventSource` (`lib/owner-stream`) и перечитывает память, только если слово про её чат.
- В чате (`components/chat/chat-memory.tsx`): под ответом — «Запомнено: …» с «Отменить» (строка прячется сразу, тост «Удалено из памяти · Вернуть» ждёт 5 с, потом отмена уходит на сервер) и плашка вопроса с кольцом подсветки. Если вопрос пришёл, пока чат открыт, и плашку не видно (вне экрана или за полем ввода), — тост sonner с вариантами прямо в нём (P18, по образцу ReUI `c-sonner-9`); тосты памяти — в правом нижнем углу над полем ввода. Над видимой плашкой тоста нет: он повторил бы её.
- Состояние памяти — в контексте: строки ленты рисуются из `memo` и перерисовываются при смене контекста.

### 19.5 Чтение в чате — Б4 (сделано)

Пока память включена у человека, `core/memory-read.ts`:

- **О самом человеке — в каждом блоке.** До восьми свежих фактов о «я» — цели и подход к работе («развиваю своих подчинённых»), которые служебная модель записывает как факты о пользователе, — идут с каждым сообщением, даже если оно никого не называет.
- **Блок перед сообщением.** Карточки, которые сообщение называет, ищутся в процессе приложения по словам имени и других имён с учётом падежей: общее начало, кроме двух последних букв, и не короче четырёх («Ольге» — «Ольга Ли», «Вектора» — ООО «Вектор»; «ли» не находит никого). До пяти карточек: открытые обязательства («кто кому должен», срок, «важно», «ждёт проверки»), до пяти текущих фактов и оценок, два последних события. Блок `<memory>` кладётся в начало последнего сообщения человека только на этот запрос — история хранит его слова, кэш префикса не меняется.
- **Инструменты** (только чтение, прямо, не через `find_tools` — их три и они маленькие): `list_commitments` (открытые, «важно» и ближний срок первыми, `overdueOnly`), `memory_card` (всё об одной карточке: сначала открытое, потом что известно, события, затем закрытое и «Раньше», до 80 записей; по id или по имени — если имя подходит к нескольким, возвращаются кандидаты, и модель спрашивает «какой Андрей?»), `search_memory` (по словам, закрытые тоже; модель просят искать несколько раз разными словами), `list_cards` (все люди, организации или проекты с ролью и тем, что известно, — до восьми фактов и оценок на каждого: «кому поручить», «кто разбирается в …» модель решает по смыслу сама, без эмбеддингов). Эмбеддинги — когда поиск по событиям и обещаниям начнёт промахиваться на деле: векторы зашифрованы, как тексты, сравниваются в процессе, отдельный слот служебной модели. Шаги в ленте подписаны словами («Поиск в памяти»).
- **Короткие id.** Карточки в блоке, в `list_cards` и в поиске помечены первыми восемью знаками uuid (`[a1b2c3d4]`) — модель передаёт их в `memory_card`, двух Андреев не путает; в ответах их не показывает. Чужой или выдуманный id не находится: карточки берутся только из памяти владельца.
- **Заметка модели** (`MEMORY_NOTE`): память читается из блока и инструментами, ссылаться «по памяти», слова человека сейчас важнее; менять её модель не может.

Проверено на Gemini 3.5 Flash через Gateway: «кому отдать подготовку демо», «кто разбирается в базах данных», «почему упали продажи — кого подключить», «кто проверит форму оплаты» — верный человек по смыслу («сильный в SQL», «вела презентации для клиентов»), одним вызовом `list_cards`; «что мне должна Ольга» — ответ из блока; «что просрочено» — сама вызвала `list_commitments`; «что я обещал Марине» — блок и поиск, сроки в часовом поясе человека верны.

### 19.6 Предложения «Не упустить» — Б5 (первый шаг сделан)

Раздел на экране нового чата над «Начать с» (P17 «Строки»; в документах — «На сегодня», на экране — «Не упустить»: там и завтрашнее, и просроченное). `core/memory-today.ts` собирает его чтением при каждом открытии экрана, без модели: открытые обязательства — просроченные, со сроком сегодня или завтра, «ждёт проверки», «важно»; порядок — «важно», дольше всего просроченное, «ждёт проверки», сегодня, завтра. Дни — в часовом поясе человека. Строка — текст обязательства (с другой стороной впереди, если текст её не называет) и «почему» справа; нажатие кладёт в поле просьбу без склонений («Составь короткое вежливое напоминание. Кому: … О чём: … Срок был …»), отправляет человек. Меню: «Уже сделано» / «Подтвердить», «Перенести срок», «Открыть в памяти», «Убрать» — у каждого тост с «Вернуть». «Убрать» — строка в `memory_dismissals` со сроком (`as_of`) и статусом на тот момент: новый срок или статус возвращают обязательство в раздел. Строка этой таблицы — вид (`kind`: `commitment`, `rhythm`, `date`, `keep`, `reminded`, `review`, `mail`, `mail_offer`, `merge_pair`) и колонки того, что убрано (`record_id`, `entity_id`, `other_entity_id`, `mailbox_id`, `letter`, `day`), уникальные вместе; в коде — `DismissalTarget` в `core/memory.ts`. До миграции 0066 вид и цель склеивались в текстовый ключ. Говорим «собрано», не «Metobe следит» (D38).

**Второй шаг — правила (сделано).** У правила открытые столбцы `rule_kind` (`rhythm` — как часто человек хочет быть на связи с кем-то; `wait` — сколько можно ждать ответа или результата от других), `interval_days`, `working_days`; служебная модель отдаёт их вместе с текстом правила («с каждым из моей команды» — ссылка на группу, см. ниже; правило «про себя» — для всех). Раздел, без модели:

- **ожидание** — открытое обязательство другой стороны передо мной без срока, которое ждёт дольше правила для этой стороны (или общего): «ждём 6 дн.», рабочие дни — без суббот и воскресений; меню — как у обязательства;
- **ритм** — человек, с которым по правилу пора: дней с последнего события с ним (нет событий — с того дня, когда правило сказано) не меньше периода: «не было 18 дн.»; нажатие кладёт просьбу договориться о встрече, «Уже было» записывает контакт сегодняшним днём (событие, «Вернуть» удаляет его), «Убрать» — до следующего контакта (`memory_dismissals` вида `rhythm`: правило, карточка и день последнего контакта). Новое правило о том же человеке и того же вида заменяет старое без закрытия («теперь раз в неделю»). На наборе S13 Gemini 3.5 Flash разобрала все три правила (14 дней по команде, 5 рабочих дней ожидания, 7 дней с Игорем).

### 19.6a Группы (сделано)

«Моя команда», «отдел продаж», «бухгалтерия», «подрядчики» — карточка вида `group` (другая компания — организация, не группа). Кто в группе, хранится не на карточке, а фактами: «Павел — в моей команде» — запись со ссылками на человека (`about`) и группу (`group`); «Марина ушла из команды» служебная модель отдаёт в `leaves`, и запись закрывает её факт членства (`valid_to`, «Отменить» открывает снова). Состав читается каждый раз заново (`core/memory-groups.ts`): живые, не удалённые, не заменённые и не закрытые факты. Правило «с каждым из команды» ссылается на группу, и «Не упустить» раскрывает её в тех, кто в ней сейчас: новый человек попадает под правило сразу, ушедший выпадает; правило, названное про самого человека, важнее группового. Служебная модель видит группы со списком участников, чтобы «моя команда» в разных сообщениях была одной карточкой. На странице «Память» — раздел «Группы», у группы — «Участники» со ссылками на их карточки. Проверка — S13, часть 7 (`pnpm groups`): Gemini 3.5 Flash 8/8.

### 19.7 Порядок работ

Б1 хранилище и шифрование → Б2a запись → Б2b слот «Решения» → Б3 API страницы «Память» и «Запомнено» → Б4 чтение в чате → Б5 предложения → интерфейс (P16, P17). Дальше — второй проход (§19.8, D40): В1 надёжная запись → В2 уборка → В3 качество → В4 память без экрана нового чата → В5 удаление упоминаний. Бэкенд раньше интерфейса: прототипы решены, а то, что можно проверить без экрана, проверяется тестами и скриптом оценки на S13.

### 19.8 Второй проход (D40)

Что не учли и что решено — D40, этапы — PLAN, «Память, второй проход». Пункты D40.1–3 решены 2026-11-09.

**19.8.1 Очередь по человеку (В1, сделано 2026-11-09).**

- `queueMemoryWrite` сразу создаёт строку `memory_writes` (`queued`) — новые столбцы `sent_at` (время сообщения), `time_zone` (пояс при отправке, D31), `attempts` — и ставит задание `{ ownerId }`. Повторная постановка того же сообщения попадает в ту же строку (unique по сообщению).
- Worker берёт замок `memory:lock:<owner>` в Redis (`SET NX PX 120000`, свой токен). Не взял — задание откладывается на 5 с (`moveToDelayed` + `DelayedError`). Взял — читает строки человека `queued` по `sent_at` по одной, продлевает замок после каждой, в конце снимает его своим токеном. Задания того же человека, пришедшие во время чтения, находят очередь пустой.
- Сбой модели на строке: `attempts + 1`, задание падает и повторяется BullMQ с паузой; следующая строка не читается раньше упавшей — порядок держится. После трёх попыток строка — `failed`, очередь идёт дальше.
- `forgetMessages` у строки `queued` просто удаляет её. Выключенная память — строки не создаются, как сейчас.
- Чтение очереди — `core/memory-drain.ts` (без базы и Redis, тест `memory-drain.test.ts`: порядок, повтор упавшего без обгона, отказ после трёх попыток, нет модели, потерян замок); строки — `nextQueuedWrite`, `failWriteAttempt` в `core/memory.ts` (тест на отдельной базе), замок и задание — `core/memory-queue.ts`, миграция 0049. Задания, поставленные до очереди (с сообщением в данных), сначала кладут своё сообщение в очередь.
- Живая проверка — `apps/cli/dev/memory-queue-check.ts` (одноразовый пользователь в dev-базе, три сообщения подряд в очередь разом, модель слота «Память»): «Созвонился с Павлом Гуровым из „Вектора"», «Павел обещал прайс к пятнице», «Он уже прислал» — одна карточка «Павел Гуров», обещание «выполнено». Два прогона на Gemini 3.5 Flash — оба верно. До очереди тот же сценарий не воспроизводился: гонка выведена из кода.

**19.8.2 Контекст (В1, сделано 2026-11-09).** Вместо одного обмена (`exchangeBefore`) — последние сообщения того же чата перед прочитанным (`chatBefore` в `core/memory-write.ts`): до 6 сообщений и 4000 знаков, считая с ближнего конца, ответ ассистента — до 800 знаков; ближнее сообщение входит всегда, длинное — обрезанным (`chatContext` в `core/memory-extract.ts`, тесты в `memory-extract.test.ts`). То же окно получает модель «Решений» (`gateState`, поле `earlier` — список `{ role, text }`). Записи из этих сообщений уже лежат (очередь по порядку), правило «не записывать снова» в промпте остаётся. Нижней границы «после прошлого прочитанного» нет: при очереди прошлое прочитанное — это предыдущее сообщение человека, и граница по нему вернула бы один обмен; рассказ в несколько сообщений держится окном.

Проверка — S13, часть 5 (`pnpm context`), к прежним 8 случаям добавлены два рассказа, где «он» и «она» названы два сообщения назад: Gemini 3.5 Flash — 9/10, 10/10, 9/10 (оба рассказа — все три раза; промах — «Ланьшин, встречи не будет», неустойчивый и до правки: база 7/8). Вопросы «Решений» (`pnpm gate`) — ничего нужного не потеряно; Decision-1 и Mammoth-1 отсеяли 13/13 пустых, Jev 7/13 (было 8/13). Живая проверка `memory-queue-check.ts` — верно.

**19.8.3 Кандидаты (В1, сделано 2026-11-10, цели плана — на решении).** Модели «Память» показывается не вся память, а то, о чём может быть сообщение. Функции подбора — в `core/memory-candidates.ts`, без базы: S15 вызывает их напрямую. Тесты — `memory-candidates.test.ts`.

- Карточки (`candidateCards`), не больше 40, обрезаются в таком порядке:
  1. названные в тексте сообщения и окна чата (§19.8.2) по имени или другому имени (`mentionedCards`, перенесена из `memory-read`);
  2. все группы;
  3. карточки записей за 14 дней, до 10, сначала новые — для «он» и «она»;
  4. карточки, у которых слово подписи от пяти букв совпало с текстом («закупщик», «поставщик»).
- Обязательства (`candidateCommitments`) — открытые и «ждёт проверки», не больше 40, ступенями:
  1. со стороной из подобранных карточек, в порядке карточек;
  2. где сторона — сам человек и данные за 30 дней;
  3. совпавшие с текстом по словам от пяти букв; месяцы, дни недели и «будет», «через» не считаются; чем больше общих слов, тем выше.

  Внутри ступени — ближний срок первым. Ступени нужны, чтобы частое слово не вытесняло обязательства названного человека.

- Совпадение слов (`sameWord`): общее начало не короче четырёх букв, а остаток каждого слова — падежное окончание. Так «Ольге» совпадает с «Ольга», «Седову» — с «Седов», «Андреем» — с «Андрей». «Марина» с «Марией», «пришёл» с «пришлёт», «отправил» с «отправить» не совпадают. Без этого на S15 подбор приносил шесть Марий и вытеснял нужное обязательство. Правило действует и в блоке `<memory>` чата.
- Запись (`readWrite`) расшифровывает всю память человека одним `listRecords`; в промпт идёт только подобранное. Факты для групп и `planWrite` берутся из того же списка.
- **Проверка — S15, часть «300 карточек»** (`spikes/S15-memory`). Подбор: записи 95 %, даты 90 %, вопросы 16/16, без лишнего вопроса 26/28, статусы 26/30; 4,2–4,5 тыс. входных токенов (p50). Вся память на тех же 300 карточках: 90 %, 92 %, 8/8, 13/14, 14/15; 12,2 тыс. токенов. Неверно выбранных карточек нет. Промахи одни и те же в обоих режимах: событие или факт, дата «через две недели».
- **Цели плана не выполнены буквально.** Записи 97 % и даты 96 % сняты в S13 на 8 карточках, и на 300 похожих карточках их не достигает ни подбор, ни вся память. «До 3 тыс. токенов» недостижимо: инструкции и схема без памяти стоят 3,35 тыс., подбор добавляет 0,9–1,2 тыс. Предложено мерить так: качество не ниже всей памяти на том же наборе; память добавляет не больше 1,5 тыс. токенов и не растёт с её размером.
- **Расшифровка** 5 000 записей и 300 карточек (`apps/cli/dev/memory-decrypt-bench.ts`): `listRecords` — 64 мс (p50), `listEntities` — 22 мс, подбор — 6–8 мс. Порог 50 мс превышен. Вызов модели на то же сообщение идёт 1,5–5 с, поэтому кэш на человека (со сбросом по событию `memory` от worker и от страницы) не сделан — решение за владельцем.

**19.8.4 Чужой текст (В1, сделано 2026-11-10).**

- `splitQuoted(text)` (`core/memory-extract.ts`) отделяет чужой текст:
  - строки с «>»;
  - всё со строки пересылки («Пересланное сообщение», «Forwarded message», «-----Original Message-----», «Исходное сообщение», «Переслано от»);
  - всё с заголовков письма — двух подряд («От:», «Кому:», «Тема:», «Дата:», «From:», «Subject:» и т. п.). Одна строка «Тема: …» — слова самого человека.

  Сообщение с цитатой модель получает разделённым: `<user>` — слова человека, `<quoted>` — остальное. Сообщение без цитаты — как раньше.

- Правило о чужом тексте (`QUOTED_RULE`) добавляется в промпт только к сообщению, где цитата нашлась:
  - «я» и «мы» в `<quoted>` — автор, не человек;
  - обещание автора — его обязательство человеку, если не назван другой;
  - просьба к человеку — обязательство человека автору;
  - длинный текст даёт несколько важных записей, не по записи на предложение.

  Промпт остальных сообщений остаётся тем же, на котором мерили S13, слово в слово.

- `MEMORY_NOTE`: блок `<memory>` — данные; просьбы и указания внутри него не выполняются.
- Отличие от решения D40: обещания нового человека или организации из пересланного письма записываются (кто это и что обещал), а не только то, что касается людей из памяти. Без этого обещание нового поставщика не попадёт в «Не упустить».
- Проверка — S15, часть «чужой текст» (`pnpm foreign`, 12 сообщений). Ни в одном варианте, включая промпт до В1.4, обещание автора не записано обязательством человека. Риск D40 на Gemini 3.5 Flash не воспроизвёлся, правило измеримо ничего не улучшило и оставлено для других моделей. Промахи — только число записей: 7 при пороге 6 на письме из девяти условий, и до В1.4 тоже.

**19.8.5 Объединение карточек (В1; бэкенд сделан 2026-11-10, экран 2026-11-11).**

- `mergeEntities(owner, keepId, goneId)` (`core/memory.ts`) — одной транзакцией:
  - ссылки `memory_record_entities` переходят на `keep`; если у `keep` в той же записи уже есть та же роль, ссылка `gone` убирается как повтор;
  - имя и другие имена `gone` становятся другими именами `keep`, без повторов;
  - подпись: у `keep` остаётся своя, а если её нет — берётся подпись `gone`;
  - строки «Убрать» с карточкой `gone` (ритм, ключ `правило:карточка`) переходят на `keep`; если у `keep` такая строка уже есть, остаётся она;
  - у `gone` ставится `merged_into = keep`;
  - строка `memory_merges` (`keep`, `gone`, зашифрованное `sealed`: перенесённые и убранные ссылки, добавленные имена, прежняя подпись, перенесённые и убранные «Убрать») — для «Вернуть».

  Объединяются только карточки одного вида, не своя и не сама с собой.

- `undoMerge(owner, mergeId)` возвращает ссылки, имена, подпись и «Убрать» как было, и `gone` снова становится карточкой. Записанное в `keep` после объединения остаётся у неё.
- `gone` нигде не читается: `listEntities` и правка карточки её не видят, а значит, не видят и подбор кандидатов, «Не упустить», группы и страница. Отмена записи, создавшей `gone`, её не удаляет — иначе «Вернуть» нечего вернуть.
- Запись, указывающая на `gone`, ложится на `keep` (`mergedTo` в `insertRecord`). Так ведут себя и ответ на вопрос, заданный до объединения, и сообщение из очереди. В вопросах «Какой Андрей?» кандидат `gone` показывается как `keep`, один раз.
- Отличия от первоначального плана:
  - у `gone` нет `deleted_at` — хватает `merged_into`;
  - подпись берётся у `keep`, а не «новее из двух»: подпись, сказанная в чате (факт о должности), и так уходит к `keep` вместе с фактом;
  - у `memory_dismissals` `record_id` стал необязательным — для «Разные». Миграция 0050.
- Предложения «Один человек?» (`likelySame` в `core/memory-candidates.ts`, `mergeSuggestions`) — без модели, не больше трёх. Пара предлагается, если карточки одного вида и выполнено одно из условий:
  - все слова одного имени есть в другом: «Ольга» — «Ольга Ли», «Вектор» — «ООО „Вектор“»;
  - у людей совпадает фамилия, а имя совпадает или стоит инициалом: «Андрей Ковалёв» — «А. Ковалёв», «Ковалёв Андрей».

  Тёзки с разными фамилиями и «Марина» — «Мария» не предлагаются. Остаётся карточка с более длинным именем. «Разные» — `memory_dismissals` вида `merge_pair` (карточки в порядке id).

- API:
  - `POST /api/memory/cards/[id]/merge {into}` — объединить, в ответе `id` для «Вернуть»;
  - `POST /api/memory/merges/[id]/undo` — вернуть;
  - `GET /api/memory/merges` — предложения;
  - `POST /api/memory/merges/dismiss {a, b}` — «Разные».
- Проверка — тест на отдельной базе: до объединения правило команды считает «Лену» и «Лену Котову» двумя людьми, после — одной; группа — одна участница; «Убрать» переходит и возвращается; «Вернуть» возвращает обе карточки как были. Экран — `components/memory/merge-dialog.tsx` (меню «⋯» карточки) и блок «Один человек?» в «Не записано»; пары приходят в `GET /api/memory` (`merges`).

**19.8.6 Уборка (В2).**

- «Давно открыто» — открытое или «ждёт проверки» обязательство без строк в `memory_changes` за 30 дней, данное раньше 30 дней назад, со сроком не в будущем. В «Не упустить» — одна строка «Сверка: N давно открытых», в понедельник или пока сверку на этой неделе не открывали; нажатие — страница «Память» с фильтром «Давно открыто», у каждого «Выполнено», «Отменено», «Оставить» (`memory_dismissals` вида `keep`, на 30 дней). Вид — прототип P20.
- Вопрос `memory_drafts` старше 14 дней получает статус `expired` (новый в проверке статуса) при сборе «Не записано»; записи, которые его ждали, не ложатся.

**19.8.7 Повторяющиеся даты (В2).**

- `rule_kind = 'date'`, новый столбец `repeat` (`year` | `month` | `week`), опора — `occurred_at` (день); правило ссылается на карточку (`about`). Проверка `memory_records` меняется: у `date` нет `interval_days`, есть `repeat` и `occurred_at`.
- Служебная модель отдаёт `repeat` вместе с текстом: «у Ольги день рождения 14 ноября» — правило `date`/`year` о ней, «отчёт каждую пятницу» — `date`/`week` о самом человеке.
- «Не упустить» — ближайший повтор сегодня или завтра, день рождения — за 3 дня. Нажатие кладёт просьбу: для дня рождения — составить поздравление, иначе — напоминание о сроке. «Уже сделано» — до следующего повтора (`memory_dismissals` вида `date`: правило и день повтора).
- Проверка — S15, часть «даты».

**19.8.8 Качество (В3).**

- Считается запросами, тексты не читаются: `memory_writes` — `done`, `skipped`, `failed`, `undone` (отменено под ответом); удалено руками — `deleted_at` у записи, чья запись не `undone`; исправлено руками — новая версия с тем же `write_id`, что у старой; «Не запоминать» — `memory_drafts.status = 'dismissed'`; цена — `model_runs` с назначением `memory` и `decide`.

- `pnpm memory:eval` в `spikes/S13-jev` — все наборы S13 и S15 одной командой со сводкой; прогоняется при смене модели слота.

**19.8.9 Память в задачах (В4).** `toolsFor` в `core/task-run.ts` добавляет `memoryTools(ownerId, timeZone)` и заметку о памяти, если память включена у владельца задачи; блок `<memory>` — по тексту инструкции задачи. Запуски задач в память не пишутся.

**19.8.10 Ответ ассистента (В4).** Служебная модель получает и ответ на это сообщение (`<answer>`, до 2000 знаков) с правилом: из ответа — только `updates`, только «ждёт проверки» и только когда ответ сообщает полученное из инструмента (почта, CRM), а не совет или план ассистента. Под ответом — «Ждёт проверки: …» с «Отменить»; в «Откуда» — «из ответа». Проверка — S15, часть «ответ».

**19.8.11 Письмо по утрам (В4).** Настройки памяти: «Письмо по утрам» (выключено) и час. Тик задач (`dispatch`, раз в минуту) находит людей, у кого час настал по их поясу и письма сегодня не было, собирает «Не упустить» (`core/memory-today`) и шлёт письмо, только если в нём есть пункт, которого не было в прошлом (ключи пунктов прошлого письма — `memory_letters`). Письмо `@metobe/emails/memory-letter` по образцу `task-letter`: до 7 строк, у каждой ссылка на экран нового чата с просьбой (`/?say=`). Вид — прототип P21.

**19.8.12 Удаление упоминаний (В5).** `metobe memory:forget-person "<имя>"` в CLI владельца сервера: расшифровывает карточки всех людей, находит по имени и другим именам, показывает число совпадений и после подтверждения удаляет карточки; записи, где человек — единственный предмет или сторона, удаляются, в остальных убирается ссылка. В журнал установки — дата и число, без имён.

**19.8.13 «Не запоминать этот чат» (Д7.2, сделано 2026-11-11).** `chats.memory_off` (миграция 0054). `queueMemoryWrite` не ставит в очередь сообщение чата с флагом (`isChatMemoryOff`), поэтому строки в `memory_writes` нет и «Запомнено» под ответом не появляется. Выключается только запись: блок `<memory>` и инструменты чтения в таком чате работают, а уже записанное остаётся. Пункт в меню «⋯» шапки чата (только при включённой памяти) и пометка «Не запоминается» рядом с названием.

**19.8.14 Список памяти в боковой панели (2026-11-11).** На страницах `/memory` боковая панель приложения уходит на уровень вглубь, как настройки: «‹ Чаты», название, строка «N карточек · открыто M», поиск и строки — «Давно открыто», «Не записано», «Календарь», «Обо мне», карточки по видам с «+», «Правила». Строка, заголовок группы, шапка и скользящая подсветка — общие части `components/sidebar-list`, те же, что у списков настроек. Карточка и календарь занимают страницу целиком. Состояние одно: `MemoryStoreProvider` в `ChatShell` держит список, сроки, число давно открытого, открытую карточку, поиск, выбор (в адресе) и действия; читает только на страницах памяти и заново при каждом входе. Счётчики «просрочено» в списке и в строке «Календарь» считаются из тех же строк сроков, что и календарь (`lib/memory-late`). На телефоне, пока ничего не выбрано, те же строки стоят на самой странице. Так же устроен уровень заданий на страницах `/tasks` (`components/tasks/task-level`): «‹ Чаты», «+» для нового задания, «Обзор» и задания по группам «Ждут вас», «Остальные», «Выключены» с цветом, расписанием и кольцом, пока задание ждёт человека. В корневом меню у «Памяти» и «Заданий» справа шеврон — пункт ведёт на уровень вглубь, как в настройках.

### 19.9 Третий проход (D41)

Что берём у других и в каком порядке — D41, этапы — PLAN, «Память, третий проход».

**19.9.1 Время в ответе модели (Г1.1, сделано 2026-11-10).** В схеме ответа (`extractionSchema`) поля `when` и `due` обязательны: «времени нет» — точность `none` и пустая дата; период правила `interval_days` — число, `0` — «периода нет». Причина: модель, которой разрешён `null`, выбирает его, даже написав дату в текст записи. DeepSeek v4.1 Flash 1017 оставлял пустой треть дат («перенесена на 20 ноября» в тексте, `when: null`). Не помогли: правило-самопроверка в промпте (79 %), поля времени перед текстом (58 %), рассуждения по умолчанию вместо `low` (42 %). `planWrite` считает `none` и дату с точностью `none` отсутствием времени. S13, записи и даты: DeepSeek — 93–100 % и 88–92 % в трёх прогонах, Gemini 3.5 Flash — 97 % и 100 %.

**19.9.2 Имена (Г1.2, сделано 2026-11-10).**

- Память до 40 карточек показывается модели целиком: подбор (§19.8.3) нужен большой памяти, а имя, которого слова не ловят («Лёха», «шеф»), модель расставит сама.
- `core/memory-names.ts` — словарь коротких имён («Оля» — Ольга, «Саша» — Александр и Александра) и имён с беглой гласной («Павлу» — Павел, «Льва» — Лев). `sameName` в `core/memory-candidates.ts` сравнивает через него и подбор карточек, и блок `<memory>` чата, и предложения «Один человек?» («Оля» — «Ольга Ли»).
- В словарь не взяты имена, чья короткая форма — частое слово: Люда («люди»), Люба («любой»), Поля («поля»), Тёма («тема»), Лида («лиды»), Тоня («тона»).
- До правки «Написал Павлу и Оле» не показывало модели ни одной карточки, и она заводила вторые.

**19.9.3 Замена устаревшего (Г1.3, сделано).** «Встречу перенесли на четверг», «„Склад 2.0“ перешёл в тестирование», «договор не к пятнице, а к понедельнику» больше не добавляют запись рядом со старой.

- **Что видит модель** (`candidateKnown`, `core/memory-candidates.ts`): действующие факты подобранных карточек и самого человека — до пяти новейших на карточку, тридцать всего, без фактов о составе групп (это `leaves`); события этих карточек — будущие и за последние семь дней, пятнадцать, ближние к сегодняшнему дню первыми. Оценки не показываем: «стал надёжнее» — вторая оценка с датой, а не замена. Блок «Current facts and coming events» — после списка обязательств, у каждой записи ссылка (`f1`, `e1`), день и карточки (`about c3`), чтобы новая запись указала те же. Пока известных записей нет, блока и правила замены в промпте нет вовсе — S13 мерили без них; правило про перенос срока (`moves`) добавляется, пока в промпте есть открытые обязательства.
- **Что отвечает модель:** у записи последнее поле `replaces` (ссылка или «none»; последним — чтобы порядок остальных полей остался тем, на котором меряли S13), отдельный массив `moves: [{ ref, due }]` для обязательств, у которых сообщение меняет срок. «Ничего не заменяет» — явное значение «none», а не пустая строка: DeepSeek заполняет пустое поле ссылкой на первый факт карточки (тот же урок, что в §19.9.1). Правило в промпте даёт проверку: если старая запись и новая могут быть верны одновременно — «none».
- **Что принимает код** (`resolveReplaces` в `planWrite`): ссылка была показана; вид тот же (факт заменяет факт, событие — событие); у новой и старой записи общая карточка; старую не заменяет вторая запись того же ответа; запись, которая ждёт вопроса «какой Андрей?», не заменяет ничего. Иначе `replaces` молча снимается, запись остаётся рядом. Перенос срока принимается, если ссылка среди показанных обязательств, день настоящий и отличается от нынешнего, обязательство не закрывается тем же ответом.
- **Хранилище** (`applyWrite`, миграции нет): факт — у старого `valid_to` на день начала нового (или сейчас), `closed_by_write` сообщение, только если новый не начался раньше старого («в сентябре был на этапе дизайна» — история, не конец); событие — у старого `superseded_at` и `superseded_by` новое; срок — `changeCommitment` со строкой `memory_changes`. Чужая, удалённая или уже заменённая запись не трогается. «Отменить» возвращает факт, событие и срок.
- **Что видит человек:** под ответом «Запомнено: … · заменило: «…»» и «Срок перенесён: … · 13 ноя → 16 ноя»; на странице «Память» заменённое сообщением событие — в свёрнутом «Раньше» под «Событиями» (старая версия ручной правки не видна: у неё то же сообщение, что у новой), факт с `valid_to` и так в «Раньше». Для модели чата заменённое событие в `memory_card` помечено и идёт в конце.
- **Допущение:** «заменило» у факта — это закрытый тем же сообщением факт с общей карточкой; если одно сообщение закрыло и заменило факты одной карточки, пары могут встать не так. Точной связи нет: она потребовала бы колонки.

Проверка — S15, часть 3, 26 сообщений, 15 нужных замен, 4 переноса срока.

- **Gemini 3.5 Flash**, первая редакция правила: замены 15/15 (до ссылок на карточки в блоке — 14/15), неверных 0, переносы 4/4.
- **DeepSeek v4.1 Flash 1017** (модель слота), первая редакция: замены 15/15, но на сообщениях «новое рядом со старым» («Андрей Смирнов ещё ведёт код-ревью», «Игорь Белов любит, когда отчёты приходят утром») — неверная замена в 5 вызовах из 20: новая запись закрывала факт о должности или этапе. На Gemini этого не было, и на DeepSeek Г1.3 сначала не мерили.
- **DeepSeek, вторая редакция** («none» в поле и проверка «могут ли обе быть верны»): в двух прогонах замены 30/30, переносы 8/8, неверных 0 из 52; на сообщениях «рядом со старым» — 0 из 20.

S13 с блоком на DeepSeek, по два прогона, у каждой карточки роль записана фактом. На восьми карточках: записи 56/57, даты 46/48. На трёхстах: записи 52/56 (93 %), даты 39/48 (81 %); тот же набор без блока (`NOKNOWN=1`) — 52/58 (90 %) и 41/48 (85 %). Блок обычным сообщениям не мешает: разница меньше разброса между прогонами. Просадка на Gemini (90 % при 95 %, 29 записей) парным прогоном не проверена; Gemini больше не стоит в слоте. Попутно: «Игорь теперь руководит отделом продаж» при известном факте «Игорь Белов — руководитель отдела продаж» модель не записывает вовсе — второго факта рядом с первым нет, разметка S13 это теперь принимает.

**Проверка замены моделью решений (2026-11-10).** Писатель называет, что заменяет (`replaces`), код проверяет ссылку, и перед записью модель решений слота «Решения» получает по каждой такой паре один вопрос `choice`: заменяет / дополняет / то же / не связано (`core/memory-relations.ts`, `withRelations` в `core/memory-write.ts`). В состоянии — сообщение, тексты новой и старой записи и **их дни** в поясе человека. Замена остаётся только при уверенном «заменяет», P ≥ 0,9 (в S13 ответы моделей решений с P ≥ 0,9 не ошибались); иначе запись ложится рядом со старой. Нет модели в «Решения», нет ответа, сбой или таймаут — остаётся слово писателя, как до этого шага: проверка только придерживает, записей не теряет. Цена пары — около 130 токенов, $0,000005 и 0,5 с.

Почему дни: если старое событие записано «в среду», а новое — «Встреча с „Вектором“» с днём в поле, без дней Decision-1 принимала «ещё одну встречу в пятницу» за перенос с P = 0,87–0,95 (ложная замена); с днями — «дополняет» (замена 0,13–0,5). На встрече без дней в тексте с днём 1,0, без него 0,85.

Что измерено (S15, набор `relation`: 19 пар «обновления», 5 прогонов, Decision-1): настоящие замены сохранены 75/75, дополнения сняты 20/20, около $0,001. Писатель с блоком и «none» на наборе «обновление», замены писателя: DeepSeek 45/45 и 0 неверных из 78 (три прогона), GPT-OSS 120B 28/30 и 0 неверных из 52, Qwen 3.7 Flash 9/30 и 0 неверных из 52. **Пользы от проверки на этих наборах пока нет: неверных замен нет ни у одного писателя.** Она страхует писателя, которого не меряли (в слоте на dev уже побывали DeepSeek и локальная `gpt-oss:120b`), и ловит дорогую ошибку за доли цента. Живая проверка на dev (`apps/cli/dev/memory-update-check.ts`: встреча, факт и срок; писатель `gpt-oss:120b`, решает Decision-1) — все три верно.

Отвергнутая редакция (ветка `wip/g13-postpass`): писателю блока не показывать, замену решает только модель решений. S13 у писателя возвращался к базе (Gemini 97 % и 100 % против 90 % и 92 % с блоком до «none»), но писатель без блока не знает, что уже записано, и пропускает часть: новые записи 9/15 (Gemini) и 12/15 (DeepSeek), перенос срока 3/4, отмены встреч не записываются. На DeepSeek с блоком и «none» было 100 % замен при S13 в пределах шума, поэтому остался дизайн с блоком.

**19.9.4 Все наборы одной командой (Г1.4, сделано 2026-11-10).** `pnpm memory:eval` в `spikes/S15-memory` прогоняет двенадцать наборов S13 и S15 — пропуск сообщений, записи и даты, «какой Андрей», контекст, закрытие обязательств, цели человека, группы, то же на трёхстах карточках, чужой текст, обновление — 238 сообщений, на DeepSeek около $0,30 и две минуты. Каждый набор отдаёт свои случаи (`evalCases`): что отправить модели и как оценить ответ; оценка — по тому, что примет `planWrite`. Своя команда набора остаётся.

- Перед прогоном — число случаев и оценка цены (случай, который уже прогоняли, стоит столько, сколько стоил); выше $1 нужен `YES=1`. `DRY=1` — только оценка.
- Результат — `results/eval/<модель>/<время>.app.json`: по случаю — номер, сколько раз из скольких верно, токены, цена. Текстов и ключей в нём нет. В git лежит только `baseline.json` модели; `BASELINE=1` делает наборы прогона базой.
- Сводка — показатель, значение, база, разница в процентных пунктах; расход по ответам Gateway и по балансу.
- `FAILED=1` — только то, что упало в прошлом прогоне; `ONLY=набор/номер`; `SHOW=1` — ответы модели. Такие прогоны не сохраняются.
- `NOKNOWN=1` — без блока известных фактов, для сравнения; `MODEL=` — другая модель, у неё своя папка и своя база.

Один прогон набора из 30 сообщений на DeepSeek гуляет на 5–7 пунктов (записи на трёхстах карточках: 97 % и 90 % в соседних прогонах), поэтому база снята в два прогона, а разницу меньше этого сравнением с базой не увидеть.

**19.9.5 Источник материала (И1, первый кусок сделан 2026-11-10).** Чат, письмо, расшифровка встречи — способы добыть материал; память читает то, что отдаёт адаптер, и ни одного из них не знает.

- **Очередь.** Строка `memory_writes` называет источник и материал в нём: `source` (`chat` по умолчанию) и `source_key` (для чата — id сообщения; без внешнего ключа, как и прежде: удаление или правка сообщения отменяет запись вручную). Единственность — `(owner_id, source, source_key)`: тот же материал, поставленный дважды, — одна запись. Миграция 0051 переносит `message_id` в `source_key` (на dev-базе 4 записи, ни одной не потеряно) и убирает колонку. `queueMemoryWrite` принимает `{ ownerId, source, sourceKey, chatId?, at?, timeZone }`; порядок в очереди — когда сказано: то, что назвал вызывающий, иначе то, что скажет источник (`saidAt`), иначе сейчас. Задание, поставленное в очередь BullMQ до миграции (поля `messageId`), принимается как сообщение чата.
- **Адаптеры** (`core/memory-sources.ts`): `load` отдаёт `MemoryInput { at, text, context }` (null — материала уже нет или в нём нет слов), `saidAt` — время для порядка, `announce` — кому сказать, что память изменилась. Адаптер `chat` читает сообщение, до `CONTEXT_TURNS` предыдущих реплик чата и оповещает открытый чат. Новый источник — новый адаптер; чтение (отсев, подбор, модель, план, запись), хранилище и очередь не меняются.
- **Проверка:** тесты ядра 411, веб 215; на dev-базе три сообщения одного человека подряд, прочитанные настоящим воркером с моделью слота «Память» (`apps/cli/dev/memory-queue-check.ts`), — одна карточка Павла, обещание закрыто, записи `done`.
- **Второй источник — заметка на карточке (2026-11-11, P22 «Записать…»).** Адаптер `note` (`NOTE_SOURCE`): материала в чужом хранилище нет, поэтому текст лежит на самой записи очереди — `memory_writes.sealed` (миграция 0052, запечатан ключом владельца, `{ text, about }`; читается `materialOf`). `load` кладёт перед заметкой реплику «What should I remember about <имя> (<роль>)?» (`noteTurn`): «обещал отчёт к пятнице» читается как о человеке этой карточки. Запись, где модель назвала только самого пользователя (или никого), код привязывает к карточке (`onCard` в `memory-extract.ts`, роль по виду записи); назвавшая другого человека остаётся как прочитана. Адаптер помечен `meant`: заметка написана, чтобы её помнили, и модель решений не спрашивается, есть ли что хранить (Б2b). `POST /api/memory/cards/[id]/notes` ставит заметку в очередь и ждёт её до 20 с; ответ — записанное (для «Записано в «Ждёте»: … · Отменить»), «Не нашлось, что запомнить» или «запишется позже». Проверка: набор `note` в S15 (12 случаев, DeepSeek 23/24; локальная `gpt-oss:120b` на dev на двух случаях из четырёх отвечает пусто — настройка, не промпт) и `apps/cli/dev/memory-note-check.ts`.
- **Ещё не сделано из И1:** материал из реплик с говорящими и `memoryPrompt(input)` вместо `memoryPrompt(message, context)` (промпт сообщения чата должен остаться слово в слово — тест на равенство строк), таблица «что может записать материал» по голосу, `forgetSources` вместо `forgetMessages`, набор «источники» в S15 и сверка S13/S15 после шага (MEMORY-PLAN §5).

**19.9.6 Больше работы моделям решений (предложено 2026-11-10, не сделано).** Модель решений отвечает на типизированные вопросы — «да/нет», выбор из названных вариантов, шкала — с вероятностями, ничего не пишет и стоит в десятки раз дешевле писателя. Шлюз уже задаёт ей шесть вопросов «да/нет» и использует только «все ниже 0,1»: остальные вероятности выбрасываются. Предложено, по возрастанию цены:

- **Маршрутизация правил.** Подсказка писателя — 7,3 тыс. знаков инструкций и около 2 тыс. токенов схемы. Узкие правила (замена, закрытие обязательств, группы, цитата, ритм) — около 4 тыс. знаков, примерно 1,3 тыс. токенов; давать их только когда нужны. Решает уже посчитанное шлюзом («изменилось ли что-то», «правило») плюс новые вопросы. Для цитаты это уже так и без потерь. Ложное «нет» ухудшает запись, поэтому порог смещён к полноте, сомнение и отказ модели — полный путь.
- **Выбор карточки и «спросить или угадать».** Выбор из кандидатов с вероятностью; ниже порога — вопрос человеку (P18). Это слабое место писателя («какой Андрей» 75–81 %).
- **Закрытие и перенос обязательств** выбором среди открытых: писателю список не нужен.
- **Дешёвый писатель с каскадом.** Слабые писатели (Qwen 3.7 Flash, GPT-OSS) промахиваются в структуре — не создают карточку, не привязывают запись, не замечают, что уже записано, — а текст пишут нормально. Если структуру отдать модели решений, а полноту проверять по её же вероятностям («факт: 0,95» — писатель факта не вернул — повтор на сильной модели), писатель может стоить $0,0002–0,0007 за сообщение вместо $0,009.
- **Что она не может:** писать текст, имена, точные даты (шкала есть, дат нет). Каждый новый вопрос мерить на своём наборе до включения: «назван ли проект» у Decision-1 7 из 10, у Jev 8 из 10 («переезд офиса», «Бюджет 2027» они проектами не считают), как маршрутизатор ненадёжен.

**19.9.8 Речь помощника о том, что он помнит (исправлено 2026-11-11).** В чате ответы звучали как отчёт о хранилище: «По памяти, Владислав — ваш заместитель», «записи про портал у меня нет», «могу зафиксировать это как обязательство. Сказать?» — и предложение записать то, что записывалось само. Причины были в тексте для модели чата, не в моделях: `MEMORY_NOTE` велел «сказать, откуда известно («по памяти, Ольга обещала…»)» — единственный русский образец в нём, модель повторяла его дословно; описывал помощника как читателя чужой памяти, которая «сама записывает после ответа», — отсюда рассказ об устройстве; не говорил, что делать с новостью от человека, — модель отвечала на неё как на вопрос к базе; блок `<memory>` и инструменты называли вещи словами хранилища (`commitment:`, `fact:`), и те же слова возвращались в ответе. Теперь помощник сам помнит; о знаемом говорит как о знаемом; чего не знает — «вы не называли»; новое от человека — новость, ответ по сути, без «записать?»; «хорошо, запомню» на «запомни»; не обещает «напомню позже» (чат отвечает только на сообщение). Блок читает вид записи как `promise`, `known`, `happened`; описания инструментов переписаны без «memory/commitments». Уроки: пример в тексте модель копирует дословно, и процитированный запрет возвращается вместе с запрещаемой фразой — запрещаемое описывать, не цитировать. Проверка — `apps/cli/dev/memory-voice-check.ts` (одноразовый пользователь, настоящий путь чата, разговор из пяти реплик с проверкой слов хранилища, предложений записать и обещаний «напомню»): на `deepseek-v4-flash` было 0/5, стало 12–13 из 15 за 3 прогона; остаток — «карточка», «могу внести в список», «в памяти» в одном ответе из семи. Не измерено: качество ответов по памяти (набор на чтение Г1.5).

**«Обо мне» (2026-11-11).** Факты, где человек сам — предмет (`about`), раньше нигде не показывались: его карточки на странице нет. `memoryOverview` отдаёт их как `me`, страница — пунктом «Обо мне» над «Люди»; правка, удаление и «Откуда» — как у других записей. Обязательства человека и то, что о нём говорят другие, сюда не входят.

**19.9.9 Свои типы карточек (D42, сделано 2026-11-11).** Вид `custom` (миграция 0053 — в проверке `memory_entities_kind`) и поле `type` в запечатанном теле карточки: слово, как его говорит человек («автобус», «кот»). **Карточки и правила руками (2026-11-11).** У заголовка каждого раздела списка — «+» (по наведению, на сенсорном экране всегда): открывается окно «Добавить в «…»»: имя (Enter или «Создать») — карточка создана и открыта. У «Другое» и своих типов — вещь: слово типа берётся у раздела, у «Другое» спрашивается вторым полем. `POST /api/memory/cards` (`createCard`): имя, уже занятое карточкой или её другим именем, возвращает ту карточку (`existed`, тост «Такая карточка уже есть»), а не вторую. Правило — словами: «+» у «Правил» открывает окно с полем (⌘/Ctrl+Enter отправляет); на странице «Правила» остаётся и тихая строка. Текст идёт тем же путём, что заметка на карточке (источник `note`, материал с `intent: "rule"`; `POST /api/memory/rules`), перед ним модели задаётся вопрос, на который правило отвечает (`RULE_TURN`: «какое постоянное правило запомнить — как или как часто напоминать, за чем следить»); писатель сам выбирает вид правила и период. Набор `note` (S15), 3 случая правил по 3 прогона: вид и период 9/9 (раз в две недели, пять рабочих дней, без периода).

**Контакты у карточки (2026-11-11).** У человека и организации — почта и телефон, в запечатанном теле карточки рядом с именем и ролью (`email`, `phone`; карточки, запечатанные раньше, читаются с пустыми — миграции нет). Вносятся руками на странице («Добавить почту» → ссылка `mailto:`/`tel:`, карандаш по наведению; неверный адрес не сохраняется), `PATCH /api/memory/cards/[id]` проверяет формат. Поиск находит карточку по ним; чату они идут строкой `reach:` в блоке карточки и полями `memory_card`. При объединении карточка берёт у другой то, чего у неё нет, «Вернуть» снимает взятое. Из сообщений чата не читаются: для этого писателю нужно своё поле в схеме и замер на S13/S15 — отдельным шагом; из заголовков писем (Г3) заполнятся сами, а по адресу отправителя письмо найдёт своего человека.

**Источник `openai-compatible` и схема ответа (исправлено 2026-11-10).** Провайдер создавался без `supportsStructuredOutputs`, и схема структурированного ответа модели не отправлялась: писатель на локальной `gpt-oss:120b` отвечал в собственной форме (`facts`, `events`, `commitments`…), три записи подряд падали с «response did not match schema», очередь памяти человека стояла. С флагом ответ по схеме. Касается любой модели из такого источника (Ollama, llama.cpp, vLLM); Яндекс собирается отдельно и не менялся.

## 20. Организации, тарифы и лимиты (D48)

Продуктовые правила — в [ORGS-PLAN.md](ORGS-PLAN.md): роли, тарифы, места, оплата, что видит человек. Здесь — как это устроено в коде. Это самая большая переработка со времени v1: меняются данные, вход, проверки прав, настройки, запуск моделей и фоновые задачи. Спайки — PLAN, этап 0 (S20–S28; все, кроме отменённого S25, пройдены 2026-11-24, их итоги ниже); этапы работ — ORGS-PLAN §12.

С 2026-11-28 схем две (D49). Этот раздел описывает облако и общий механизм. Лицензия self-hosted, главный узел и отличия сервера клиента — §21.

### 20.1 Три уровня данных

- **Платформа** — установка: источники, модели, служебные модели, прокси, почта сервиса, хранилище, обновления, тарифы, курсы, счета. Правит суперюзер и админ установки. В self-hosted это суперюзер и админ клиента; тарифов и счетов на сервере клиента нет (§21.1).
- **Организация** — компания внутри установки: люди, места, каталог MCP, общие скиллы, вход по домену, политики, защита данных, разрешённые модели. Правят владелец и админ организации.
- **Человек** — чаты, файлы, память, задачи, свои подключения и скиллы.

**Организация есть всегда.** Claim создаёт первую организацию, и её владельцем становится суперюзер.

**Схему задаёт лицензия установки, а не переменная окружения** (допущение, §21.3). Лицензия подписана ключом главного узла, поле `scheme`:

- `cloud` — много организаций, тарифы, места по тарифам, счета, деньги видит только платформа. Облако выдаёт эту лицензию само себе;
- `self_hosted` — одна организация: вторую не создать, тарифов нет, места из лицензии (§21.7), лимиты задаёт админ клиента (§20.8), деньги видны, как сейчас.

Нет лицензии — сервер не активирован и показывает только экран ввода кода (§21.8). Внутри схемы поведение задают данные:

- у места есть тариф — работают лимиты тарифа и места по тарифам (облако);
- у человека есть лимит — работает он (self-hosted);
- у организации есть цена мест — выставляются счета (облако, в том числе организации клиентов self-hosted на узле, §21.1).

**Человек — в одной организации.** `user.organization_id` обязателен, почта уникальна во всей установке, как сейчас. Суперюзер облака тоже состоит в организации — в собственной организации платформы. Отдельного вида аккаунта «без организации» нет, поэтому у каждого запроса есть организация.

### 20.2 Контекст запроса

Один раз на запрос собирается `ctx` (React `cache()` в серверных компонентах, явный вызов в route handlers и server actions):

```ts
interface RequestContext {
  userId: string;
  orgId: string;
  platformRole: "superuser" | "admin" | "user"; // user.role
  orgRole: "owner" | "admin" | "member"; // user.org_role
  scheme: "cloud" | "self_hosted"; // из лицензии установки (§21.3)
  tariffId: string | null; // null — без тарифа (self-hosted)
  limits: {
    fiveHours: number | null;
    week: number | null;
    currency: string;
  } | null; // тариф или лимит человека (§20.8)
  orgStatus: "trial" | "active" | "disabled";
  readOnly: boolean; // self-hosted: не оплачено, нет связи дольше запаса, установка перенесена (§21.8)
  seesMoney: boolean; // платформа или схема self_hosted
}
```

- **Сессия Better Auth остаётся на пользователе.** Организация, роль и статус читаются из базы на каждый запрос одним запросом с join. Отключение организации должно действовать сразу, поэтому статус в cookie не кешируется. **Проверить:** включён ли `session.cookieCache` и что в нём лежит.
- **Функции `@metobe/core`, которые трогают общее, принимают `orgId` аргументом.** Глобального «текущего пользователя» в ядре нет. Фоновая задача берёт организацию из своей полезной нагрузки (владелец задачи → его организация).
- **Ворота:**
  - Организация отключена или человек отключён платформой: страницы ведут на экран `/disabled` с причиной, API отвечает 403 с кодом `org-disabled`, `worker` пропускает задачи.
  - Человек, отключённый организацией (`disabled_at`), не входит — как сейчас.
  - `ctx.readOnly` (только self-hosted): страницы открываются, вызовы моделей отклоняются — API отвечает 403 с кодом `license-read-only`, `worker` пропускает задачи, память и сводки (§21.8).
  - Человек не в списке мест лицензии (только self-hosted) — экран «Свободных мест нет», API отвечает 403 `no-seat`. Проверка при каждой сборке `ctx`, с кешем (§21.7).

### 20.3 Роли

- **`user.role`** остаётся ролью установки: `superuser` (один), `admin` (сотрудник платформы; в self-hosted — нынешний админ), `user`.
- **`user.org_role`** — роль в организации: `owner` (один на организацию), `admin`, `member`.
- **Правила — чистые функции в `contracts/members.ts`**, их читают и сервер, и экран. Каждое правило получает обе роли и признак «своя организация». Например, `canInvite(actor, target)`, `canChangeTariff`, `canManageSeats`, `canDisableOrg` (только платформа).
- **Таблица прав** — ORGS-PLAN §4. Тесты правил — таблицей, на все пары ролей.

### 20.4 Данные

```ts

// status: 'trial'|'active'|'disabled', disabled_reason: 'unpaid'|'manual'|null,
// trial_ends_at, time_zone (по умолчанию Europe/Moscow), settings jsonb (§20.6), billing jsonb — реквизиты,

catalog_items; // + organization_id; unique (organization_id, key) вместо unique (key)
```

- **Миграция — в три шага (expand → backfill → contract).** Проверено спайком S28 (ветка `t3/s28-org-migration-spike`) на синтетике размера живой установки:
  1. **Expand.** Первая команда — `LOCK TABLE "model_runs", "invitations", "catalog_items", "skills", "user"`: сначала таблицы со ссылкой на `user`, `user` последним, в том же порядке, что у писателя `model_runs` при проверке FK. Без этого миграция ловит deadlock с писателем `model_runs` (4 прогона из 10). Дальше:
     - `organizations` и сразу первая организация, если в установке есть хоть одна строка;
     - `organization_id` во всех пяти таблицах — с `DEFAULT` = id этой организации, а не через `UPDATE`. Существующие строки не перезаписываются (значение берётся из каталога, PG 11+), старый код при вставке получает организацию сам;
     - `org_role`, `blocked_at`, CHECK и FK — `NOT VALID`, без сканирования;
     - организационные части `policies` (`access`, `personalConnections`, `personalApprovalDefaults`, `privacy`) копируются в `organizations.settings`. Из `policies` они удаляются в О3: старый код читает их там.
  2. **Backfill** — только роли: `superuser → owner`, `admin → admin`, `user → member`, в приглашениях `admin → admin`, `user → member`. Нет суперюзера — владелец старейший админ, иначе старейший человек (так выглядит база `upgrade-check.sh`). Повторный запуск ничего не меняет.
  3. **Contract.** Тот же `LOCK TABLE`, затем догон: организация, если первые строки появились после expand; `organization_id` и `org_role` у строк, которые старый код записал после backfill. Потом `DROP DEFAULT`, `VALIDATE`, `SET NOT NULL`, `unique (organization_id, key)` вместо `unique (key)`, `skills_shared_name` по `(organization_id, name)`, один владелец на организацию, индексы ниже.

  Название первой организации — домен почты суперюзера (решено, ORGS-PLAN §13). Пустая неклеймленная установка организацию в expand не получает, её создаёт claim. **Claim должен создавать организацию до contract:** нынешний `redeemClaimToken` после contract падает на вставке без `organization_id`.

  Все три шага — миграции Drizzle, их применяет entrypoint, как сейчас. **Drizzle (`drizzle-orm@0.45.3`) применяет все ожидающие миграции одной транзакцией.** Отсюда:
  - обновление через несколько релизов выполняет expand, backfill и contract атомарно, `ACCESS EXCLUSIVE` держится до конца всей пачки;
  - `CREATE INDEX CONCURRENTLY` недоступен. На миллионе строк `model_runs` индекс строится 0,64 с — приемлемо;
  - contract ломает старый код (вставки без `organization_id`), поэтому идёт **отдельным релизом** после expand + backfill и **до второй организации** (О4, О5). `DEFAULT` с id первой организации при двух организациях — утечка.

  Цифры S28:
  - миграция: малая установка (≈30 МБ, ≈1,3 тыс. `model_runs`) — 0,11 с; год (догадка, ×12) — 0,20 с; 1 млн `model_runs` — 1,04 с. Вариант с `UPDATE … SET organization_id` на миллионе строк — 43,6 с;
  - всё время миграции приложение ждёт: любой запрос с сессией читает `user`. В self-hosted оно и так остановлено — compose гасит старые `app` и `worker` до старта нового. Простой обновления определяют `pg_dump` (0,7–7 с), drain (до 60 с) и старт контейнера;
  - старый код после expand + backfill работает: функции ядра 4/4, DB-тесты ядра 88/88. После contract — падают.

- **Откат миграции** (S28):
  - до contract — только образ, без базы; записанное после обновления сохраняется;
  - после contract — `down_contract.sql` возвращает расширенную схему с `DEFAULT` (38–70 мс, пока организация одна), или копия апдейтера;
  - копия апдейтера (`restoreBase`) сейчас не работает на Postgres 15+ (§20.15). Починить до О1 и проверять откат в CI.
- **Таблицы лицензии и узла** — §21.1.
- **Домены входа.** `organization_domains (domain PK, organization_id)` (S23): уникальный ключ сам даёт «организации с разными доменами не пересекаются» (О6). Человек, вошедший по домену, получает тариф по умолчанию из настроек организации (`organizations.settings`, ORGS-PLAN §13); своего тарифа у домена нет.
- **Индексы.** `model_runs (organization_id, created_at)` — для отчётов организации и прогноза. `user (organization_id)`. `invitations (organization_id, expires_at)`. `model_runs_user_time` заменяется покрывающим `(user_id, created_at) include (charge)` (§20.8).
- **Чаты отдельной колонки не получают.** «Чат для команды» открыт, если организация читателя совпадает с организацией автора.
- **Срок хранения «что ушло в модель» (`model_payloads`)** — у каждой организации свой, чистка идёт по организации.
- **Удаление неподтверждённых аккаунтов** перестаёт быть побочным действием списка людей и становится задачей платформы в `worker` (§20.15).

### 20.5 Изоляция

Утечка между организациями — главный риск. Защита в три слоя:

1. **Функции с организацией.** Каждое чтение и запись таблиц с `organization_id` идёт через функцию ядра, которая принимает `orgId` и ставит условие сама. Функции «для платформы» (суперюзер видит всех) лежат отдельно, в `core/platform/*`, и вызываются только из разделов платформы.
2. **Правило импорта.** Веб-приложение уже не импортирует `@metobe/db`, все запросы — в ядре, так что правило ставится внутри ядра. Схемы таблиц с `organization_id` импортируют только модули, которые за них отвечают: `catalog.ts`, `skills.ts`, `invitations.ts`, `organizations.ts` и т. д. Ограничение — `no-restricted-imports` в oxlint: запрет на путь схемы каждой организационной таблицы, исключение — модуль-владелец. Проверено в S20 (`oxlint 1.85.0`): импорт схемы `catalog_items` из чужого модуля — ошибка, модуль-владелец проходит. Правило смотрит на строку пути импорта, поэтому обход через общий barrel-экспорт закрывается отдельным запретом на barrel.
3. **Тесты на две организации.** Общий набор создаёт организации А и Б. Для каждого маршрута и действия с общими данными проверяет: человек из А не видит, не меняет и не узнаёт о существовании объекта Б — ответ 404, не 403. Список маршрутов — §20.15.

**RLS в Postgres — четвёртый слой** на `catalog_items`, общих `skills`, `invitations` и `model_runs` (S20, ветка `t3/s20-org-isolation-rls-spike`). Первые три слоя он не заменяет.

- **Роль.** `app` и `worker` подключаются ролью без `SUPERUSER` и `BYPASSRLS`, не владельцем этих таблиц: суперюзер RLS обходит. Сейчас миграции применяет тот же образ (`metobe migrate`), так что роль для миграций и роль приложения нужно развести. Как именно — спайк не проверял.
- **Контекст — только в короткой транзакции.** Каждая операция с такой таблицей идёт в `sql.begin`, первая команда — `set_config('app.org_id', orgId, true)`. Ответ чата транзакцию минутами не держит: короткая транзакция на каждое обращение к базе.
- **Сессионный `set_config(..., false)` запрещён.** Значение остаётся в соединении после возврата в пул, и следующий запрос из пула видит строки чужой организации. Транзакционный `true` поверх такого соединения не спасает: после commit возвращается сессионное значение.
- **Цена.** 40 ответов по 2 минуты, транзакция раз в секунду, пул 10: без RLS p50 7,9 мс / p95 48,7 мс, с RLS 5,6 / 24,7 мс, ошибок нет. Хвост шумный, направление между прогонами менялось — вывод только «явной цены нет». Профиль нагрузки угадан, с живой установки не снят.
- **Проверено:** запрос без контекста видит 0 строк, вставка в чужую организацию отклоняется (`42501`).
- **Путь платформы не проверен.** Межорганизационный доступ (`core/platform/*`, консоль, аналитика по `model_runs`) идёт отдельным явно ограниченным путём; какой он под RLS — решить до О4. Глобальные таблицы платформы под RLS не подпадают.

### 20.6 Настройки: платформа и организация

- **`system_settings.policies`** оставляет платформенное: `mail`, `updates`, `updateAutomation`, `builtinTools`, `searxngUrl`, `searchCheck`, сервисную часть `privacy` (адрес шлюза), `rateLimits` (минутный антифлуд), `billing` (`serversPerMonth`, дни счёта и срока).
- **`organizations.settings`** — то же устройство (части по ключам, у каждой своя схема Zod, `readOrgSettings(orgId)` / `mergeOrgSettings(orgId, patch)` как у `readPolicies` / `mergePolicies`):
  - `access` — домены входа;
  - `personalConnections`, `personalApprovalDefaults`;
  - `privacy` — что прятать, где, что делать с найденным, сколько хранить «что ушло в модель»;
  - `allowedModels` — подмножество моделей тарифов, null — все;
  - `builtinToolsOff` — встроенные инструменты, выключенные у себя.
- **Модули, которые читают эти части сейчас** (`access.ts`, `personal.ts`, `privacy-settings.ts`, `web-settings.ts`), получают `orgId` и читают организационную часть. Платформенная часть остаётся у них же.
- **Меню настроек.** Три группы вместо двух: «Моё» (`scope: 'user'`), «Организация» (`'org'` — владелец и админ организации), «Платформа» (`'platform'` — суперюзер и админ установки). `canOpen(section, ctx)` в `apps/web/lib/settings-nav.ts` решает по группе. В self-hosted админ видит обе группы, как сейчас видит одну.

### 20.7 Какие модели доступны человеку

```
модели человека = включённые модели платформы
                ∩ модели его тарифа        (нет тарифа — все включённые, как сейчас)
                ∩ разрешённые организацией (allowedModels; null — без ограничения)
```

- **Проверка на сервере, не только в выборе модели.** Маршрут чата отклоняет модель не из списка. Запуск задачи с недоступной моделью завершается статусом «Модель недоступна в тарифе» с кнопкой «Выбрать другую». Чат в Telegram берёт модель тарифа по умолчанию.
- **Служебные модели** (названия, зрение, память, решения, сжатие) выбирает платформа, тариф их не ограничивает. Расход идёт в лимит человека, который их вызвал.
- **«×N к лимиту».** Считается как отношение цены среднего ответа модели к цене среднего ответа модели тарифа по умолчанию. Цена ответа — прайс × средние токены ответа чата этой установки за 30 дней (вход без кеша, чтение кеша, выход), из `model_runs`. Пересчёт раз в сутки, кеш — в Redis. Клиенту уходит только `limitFactor`, цен нет.

### 20.8 Лимиты

- **Откуда значения.** `ctx.limits` в облаке берётся из тарифа места, в self-hosted — из лимита человека (`user.limit_id → limits`). Лимит self-hosted задаёт админ клиента: сколько угодно лимитов, у каждого свои значения, цены нет (ORGS-PLAN §14.4). Лимит для новых людей — `organizations.settings.defaultLimitId` (допущение). Дальше механизм один.
- **Стоимость в валюте лимита.** `recordRun` (`core/chat-run.ts`) дописывает к строке:
  - `organization_id`;
  - `charge` = `cost` × курс дня (`fx_rates`: курс × (1 + комиссия) × множитель НДС агента), если валюта модели не совпадает с валютой лимита;
  - `charge_currency`.

  Строка без тарифа и без лимита получает `charge = null`. В self-hosted валюта лимитов одна на организацию (`organizations.settings.limitsCurrency`), комиссия и НДС агента по умолчанию нулевые; при смене валюты строки в старой валюте в окна не входят (допущение).

- **Окна.**
  - 5 часов: строка `limit_windows (user_id, '5h')`. Если с `started_at` прошло 5 часов, при следующем запросе окно начинается заново с `now()`.
  - Неделя: с понедельника 00:00 по часовому поясу организации, вычисляется (`@date-fns/tz`), строки не нужно.
- **Израсходовано** = `sum(charge)` по `(user_id, created_at ≥ начало окна)`. Спайки S21 (ветка `t3/s21-stop-by-cost-spike`) и S22 (ветка `t3/s22-limit-counters-spike`).
  - Индекс `model_runs_user_time` заменяется покрывающим `(user_id, created_at) include (charge)`: Index Only Scan без обращений к таблице. p95 проверки у человека со 100 тыс. строк за год ≈1 мс; если все 100 тыс. за одну неделю — 8–14 мс (граница критерия, машина была занята). С нынешним индексом — 23–70 мс.
  - Агрегата (`limit_usage`) нет: сумма — единственный источник правды. Вводить его, только если на живых данных проверка дольше 10 мс.
  - Покрывающий индекс быстр, пока страницы таблицы отмечены в карте видимости. Без `VACUUM` 100 тыс. свежих строк дают p95 70 мс. Для `model_runs` — `autovacuum_vacuum_insert_scale_factor` ≈0,01 (допущение по документации Postgres, в спайке не проверено).
  - Тип `charge` не важен: `numeric` и `bigint` отличаются на 10–20 %.
- **Проверка до запроса** — `checkLimits(ctx)` в `core/limits.ts`. Возвращает `{ ok, fiveHours?: { used, resetAt }, week: { used, resetAt }, blocked?: 'five-hours' | 'week' }`.
  - Два запроса: окно из `limit_windows`, затем одна сумма с двумя `filter` при `created_at ≥ least(начало 5 ч, начало недели)` — окно в 5 часов, открытое в воскресенье вечером, переходит через понедельник. Один запрос с CTE медленнее (10–30 мс против 6–14).
  - Вызывается в маршруте чата рядом с нынешним `checkChatLimit`, перед запуском задачи в `worker`, перед ответом в Telegram.
  - **Это единственная защита продолжения после подтверждения тула:** `streamText` выполняет одобренный тул до первого вызова модели, а `stopWhen` до первого шага не спрашивается. Без проверки при остатке 0 проходят тул и ещё один платный шаг.

  Отказ в чате — карточка с временем сброса (UX-принцип 4), а не ошибка.

- **Остановка внутри ответа.**
  - **Остаток перечитывается после каждого шага**, а не фиксируется на старте: в сумму человека должен войти расход шагов всех его идущих ответов. С остатком, зафиксированным на старте, два параллельных ответа тратят его каждый целиком (S22: при остатке в 50 шагов перерасход в среднем 50,7 шага). С перечитыванием — не больше шага на каждый одновременный ответ (S22: max 2,0 шага при двух ответах; перечитывание p95 1,8 мс).
  - **Основной путь — мягкий:** `prepareStep` снимает тулы со шага, который по оценке (стоимость прошлого шага) дойдёт до остатка, и ответ кончается текстом без лишнего вызова. Перерасход — один отвечающий шаг, он длиннее шага с тулом (мок S21: 0,0037 $ сверх остатка против 0,0020 $ у жёсткого варианта).
  - **`stopWhen` по сумме — страховка.** В `ai@7.0.173` он спрашивается только после шага с вызовами тулов, когда тулы уже выполнены. Шаг с текстом и шаг, ждущий подтверждения, кончают цикл сами, без `stopWhen`. Поэтому после шагов без тулов нужна отдельная проверка «готовые шаги дошли до остатка» — она решает, ставить ли строку про лимит.
  - **Стоимость шага:** у Gateway — `providerMetadata.gateway.cost` шага, у остальных — токены шага × прайс (`costOf`). У модели без прайса и не через Gateway стоимость 0, и остановки не будет: такие модели не входят в тарифы, либо для них нужна оценка.
  - **Строка про лимит** — data-часть `data-limit` (`{ window, resetAt }`) в сообщении ответа, не текст: «Лимит … исчерпан, ответ остановлен. Сброс в …». Ставится, если ответ остановлен или последний шаг ждёт подтверждения при исчерпанном остатке. Модель её не видит (`convertToModelMessages` отбрасывает data-части), resume отдаёт её из записи стрима, после сохранения — из базы. При продолжении после подтверждения `applyToLast` убирает старую `data-limit` из последнего сообщения, иначе она остаётся над новым текстом.
- **Расход — по готовым шагам, строка — одна на проход** (S21).
  - Стоимость копится в `onStepEnd` (`usage` и `providerMetadata` каждого шага). `totalUsage` не используется: при сбое он пустой.
  - Строка `model_runs` пишется один раз после `await result.consumeStream({ onError })`. Статус — из флагов `onError`, `onStepError`, `onAbort`.
  - Почему не в колбэках: `onError` шагов не получает; при отклонённом вызове провайдера после `onError` всё равно зовётся `onEnd`; при обрыве потока посреди шага не зовётся ни `onError`, ни `onEnd`, ни `onAbort`. «Стоп» — `onAbort({ steps })`.
  - Шаг, прерванный посреди потока, usage не отдаёт: недосчёт — не больше шага. Выставит ли провайдер счёт за прочитанные токены — не проверено.
  - Так же в задачах, Telegram и правке задачи.
  - **Не согласовано между S21 и S22.** S21 пишет строку один раз в конце прохода, а перечитывание остатка (S22) требует, чтобы расход шагов идущего ответа был виден другим ответам человека сразу. Варианты: строка прохода вставляется после первого шага и обновляется после каждого, финальный статус — после `consumeStream`; или расход идущих ответов держится в Redis рядом с арендой слота. Ни один не проверен — решить в О8.
- **Проход «итог».** После остановки по деньгам итог не запускается: остаток уже 0, его заменяет мягкий последний шаг. Итог остаётся для остановки по `MAX_STEPS` и запускается, только если остаток больше 0. Он стоит как ещё один шаг — в 1,1–1,8 раза дороже последнего (мок S21, без кеша промпта). Если итог понадобится и на границе лимита — резерв ≈1,5 × последний шаг.
- **Одновременные ответы.** Не больше двух на человека, считая задачи (S22):
  - sorted set `limits:inflight:{userId}`: член — id ответа, оценка — конец аренды по часам Redis (`TIME` внутри Lua), общий для `app` и `worker`;
  - acquire — убрать просроченных, при двух живых отказать («Дождитесь ответа»), иначе добавить; пульс — тот же скрипт каждые 10 с, аренда 30 с; release — `ZREM` в `finally` и по SIGTERM;
  - упавший процесс отпускает слот не позже конца аренды (на тесте с арендой 3 с — 2,2–3,0 с). TTL «как у самого долгого ответа» держал бы человека без ответа десятки минут;
  - пять вкладок и задача одновременно — приняты две; acquire p50 0,4 / p95 1,8 мс;
  - цикл событий, стоящий дольше аренды, пускает третий ответ — цена короткой аренды;
  - задача `worker` без слота не получает отказ, а уходит в отложенный повтор (BullMQ `moveToDelayed`, 10–15 с) — предложение, не проверено;
  - Redis недоступен или ключ потерян — счётчик открыт, лимит в деньгах всё равно держит (допущение спайка, решение за владельцем).
- **Состояние для экрана.** `GET /api/limits` — проценты и время сброса. После каждого ответа то же приходит частью `data-limits` в стриме, без опроса.
- **Без тарифа и без лимита** (self-hosted, человек без лимита) лимитов в деньгах нет, нынешние `rateLimits` работают как сейчас.
- **Self-hosted видит суммы.** `GET /api/limits` при `ctx.seesMoney` отдаёт вместе с процентами израсходованное и лимит в деньгах (допущение).

### 20.9 Деньги не уходят клиенту

`ctx.seesMoney` ложно у людей облачных организаций; в схеме `self_hosted` оно истинно у всех, деньги видны, как сейчас. Когда ложно, сервер не отдаёт `cost`, `price*`, `currency` и `charge` ни в одном ответе:

- `/api/usage` и серверные компоненты «Расходов» отдают проценты и число запросов;
- данные выбора модели — `limitFactor` вместо `price`;
- «Использование» владельца — проценты.

Тест обходит все маршруты API под участником организации с тарифом и ищет в ответах ключи с деньгами.

### 20.10 Места и счета

Облако и организации клиентов self-hosted на узле. На сервере клиента своих счетов нет, места приходят с узла: строка `org_seats` без тарифа, число мест — из лицензии (§21.6, §21.7).

- **Занято по тарифу** = активные люди с этим тарифом + приглашения на этот тариф без ответа. При принятии приглашения считаются только активные: приглашение своё место уже держит.
- **Каждое изменение мест — в транзакции** с `SELECT … FOR UPDATE` строки `org_seats (организация, тариф)`. Сюда относятся: приглашение, принятие приглашения, вход по домену, включение человека, смена тарифа человеку, изменение числа мест. Двое, которые одновременно берут последнее место, не пройдут оба. Проверено спайком S23 (ветка `t3/s23-auth-seat-transaction-spike`, Better Auth 1.7.5):
  - **Хуки Better Auth работают вне транзакции.** `signInEmailOTP` не оборачивает `createUser` в `runWithTransaction`, у `drizzleAdapter` по умолчанию `transaction: false`. Блокировка, взятая в хуке, снимается до вставки пользователя: перебор мест в 30 гонках из 50.
  - **Приглашения и claim — наши функции в своей транзакции**, Better Auth пользователя не создаёт. Принятие приглашения — `FOR UPDATE` строки приглашения, затем `FOR UPDATE org_seats`; глобальный advisory-lock 7272703 больше не нужен. Выдача приглашения, включение человека, смена тарифа, изменение числа мест — `FOR UPDATE org_seats` в той же транзакции. Claim сохраняет свой advisory-lock и создаёт организацию с суперюзером-владельцем.
  - **Вход по домену** — единственный путь, где пользователя создаёт Better Auth. Действие `verifyCode` вызывает `signInEmailOTP` внутри `runWithTransaction`, `drizzleAdapter(db, { transaction: true })`, где `db` — обёртка, которая кладёт drizzle-транзакцию в свой `AsyncLocalStorage`. Хук `user.create.before` берёт эту транзакцию, блокирует `org_seats` и при нехватке мест бросает `APIError("FORBIDDEN", { code: "NO_FREE_SEATS" })`. Откатывается всё, включая расход кода: тот же код можно ввести снова. Без транзакции (прямой POST в обход действия) хук бросает `SIGN_UP_OUTSIDE_TRANSACTION`. На последнее место входит ровно один в 50 из 50; `verifyCode` показывает «Свободных мест нет», а не «Неверный код».
  - **Внутри транзакции читать только через неё**, не через пул. Иначе при наплыве входов пул взаимно блокируется: 20 входов на пуле 10 зависли дольше 10 с, Postgres этого не видит. Касается и `isSignInAllowed` в `session.create.before`.
  - **Отказ из хука — только `throw APIError`.** `return false` роняет `signInEmailOTP` (§20.15).
  - Действие с двумя тарифами (смена тарифа человеку) блокирует строки `org_seats` в порядке `tariff_id`, иначе возможен deadlock — допущение по общему правилу, не проверено.
  - Решение опирается на поведение Better Auth (адаптер в `AsyncLocalStorage`, `queueAfterTransactionHook`), а не на документированный контракт хуков. Гонки S23 переносятся в тесты `core` как регрессия при обновлении Better Auth.
- **Журнал мест.** Любое изменение пишется в `seat_changes` вместе с доплатой. Доплата = Δмест × цена × оставшиеся дни / дни месяца, дни — по часовому поясу организации, день изменения входит. Повышение тарифа — разница цен × та же доля, ставка и режим НДС — нового тарифа (допущение S24). Понижение — без доплаты, с 1-го числа.
- **Задачи биллинга** — в `worker`, **каждый час** (S24, ветка `t3/s24-billing-calendar-spike`): повторяемая задача `billing-tick` в отдельной очереди BullMQ `billing`, `concurrency: 1`. Не в `tasks`: там идут вызовы моделей, и тик ждал бы за ними. Раз в сутки не годится: 00:00 по поясу организации — разный час UTC, отключение и перекат опоздали бы до суток. Пропущенные тики не копятся: после простоя в очереди одно задание.
  - **Идемпотентность.** Ключ действия (`invoice:org1:2026-12`, `notify:owner:1d:org1:2026-12`) — в `billing_actions (key primary key)`, в той же транзакции, что и эффект, под `FOR UPDATE` организации и её `org_seats`. Состояние перечитывается под блокировкой, эффект пересчитывается. `unique (organization_id, period)` защищает только счёт; перекат, отключение и письма без ключа не защищены. Письма — строкой outbox в той же транзакции. 50 одновременных коммитов одного ключа — применён один.
  - **Счёт:** с 00:00 25-го — за следующий месяц. Мест в счёте — `max(seats_next, занято)` по каждому тарифу × цена, плюс доплаты из `seat_changes` без счёта, НДС по строкам. Тик, пришедший после 25-го, ставит срок не раньше «сегодня + 3 дня» (допущение).
  - **Перекат:** 1-го числа в 00:00 по часовому поясу организации `seats = max(seats_next, занято)`, в журнал пишется `rollover`. Если мест стало больше, чем в выставленном счёте (место добавили после 25-го), строка `rollover` несёт сумму за полный месяц на разницу — она уйдёт в следующий счёт. Стало меньше — возврата нет.
  - **Срок:** 1-го числа в 00:00 неоплаченный счёт этого периода делает организацию `disabled` с причиной `unpaid`. В журнал — событие с номинальным моментом срока и временем прогона, владельцу и суперюзеру — уведомление. Отметка «Оплачен» включает организацию, если она была отключена за неоплату. Простой задачи дольше срока — отключение на первом тике, льготы нет (решено, ORGS-PLAN §13).
  - **Напоминания:** владельцу — за 5 дней и за день до срока, суперюзеру — за 3 дня, списком; с 09:00 местного (допущение), не раньше дня после выставления, после срока не шлются. В феврале между 25-м и 1-м 4 дня — «за 5 дней» не отправляется.
- **Календарь** (S24, 259 тестов): дни считаются по календарю пояса, 23- и 25-часовые сутки на доплату и срок не влияют; если 00:00 в поясе не существует, берётся первая минута суток; `invoiceDay` и `dueDay` — 1–28. Округление — половина вверх, одно на строку журнала и одно на строку счёта; НДС по строкам, итог — сумма строк (сверить с бухгалтерией). Тик на 1000 организаций — 0,55–0,75 с.
- **Организация клиента self-hosted** (`kind = 'self_hosted'`) идёт тем же тиком. Отличия (допущение):
  - людей в ней нет: «занято» — число мест в списке `seat_holders` (§21.1, §21.7). Перекат 1-го ставит `seats = seats_next` и убирает лишних из списка: кого оставить, выбирает владелец, иначе остаются назначенные раньше всех (§21.6). Мест в счёте — `seats_next`;
  - изменения мест приходят запросом с сервера клиента (§21.6) и пишутся в `seat_changes` с `by` = установка;
  - разовая плата за лицензию сервера — счёт `kind = 'license'`, вне календаря;
  - неоплату сервер видит сам: «оплачено до» уже в лицензии, и в 00:00 1-го он встаёт в «только чтение» в тот же момент, что облачная организация отключается (§21.8). Ручное отключение — лицензия с «оплачено до» = момент отключения, сервер получает её при следующей связи.
- **Не покрыто S24:** реальная схема БД, запись `seat_changes` при изменении мест, письма. Угаданы правила месяца создания (доплаты уходят в счёт 25-го), пробного периода (периоды до `trial_ends_at` бесплатны) и отключённой организации (новых счетов нет, после включения — запоздавший счёт на текущий месяц).

### 20.11 Прогноз

Проверено спайком S26 (ветка `t3/s26-spend-forecast-spike`).

- **Ядро — чистая функция `replayLimits(runs, seats, tariffs, options)`** в `core/forecast.ts`: прогон записанных ответов через лимиты, та же логика, что во внутреннем калькуляторе. Без часов и БД.
  - `runs` — колонками (типизированные массивы), не массивом объектов; `seats` — `{ тариф, since }`, без них людей не разложить по тарифам и не посчитать дни места.
  - Результат — по человеку: расход, отклонённые запросы, остановленные ответы, упоры в окна, самая дорогая неделя и окно без лимитов. Сводка по тарифам — отдельная чистая функция `forecastNextMonth`.
  - Сверка с калькулятором: живой набор, 300 сценариев × 3 тарифа — 0 расхождений; синтетика на 935 местах, 101 304 сравнения — 0. В тестах — `golden.json` с ответами калькулятора на синтетике; живой набор в репозиторий не кладётся, его сверяют вручную.
  - Смещение пояса для недели передаётся в ядро.
- **Данные** — `model_runs`: человек, время, назначение, `cost` + `currency` и токены. Из `charge` курс, комиссию и НДС не покрутить — он уже в валюте тарифа по курсу своего дня; `charge` нужен только для «как записано». «Все ответы на модели X» переоценивает только запросы человека (`chat`, `task`), служебные строки остаются как записаны.
- **Окно по умолчанию — 4 недели**, 8 недель — по просьбе. На 1000 мест холодный запрос: 4 недели (137 тыс. строк) — 0,3 с; 8 недель (265 тыс.) — 0,5–0,6 с, на загруженной машине до 0,85 с; 1 млн строк — 2,2–2,7 с. Граница 1 с — около 400–500 тыс. строк в окне: дальше «считаю…» и расчёт в `worker` или окно короче. Узкое место — выгрузка строк в Node, сам расчёт — 3–25 мс.
- **Чтение.** Порядок `(user_id, created_at, id)` — id нужен для совпадения с порядком записи при равном времени. `date_part` вместо `extract`, `(cost * 1e12)::bigint` вместо `cost::float8` (иначе +240 мс на 265 тыс. строк; точно до 12 знаков после запятой у `cost`). Строки сразу в типизированные колонки, 53 байта на строку.
- **Кеш колонок** в памяти `app`: ключ `(организация, окно, число строк / max(created_at))`, срок — несколько минут, ≈55 МБ на миллион строк. «Покрутить» по кешу — 3–25 мс.
- **SQL-агрегаты — не основной путь.** Окно в 5 часов они считают фиксированным ведром, отклонений и остановок не дают, людей в упоре по 5 часам занижают на 20–30 %, с калькулятором не совпадают. Допустимы как быстрый первый показ с пометкой «примерно».
- **Следующий месяц:**
  - выручка — `org_seats.seats_next` × цены, с НДС;
  - модели по каждому тарифу — расход места в окне ÷ дни места в окне × 30,4 × места. Дни — от `max(since, начало окна)`, места без единой строки считаются. Калькулятор считает место с первой строки — разница зафиксирована в тесте;
  - серверы — из настроек.
- **«Покрутить»** считает на сервере по запросу. Ничего не сохраняется, пока не нажато «Применить к тарифу».
- **Не проверено:** скорость чтения в базе с несколькими организациями (проверена одна), задачи (`purpose = task`) в синтетике, тариф Макс без окна в 5 часов — только через параметр ядра.

### 20.12 Фоновые задачи

Каждая задача `worker`, которая действует за человека, перед работой проверяет:

- человек активен и не отключён платформой;
- организация не отключена;
- возможность входит в его тариф (задачи — число и частота, память из почты);
- лимит не исчерпан — иначе пропуск со статусом.

В self-hosted к этому добавляется `ctx.readOnly` (§21.8). Список задач — §20.15. Новые задачи: биллинг (§20.10), курс дня и ежедневная связь с узлом (§21.4). Биллинг идёт только в облаке; курс дня в self-hosted нужен, если валюта лимитов не совпадает с валютой моделей. Курс раз в сутки берётся с сайта ЦБ через исходящую сеть платформы (§18), руками его можно переписать. **Проверить**, доступен ли сайт ЦБ с сервера.

### 20.13 Журнал платформы

`platform_events` пишет всё, что меняет деньги или доступ:

### 20.14 Нагрузка

Один процесс `app` на всю установку (D2): стримы, MCP-клиенты и отмена живут в памяти. Спайк S27 (ветка `t3/s27-app-load-spike`): продуктовый маршрут `/api/chat` целиком на моке модели, production-сборка, Node 23, ответ 30–120 с, 30–60 ток/с, 1–3 шага с тулом.

- **Потолок — ≈40 одновременных ответов на процесс**, 50 — край, на 60 первый токен у части ответов приходит через 11 с. Дальше ответы не теряются и процесс не падает, но всё становится очередью: при 200 ответах p95 первого токена 75 с.
- **Предел — CPU главного потока Node**: ≈2 % ядра на ответ, ≈0,65 мс на кусок текста. Цена размазана по конвейеру (Web Streams, `AsyncLocalStorage` Next, микрозадачи), горячей точки нет. Потолок чувствителен к соседям по CPU: тот же уровень 50 на занятой машине сорвался.
- **Память не ограничивает:** живая куча +1,2–1,4 МБ на ответ, запись для докачки отпускается через 120 с. Физическая память при срыве (400 ответов) — до 1,6 ГБ мусора, без OOM.
- **MCP-клиенты** (общий пункт — один клиент, «у каждого свой» — на человека) стоят ≈80 КБ и один постоянный HTTP-поток каждый, на потолок не влияют. Вытеснения и срока жизни нет: клиенты уволенных и отключённых людей живут до перезапуска — копейки, но счётчика нет.
- **Мест на установку** = потолок / (доля людей с идущим ответом в пик × 1,3 ответа на такого человека). Доля не измерена: при 30 % — ≈100 мест, при 20 % — ≈150 (допущение). В v1 не продавать больше ~100 мест на один `app`; больше 150 — после замера доли на живой установке по `model_runs`.

Правила:

1. **Стоп-кран.** В `app` счётчик идущих ответов процесса; сверх 40 новый ответ получает 503 «Сейчас много запросов, повторите через минуту» с `retryAt`, а не очередь, в которой ждут все. Делается тем же счётчиком, что `apps/web/lib/generations.ts` (§20.15).
2. **Пул `postgres-js`** — 20–30 соединений вместо 10: с 40 ответов пул 10 занят целиком.
3. **Лимит памяти контейнера** — 2 ГБ, чтобы пережить срыв без OOM; на здоровой нагрузке хватает 0,5 ГБ.
4. **Метрика «идущих ответов»** — в панели платформы.
5. **Пересмотр D2** — когда на живой установке p95 идущих ответов ≥30 или мест больше 100.

Не проверено: Linux в Docker (мерили на macOS), реальные вызовы MCP-тулов, длинные истории чатов, склейка кусков на входе в продуктовом маршруте (на стенде одного SDK склейка по 50 мс даёт ≈2×, для продукта оценка 1,5–2×).

## 21. Self-hosted: лицензия и главный узел (D49)

Продуктовые правила — [ORGS-PLAN.md §14](ORGS-PLAN.md#14-self-hosted-лицензия-места-и-лимиты). Здесь — как это устроено в коде. Решения владельца 2026-11-28 — в ORGS-PLAN §13. Остальное — предложение, помечено «(допущение)». Спайки — PLAN, этап 0 (S29–S32), этапы работ — ORGS-PLAN §12, этапы 8–11.

- **Главный узел — раздел суперюзера в облаке, не отдельный сервис.** Тот же образ, та же база облака, маршруты `/api/node/v1/*`. Они работают только в установке с лицензией `cloud`, в остальных отвечают 404.
- **Сервер клиента** — та же установка из того же образа с лицензией `self_hosted`: одна организация, места из лицензии, лимиты админа (§20.8), деньги видны.
- **Без активации сервер не работает** (решено 2026-11-28): показывает только экран ввода кода.
- **Места привязаны к людям** (допущение). В лицензии лежит список мест — хеши почт тех, кто их занимает. Сервер пускает только людей из этого списка (§21.7).

### 21.1 Данные: что в облаке, что на сервере

**Облако (узел).** Клиент self-hosted — организация `kind = 'self_hosted'` без людей (§20.4). Места, цена, журнал мест, счета и статус у неё как у облачной (§20.10), строка `org_seats` — без тарифа.

```ts
organizations; // kind = 'self_hosted'; trial_ends_at — пробный период клиента, billing jsonb — почта для счетов, реквизиты
activation_codes; // organization_id PK, code_hash, created_by, created_at — один действующий код на клиента;
// новый код заменяет старый
installations; // id PK — id установки, organization_id, public_key — Ed25519, 32 байта, status: 'active'|'moved'|'revoked',
// activated_at, moved_at, last_seen_at, last_version, last_seats_used, last_people, chain — два последних nonce (§21.5),
// copy_flag_at, silent_flag_at, flags jsonb — отметки; unique (organization_id) where status = 'active'
installation_reports; // id, installation_id, seq, at — время сервера, received_at, version, seats_used, people,
// errors jsonb, ip — хранятся 90 дней (допущение)
seat_holders; // (organization_id, email_hash) PK, since — с какого момента держит место, kind: 'person'|'invite'
pending_moves; // id, organization_id, installation_id — новая установка, requested_at, confirmed_by — перенос,
// который ждёт суперюзера (§21.5)
```

- **Цена места self-hosted и плата за лицензию сервера** — `system_settings.policies.billing.selfHosted`: цена места, цена лицензии, валюта, НДС. У клиента может быть договорная цена места в `org_seats.price`. Значения в репозиторий не пишутся.
- **Ключ подписи узла** — переменная `NODE_SIGNING_KEY` только в окружении `worker` облака (§21.3).

**Сервер клиента.**

```ts
installation; // одна строка: id — создаётся при первом старте, key — приватный ключ установки (секрет вида 'installation',
// шифруется SECRETS_KEY, §17), seat_salt — соль хешей почт, узлу не уходит, license — последняя принятая лицензия
// как пришла, license_issued_at, activated_at, last_contact_at, last_error, time_high — максимум виденного времени
// (§21.3), chain — nonce из последнего ответа узла, report_seq, errors_off, telemetry_off
seat_requests; // id — id запроса, at, by, ops jsonb — добавить и убрать хеши, seats, seats_next, keep — кто остаётся
// с 1-го (§21.6), expected — число мест и версия списка из текущей лицензии, status: 'pending'|'done'|'rejected', error
error_events; // буфер ошибок до отправки (§21.9): code, component, name, frames, provider, status, actor, count,
// first_at, last_at
org_seats; // одна строка (организация, tariff_id null), seats — из лицензии (§21.7)
```

Лимиты админа (`limits`, `user.limit_id`) — §20.4 и §20.8. Тарифов, курсов облака, счетов и `billing-tick` на сервере клиента нет.

### 21.2 Активация

Допущение, кроме привязки кода к клиенту и переноса тем же кодом (решено 2026-11-28).

1. **Суперюзер заводит клиента** в разделе «Self-hosted»: название, почта для счетов, места, пробный период (если он будет, §21.8). На выходе — код активации.
2. **Код привязан к клиенту, а не к машине.** Стойкость — не меньше 128 бит: 26 знаков base32 группами. Код показывается один раз, на узле хранится хешем. «Новый код» и «Отозвать» (§21.5) заменяют старый, старый перестаёт действовать.
3. **Админ клиента вводит код** при установке или на экране кода:
   - `scripts/install.sh` спрашивает код после прокси и пишет его в `.env` (`METOBE_ACTIVATION_CODE`). `worker` активирует установку этим кодом сам, **только если установка пустая** — людей в ней ещё нет. После активации обновлятель, у которого есть доступ к каталогу установки (D35), стирает код из `.env`; без обновлятеля код остаётся, но на непустой установке не действует. Метрика №1 (время до первого ответа) не страдает: код вводится там же, где ключ;
   - кода в `.env` нет или установка не пустая — первая страница сервера, в том числе ссылка claim, ведёт на экран кода. Claim и всё остальное — после активации.
4. **Сервер создаёт ключ установки** Ed25519 (`node:crypto`, `generateKeyPairSync('ed25519')`) и соль хешей почт. Отправляет `POST /api/node/v1/activate`: код, id установки, публичный ключ, версия, хеши почт занятых мест (§21.7). Запрос подписан новым ключом — так узел видит, что ключ у отправителя есть.
5. **Узел в одной транзакции** проверяет код, создаёт строку `installations`, переводит прежнюю активную установку клиента в `moved` (с правилом 30 дней, §21.5), записывает список мест и отвечает лицензией.
6. **Повтор с тем же id и ключом** возвращает ту же установку: ответ мог потеряться.

- **Тот же код на второй машине — перенос** (решено 2026-11-28). Активной у клиента остаётся одна установка, прежняя больше не получает лицензию (§21.5).
- **Перенос — только руками на экране кода.** Если у клиента уже есть активная установка, узел отвечает «это перенос», и экран показывает предупреждение: «Прежний сервер перейдёт в режим чтения». Активация продолжается только после подтверждения.
- **О каждой активации и переносе** уходит письмо на почту клиента для счетов и запись в журнал суперюзера (§20.13).
- **Нынешняя установка с людьми** отправляет при активации хеши всех занятых мест. Людей больше, чем мест у клиента, — в список попадают первые по времени, когда человек занял место; остальные не входят, владелец видит их списком и может докупить места.

**Адрес узла** зашит в образ. Переменная `METOBE_NODE_URL` принимается только в образе, собранном с флагом разработки (§21.3).

### 21.3 Лицензия и подпись

**Лицензия — запись, подписанная ключом узла.** Формат — как JWS compact с `alg: EdDSA`: `base64url(заголовок).base64url(данные).base64url(подпись)`. Подпись — над байтами первых двух частей, канонизация JSON не нужна. Проверка — `crypto.verify(null, …)` из `node:crypto`, без библиотеки (допущение, S29).

```jsonc
// заголовок
{ "alg": "EdDSA", "typ": "metobe-license", "kid": "node-1" }
// данные, значения для примера
{
  "v": 1,
  "scheme": "self_hosted",          // или "cloud" — лицензия облака самому себе
  "installationId": "…",
  "organizationId": "…",            // организация клиента на узле
  "status": "active",               // "moved" | "revoked" — работа запрещена
  "perpetual": true,                // лицензия сервера оплачена
  "trial": false,
  "seats": 10,                      // куплено мест
  "holders": ["…", "…"],            // список мест: sha256(соль установки + почта), не больше seats
  "holdersVersion": 37,             // растёт с каждым изменением списка
  "paidUntil": "2026-12-31T21:00:00Z", // конец последнего оплаченного месяца по поясу организации
  "issuedAt": "2026-11-28T09:00:00Z",  // время узла
  "expiresAt": "2026-12-05T09:00:00Z", // min(issuedAt + 7 дней, paidUntil)
  "nonce": "…"                      // для цепочки (§21.5)
}
```

- **«Оплачено до» считает узел.**
  - Первый месяц нового клиента — конец месяца, в котором клиент заведён, если счёт за лицензию сервера оплачен (допущение).
  - Дальше — конец последнего месяца с оплаченным счётом.
  - В пробный период — `trial_ends_at`.
  - Лицензия сервера не оплачена и пробного нет — `paidUntil` = момент выдачи.
  - Счёт за следующий месяц выставляется 25-го (§20.10): как только суперюзер отметил оплату, следующая связь приносит лицензию с новым «оплачено до».
- **Срок действия — запас на обрыв связи, не отсрочка оплаты** (решено 2026-11-28, 7 дней — допущение). `expiresAt` не дальше `paidUntil`.
- **Код выдачи лицензий публичный.** Защиту это не ослабляет: всё держится на ключе подписи.

**Ключи** (допущение):

- **Публичные ключи узла вшиты в образ** — `packages/core/src/license/node-keys.ts`, список с `kid`: действующий и следующий, для смены ключа. Там же — список отозванных `kid`.
- **Подписывает только `worker` облака.** `NODE_SIGNING_KEY` есть только в его окружении. `app`, который смотрит в интернет, ключа не видит: маршрут узла проверяет подпись установки, ставит задание в очередь BullMQ `node-sign` и ждёт ответа `worker`.
- **Утечка ключа подписи.** Утёкший ключ действует во всех образах, пока его `kid` не отозван, а отозвать его можно только обновлением: новые образы несут список отозванных `kid`. Установки, которые не обновились, принимают лицензии, подписанные утёкшим ключом.

**Флаг разработки** (допущение). Тестовый ключ узла и переменная `METOBE_NODE_URL` принимаются только в образе, собранном с аргументом сборки Docker `METOBE_DEV_LICENSE=1`. Аргумент пишется в файл флагов при сборке, а не в переменную окружения образа: переменную окружения админ поменял бы в `compose.yml`. С флагом собирают свои образы e2e, задача CI `upgrade` и разработка. Публикуемый образ — задача `image` в `.github/workflows/ci.yml` — собирается без него.

**Сервер принимает лицензию**, если:

- подпись сходится с известным и не отозванным `kid`;
- `installationId` — свой;
- `issuedAt` не раньше, чем у текущей лицензии: старую лицензию не подсунуть.

Принятая лицензия пишется в `installation.license`, `seats` — в `org_seats.seats` под `FOR UPDATE` этой строки (§21.7). Процессы узнают о новой лицензии через `config:changed` в Redis (D2).

**Время.** Лицензионное «сейчас» = `max(часы сервера, time_high)`. `time_high` растёт: каждая проверка поднимает его до часов сервера, пишется не чаще раза в минуту; принятая лицензия поднимает его до `issuedAt`. Перевод часов назад срок не продлевает. Часы, ушедшие далеко вперёд, узел возвращает: если `time_high` больше `issuedAt` свежей лицензии больше чем на сутки, `time_high` = `issuedAt` (допущение, S29). Правку `time_high` в базе и подмену часов процесса это не ловит (§21.11).

**Схема установки** — из `scheme` принятой лицензии (§20.1). Облако выдаёт лицензию `cloud` само себе тем же `worker`. Переменной, которая включает облако или выключает проверку, нет.

### 21.4 Ежедневная связь

- **Направление** — всегда от сервера к узлу. Входящих соединений сервер не принимает.
- **Сеть** — по правилам §18: напрямую или через прокси, отмеченный для домена узла. Если прокси задан в `install.sh`, а напрямую узел не отвечает, активация пробует через этот прокси и закрепляет его за доменом узла, как источник (§18, «прокси подбирается сам») — допущение.
- **Расписание.** Задача `node-sync` в отдельной очереди BullMQ `node`, `concurrency: 1`.
  - Раз в сутки в случайный час: узлу не нужен наплыв в полночь.
  - При сбое — повтор через 15 минут, час, 4 часа.
  - Раз в час, если сервер в «только чтении» или лицензия истекает в ближайшие сутки (допущение): после оплаты сервер оживает в течение часа.
  - Сразу — после активации, изменения мест и по кнопке «Проверить сейчас».
- **Запрос** — `POST /api/node/v1/report`. Тело — JSON из §21.9, заголовок `X-Metobe-Signature` — подпись тела ключом установки. Узел проверяет подпись по `installations.public_key`, сверяет цепочку (§21.5), пишет `installation_reports` и обновляет `installations.last_*`.
- **Ответ** — свежая лицензия (§21.3) и данные для экрана владельца без подписи: цена места, валюта, НДС, статус счетов, сумма следующего счёта. Подписи им не нужно, работа от них не зависит.
- **Без связи больше суток** админ видит плашку (допущение): «Нет связи с узлом лицензий с 28 ноября. Сервер перейдёт в режим чтения 5 декабря».

### 21.5 Копии и перенос

- **Копия, которая выходит на связь, видна.** Каждый ответ узла несёт новый `nonce`, следующий отчёт возвращает его. Узел помнит два последних: потерянный ответ даёт повтор с предыдущим `nonce`, и это не отметка. Отчёт со старым `nonce`, два отчёта с одним `seq` или чередование веток — отметка о копии `copy_flag_at`. Суперюзер видит: «Похоже на копию: два сервера с одним id», версии, адреса, время.
- **Молчащая копия не видна, но ей нечего дать** (допущение). Копия, которая сама на узел не ходит, может брать свежую лицензию у оригинала: копировать `installation.license` по расписанию или пересылать ответы узла. Узел её не слышит. Но лицензия пускает только людей из списка мест (§21.7), а вход — по коду на почту. Новых людей копии не добавить, не подделывая сессии в базе под чужими именами. Она обслуживает тех же людей, за чьи места заплачено.
- **Молчание видно.** Установка, которая не выходила на связь дольше запаса (7 дней), получает отметку `silent_flag_at`: «Установка молчит с …». Так видны и закрытый узел, и подмена часов, и откат на версию без лицензии (§21.11).
- **Отметка не блокирует** (допущение). Это может быть восстановление из копии. Суперюзер решает сам и может нажать «Отозвать»: обе ветки получают `revoked`, клиенту выдаётся новый код, старый перестаёт действовать. Клиент активирует нужный сервер новым кодом — это перенос.
- **Перенос — не чаще раза в 30 дней** (допущение). Чаще — узел записывает перенос в `pending_moves` и держит, пока его не подтвердит суперюзер. Новая установка до подтверждения видит «Перенос ждёт подтверждения», прежняя продолжает работать.
- **Повторная активация установки в состоянии `moved`** — это перенос обратно. На неё действует то же правило 30 дней.
- **Как переносят:**
  - новая установка с тем же кодом — перенос (§21.2): прежняя при следующей связи получает `moved` и встаёт, а не выходит на связь — встаёт, когда кончится запас;
  - копия базы вместе с `SECRETS_KEY` на новом железе — та же установка, кода не нужно. Если старый сервер выключен, цепочка не рвётся;
  - копия базы без ключа установки (нет `SECRETS_KEY`) — сервер не активирован, нужен код, это перенос.

### 21.6 Изменение мест

Допущение. Любое изменение состава — новый список мест, подписанный узлом.

1. **Владелец меняет места.** Что это бывает:
   - пригласить человека — его почта занимает место. Приглашения в self-hosted — только с почтой;
   - вход по домену — новый человек занимает место в момент входа;
   - освободить место — отключить или удалить человека, отозвать приглашение;
   - отдать место другому — освободить и занять в одном запросе;
   - докупить места или убрать со следующего месяца.

   Экран показывает цену и доплату за остаток месяца из последнего ответа узла.

2. **Сервер пишет `seat_requests`** со своим id: какие хеши добавить и убрать, сколько мест купить (`seats`) или оставить на следующий месяц (`seats_next`), и что он видит сейчас (`expected`: число мест и `holdersVersion`).
3. **`POST /api/node/v1/seats`**, подписанный ключом установки.
4. **Узел в одной транзакции:**
   - `FOR UPDATE` строки `org_seats` клиента — тот же порядок блокировок, что у суперюзера и `billing-tick`;
   - ключ `seats:{installationId}:{requestId}` в `billing_actions`. Уже есть — запрос повторный, узел отвечает текущей лицензией;
   - `expected` не совпадает — места уже поменял кто-то другой. Отказ `seats-changed` с текущей лицензией, экран показывает новое состояние;
   - хешей больше, чем мест, — отказ `no-free-seats`;
   - иначе пишет `seat_holders`, при покупке — `seat_changes` `add` с доплатой по дням, как в §20.10 (в счёт 25-го), или `next` для следующего месяца;
   - ответ — новая лицензия, `holdersVersion` + 1.
5. **Сервер принимает лицензию** (§21.3) и только после этого создаёт приглашение или пускает человека. Запрос — `done`.

- **Без связи с узлом состав людей не меняется.** Пригласить, пустить по домену, отдать место нельзя. Отключить человека можно сразу: доступ он теряет локально, а место освобождается при следующей связи. Файлом — позже (§21.10).
- **Обрыв после коммита на узле** — запрос остаётся `pending`, сервер повторяет его с тем же id при следующей связи или по кнопке. Узел отдаёт тот же результат, двойной доплаты нет.
- **Смена почты человека** — новый хеш, тот же запрос «отдать место».
- **Уменьшение мест — с 1-го числа, как в облаке** (ORGS-PLAN §6). До этого владелец выбирает, кто остаётся (`keep`). Не выбрал — остаются назначенные раньше всех по `seat_holders.since`. В отличие от облака, лишние с 1-го не считаются в счёт, а выходят из списка: список мест на узле — источник правды.
- **Права** — `canManageSeats`: владелец (§20.3). Приглашать могут и админы организации (ORGS-PLAN §4), но только на свободное место.
- **Разовая плата за лицензию сервера** — счёт `kind = 'license'` организации клиента. Его выставляет суперюзер при заведении клиента. Отметка «Оплачен» ставит `perpetual` в лицензии.

### 21.7 Потолок мест

- **Сервер пускает человека, только если хеш его почты есть в списке мест** (допущение). Хеш — `sha256(seat_salt + нормализованная почта)`: нижний регистр, без пробелов по краям. Соль узлу не уходит, узел хеши не раскрывает.
- **Проверка — при сборке `ctx`** (§20.2), а не только при входе: сессия, вставленная прямо в базу, её не обходит. Кеш в памяти процесса: множество хешей по версии лицензии и хеш почты по id человека, сброс по `config:changed`. Человек не в списке — экран «Свободных мест нет: обратитесь к владельцу». Ту же проверку проходят `worker` (задачи, память, сводки, проверка почты) и Telegram.
- **Та же транзакция, что в облаке** (§20.10): `FOR UPDATE org_seats` при приглашении, принятии приглашения, входе по домену, включении человека. Строка — без тарифа, число мест и список — из лицензии. Двое на последнее место — проходит один.
- **Занято** = включённые люди + приглашения без ответа. Каждый из них — хеш в списке.
- **Люди, дописанные прямо в базу**, не входят: их хешей в списке нет. Отчёт узлу считает людей по базе: людей больше, чем мест, — отметка у суперюзера.

### 21.8 Без связи, неоплата, без активации

Решено 2026-11-28: льготного срока нет, режима «без лицензии» нет. Состояние считает чистая функция `licenseState(license, now)` в `core/license/state.ts`:

| Состояние | Когда | Что работает |
| --- | --- | --- |
| не активирован | лицензии нет или ключ установки не читается | только экран ввода кода |
| работает | `status = 'active'`, сейчас ≤ `expiresAt` | всё для людей из списка мест |
| работает, нет связи | то же, последняя связь больше суток назад | всё, плашка у админа (допущение) |
| только чтение: не оплачено или нет связи с узлом | сейчас > `expiresAt` = `paidUntil`. Без связи сервер не знает, оплачен ли следующий месяц | вход, чтение, выгрузка, настройки, экран «Лицензия»; если связь есть — изменение мест |
| только чтение: нет связи | сейчас > `expiresAt`, `paidUntil` впереди | вход, чтение, выгрузка, настройки, экран «Лицензия» |
| только чтение: перенесён или отозван | `status` — `moved` или `revoked` | то же, плюс «Активировать заново» |

- **Не оплатили к сроку — сразу только чтение**, как отключение в облаке (ORGS-PLAN §6). Отличие: история открыта. Бессрочная лицензия сервера остаётся, после оплаты всё возвращается в течение часа (§21.4, допущение).
- **«Только чтение»** = `ctx.readOnly` (§20.2). Вызовы моделей отклоняются: чат и предпросмотр отвечают 403 `license-read-only` с карточкой причины, `worker` пропускает задачи, очередь памяти, напоминания, сводки и проверку почты, Telegram отвечает строкой о причине.
- **Пробный период**, если будет, — лицензия от узла с `trial: true` и `paidUntil` = `trial_ends_at` организации клиента (решено 2026-11-28). Пробный период привязан к клиенту, а не к машине: переустановка нового пробного не даёт.

**Нынешние установки** (допущение). Условие везде одно — **«есть принятая лицензия»**, а не «код введён».

- Код выдаём до выхода версии с лицензией.
- **Версия N** умеет активироваться и связываться с узлом, но работу не останавливает.
- **Признак «нужна лицензия» — в описании релиза.** Обновлятель читает описание в `fetchReleases` (`packages/core/src/updates.ts`): поле `body` разбирает `parseNotes` (`packages/core/src/updates-notes.ts`). Релизный CI дописывает в `body` строку-признак, `parseNotes` получает поле `requiresLicense`.
- **Проверка — в общем `update()`** (`apps/worker/src/updater.ts`). Через него идут и обновление по кнопке, и ночное автообновление, так что обойти её нельзя. Версию с признаком обновлятель N не ставит, пока на сервере нет принятой лицензии.
- **Ночное автообновление прыгает через любые номера.** Оно берёт самый новый релиз (`newer[0]` при `nightlyAt`), а не следующий по порядку. Обновлятель старше N признака не знает и с ночным обновлением прыгнет сразу на N+1 — после этого сервер покажет экран кода.
- **Поэтому N+1 выходит только минорной или мажорной версией** — автоисправления (`autoPatches`) её не ставят — и **только после того, как узел увидит активацию всех известных установок на N**.
- Предупреждение — в описании релиза N+1 и в письме клиентам.
- **Старые версии работают всегда**, но без обновлений. Миграций, которые ломают старый код, не делаем: откат `METOBE_IMAGE` в `.env` на версию до лицензии возможен (§21.11).

### 21.9 Что уходит на узел: поля, ошибки, телеметрия

Этот список публичный — для безопасников клиента. Последний отправленный отчёт админ видит на экране «Лицензия» как есть (допущение).

| Поле | Пример | Зачем |
| --- | --- | --- |
| `installationId`, `seq`, `at` | `…`, `412`, время сервера | установка, порядок отчётов, сдвиг часов |
| `chain` | `nonce` из прошлого ответа | копии (§21.5) |
| `version` | `0.14.2` | какие версии живут, кому нужно обновление |
| `seatsUsed`, `people`, `invited` | `9`, `8`, `1` | места: занято = люди + приглашения |
| `holdersVersion`, `holdersDigest` | `37`, `sha256` отсортированного списка | совпадает ли список мест на сервере со списком узла |
| `errors[]` | см. ниже | ошибки, если админ их не выключил |

**Хеши почт** уходят только в запросах изменения мест (§21.6) и при активации: `sha256` с солью установки, соль узлу не уходит. Узел видит, что место занял новый человек, но не кто это.

**Ошибки** (допущение):

- **Что уходит.** Код ошибки (`chat.stream-failed`), часть системы (`app`, `worker`, `updater`), класс (`TypeError`), кадры стека — файл и строка только нашего кода, без аргументов. Провайдер модели и HTTP-статус, если ошибка от провайдера. Сколько раз, первый и последний раз.
- **Человек — обезличенный номер**: HMAC от id человека с солью установки, первые 8 символов. Узел видит «у одного человека 40 ошибок», но не кто это.
- **Что не уходит никогда:** текст `error.message` — в нём бывают данные; тексты сообщений, промпты, аргументы и результаты тулов, файлы; имена, почты, id чатов, адреса страниц и людей.
- **Буфер** — `error_events`, одна строка на код и место, в отчёт уходят накопленные за сутки, не больше 100 строк (допущение).
- **Выключатели** — `errors_off` и `telemetry_off`, у админа клиента. Связь для лицензии не выключается (допущение, ORGS-PLAN §13).
- **Хранение на узле** — 90 дней (допущение).

**Телеметрия пользовательских сценариев** — отдельный поздний этап: свой список полей, своя проверка на персональные данные, свой выключатель.

### 21.10 Файл для закрытого контура (позже)

Не делаем на этом этапе (решено 2026-11-28). Формат выбран так, чтобы потом ничего не менять (допущение):

- **Лицензия файлом** — тот же токен (§21.3) со списком мест, админ загружает его на экране «Лицензия». Срок у такой лицензии длиннее, например месяц с запасом.
- **Отчёт файлом** — то же тело, что у ежедневного отчёта (§21.9), подписанное ключом установки. Клиент раз в месяц отправляет его сам, суперюзер загружает на узле и получает файл лицензии. Так делают GitLab, n8n и Metabase.
- **Изменение мест файлом** — запрос `seat_requests` файлом, в ответ — лицензия файлом.
- **Цепочка** для файлов не работает. Копии в закрытом контуре держит список мест: новых людей в них не добавить.

### 21.11 Угрозы: что ловим и что не ловим

Код публичный, у клиента root. Пересобрать образ без проверки можно всегда. Защита рассчитана на обычные попытки, от пересборки защищают договор и лицензия кода (ORGS-PLAN §14.8).

| Что делают | Ловим | Чем |
| --- | --- | --- |
| Правят `seats` или список мест в лицензии | да | подпись не сходится |
| Подсовывают старую лицензию | да | `issuedAt` не раньше текущей |
| Дописывают людей прямо в базу | да | их хешей нет в списке мест (§21.7), отчёт показывает лишних |
| Вставляют сессию прямо в базу | да, если человека нет в списке | проверка списка при сборке `ctx`, а не только при входе (§21.7). Сессия под человеком из списка занимает его же место |
| Переводят часы назад | да | `time_high` (§21.3) |
| Правят `time_high` в базе или подменяют часы процесса (libfaketime через `LD_PRELOAD` в `compose.yml`) и закрывают узел | нет | видим по молчанию: отметка «установка молчит дольше запаса» (§21.5) |
| Закрывают узел файрволом | да, с задержкой | лицензия кончается не позже чем через 7 дней; отметка о молчании |
| Откатываются на версию до лицензии (`METOBE_IMAGE` в `.env`) | нет | старые версии работают всегда, но без обновлений; видим по молчанию. Миграций, ломающих старый код, не делаем (§21.8) |
| Ставят вторую установку копией базы с ключом, и она выходит на связь | видим | цепочка `nonce`, отметка суперюзеру (§21.5) |
| Держат молчащую копию, которая берёт лицензию у оригинала | не видим | ей нечего дать: пускает только людей из списка, новых без подделки сессий под чужими именами не добавить (§21.5) |
| Переустанавливают ради нового пробного периода | да | активация по клиенту: пробный период — у организации на узле, не у машины (§21.8) |
| Ставят новую установку на восстановленную базу — «убрать ключ, оставить историю» | да | активация по клиенту: без ключа установки нужен код, а код переносит лицензию, старая установка встаёт (§21.2, §21.5) |
| Часто переносят лицензию между серверами | да | не чаще раза в 30 дней, чаще — через суперюзера; письмо клиенту о каждом переносе (§21.5) |
| Ставят переменную, которая включает облако или выключает проверку | да | такой переменной нет, схема — из подписанной лицензии (§21.3) |
| Подменяют адрес узла или тестовый ключ через окружение | да | `METOBE_NODE_URL` и тестовый ключ — только в образе с флагом разработки (§21.3) |
| Подменяют публичный ключ узла в образе или вырезают проверку | нет | пересборка; договор и лицензия кода |
| Крадут ключ подписи узла | нет | ключ только у `worker` облака; утёкший ключ действует, пока установки не обновятся до образа, где его `kid` отозван (§21.3) |
| Читают отчёт по пути | — | TLS; персональных данных в отчёте нет (§21.9) |

### 21.12 Что меняется в коде

- **Ядро, сервер клиента** — `packages/core/src/license/`:
  - `token.ts` — подпись и проверка;
  - `node-keys.ts` — публичные ключи узла и отозванные `kid`;
  - `state.ts` — `licenseState`;
  - `sync.ts` — активация и ежедневный отчёт;
  - `seats.ts` — хеши почт, проверка списка мест, запросы изменения мест;
  - `errors.ts` — сбор ошибок без персональных данных.
- **Ядро, узел** — `packages/core/src/platform/node/`: коды активации, установки, переносы и правило 30 дней, приём отчёта, `issueLicense(orgId, installationId)`, список мест, запросы мест, отметки о копиях и молчании, письма об активации.
- **Маршруты узла** — `apps/web/app/api/node/v1/{activate,report,seats}/route.ts`: только при лицензии `cloud`, ограничение частоты по установке и адресу. Подпись — заданием `node-sign` в `worker`.
- **`worker`** — очередь `node`, задача `node-sync` (§21.4); в облаке — очередь `node-sign` с `NODE_SIGNING_KEY`.
- **Контекст и ворота** — `ctx.scheme`, `ctx.readOnly`, `ctx.limits` (§20.2) и проверка списка мест (§21.7). `readOnly` и список мест проверяются там же, где «организация отключена» (§20.15, «Фоновые задачи»): маршрут чата рядом с `checkChatLimit`, предпросмотр, задачи, Telegram, очередь памяти, напоминания, сводка, проверка почты. Экран кода — в `apps/web/app/(app)/layout.tsx` до сборки `ctx` и на странице claim.
- **Одна организация.** `createOrganization` при схеме `self_hosted` отказывает.
- **Места.** `org_seats` с `tariff_id null`; приглашение, принятие, вход по домену и включение человека ждут новой лицензии от узла (§21.6); приглашения только с почтой.
- **Настройки.**
  - «Платформа» → «Лицензия»: состояние, места, «оплачено до», последняя связь, последний отчёт как есть, ввод кода, выключатели ошибок и телеметрии;
  - «Организация» → «Места» без тарифов (P37 без тарифов) и «Лимиты» (P39);
  - у суперюзера облака — «Платформа» → «Self-hosted» (P40).
- **`install.sh`** — вопрос о коде активации, `METOBE_ACTIVATION_CODE` в `.env`; обновлятель стирает код после активации.
- **Обновлятель.** `parseNotes` получает поле `requiresLicense`, `update()` в `apps/worker/src/updater.ts` не ставит такую версию без принятой лицензии; релизный CI дописывает признак в описание релиза (§21.8).
- **Сборка.** Аргумент `METOBE_DEV_LICENSE` в `docker/Dockerfile`; e2e и `upgrade` собирают образ с ним, задача `image` — без него (§21.3).
- **Миграции.** `installation` с id и солью при первом старте; `organizations.kind`; `org_seats` — уникальный ключ `nulls not distinct` вместо PK; `invoices.kind`; `limits`, `user.limit_id`; таблицы узла (§21.1).
- **Секреты.** Вид `installation` для ключа установки (§17). `NODE_SIGNING_KEY` — только в окружении `worker` облака.
- **CI.** e2e и `upgrade` работают с тестовым ключом узла и моком узла.
- **`LICENSE`** — после решения владельца (ORGS-PLAN §13).
